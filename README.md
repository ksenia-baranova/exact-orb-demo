# exact-orb

**Исследовательский проект. Не продукт, не сервис, не коммерческое предложение.**

Предмет исследования — управляемая разработка с AI-агентами: как делегировать
исполнение, сохраняя контроль над требованиями, решениями и качеством.
Цель — методология, которую можно проверить и перенести в enterprise-команду.

Полигон — система расчёта астрологических карт, сочетающая строго вычислимые
факты и будущую LLM-интерпретацию. Проект не исследует и не утверждает научную
валидность астрологии, не оказывает услуг и никому ничего не предсказывает.

`Python 3.11+` · `Swiss Ephemeris` · `FastAPI` · `AGPL-3.0` · активная R&D-разработка

## О проекте

Исследовательский вопрос: насколько далеко можно масштабировать разработку,
делегируя AI-агентам код и техническую проработку, но сохраняя за человеком
управление требованиями, архитектурой и качеством? Какие механизмы контроля
для этого необходимы и сколько они стоят?

**Кто ведёт разработку.** Проект ведёт один человек; весь код написан
AI-агентами, а не вручную. Автор формулирует требования и сценарии, принимает
архитектурные решения, читает и ревьюит реализацию, анализирует диагностические
журналы. Проверка качества опирается на явные контракты, исполняемые проверки
и независимое тестирование. Это опыт одного оператора; его результаты пока
нельзя автоматически переносить на команду.

### Отличительные особенности подхода

Метод исследуется с позиции руководителя инженерной команды: как управлять
результатом, когда существенную часть исполнения берут на себя AI-агенты.

- **Формализованный процесс, вероятностные исполнители.** Изменения проходят
  через роли, состояния и gates. Детерминированная автоматизация переходов —
  планируемый следующий шаг, а не уже реализованная возможность.
- **Решение отделено от рекомендации.** Агент может находить развилки и
  предлагать варианты; значимые решения подтверждает уполномоченный человек.
- **Артефакты важнее истории диалога.** Требования, ADR, реестр решений и
  результаты проверок сохраняют инженерный контекст; prompts — журнал поручений,
  а не source of truth.
- **Проверка независима от исполнителя.** Зелёные тесты и совпадение мнений
  моделей сами по себе не доказывают корректность: нужны контракты,
  воспроизводимые контрпримеры и независимое тестирование.

### Почему собственный процесс

Автор длительное время работала QA-инженером, бизнес- и функциональным аналитиком,
тимлидом и руководителем инженерных команд. Этот опыт позволяет рассматривать
процесс с позиции разных ролей: что каждой нужно для работы и что руководителю
необходимо для контроля результата. Сопоставимого опыта непосредственного
написания кода у автора нет.

Цель — перенести накопленный инженерный и управленческий опыт в среду агентной
разработки. Сначала автор определяет необходимую модель управления и проверяет
её на реальных изменениях проекта. Следующий шаг — сопоставить проверенную модель
с готовыми решениями и выбрать подходящие инструменты и компоненты.

### Как читать репозиторий

Это дневник эксперимента. Код и документация показывают текущее состояние,
а каждый PR в `main` сохраняет контекст очередного изменения: что обнаружилось,
что пришлось пересмотреть и на чём основаны последующие решения.

### Почему такой полигон

Главный архитектурный принцип полигона:

> **LLM не является источником расчётных фактов.**

Положения, дома, аспекты, конфигурации и другие показатели появляются только
в детерминированном расчёте. Языковая модель может объяснять рассчитанное,
но не достраивает отсутствующие факты.

```text
structured input → deterministic resolution → deterministic calculation
    → validated chart artifact → evidence selection → LLM interpretation
```

Предметная область заменяема: тот же контур — детерминированный источник фактов,
явные контракты, вероятностный слой строго за ними — применим к любой области,
где ошибка модели в фактах недопустима. Зато она позволяет публиковать процесс,
требования и код без корпоративных данных.

## Метод разработки

Единица работы — change с ролями Owner, Manager, Analyst, Developer, Tester
и Reviewer. Каждый запуск агента — одна задача в git; роль меняет только
статус своей задачи, а статус change выводит оркестратор по таблице переходов
(сейчас это человек). Один файл — один автор. Вопросы к Owner задают двое:
Manager — о скоупе, сроках и приёмке, Analyst — о требованиях. Роли может
совмещать один человек, запуская каждую отдельной задачей.

```text
INTAKE → ANALYSIS → ALIGNMENT → APPROVAL → READY_FOR_DEVELOPMENT
  → IN_DEVELOPMENT → READY_FOR_TEST ⇄ BUG_FIX → DONE → ACCEPTED
```

Analyst пишет инкремент требований с источниками, Developer и Tester делают
ревью, план и оценки (чч и мч), Owner утверждает план. Developer реализует
по одному промту на задачу, Tester пишет приёмочные тесты, Reviewer другой
моделью в отдельной сессии проверяет код. После DONE Analyst переносит
инкремент в requirements/current/, Owner принимает изменение. Для
рефакторинга без изменения поведения анализ пропускается.

Если найден дефект реализации, Developer устраняет его с regression-тестом,
а перепроверяет тот, кто завёл баг: Tester или Reviewer. Пробел в требованиях
оформляется как decision point (DP) и возвращается к Analyst.

Проверки включают component, contract, property-based, integration,
persistence conformance, concurrency, golden и module-boundary tests;
mock не считается доказательством интеграции, а количество тестов само
по себе не служит метрикой качества.

Документы метода: [принципы](docs/development_approach/development-approach.md),
[процесс](docs/development_approach/process/change-process-v2.md),
[роли](docs/development_approach/roles.md),
[шаблоны](docs/development_approach/artifacts/README.md),
[инструкции ролей](docs/development_approach/skills/README.md).

## Примеры: что показал эксперимент

Примеры отдельных изменений, а не статистика эффективности метода:
они показывают классы найденных ошибок и ограничения проверок.

### Дефекты, найденные человеком

Часть дефектов обнаружена при зелёных тестах, часть — до реализации.
Подробности — в [разборах](docs/project_management/problems_detected_by_human/):

| № | Что обнаружено | Итог |
|---|---|---|
| 001 | Полный DEBUG-вывод показал, что BuildNatalSuccess хранит одни данные в нескольких местах: структурно валидный, но противоречивый результат | ADR-0027, канонические владельцы значений |
| 002 | Разбор полной карты выявил ошибки самих требований: два пространства имён точек, аспект оси узлов к себе, ложная точность при неизвестном времени | ADR-0029…0032 |
| 003 | Ревью спецификации Orchestrator: ответственность незаметно перетекала между компонентами, outcome-контракты неполны | Требования отправлены на переработку до реализации |
| 004 | Ревью реализации Orchestrator: внутренние сбои commit-flow теряли terminal-событие | Воспроизведено, исправлено, regression-случаи |
| 005 | Журнал не показывал, кто координирует вызовы: поток выглядел как хореография | ADR-0035…0038, интеграционный тест |

> **Структурно валидная модель ≠ семантически корректная модель.**

### Пример: кто находил дефекты в UI-change (M1-7)

В этом изменении из 10 дефектов реализации 8 нашло ревью кода другой моделью ещё
до независимого тестирования, 1 — ручная проверка владельца, 1 — Tester. На момент
ревью 126 зелёных UI-тестов найденных моделью случаев не покрывали
([реестр](docs/testing/ui-birth-form-and-facts/manual-test-bugs.md),
[разбор](docs/project_management/problems_detected_by_human/006-ui-review-found-counterexamples-missed-by-green-tests.md)).

На одном change ревью другой моделью помогло найти воспроизводимые
контрпримеры, но его результат нельзя обобщать без дальнейших измерений.

Открытый вопрос: сколько стоит такой контроль? По наблюдению автора, документация
и артефакты change растут быстрее кода. Это качественное наблюдение, а не результат
количественного сравнения. Стоимость ведения артефактов и польза каждого правила
процесса требуют дальнейших измерений.

## Текущее состояние

Работает первый пользовательский сценарий: в браузере ввести данные рождения,
выбрать место из подсказок, построить натальную карту или космограмму и прочитать
таблицы фактов. Интерпретации пока нет.

| Область | Состояние |
|---|---|
| Детерминированный расчёт натала и космограммы | Реализован; аспектная модель пересмотрена ADR-0029…0032, достоинства и диспозиторы — ADR-0033 |
| Транзиты | Реализованы в engine/; application flow для них нет |
| Resolution данных рождения и каталог мест | Реализованы (M1-5) |
| Calculation identity, cache артефактов, single-flight | Реализованы |
| Сессии: in-memory и SQLite, ContextService | Реализованы |
| Application Orchestrator, BuildNatalHandler, process runtime | Реализованы, приняты на реальном стеке |
| HTTP API: FastAPI, анонимная сессия, поиск мест, построение карты | Реализован (M1-6); формальный итог приёмки M1-6 не записан |
| Web UI: форма, подсказки мест, построение, таблицы точек, домов и аспектов, восстановление сессии | Реализован и принят (M1-7) |

| Research corpus | Whitelist-проекция и in-memory corpus |

## Быстрый старт

Требуется Python 3.11+.

```bash
git clone https://github.com/ksenia-baranova/exact-orb-demo.git
cd exact-orb-demo
python -m venv .venv
```

Linux / macOS:

```bash
source .venv/bin/activate
```

Windows:

```powershell
.venv\Scripts\Activate.ps1
```

Установка и проверки:

```bash
pip install -e ".[dev]"
pytest
```

**CLI — прямой вызов расчётного движка:**

```bash
exact-orb "02.09.1985 00.45 gmt+4" --lat 55.7522 --lon 37.6155 --place "Moscow"
exact-orb "02.09.1985 00.45 gmt+4" --lat 55.7522 --lon 37.6155 --place "Moscow" --format json
```

CLI пока не проходит через Application Orchestrator; браузерный сценарий проходит.

**Web UI локально.** HTTP API требует HTTPS во всех окружениях
([ADR-0039](docs/requirements/decisions/0039-https-in-all-environments.md)), поэтому
локальный стенд — Uvicorn за Caddy с сертификатом mkcert на
https://exact-orb.localhost. Пошаговая инструкция (PowerShell):
[`docs/runbooks/http_api_local_https.md`](docs/runbooks/http_api_local_https.md).

Каталог мест [`data/places.sqlite`](data/README.md) приходит вместе с checkout.

## Архитектура

Modular monolith с явными границами
([service_ready_architecture.md](docs/architecture/service_ready_architecture.md),
[ADR-0021](docs/requirements/decisions/0021-modular-monolith-service-seams.md)).

Путь построения карты:

```text
Browser ─HTTPS─▶ FastAPI ─▶ Application Orchestrator
                               │  load SessionSnapshot (ContextService)
                               ▼
                         BuildNatalHandler
                          │              │
              BirthDataResolver     ChartArtifactResolver
              (каталог мест, tz)     │ cache ─ codec ─ validation
                                     ▼
                              EngineService → Swiss Ephemeris
                               │
                               ▼  BuildNatalSuccess {artifact, delta}
                         Orchestrator: проверка версии → CAS commit
                               │
                               ▼  типизированный ApplicationResult
```

Ключевые решения:

- **Владение состоянием.** Handler возвращает BuildNatalOutcome; при успехе
  BuildNatalSuccess содержит артефакт и StateDelta. Orchestrator координирует
  CAS commit через ContextService. Устаревший
  результат не перезаписывает новое состояние
  ([ADR-0006](docs/requirements/decisions/0006-application-orchestrator.md),
  [ADR-0014](docs/requirements/decisions/0014-explicit-state-mutations.md)).
- **Неизвестное время рождения.** Строится космограмма. Техническое полуденное
  положение не выдаётся за время рождения; зависящие от времени аспекты
  не представляются достоверными фактами момента рождения
  ([ADR-0032](docs/requirements/decisions/0032-unknown-birth-time-aspect-semantics.md)).
- **Cache не источник истины.** Ключ учитывает ChartSpec и CalculationVersion,
  включая версии движка, профилей и эфемерид; повреждённый или устаревший
  артефакт пересчитывается, сбой cache не блокирует расчёт. Одновременные
  запросы с одинаковым расчётным ключом объединяются через single-flight
  ([ADR-0017](docs/requirements/decisions/0017-calculation-cache-and-chartspec.md)).
- **LLM отделена от расчёта.** Детерминированные операции не проходят через
  agent runtime; будущий runtime располагается за interpretation handler
  ([ADR-0020](docs/requirements/decisions/0020-agent-runtime-behind-handlers.md)).
- **Наблюдаемость и данные.** Полные DEBUG payload помогают находить
  межкомпонентные дефекты, но не считаются production-safe
  ([ADR-0028](docs/requirements/decisions/0028-full-debug-component-boundary-payloads.md),
  [ADR-0034](docs/requirements/decisions/0034-birth-data-and-terms-of-use.md)).
- **Research corpus** получает только whitelist-проекцию признаков
  ([требования](docs/requirements/component_responsibilities/exact-orb_research_corpus.md),
  [ADR-0023](docs/requirements/decisions/0023-research-corpora-and-consent.md)).

### Архитектура как исполняемое ограничение

Правило зависимости, которое можно проверить, становится тестом.
[`tests/test_module_boundaries.py`](tests/test_module_boundaries.py) помимо разбора
импортов импортирует модули в отдельном процессе (транзитивные протечки) и сканирует
AST research-слоя на скрытые входы: `datetime.now()`, `uuid4()`, `random` и чтение
`os.environ`. Такие проверки ловят нарушения заданных границ даже при зелёных
функциональных тестах.

Проверяемые архитектурные инварианты закрепляются автоматическими тестами;
остальные ограничения контролируются при review.

Подробнее: [component responsibilities](docs/requirements/component_responsibilities/),
[sequence diagrams](docs/sequence_diagrams/), [реестр ADR](docs/requirements/decisions/README.md).

## Известные ограничения

Ограничения и условия возврата собраны в
[реестре технического долга](docs/project_management/technical_debt.md).

Миграционная опись ещё требует согласования недостающих обязательных реквизитов;
исходные решения и ограничения сохраняются.

| Ограничение | Где отслеживается |
|---|---|
| Методология проверена только одним оператором, совмещающим все роли; работа распределённой команды и интеграции с корпоративными системами не проверялись | Этапы 2–3 развития методологии |
| Интерпретации нет; соляр и синастрия не входят в текущие требования | Roadmap M2 |
| Публичный запуск закрыт: нет страницы условий использования, общего IP-limit на прокси, решений по PII в журналах | DEBT-UI-001, DEBT-HTTP-002, DEBT-LOG-001, ADR-0034 |
| Нет CI; воспроизводимость golden-эталонов на других платформах не подтверждена | Roadmap M1-11 |
| Один property-тест конфигураций аспектов пропущен до исправления генератора | DEBT-CALC-001 |
| Расчётный движок читает процессную конфигурацию | DEBT-ARCH-001 |
| NatalTool вызывает расчёт мимо ChartArtifactResolver | Roadmap M3-1 |
| CLI не проходит через application-слой | — |

## Что дальше

Развитие методологии: сначала проверка изменений на одном полигоне,
затем разделение ролей между участниками enterprise-команды, после этого —
интеграции с Jira, Confluence и другими системами. Автоматизация состояний,
переходов и запуска ролевых агентов должна закреплять уже проверенный процесс,
а не подменять его. Сейчас состояние change хранится в Markdown рядом с кодом.

Развитие полигона:

- **M1 — UI и развёртывание.** Колесо карты (M1-8), перенос прототипа V2
  (M1-8.1), условия использования (M1-9), замеры конкурентности, CI,
  развёртывание и сквозная приёмка (M1-10…M1-13).
- **M2 — интерпретация.** InterpretSelectionHandler → InterpretationService
  → LLM Gateway, с отбором evidence, проверкой выхода на «чужие» факты
  и бюджетом расходов.
- **M3 — агентный слой.** Agent Runtime, tools и streaming.

Сначала детерминированный расчёт и lifecycle карты, затем проверенная
интерпретация и только после этого — runtime агентов.
