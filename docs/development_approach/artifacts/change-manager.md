# Шаблоны рабочих документов руководителя изменения

Руководитель изменения ведёт три документа: черновое описание, согласованный план и итоговую приёмку. Все вопросы,
варианты, рекомендации и принятые решения хранятся в отдельном
[едином реестре решений](decision-register.md). Ролевые документы и план ссылаются на строки `DP-*` и не копируют их.

## Термины

- **Изменение** — ограниченная работа от сформулированной потребности до принятого результата.
- **Интеграционная ветка** — ветка `change/*`, которая собирает результаты всех ролей по одному изменению.
- **Коммит Git** — зафиксированное состояние файлов с уникальным идентификатором.
- **`HEAD` ветки** — последний коммит выбранной ветки Git на момент проверки.
- **`main`** — основная ветка проекта, от которой начинается изменение. После создания `change/*` рабочей исходной
  точкой ролей становится `HEAD` интеграционной ветки.
- **Зафиксированная версия** — конкретный коммит и набор документов, использованные как исходная точка.
- **ADR** — запись об архитектурном решении. Архитектурная строка реестра ссылается на ADR.
- **Подтверждение** — проверяемая ссылка на документ, комментарий, коммит, результат проверки или протокол.
- **`FIND-*`** — идентификатор найденной проблемы, противоречия, риска или неопределённости.
- **`DP-*`** — стабильный идентификатор строки единого реестра. Он сохраняется от открытого вопроса до принятого или
  заменённого решения.

## Статусы изменения

| `ChangeStatus` | Когда используется |
|---|---|
| `INTAKE` | Потребность обсуждается, исходные сведения ещё собираются. |
| `DRAFT` | Черновое описание создано, но функциональный анализ ещё не завершён. |
| `ANALYSIS` | Функциональный аналитик уточняет требования, сценарии и вопросы для решения. |
| `ALIGNMENT` | Руководитель сопоставляет результаты ролей и согласует план. |
| `READY_FOR_DEVELOPMENT` | Требования, обязательные решения, оценки и план позволяют начать разработку. |
| `IN_DEVELOPMENT` | Разработчик выполняет согласованный план. |
| `READY_FOR_TEST` | Реализация передана на независимую проверку. |
| `IN_TEST` | Тестировщик выполняет проверку. |
| `READY_FOR_ACCEPTANCE` | Результаты ролей и подтверждения готовы для итогового решения. |
| `ACCEPTED` | Результат принят и изменение завершено. |
| `REVORK` | Результат проверки возвращён указанной роли; записаны причина, исправление и условие повторной передачи. |
| `PARTIALLY_BLOCKED` | Часть работы остановлена, но независимые задачи могут продолжаться. |
| `BLOCKED` | Следующий обязательный шаг невозможен до решения указанной проблемы. |
| `DEFERRED` | Работа отложена; записаны состояние продолжения, ответственный и условие возврата. |
| `REJECTED` | Потребность, план или результат отклонены уполномоченным владельцем. |

Статусы строк решений определены в [едином реестре](decision-register.md#статусы-строки).

## Кто заполняет документы

Пользователь формулирует потребность, отвечает на содержательные вопросы и принимает решения в своей области. Агент
руководителя сам заполняет служебные поля и не просит пользователя переносить сведения в таблицы.

Агент в роли руководителя изменения:

1. восстанавливает исходное состояние по репозиторию и текущей ветке `change/*`;
2. создаёт черновое описание и единый реестр решений;
3. готовит отдельные задания функциональному аналитику, разработчику и тестировщику от общего исходного коммита;
4. собирает ролевые документы и следит, чтобы вопросы и рекомендации попадали в соответствующие строки `DP-*`;
5. получает решения владельцев и проверяет подтверждения, не выбирая за них;
6. составляет план из ссылок, оценок и контрольных результатов;
7. после разработки и проверки оформляет итоговую приёмку.

Если платформа не запускает ролевых агентов автоматически, руководитель передаёт пользователю готовые задания для
отдельных задач. Отсутствующий результат роли не заменяется предположением руководителя.

## 1. Черновое описание изменения

### Назначение

Документ передаёт потребность и предварительные границы до функционального анализа. Статус `DRAFT` означает, что они
могут измениться после консультаций ролей.

Порядок поиска и приоритет источников задаёт
[skill руководителя изменения](../skills/change-manager/SKILL.md#первичный-анализ-входных-материалов). В черновике
сохраняется только фактически прочитанный набор: путь, причина относимости и проверенная версия.

Неясный вопрос не описывается повторно в черновике. Руководитель создаёт строку `DP-*` в едином реестре, а здесь хранит
ссылку на baseline реестра и нужные идентификаторы.

### Что означает каждый пункт

| Пункт | Что написать и зачем это нужно | Пример |
|---|---|---|
| Название | Коротко назвать требуемый результат, а не способ реализации. | `Восстановление текущей карты после обновления страницы` |
| Статус изменения | На этом этапе используется `DRAFT`. | `DRAFT` |
| Руководитель изменения | Назвать владельца актуальности черновика, плана и реестра. | `Ксения Баранова` |
| Интеграционная ветка | Указать ветку, куда возвращаются результаты ролей. | `change/http-api-and-session-middleware` |
| Исходная точка | Зафиксировать текущий `HEAD` ветки `change/*` перед выдачей заданий. Коммит `main` записывается отдельно только как происхождение ветки. | `f11275c — HEAD change/http-api-and-session-middleware` |
| Входные материалы | Перечислить фактически прочитанные правила, требования, ADR, диаграммы, планы, код и проверки и объяснить их связь с потребностью. | `src/exact_orb/session/state.py — текущее состояние сессии; tests/session/test_state.py — проверки переходов.` |
| Потребность пользователя | Описать, кого затрагивает проблема, когда возникает, что происходит сейчас и какой результат нужен. Технические термины объяснить. Предельный объём — 3000 знаков. | `После обновления страницы пользователь теряет уже построенную карту и вынужден вводить данные повторно.` |
| Ожидаемый результат | Описать наблюдаемое состояние без выбора классов, библиотек и внутренней реализации. | `После обновления страницы отображается сохранённая карта либо понятное сообщение об её отсутствии.` |
| Предварительные границы | Назвать предполагаемые включения и исключения. До консультаций это гипотеза. | `Входит одна текущая карта; история карт не входит.` |
| Известные ограничения | Указать действующие решения, даты, зависимости и требования, которые роли не могут менять самостоятельно. | `Новое сетевое хранилище не добавляется; действующие ADR сохраняются.` |
| Реестр решений | Дать путь, baseline и идентификаторы строк, связанных с изменением. Содержание строк не копировать. | `http-api-and-session-middleware-decisions.md @ f11275c; DP-HTTP-04.` |
| Задания ролям | Для каждой роли указать исходные материалы, `FIND/DP` IDs, конкретный результат и условие завершения. | `Developer: проверить реализуемость DP-HTTP-04 и дать диапазон оценки.` |
| Признаки успеха | Назвать наблюдаемые признаки удовлетворения потребности. Это ещё не полный test plan. | `После обновления сохранённая карта отображается; повторный ввод не требуется.` |

## 2. Согласованный план изменения

### Назначение

План связывает утверждённые baselines, контрольные результаты, зависимости, оценки и календарь. Он не повторяет
пользовательскую потребность, полные границы, ролевые выводы или решения. Для них указываются ссылки на черновик,
requirements, handoff и единый реестр.

Если консультации изменили цель, границы или ограничения, план записывает только отличие от зафиксированного черновика и
его основание. При отсутствии отличий указывается `нет`.

### Что означает каждый пункт

| Пункт | Что написать и зачем это нужно | Пример |
|---|---|---|
| Статус изменения | Во время согласования используется `ALIGNMENT`; после выполнения gate — `READY_FOR_DEVELOPMENT`. | `ALIGNMENT` |
| Baselines | Сослаться на черновик, исходные нормативные требования, утверждённые требования/scenarios change и единый реестр с точными коммитами. | `current/http_api.md @ a1b2c3d + changes/http-api/requirements.md @ d4e5f6a` |
| Ролевые основания | Дать по одной ссылке на handoff Analyst, Implementation Plan с estimate Developer и testability/estimate Tester. Выводы из них не пересказывать. | `developer-implementation-plan.md @ d4e5f6a` |
| Изменения относительно черновика | Зафиксировать только согласованные изменения цели, границ или ограничений и их источник. | `История карт исключена по DP-HTTP-07.` |
| Контрольные результаты | Назвать межролевые результаты и gates, включая подготовку чистовой редакции Analyst и сверку Tester перед финальной приёмкой. | `DEL-03 — перенос принятой дельты в current/ и сверка; evidence — карта переноса и acceptance report.` |
| Календарь | Разместить контрольные результаты во времени по оценкам и зависимостям ролей. | `Разработка 3–7 октября; проверка 8–9 октября.` |
| Открытые элементы | Перечислить только идентификаторы `FIND/DP`, которые остаются открытыми, и ссылку на их источник. Детали не копировать. | `FIND-HTTP-021; DP-HTTP-09.` |
| Условия начала | Дать проверяемый gate со ссылками. Blocking строки реестра должны иметь `ACCEPTED` и evidence. | `DP-HTTP-04 — ACCEPTED в реестре @ a1b2c3d.` |

## 3. Итоговая приёмка изменения

### Назначение

Приёмка фиксирует фактически поставленный результат, отклонения от плана и управленческий вывод. Она ссылается на
исходный черновик, согласованный план, реестр решений и ролевое evidence. Полные решения и ролевые отчёты сюда не
копируются.

### Что означает каждый пункт

| Пункт | Что написать и зачем это нужно | Пример |
|---|---|---|
| Статус изменения | `ACCEPTED`, `REVORK`, `REJECTED` или `DEFERRED`; для всех, кроме принятия, указать причину и следующий владелец. | `REVORK: Tester обнаружил blocking defect; исправляет Developer.` |
| Проверенные baselines | Указать точный план, реестр решений и commit реализации, который проверял Tester. | `implementation a1b2c3d; decisions d4e5f6a.` |
| Чистовые требования | Дать ссылки на подготовленную редакцию, карту переноса Analyst и сверку Tester по [правилам требований](../../requirements/README.md). | `current/http_api.md @ d4e5f6a; карта в changes/http-api/analysis.md; сверка Tester.` |
| Поставленный результат | Кратко описать фактически доступное поведение и сослаться на evidence. | `Действующая сессия возвращает сохранённую карту; TEST-EV-12.` |
| Отклонения от плана | Назвать только непоставленное или изменённое относительно согласованного плана и связанный `FIND/DP`. | `История карт не поставлена согласно DP-HTTP-07.` |
| Результаты ролей | Дать статус и ссылку на итоговый handoff каждой роли без пересказа документа. | `Tester — PASS; acceptance-evidence.md @ a1b2c3d.` |
| Фактические проверки | Указать окружение, точные команды или действия и реальные результаты. | `pytest tests/http/test_current_chart.py — 12 passed.` |
| Ограничения и риски | Сослаться на открытые `FIND/DP` и их актуальный baseline. | `DP-HTTP-09 — DEFERRED до 2026-10-15.` |
| Что не проверено | Назвать непроведённую проверку и влияние на уверенность. | `Промышленное окружение не проверялось.` |
| Итоговое решение | Связать статус с фактическим результатом, обязательным evidence и открытыми blockers. | `ACCEPTED: критерии поставки подтверждены, blocking items отсутствуют.` |

## Проверка качества заполнения

Перед передачей документа руководитель убеждается, что:

1. исходные документы и baselines указаны точными ссылками;
2. содержание решений существует только в едином реестре, а остальные документы используют `DP-*`;
3. рекомендации ролей подписаны и не выданы за решение владельца;
4. оценки принадлежат Developer и Tester;
5. каждый статус готовности имеет проверяемое подтверждение;
6. plan содержит межролевые результаты, а не копию implementation plan;
7. отложенная работа имеет причину, владельца и условие возврата.
8. для финальной приёмки есть карта переноса требований и сверка Tester; их версии совпадают с подготовленной чистовой редакцией.
