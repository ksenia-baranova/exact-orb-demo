# Единый артефакт Manager

Manager создаёт папку change и manager_artifact.md и индексы участвующих ролей по process.md, раздел 7. Его основной файл:

`docs/project_management/change_plans/<change-id>/manager_artifact.md`

Он объединяет brief, текущую сводку, задания ролям, реестр DP, оценки и Change Plan, журнал переходов и итоговую приёмку. Корневые индексы остальных ролей — `analyst_artifact.md`, `developer_artifact.md`, `tester_artifact.md`; подробные требования, планы и evidence находятся в `analyst/`, `developer/`, `tester/`, дополнительные материалы Manager — в `manager/` и передаются ссылками с версиями.

Состояния, события и условия переходов определены в [process.md](../process/process.md). Manager назначает задания, reviewers и допуски; подтверждённые события ролей обновляют служебную сводку и журнал по правилам сборки. По умолчанию применяется минимальный ручной режим раздела 1.1 процесса; метаданные сборщика добавляются при выборе автоматизации. Авторские verdicts и явные решения сохраняются. [Заполненный учебный пример](examples/example-limit-boundary/manager_artifact.md) показывает обновление main без повторной приёмки неизменного поведения.

## Как заполнять

1. На старте создай manager_artifact.md: change ID, Owner, Manager, исходный main SHA, ветку и сводку. Участие ролей отметь в таблице; для неназначенной / неучаствующей роли файл не создавай. Индексы участвующих ролей и подробные материалы — по разделу 7 процесса; малый вариант допускает один файл.
2. Записывай прочитанные источники, причину относимости и проверенный commit по [skill Manager](../skills/change-manager/SKILL.md#первичный-анализ-входных-материалов).
3. Ролевые задания содержат входы, разрешённый объём, результат, reviewer, критерий принятия, сроки исполнения / ответа / эскалации и адресата эскалации. Консультация и выполнение — отдельные задания.
4. DP оформляются одной записью в разделе реестра по [шаблону DP](decision-register.md). Требования и handoffs ссылаются на неё, сохраняя собственные материалы и evidence.
5. План заполняется по оценкам ролей. Обновляй затронутые оценки при изменении scope и зависимостей.
6. Журнал объясняет каждый переход. Приёмка относится к названному scope и проверенным версиям; финальная интеграция записывается отдельно.
7. Для малого варианта сокращённого маршрута ([process.md](../process/process.md), раздел 3.4) используй [шаблон малого изменения](#шаблон-малого-изменения) вместо полного.

## Перенос и допуск финальной интеграции

После финальных approvals и приёмки Owner назначь перенос / сверку только изменённых требований и sequences по process.md, раздел 6.2. Если изменений нет, достаточно подтверждения Tester на G5, без нового задания. Ошибка переноса → REWORK задания при сохранении ACCEPTED и «Поставка: нет»; противоречие контракта → ANALYSIS. При неизменной семантике повторная приёмка не нужна; после merge фиксируй MergeSHA и сверку поставки.
