# Единый реестр решений

Для каждого нового change ведётся один реестр как раздел
`docs/project_management/change_plans/<change-id>/artifacts.md#decision-register`.
В нём вопрос проходит весь путь от обнаружения до решения. Исторические реестры сохраняют свои опубликованные пути.
Новый идентификатор после принятия решения не создаётся: одна строка `DP-*` хранит вопрос, варианты, рекомендации,
решение владельца и подтверждение.

Ролевые requirements, планы и handoff не повторяют содержание строки. Они указывают baseline реестра и нужные
идентификаторы `DP-*`. Так рекомендация одной роли не превращается в решение из-за копирования в чужой документ.

Если выбор меняет архитектурные границы, строка связывается с ADR. Действующий ADR остаётся источником архитектурного
контракта, а реестр показывает, какой вопрос привёл к нему и где находится решение.

## Статусы строки

| `DecisionStatus` | Когда используется |
|---|---|
| `OPEN` | Вопрос, контекст и владелец записаны; сведений для сравнения вариантов пока недостаточно. |
| `IN_REVIEW` | Названные роли дополняют варианты, evidence и рекомендации. |
| `READY_FOR_DECISION` | Обязательные консультации завершены; владелец может сделать выбор. |
| `ACCEPTED` | Владелец выбрал вариант, объяснил основание и дал проверяемое подтверждение. |
| `DEFERRED` | Решение отложено; указаны ответственный, дата или условие возврата и влияние на change. |
| `SUPERSEDED` | Решение заменено другой строкой `DP-*` или ADR, на которые дана ссылка. |
| `REVOKED` | Владелец отменил ранее принятое решение без замены; влияние на продолжение change указано явно. |

## Кто заполняет строку

1. Change Manager создаёт файл, назначает идентификаторы, поддерживает baseline и проверяет полноту blocking строк.
2. Роль, обнаружившая вопрос, заполняет вопрос, контекст, различающий пример и связанные источники.
3. Functional Analyst, Developer, Tester и Technical Reviewer добавляют только свои варианты, evidence и подписанные
   рекомендации в ту же строку.
4. Только названный decision owner заполняет выбор, обоснование, дату и подтверждение и переводит строку в `ACCEPTED`.
5. Change Manager следит, чтобы требуемые обновления были выполнены, но не принимает решение вместо владельца.

При параллельной работе роль может вернуть Manager готовое изменение конкретной строки. После интеграции содержимое
решения хранится только в реестре; ролевой handoff оставляет ссылку на `DP-*`.

## Что содержит одна строка

| Колонка | Подробное содержание |
|---|---|
| ID | Стабильный идентификатор `DP-<ОБЛАСТЬ>-NN`, который не меняется после принятия решения. |
| Статус и gate | `DecisionStatus`, этап или work item, который зависит от ответа, и допустимость независимого продолжения. |
| Вопрос, контекст и пример | Один однозначный вопрос; причина его появления; участники; конкретный сценарий, в котором варианты дают разное наблюдаемое поведение, стоимость или риск. |
| Источники | Связанные `FIND-*`, requirements, код, тесты, комментарии и ADR с проверенной версией. |
| Владелец и консультанты | Роль и имя владельца выбора; роли, чьё заключение требуется до решения. |
| Варианты и влияние | Для каждого реального варианта: что произойдёт, плюсы, минусы, влияние на пользователя, разработку, тестирование, эксплуатацию и обратимость. |
| Рекомендации ролей | Отдельно подписанная рекомендация каждой консультирующей роли с основанием. Пустое поле не трактуется как согласие. |
| Решение владельца | Выбранный вариант, однозначное правило поведения, обоснование, дата и роль владельца. До выбора указывается `не принято`. |
| Последствия и evidence | Польза, принятый риск, отложенная работа, обязательные обновления, ссылка на подтверждение и ADR при необходимости. |

## Подробный пример одной строки

Пример показывает полноту заполнения и не является решением проекта.

| ID | Статус и gate | Вопрос, контекст и различающий пример | Связанные источники | Владелец и консультанты | Варианты и влияние | Рекомендации ролей | Решение владельца и обоснование | Последствия, обновления и подтверждение |
|---|---|---|---|---|---|---|---|---|
| `DP-HTTP-04` | `ACCEPTED`<br>Блокировал утверждение требований и implementation plan. | **Вопрос:** должна ли система автоматически повторять построение карты после истечения времени ожидания?<br>**Контекст:** ответ об истечении времени не доказывает, что первый расчёт остановлен.<br>**Пример:** клиент получает timeout, автоматически повторяет запрос, а первый расчёт позднее тоже завершается; появляются два результата. | `FIND-HTTP-019` — исход операции после timeout неизвестен.<br>`http_api.md @ a1b2c3d` — сценарий восстановления.<br>`test_timeout.py @ a1b2c3d` — проверяемое текущее поведение. | **Владелец:** Change Manager — Ксения Баранова.<br>**Консультанты:** Functional Analyst, Developer, Tester. | **A — автоматический повтор:** быстрее для пользователя; риск двойного действия; сложнее доказать безопасность.<br>**B — только явный повтор:** исключает скрытое повторение; требует состояния восстановления в интерфейсе.<br>**C — сначала запрос состояния:** точнее восстанавливает результат; требует дополнительного контракта и оценки. | **Analyst:** B до появления однозначного контракта состояния.<br>**Developer:** B реализуем в текущих границах; C требует отдельной оценки.<br>**Tester:** B имеет однозначные negative scenarios; для A нет наблюдаемого доказательства остановки первого расчёта. | **Выбрано:** B.<br>**Правило:** клиент не повторяет запрос автоматически; пользователь может повторить действие после получения текущего состояния.<br>**Обоснование:** исход первого запроса после timeout неизвестен, поэтому автоматический повтор может выполнить действие дважды.<br>**Дата:** 2026-10-01. | **Последствия:** нужен сценарий восстановления и дополнительное состояние интерфейса.<br>**Риск/отложено:** автоматический повтор отложен до появления идемпотентного контракта.<br>**Обновить:** requirements, acceptance scenarios, implementation plan и test plan.<br>**Подтверждение:** комментарий владельца в change request №37 от 2026-10-01.<br>**ADR:** не требуется. |
