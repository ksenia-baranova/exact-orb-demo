# Промт Developer: шаблон, пояснения и примеры

Промт описывает один проверяемый шаг implementation plan. Его пишет Developer, который выбирает порядок реализации
и проверок, задаёт границы работы и передаёт исполнителю достаточный контекст. Промт связан с требованиями,
но не заменяет их. Независимый test plan и acceptance evidence остаются у Tester.

## Как пользоваться

1. Прочитай [skill Developer](../skills/developer/SKILL.md), текущую карточку плана и требования change.
2. Выбери подход к разработке по риску, существующему покрытию и готовности контракта.
3. Скопируй [заготовку](#заготовка-для-копирования), заполни её по пояснениям ниже.
4. Сохрани новый файл в `prompts/<YYYY-MM-DD>/<change-id>/<NN>-<topic>.md`, свяжи его с карточкой `DEV-*`.
   В существующей серии используй её структуру и нумерацию. Исторические промты не редактируй.
5. Проверь источники, ссылки, команды и условия готовности. Подготовленный промт исполняется только в рамках
   уже разрешённой задачи или плана; создание файла само по себе не является разрешением на запуск.

Нумерация ниже помогает заполнить шаблон. Для простого задания разделы можно объединять; неприменимый раздел
сопровождай короткой причиной. Объём текста должен помогать исполнению конкретного шага.

**Как читать примеры:** это иллюстрации на материале исторических промтов репозитория. `REQ-DEMO-*`, `AS-DEMO-*`
и `DEV-DEMO-*` — условные IDs, `<sha>` — заполнитель. Примеры не утверждают наличие текущего дефекта,
не задают новые требования и не сообщают о выполненных здесь тестах. В настоящем промте используй актуальные IDs,
пути, commit и исходы из утверждённого контракта.

## Подробное описание разделов

### 1. Что делаем и зачем

Объясни проблему человеческим языком: что сейчас мешает пользователю или работе системы, что изменится после этого
шага и зачем нужен именно этот результат. Назови наблюдаемую границу шага. Для внутренней задачи объясни, какой риск
или зависимость она снимает. Формулировок «реализовать по ТЗ» и перечня классов недостаточно.

**Пример:**

> Одинаковое название города может содержать разные пробелы, регистр и букву «ё». Подготовим единый ключ поиска,
> чтобы каталог одинаково обрабатывал такие варианты. Пустой запрос и слишком длинный ключ должны возвращать
> определённые контрактом причины отказа. Этот шаг проверяет нормализацию строки; сам поиск в SQLite выполняется
> отдельным work item.

### 2. Паспорт, источники и готовность

Укажи change, work item, ветку/worktree, исходный commit и ссылку на карточку плана. Зафиксируй **обе части**
контракта: исходные нормативные требования и утверждённые требования/сценарии change с их версиями по
[правилам требований](../../requirements/README.md). Добавь относящиеся к шагу REQ/AS, ADR, диаграммы, код и тесты.
Для решений укажи baseline [единого реестра](decision-register.md) и применимые `DP-*`, без копирования решения.

Условия готовности должны быть проверяемыми: нужный интерфейс существует, зависимый шаг завершён, обязательное
решение принято. Исполнитель проверяет фактические Git state и код, а не доверяет историческому статусу промта.
При расхождении baseline укажи, что сверить заново; не предписывай автоматически переключать ветку или откатывать файлы.

**Пример заполнения:**

```text
Change: place-query-normalization; work item: DEV-DEMO-01.
План: <путь>#DEV-DEMO-01; checkout: <путь>, ветка: <ветка>, исходный HEAD: <sha>.
Исходный контракт: <нормативный путь>#<пункт> @ <sha>.
Контракт change: docs/requirements/changes/<change-id>/requirements.md @ <sha>, REQ-DEMO-01;
scenarios.md @ <sha>, AS-DEMO-01…03.
Реестр решений: <путь> @ <sha>; применимые DP: нет.
Перед работой: проверить git status --short, прочитать normalize_place_query и существующие тесты;
сверить порядок валидации и убедиться, что связанные решения не блокируют этот шаг.
```

### 3. Границы изменений и инварианты

Назови разрешённые файлы или узкие области и назначение каждой правки. Для нового файла обозначь, что его предстоит
создать; не представляй будущий файл существующим. Укажи существенные инварианты и исключённые соседние шаги.
Включи необходимые тесты, fixtures и документацию в разрешённую область заранее. Если требуется расширение, объясни
его причину и владельца вопроса вместо скрытой правки за пределами задания.

Сохраняй пользовательские изменения. Разрешение на реализацию не означает разрешения на commit, push или PR.

**Пример:**

```text
Разрешено:
- src/exact_orb/birth/places.py — только порядок и результат нормализации;
- tests/test_place_search_contracts.py — сценарии этого контракта, без дублирования существующих;
- <implementation-plan> — карточка DEV-DEMO-01 и фактический журнал выполнения.
Инварианты: существующие lookup-исходы и публичные модели сохранены; внутри normalizer нет I/O.
Вне шага: SQLite adapter, builder, HTTP, новые зависимости, изменение продуктовых лимитов.
Git: сохранить несвязанные изменения и index; commit/push/PR не поручены.
```

### 4. Задача и наблюдаемый результат

Опиши конкретное изменение поведения или внутреннего контракта на ответственном слое. Перечисли входы, выходы,
существенные переходы состояния и ошибки. Разделяй обязательный контракт и свободу внутренней реализации:
не фиксируй приватный алгоритм без причины. Если исправляется дефект, приведи воспроизводимый сценарий,
известное расхождение expected/actual и доказанную причину либо поручение установить причину до исправления.

**Пример:**

> Согласно REQ-DEMO-01 длина ключа проверяется после нормализации. Строка из 201 символа Unicode-пробела
> после нормализации пуста и должна давать `InvalidPlaceQuery(code="EMPTY")`. Строка из 201 буквы должна
> давать `TOO_LONG`. Обеспечить этот порядок в `normalize_place_query`, сохранив остальные этапы валидации.
> Если исходный код уже выполняет оба условия, зафиксировать это и не создавать искусственное исправление.

### 5. Подход к разработке и его обоснование

Developer выбирает подход **до исполнения work item** по [критериям skill](../skills/developer/SKILL.md#выбери-подход-к-разработке).
Запиши выбор, конкретный риск, имеющееся покрытие, пробелы и порядок работы. Укажи, что даёт тест перед кодом
либо почему отдельный TDD-цикл здесь избыточен. Размер diff и фраза «простая задача» сами по себе не обоснование.
Если пользователь задал порядок, соблюдай его; если появилась новая существенная причина его изменить, объясни конфликт.

| Подход | Пример обоснования | Что должно быть проверено |
|---|---|---|
| Тесты → реализация (TDD) | Порядок ошибок нормализации определён, чистая функция доступна; пример с 201 пробелом ловит проверку длины до нормализации. Для отмены во время save тест с events фиксирует риск нарушения порядка. | Чувствительный тест до изменения, причина RED, затем GREEN; управляемые зависимости и положительный контроль. |
| Реализация → тесты | Нужно соединить готовые компоненты; отдельный RED-этап потребовал бы временных заглушек, а контракт связи уже ясен. | После сборки проверить реальный путь, аргументы, типизированные исходы и побочные эффекты до передачи Tester. |
| Существующее покрытие | Механическая правка сохраняет поведение, а конкретные существующие тесты проверяют затронутые ветки. | Назвать и запустить эти тесты; при найденном пробеле дополнить их. |
| Документальные проверки | Исправляются ссылки на существующие диаграммы; исполняемый код и контракт не меняются. | Проверить пути/якоря, согласованность, diff; синтаксис или рендер диаграмм — если они изменены. |

**Пример записи решения:**

```text
Подход: тесты → реализация, в одном промте.
Причина: требуется доказать порядок двух пересекающихся правил валидации.
Существующее покрытие: tests/test_place_search_contracts.py::test_invalid_queries_return_typed_outcomes_in_validation_order
и test_two_hundred_code_point_search_key_is_valid в том же файле; сначала проверить текущие параметры кейсов.
Пробел: если сценарий «201 Unicode-пробел → EMPTY» отсутствует, дополнить существующую параметризацию.
Порядок: воспроизведение → минимальное исправление при подтверждённом расхождении → целевые и связанные проверки.
Если текущий тест уже ловит дефект, использовать его; дублирующий regression-тест не создавать.
```

Отдельные промты RED и GREEN нужны только при полезной границе передачи или независимом результате. Обычно один
промт может включать оба шага. Если выбран порядок «реализация → тесты» и тесты вынесены отдельно, укажи зависимый
промт и условие завершения: обязательные проверки должны закончиться до `READY FOR TEST`.

Отказ от TDD не отменяет regression-тест программного дефекта, проверку нового поведения и принятые gates.
Существующее достаточное покрытие можно переиспользовать. Не создавай тесты ради формального RED/GREEN.

### 6. Сценарии, данные и ожидаемый результат

Для каждого существенного сценария зафиксируй связь с требованием, предусловия, конкретные данные/действие,
**expected result**, способ проверки и существующее либо новое покрытие. Expected result выводится из утверждённого
контракта до сравнения с реализацией. Укажи результат вызова, изменения состояния, допустимые побочные эффекты и их
отсутствие там, где это часть требования.

Проверь обычные данные, применимые границы и невалидные значения. Ожидаемый типизированный отказ на невалидном входе
означает успешное прохождение теста; неожиданный результат или исключение — расхождение с контрактом.
Для существенного утверждения «вызова нет» добавь положительный контроль достижимости пути. Для конкурентности
используй events/barriers/fake clock; timeout защищает от зависания и не доказывает порядок.

**Пример матрицы** (в реальном промте REQ/AS должны быть ссылками на конкретные пункты):

| Требование / сценарий | Данные или действие | Ожидаемый результат | Проверка и покрытие |
|---|---|---|---|
| REQ-DEMO-01 / AS-DEMO-01 | `"  Ёлка  "` | Ключ `"елка"`; типизированного отказа нет. | Вызов настоящей функции; переиспользовать тест канонического ключа. |
| REQ-DEMO-01 / AS-DEMO-02 | 199, 200 и 201 буква `а` | 199 и 200 — допустимые ключи; 201 — `InvalidPlaceQuery(code="TOO_LONG")`. | Проверить существующую параметризацию; добавить только отсутствующую границу. |
| REQ-DEMO-01 / AS-DEMO-03 | 201 Unicode-пробел `\u2003` | `InvalidPlaceQuery(code="EMPTY")`, без `TOO_LONG`. | Переиспользовать либо расширить тест порядка валидации. |
| REQ-DEMO-02 / AS-DEMO-04 | Отмена запроса после фактического входа в save | Save получает разрешение завершиться, его исход фиксируется, затем caller получает отмену. | Events `save_entered`/`allow_save_finish`; обычный успешный save как положительный контроль. Это отдельный work item. |

В настоящем промте оставляй строки только своего work item. В тестовом docstring или комментарии сохраняй ID
и путь/ссылку на соответствующее требование; в таблице укажи файл и node ID существующего теста либо явно обозначь
планируемый тест. Это даёт прослеживаемость в обе стороны. Матрица Developer не заменяет независимую матрицу Tester.

### 7. Наблюдаемость

Если шаг меняет межкомпонентный поток, сопоставь затронутую sequence diagram с событиями журнала: кто инициировал
действие, кому передал управление, в каком порядке и с каким исходом. Укажи нужную корреляцию и способ проверки.
Соблюдай уровни и состав полей из действующих ADR; не добавляй payload или новый logging-контракт по инициативе промта.
Для чистой функции без такого потока явно напиши, почему новые события не нужны.

**Примеры:**

> Нормализация — чистая функция без I/O; межкомпонентный поток и правила логирования не меняются. Новые события не нужны.

> Для защищённого сохранения сверить реальный вход в save, завершение save и terminal-событие одной операции
> по действующей sequence. Успех фиксируется после подтверждения save, завершение caller отменой — после terminal.
> Имена событий и поля корреляции взять из указанного ADR и существующего logging-контракта.

### 8. Команды проверок и пределы свидетельств

Дай воспроизводимые команды, рабочий каталог и нужное окружение. Используй реальные пути и инструменты репозитория.
Назови, что проверяет каждый запуск, ожидаемый исход и условие перехода к следующему набору. Порядок для кода:
целевые → связанные → полный набор при требуемом gate; для текстовой правки достаточно соответствующих документальных
проверок. Не добавляй отсутствующие quality gates и не запускай сетевые или платные smoke без отдельного поручения.

**Пример команд для локального Python-окружения** (наличие `.venv` и нужных путей сверяется до исполнения):

```powershell
# Рабочий каталог — корень выбранного checkout.
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_place_search_contracts.py -q
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_birth_places.py tests/test_birth_resolver.py tests/test_birth_tz.py tests/test_module_boundaries.py -q
# Полный набор после успешных связанных проверок, если требуется gate этого шага.
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider -q
git diff --check
```

**Пример ожидаемого evidence:** на RED тест доходит до normalizer и выявляет неверный порядок исходов; на GREEN
целевые тесты проходят. В отчёте нужны настоящие node IDs, причина падения и exit code. Collection, ошибка импорта,
сломанная fixture или отказ доступа к temp не подтверждают проверку требуемого поведения. Исправь тестовую причину
в своей области или зафиксируй блокер; не скрывай его через `skip`, `xfail` или ослабление assertions.

### 9. Критерий завершения, ограничения и возвраты

Отдели завершение текущего шага от готовности всей функции и независимой приёмки. Назови критерии через наблюдаемый
результат и evidence. Приведи оставшиеся зависимости и владельцев: неоднозначная семантика — Analyst,
scope/сроки — Manager, архитектурный вопрос — Technical Reviewer. Продолжай независимые части при локальном блокере.

Для отдельного шага подготовки тестов допустим подтверждённый RED по ожидаемой причине; он не означает готовую
реализацию или пройденную приёмку. Для шага реализации обязательные проверки должны пройти. Падения будущих шагов
перечисли с причинами и ссылками на владельцев, не объявляя весь набор успешным.

**Пример:**

```text
Готово: подтверждены канонический ключ, границы длины и порядок отказов; целевые и необходимые связанные проверки
прошли; ссылки REQ/AS есть в таблице и тестах; фактический журнал обновлён.
Не доказано этим шагом: корректность SQLite-поиска, отсутствие SQL на невалидном запросе, поведение HTTP.
Если лимит или порядок исходов противоречит требованиям — finding Analyst; зависимую правку приостановить.
Если для результата нужен новый публичный исход — не вводить его самостоятельно.
```

### 10. Отчёт исполнителя и handoff

Задай формат фактического отчёта: результат, причина выбора/исправления, файлы, проверенная версия и состояние дерева,
команды, результаты и ограничения. Исполнение записывай в карточку implementation plan и
[Development Handoff](developer.md#3-development-handoff). Промт остаётся постановкой; текущий статус реализации
хранится в плане. Для TDD различай свидетельства RED и GREEN. Запланированные проверки не выдавай за выполненные.

**Пример заготовки отчёта:**

```text
Результат DEV-DEMO-01: <что фактически реализовано или какой блокер мешает>.
Подход: <выбор, фактический порядок и причина отклонения от плана, если было>.
Версия: <commit>, <чистое дерево / состав незакоммиченного diff>.
Изменены: <пути и назначение>; причина дефекта: <установленная причина либо не подтверждён>.
Проверки: <точная команда> — <exit code и фактический итог>; evidence: <путь/ссылка>.
TDD, если выбран: <node ID, причина RED, результат GREEN>.
Не проверено: <сценарии и причина>; остаток: <work item или finding, владелец>.
Следующий шаг: <кому передаётся результат и что готово к проверке>.
```
