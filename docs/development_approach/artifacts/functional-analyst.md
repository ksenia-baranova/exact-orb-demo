# Шаблоны артефактов функционального аналитика

Содержание решений хранится только в [едином реестре решений](decision-register.md). Analysis artifacts указывают baseline
реестра и идентификаторы `DP-*`, но не создают собственные описания вопросов или принятых решений.

Пути документов, форматы `DELTA`/`FULL` и порядок переноса определены в
[правилах требований](../../requirements/README.md). Заполненные артефакты не хранятся рядом с этими шаблонами.

## 1. Требования изменения

Файл: `docs/requirements/changes/<change-id>/requirements.md`. Копируй общий заголовок и нужный вариант описания
требований: дельту существующего поведения либо полную спецификацию обозначенной области. Сценарии и findings ведутся
по отдельным ссылкам, указанным в заголовке.

```markdown
# Требования изменения: <change-id>

**Статус:** DRAFT / READY FOR REVIEW / APPROVED
**Обоснование статуса:** <что подготовлено, какие согласования выполнены или что блокирует утверждение>
**Формат:** DELTA / FULL
**Область:** <какие требования/документы изменяются или впервые определяются>
**Входной commit change:** `<sha>`
**Исходные чистовые требования:** <пути, пункты и baseline commit; для новой области — отсутствуют>
**Ответственный:** Functional Analyst
**Версия реестра решений:** `<путь и commit>`
**Связанные решения:** `<DP-* IDs или нет>`
**Целевые чистовые документы:** `docs/requirements/current/<область>/...`
**Сценарии приёмки:** `scenarios.md`
**Findings и handoff:** `analysis.md`

## Назначение и границы

- ...

## Дельта требований (DELTA)

### REQ-<ОБЛАСТЬ>-NN. <Название>

- Операция: ADD / MODIFY / REMOVE.
- Исходный пункт: <путь#якорь @ commit; для ADD — отсутствует>.
- Целевой пункт: <путь в current/#якорь; для REMOVE — удаляемый ID и ссылки на последствия>.
- Сценарии приёмки: <AS-ID и ссылка в scenarios.md>.
- Основания: <DP/ADR/FIND IDs и ссылки без пересказа решений>.
- Новая полная формулировка: <условия, входы, результат, состояние, ошибки и ограничения; для REMOVE — не применяется>.
- Для REMOVE: <что прекращает действовать, последствия для сценариев/тестов/диаграмм и основание удаления>.

## Полная спецификация области (FULL)

**Создаваемая или заменяемая область:** <границы и исходные документы @ commit>

### REQ-<ОБЛАСТЬ>-NN. <Название>

<Полный наблюдаемый контракт требования с условиями, результатами, состоянием, ошибками и ограничениями.>

**Сценарии:** <AS-ID и ссылка в scenarios.md>
**Целевой чистовой пункт:** <путь в current/#якорь>

### Соответствие прежним требованиям при полной замене

| Исходное требование и commit | Сохранено / изменено / удалено | Новый пункт или основание удаления |
|---|---|---|
| <ID/путь#якорь @ sha> | <действие> | <ID/пункт или DP/ADR> |
```

## 2. Развёрнутый Finding

Раздел в `docs/requirements/changes/<change-id>/analysis.md`. Индекс findings в этом же файле содержит ссылки на полные
описания. Требования ссылаются на findings по ID, не копируя их содержание.

```markdown
## FIND-<AREA>-NNN. <Понятное название проблемы>

**Type:** requirement gap / conflict / risk / limitation / process gate
**Detected by:** <role>
**Owner:** <role, который должен устранить или принять>
**Status:** OPEN / IN REVIEW / CLOSED / ACCEPTED RISK
**Blocks:** <этап, work item или none>
**Related decision:** <DP-* или none>

### Кратко для Manager

<Что найдено, почему это важно для change и что случится без исправления или решения.>

### Где найдено

- Document/code/test: `<path>`
- Section/symbol/line: ...
- Review comment or command: ...

### Пример проявления

1. Исходное состояние: ...
2. Действие пользователя или системы: ...
3. Текущее или неопределённое поведение: ...
4. Ожидаемое свойство: ...

### Почему существующего контракта недостаточно

<Какие трактовки остаются допустимыми или какие источники расходятся.>

### Влияние

- User/API behavior: ...
- State/data: ...
- Development estimate: ...
- Testing: ...
- Operations/security: ...

<Заполняется только при закрытии.>
```

## 3. Вклад Analyst в единый реестр решений

Если finding требует выбора, Analyst создаёт или обновляет одну строку `DP-*` по
[шаблону реестра](decision-register.md#шаблон-единой-таблицы). В этой строке Analyst заполняет:

- однозначный вопрос, контекст и различающий пример;
- ссылки на findings и проверенные источники;
- наблюдаемые варианты и их влияние на пользователя и контракт;
- рекомендацию Analysis с основанием;
- decision owner, обязательных консультантов и blocking gate.

Поля решения владельца остаются `не принято`, пока владелец не даст evidence. Requirements и Analysis Handoff содержат
только baseline реестра и связанные `DP-*` IDs.

## 4. Полный пример Finding: ownership compute permit

Пример показывает форму finding и не является выводом проекта. Связанное решение `DP-HTTP-EXAMPLE` оформляется только в
едином реестре.

```markdown
## FIND-HTTP-EXAMPLE. Permit нельзя однозначно освободить по завершению HTTP request

**Related decision:** DP-HTTP-EXAMPLE

### Кратко для Manager

План связывает global compute permit с HTTP-запросом и предлагает дождаться `runtime.drain()`. Один single-flight leader
может обслуживать несколько запросов, а `drain()` ожидает все активные leaders. Поэтому система не знает, permit какого
запроса удерживает конкретный расчёт. При timeout capacity может освободиться, пока native calculation продолжается,
либо остаться занятой из-за несвязанной работы.

### Пример проявления

1. Request A получает permit и запускает calculation leader.
2. Request B с тем же ключом присоединяется к leader.
3. Request A получает HTTP timeout.
4. Calculation продолжает выполняться для B.
5. Освобождение permit A по завершению request занижает фактическую загрузку.

### Что требуется дальше

- Обновить строку `DP-HTTP-EXAMPLE` техническим evidence Developer и рекомендацией Tester.
```

## 5. Передача результатов анализа (Analysis Handoff)

Раздел в `docs/requirements/changes/<change-id>/analysis.md`. Этот документ передаётся на review вместе с требованиями
и сценариями; каждый путь сопровождается проверенной версией.

```markdown
## Передача результатов функционального анализа

**Статус:** READY FOR REVIEW / BLOCKED
**Обоснование статуса:** <готовые результаты, препятствия и следующий шаг>
**Исходные чистовые требования:** <пути/пункты и baseline commit>
**Требования change:** `requirements.md @ <sha>; DELTA/FULL; область`
**Сценарии change:** `scenarios.md @ <sha>`
**Версия реестра решений:** `<путь и commit>`

### Краткий вывод для менеджера

- ...

### Подготовленные артефакты

- Требования и сценарии: <точные ссылки>.
- Диаграммы: `docs/sequence_diagrams/<область>/... @ <sha>`.
- Связанные ADR: `docs/requirements/decisions/... @ <sha>`.
- Целевые чистовые документы: `docs/requirements/current/<область>/...`.

### Индекс замечаний

| ID и ссылка на раздел | Краткое влияние | Ответственный | Блокирует | Статус |
|---|---|---|---|---|
| FIND-... | ... | ... | ... | OPEN |

### Блокирующие решения

- <DP-* IDs или нет>

### Неблокирующие риски

- <FIND-* IDs или нет>

### Запрошенные проверки

- Developer: feasibility, technical dependencies, estimate и вклад в указанные строки DP
- Tester: testability, missing negative/boundary scenarios, estimate и вклад в указанные строки DP

### Выполненные проверки

- command — result

### Что не проверено

- ...
```

## 6. Подготовка переноса в чистовые требования

Раздел того же `analysis.md`, заполняемый Analyst перед финальной приёмкой. Карта фиксирует размещение принятого текста,
а результаты его проверки хранятся в acceptance evidence Tester. Merge в `main` подтверждает Manager отдельно по Git.

```markdown
## Перенос требований: <change-id>

**Утверждённые требования и сценарии change:** <пути и commits>
**Исходный нормативный baseline:** <пути/пункты и commit>
**Проверенная целевая ветка:** <ref и commit; результат проверки параллельных изменений>
**Commit подготовки чистовой редакции:** <sha / изменения ещё не закоммичены>

### Карта переноса

| ID требования/сценария | Исходный пункт и commit | Действие | Чистовой пункт | Основание и состояние переноса |
|---|---|---|---|---|
| <REQ/AS-ID> | <путь#якорь @ sha / новая область> | ADD/MODIFY/REMOVE/сохранено | <current/путь#якорь / удалённый ID> | <подготовлено / не перенесено и почему; ссылка на решение при исключении> |

### Согласованность

- Неизменённые требования сохранены: <проверенные области и evidence>.
- Перенос прежних путей: <старый → новый; прежний файл удалён или стал указателем>.
- Ссылки в актуальных требованиях, сценариях, diagrams, ADR и тестах: <команды и фактические результаты>.
- Сверка Tester: <ссылка на acceptance evidence и проверенный commit / ожидается>.
- Непоставленные пункты и ограничения: <IDs и ссылки на решения владельца>.

### Вывод для финальной приёмки

<Что подготовлено в change, что блокирует передачу Manager, какие подтверждения ещё требуются.>
```
