# AI-assisted development approach

**Статус:** DRAFT / WORK IN PROGRESS

**Дата начала формирования:** 2026-09-05

**Дата структурной ревизии:** 2026-09-30
**Назначение:** основные утверждения формирующегося метода разработки `exact-orb`.

> Этот документ фиксирует принципы метода. Конкретный рабочий цикл описан в [process.md](process.md), роли и ownership —
> в [roles.md](roles.md). Метод изменяется только на основании наблюдений из реальной разработки, а не одного
> рассуждения модели.

## 1. Назначение

`exact-orb` разрабатывается одним владельцем с активным использованием LLM. Модель участвует в исследовании вариантов,
формализации требований, реализации, тестировании и review. LLM расширяет пространство анализа и ускоряет работу, но не
является источником продуктовой семантики и не принимает решения вместо уполномоченной роли.

Короткая формула метода:

```text
намерение
    → пространство решений
    → явные вопросы и альтернативы
    → решение владельца
    → наблюдаемый контракт
    → согласованный план
    → ограниченная реализация
    → независимая проверка
    → evidence
    → принятие change
```

Подход соединяет:

1. **dialog-driven discovery** — намерение и пространство решений исследуются естественным языком;
2. **decision-driven specification** — существенные развилки получают владельца, варианты и явное решение;
3. **specification-driven implementation** — код создаётся после фиксации наблюдаемого контракта;
4. **test-backed acceptance** — мнение модели не является доказательством корректности;
5. **role-based ownership** — план, требования, реализация и acceptance evidence имеют разных владельцев;
6. **LLM-assisted review** — отдельный проход ищет контрпример и нарушения контракта.

## 2. Явная граница решения

Главный принцип:

> LLM может предлагать, исследовать, реализовывать и критиковать решение, но граница между предложением и разрешённым
> инженерным решением должна оставаться явной.

Рекомендация Analysis или Developer не становится решением из-за появления в документе. Принятое решение должно иметь:

- идентификатор;
- владельца;
- дату;
- выбранный вариант;
- краткое основание;
- evidence: comment, commit или approved artifact.

Finding остаётся отдельной сущностью. Вопрос, варианты, рекомендации и выбор владельца являются состояниями одной
строки `DP-*` в едином реестре решений. Change plan ссылается только на строки со статусом `ACCEPTED` и owner evidence и
не выводит approval из формулировки рекомендации.

## 3. Переносимый инженерный контекст

> Ни один контекст, критичный для продолжения разработки, не должен существовать только внутри текущей AI-сессии.

Документация достаточна для handoff, если новый исполнитель может восстановить:

- намерение change;
- принятые решения и ограничения;
- наблюдаемое поведение;
- выполненную работу;
- оставшиеся действия;
- открытые вопросы и их владельцев;
- evidence, на котором основан текущий статус.

Это не требует сохранять каждое промежуточное рассуждение. Фиксируется информация, без которой следующая роль вынуждена
заново реконструировать решение.

Искомое свойство процесса — заменяемость исполнителя:

```text
human → agent
agent A → agent B
agent → human
```

## 4. Артефакты отвечают на разные вопросы

| Артефакт | Вопрос |
|---|---|
| Change brief / plan | INTENT / DELIVERY — зачем выполняется change, что входит и как он поставляется? |
| Requirements и acceptance scenarios | WHAT — какое наблюдаемое поведение требуется? |
| Единый реестр решений | QUESTION / WHY — что требуется выбрать, какие варианты и рекомендации рассмотрены, что выбрано, кем и почему? |
| ADR | ARCHITECTURE WHY — какое архитектурное решение действует и с какими последствиями? |
| Sequence diagrams | INTERACTION — как участники взаимодействуют во времени? |
| Invariants | CONSTRAINTS — чего происходить не должно? |
| Implementation plan | HOW TO CHANGE — как Developer намерен реализовать согласованный контракт? |
| Code | IMPLEMENTATION — как система реализована сейчас? |
| Tests и acceptance evidence | EVIDENCE — что проверено и каким способом? |
| Known limitations / accepted risk | DEBT — что известно и намеренно пока не исправлено? |
| Git history | EVOLUTION — как система пришла в текущее состояние? |

Артефакты могут объединяться в одном файле, если ownership и источник истины остаются понятными. Процесс не требует
отдельного документа для каждого пункта таблицы.

## 5. Источники истины

Для выполнения задачи действует следующий приоритет:

```text
текущая явная задача и разрешённый scope
    ↓
принятые строки единого реестра решений и действующие ADR
    ↓
актуальные requirements и acceptance scenarios
    ↓
component responsibilities и invariants
    ↓
актуальные diagrams
    ↓
исполняемые tests и acceptance evidence
    ↓
текущая implementation
    ↓
historical prompts, experiments и свободное обсуждение
```

Существенное противоречие между источниками не разрешается молча. Оно оформляется как finding с описанием влияния и
владельца решения.

Для активного change актуальные requirements означают зафиксированный нормативный baseline плюс утверждённую дельту
или полную спецификацию изменяемой области. Перед финальным merge они сводятся в чистовую редакцию. Пути, границы `FULL`
и порядок переноса заданы в [правилах требований](../requirements/README.md); наличие черновика не меняет baseline.

Исторические prompts являются журналом ограниченных задач. После выполнения они не переписываются как действующая
спецификация.

## 6. Исполняемые проверки и evidence

> Там, где утверждение можно проверить механически, исполняемая проверка предпочтительнее мнения LLM или текстового
> соглашения.

Тесты и статические проверки подтверждают наблюдаемое поведение и архитектурные ограничения. Они не выбирают
продуктовую семантику и не заменяют решение владельца.

Evidence должно позволять отличить:

- проверенный факт от предположения;
- собранный тест от прошедшего теста;
- локальный commit от push, PR, approval и merge;
- структурную проверку diagram от успешного render;
- рекомендацию роли от принятого решения.

Уровень проверки выбирается по риску изменения. Component, contract, integration, boundary и full-regression проверки
решают разные задачи; ни один уровень не объявляется обязательным для каждого change. Mocks, stubs и fakes применяются на
внешних или листовых швах, а не вместо реального проверяемого взаимодействия.

## 7. Наблюдаемость как часть контракта

Для существенного межкомпонентного сценария требования описывают не только конечный результат, но и достаточное
наблюдаемое evidence переходов. По журналу или другому разрешённому сигналу должны восстанавливаться:

- инициатор и адресат существенного перехода;
- порядок взаимодействий;
- результат перехода;
- доступная корреляция операции;
- причина отказа без раскрытия запрещённого payload.

Sequence diagram, требования к событиям и acceptance checks должны описывать один и тот же поток. События начала и конца
операции недостаточны, если между ними скрыта передача управления, важная для диагностики или проверки поведения.
Observability evidence дополняет функциональные тесты, но не заменяет их.

## 8. Role ownership

Каждая роль владеет смыслом своих артефактов. Обнаружение проблемы в чужом артефакте создаёт finding или запрос на
изменение, но не даёт права молча менять его смысл.

Один человек может последовательно выполнять несколько ролей. В этом случае смена роли фиксируется явно, а решение
атрибутируется роли, в которой оно принято. Разные роли по возможности работают в отдельных сессиях с входом из
репозитория, чтобы переписка предыдущего агента не становилась скрытым источником истины.

Подробная модель приведена в [roles.md](roles.md).

## 9. Ограниченная единица исполнения

Implementation task или prompt должен быть достаточно самодостаточным, чтобы исполнитель мог восстановить цель, scope,
baseline, invariants, ссылки на источники истины, ожидаемые проверки и completion evidence без скрытой переписки.

Подготовка задачи и разрешение на её исполнение являются разными действиями. Для задачи различаются как минимум состояния
`DRAFT`, `APPROVED`, `EXECUTED` и `INVALIDATED`. Исторический prompt после исполнения сохраняется как журнал и не
переписывается в действующую спецификацию.

Единица исполнения ограничивается одним проверяемым результатом или тесно связанным набором изменений. Декомпозиция нужна,
когда части имеют разные decisions, owners, риски, проверки или могут приниматься независимо. Количество prompts и commits
само по себе не является метрикой качества.

## 10. Минимальный scope и разрешение действий

Implementation task разрешает только заявленное изменение. Она не даёт автоматического права:

- расширять scope;
- менять публичный контракт;
- принимать архитектурное решение;
- исправлять соседние проблемы;
- изменять артефакт другой роли;
- создавать commit, push, PR или внешнее сообщение без соответствующего поручения.

Независимая работа может продолжаться, если открытый вопрос блокирует только часть change.

## 11. Review ищет контрпример

Review не должен повторять рассуждение автора реализации. Его задача — найти сценарий, в котором diff нарушает
требование, invariant или обещанное доказательство.

Полезный review проверяет:

- негативные и boundary scenarios;
- несогласованность requirement, diagram, code и test;
- ложноположительный тест;
- скрытое решение без владельца;
- изменение поведения вне scope;
- отсутствие evidence для заявленного статуса.

Совпадение мнения двух LLM не создаёт независимое доказательство. Для значимых путей требуются детерминированные проверки
или независимое наблюдаемое evidence.

## 12. Критерий успешности change

Change успешен, если:

- пользовательское намерение связано с согласованным scope;
- существенные решения имеют владельца и evidence;
- requirements и acceptance scenarios описывают наблюдаемое поведение;
- реализация соответствует согласованному контракту;
- обязательные проверки фактически выполнены;
- открытые ограничения и риски явно приняты или блокируют завершение;
- новый исполнитель может продолжить работу по артефактам репозитория.

Количество документов, prompts, commits и комментариев само по себе не является показателем успеха.

## 13. Ограничения и статус метода

Подход остаётся экспериментальным. Он проверяется на реальных change и может изменяться при появлении evidence о лишних
gates, слабом handoff, высокой стоимости артефактов или повторяющихся ошибках ролей.

Особые ограничения текущего исследования:

- роли может выполнять один оператор;
- несколько ролей могут использовать модели одного семейства;
- успешный handoff не доказывает независимость review;
- документация может стать дороже создаваемого изменения;
- слишком подробный процесс способен скрыть реальный инженерный вопрос за статусами и таблицами.

Поэтому каждое правило должно оправдывать свою стоимость: предотвращать наблюдавшийся класс ошибок, обеспечивать handoff
или давать проверяемое evidence.
