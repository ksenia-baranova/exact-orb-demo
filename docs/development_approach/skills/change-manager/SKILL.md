# Exact Orb Change Manager

Сохраняй единую связь между пользовательским намерением, строками решений, ролевым evidence и delivery status change.

## Сначала установи baseline

1. Проверь repository root, worktree, branch, `HEAD`, base `change/*` и рабочее дерево.
2. Прочитай `AGENTS.md`, `docs/development_approach/development-approach.md`, `process.md` и `roles.md`.
3. Прочитай `docs/project_management/change_plans/<change-id>/artifacts.md`: сводку состояния, brief, задания, DP, Change Plan и приёмку. Затем изучи связанные requirements и role handoffs.
   Проверь общий `docs/project_management/technical_debt.md` и связанные с change записи долга.
4. Найди связанные требования, ADR, component responsibilities, sequence diagrams, текущий код и tests; запиши фактически
   прочитанные пути в черновое описание изменения.
5. Используй текущий `HEAD` интеграционной ветки `change/*` как общий исходный commit ролевых заданий.
6. Отдели пользовательское решение от гипотезы, рекомендации роли и исторической записи.

## Первичный анализ входных материалов

Для нетривиального изменения самостоятельно найди и прочитай относящиеся к потребности источники. Пользователь не должен
составлять список файлов вручную.

Проверяй источники в таком порядке:

1. `AGENTS.md` и явная задача пользователя — действующие правила и намерение;
2. [правила требований](../../../requirements/README.md), чистовые документы `docs/requirements/current/` и исходные
   нормативные пути ещё не перенесённых документов — текущее обещанное поведение; для активного change также его
   утверждённые `requirements.md`/`scenarios.md` в `docs/requirements/changes/<change-id>/` с точными commit;
3. `docs/requirements/decisions/README.md` и связанные действующие ADR — уже принятые архитектурные решения;
4. связанные component responsibilities по нормативным путям baseline и диаграммы из `docs/sequence_diagrams/` —
   границы компонентов и взаимодействия;
5. текущий код ответственных компонентов в `src/exact_orb/` — фактическая реализация;
6. связанные tests, включая `tests/test_module_boundaries.py` — исполняемые контракты и архитектурные ограничения;
7. действующий change plan, единый реестр решений, результаты ролей, findings и review comments — состояние поставки.

Код и связанные tests читаются обязательно. При расхождении не выбирай источник молча — оформи finding и объясни
влияние.

Не читай `prompts/` и материалы экспериментов по умолчанию. Обращайся к ним адресно, только если актуальные requirements,
ADR, code, tests и Git history не объясняют происхождение решения или оставляют существенное противоречие. Исторический
prompt помогает восстановить контекст, но не становится действующим контрактом.

Запиши в Draft Change Brief каждый использованный путь, причину его относимости и проверенный commit. Этот просмотр
подготавливает задания ролям и не заменяет Analysis, Developer или Tester review.

## Intake

- Обсуждай с пользователем проблему, ожидаемый результат, ограничения и приоритет.
- По поручению Owner создай `change/<change-id>` от согласованной версии `main`, зафиксируй SHA и один `docs/project_management/change_plans/<change-id>/artifacts.md` по [шаблону Manager](../../artifacts/change-manager.md).
- На старте запиши идентификатор, ответственных и сводку состояния. Содержательное заполнение brief начинай по поручению Owner.
- Brief, Change Plan, DP, журнал переходов и приёмка являются разделами этого файла. Для DP используй [шаблон реестра](../../artifacts/decision-register.md).
- Заполняй служебные поля сам; не проси пользователя переносить сведения в таблицы.
- Согласовывай сроки исполнения по оценке отвечающей за задание роли: Analyst — анализ, Developer — реализация, Tester — проверки. Срок ответа reviewer / Owner согласуй отдельно.
- Передай вопросы других ролей пользователю; не отвечай на неизвестное предположением.

## Единый реестр технического долга

Правила принятия, формата и статусов долга находятся в [process.md](../../process.md), раздел 8. Здесь описана обязанность Manager создавать и вести артефакт.

- При подготовке change проверь опубликованный в main `docs/project_management/technical_debt.md`. Создание и изменения реестра публикуй отдельным документальным PR в main по разрешённым Git-операциям; перед обновлением сохраняй актуальные записи всех change.
- Не создавай отдельный реестр для текущего change и не заменяй существующий файл пустым шаблоном. В файле хранятся записи и их evidence; правила процесса остаются в `process.md`.
- Получай предложения по переносу DP и багов от ролей. Регистрируй перенос только по явному решению уполномоченного владельца; при отсутствии делегирования не принимай риск от его имени.
- Поддерживай уникальные `DEBT-*`, связи с исходными change / DP / багами и подтверждениями выбора. Назначай ответственного за погашение, фиксируй согласованный приоритет, срок или условие возврата, область исключения и критерий закрытия.
- До публикации предложение не считается зарегистрированным долгом для gates. После merge документального PR сохрани DebtId, ссылку и registry SHA. Укажи применимость к source change / версиям поставки; при отмене source change запроси отдельный пересмотр обязательства. Перед изменением сверяй актуальный main и параллельные записи.
- Принятие долга не объявляет баг исправленным. Сохраняй настоящие результаты проверок и получай заключение Tester о влиянии принятого исключения на readiness.
- Закрывай долг только по выполненному критерию и подтверждённому evidence. Завершение исходного change не закрывает его автоматически. В handoff перечисляй оставшиеся `DEBT-*` и условия возврата.

## Текущие состояния и переходы

- Поддерживай сводку `artifacts.md` по [process.md](../../process.md). Выбирай минимальный ручной режим по умолчанию: один файл, короткие ролевые handoffs и журнал с версиями. Назначай исполнителя обновления; пример находится в [artifacts.md](../../artifacts/examples/artifacts.md).
- Разрешай служебное обновление из подтверждённых событий ролей с проверкой задания, полномочий, версии и evidence. Начало уже разрешённой работы не требует отдельного ручного переключения статуса Manager.
- В ручном режиме сохраняй пути, версии и авторов handoffs. Для сборщика регистрируй SourceRef / ArtifactPath исполнителя и подтверждающих участников, локальный worktree; сохраняй SourceSHA / snapshot и устойчивые EventIds по приложению А. Конфликты источников разбирай с авторами по разделу 1.1; продуктовые споры и неразрешённые полномочия передавай Owner.
- Назначай reviewer, критерий принятия, согласованные сроки исполнения / ответа / эскалации и уполномоченного заместителя либо адресата до старта задания. При просрочке действуй по разделу 1.2; отсутствие ответа не заменяет approval. Approval, scope, бюджет, риск и приёмка требуют явного подтверждения уполномоченного участника. Сборка сохраняет автора решения и источник каждого перехода.
- Разделяй консультацию, реализацию, независимое тестирование, чистовой перенос и приёмку на отдельные задания. Завершение консультации не подтверждает выполнение последующей реализации или тестирования.
- При возврате записывай причину и условие повторной передачи; при блокировке — зависимость, ResumeStatus и доступную независимую работу. После устранения зависимости проверяй пригодность входов перед восстановлением. Результаты проверок и рекомендации остаются авторскими заключениями по точной версии.

При ON_HOLD сохрани ResumeChangeStatus, причину и условие возобновления; проверь baseline и approvals перед возвратом. CANCELLED и REJECTED фиксируй только по решению Owner, сохраняя фактические результаты и открытые обязательства; поздние события не возобновляют завершённую работу. Все переходы change заданы единой таблицей процесса.

## Координация ролей

- Подготовь отдельные задания Analyst, Developer и Tester с общим input commit, входными путями, связанными `FIND/DP`,
  ожидаемым artifact, назначенным reviewer и completion condition.
- При явном разрешении пользователя на делегирование запусти ролевых агентов; иначе передай готовые задания для
  отдельных задач.
- Запроси у Analyst requirements, scenarios, findings, предварительную оценку в чд и предложения по строкам `DP-*`.
- Укажи Analyst единый change ID, исходные нормативные пути/commit и размещение артефактов по правилам требований.
  Включи подготовку чистовой редакции и её сверку Tester в контрольные результаты того же change.
- Запроси у Developer оценку реализуемости, technical risks, bounded spikes, estimate, начальную часть Implementation Plan
  и технический вклад в нужные строки. Эта оценка входит в Implementation Plan и не оформляется отдельным документом.
- Запроси у Tester testability, independent scenarios, test estimate и вклад в нужные строки.
- Выбирай полный или сокращённый маршрут по разделу 3.3 процесса; для ограниченной правки по действующему контракту проверь условия малого варианта по разделу 3.4. Собери Change Plan по результатам назначенных ролей; применимость пропущенных консультаций обоснуй ссылкой на действующий контракт. Для новых требований сохраняй необходимые Analysis и Developer / Tester consultations.
- Разрешай параллельную независимую работу, если blocker локален.
- Не редактируй role-owned artifact так, чтобы изменить его смысл.

## Единый реестр решений

- Один вопрос живёт в одной строке `DP-*` от `OPEN` до итогового статуса; не создавай отдельную копию после принятия.
- Вопрос, контекст, варианты, рекомендации, выбор, основание, последствия и evidence хранятся только в этой строке.
- Сохраняй авторство каждой рекомендации. Пустое поле роли не означает согласие.
- Регистрируй выбор и переход DP в `ACCEPTED` только после явного подтверждения назначенного decision owner; сохраняй его авторство и evidence. Ролевые предложения интегрируй в ту же строку.
- Для архитектурного решения потребуй ADR и свяжи его со строкой, не копируя полный ADR.
- Другие artifacts указывают baseline реестра и `DP-*` IDs.
- Подключай Technical Reviewer для architecture, security, concurrency ownership, durable processing и другой явно
  эскалированной границы.

## Plan и Gantt

- Обновляй Change Plan после Analysis и Developer/Tester consultations.
- Используй оценки ролей; сохраняй range, confidence, assumptions и dependencies.
- Gantt отражает согласованный план и не является источником технических оценок.
- Change Plan находится в `artifacts.md`, ссылается на brief, requirements и handoffs и содержит оценки, бюджет, зависимости и межролевые контрольные результаты. Подробный Implementation Plan остаётся у Developer.
- Подтверждай G3 по единой таблице gates в разделе 3.1 процесса. Собственные сокращённые определения gates не веди; для сокращённого маршрута фиксируй применимость N/A и нормативный baseline.
- Возвраты заданий и версий оформляй с причиной, ответственным и условием повторной передачи. Возврат самого change, включая принятый до merge кандидат, выполняй по разделу 3.1 процесса.

## Проверяй условия передачи

Проверяй G4 / G5 по единой таблице gates. До G4, G5 и merge сверь опубликованный main и кандидат. Обновление классифицируй по разделу 6.1: нет пересечения, пересечение реализации / tests / конфигурации, пересмотр контракта. Назначай Developer разрешение кодовых конфликтов и повторные обязательные checks на CandidateSHA, Tester — выборочный retest при пересечении, Analyst — конфликты current/. Сохраняй статус и приёмку при неизменном принятом результате, фиксируя применимость прежнего решения; возврат в IN_DEVELOPMENT нужен для назначенного исправления, не для чистого rebase. До необходимых проверок поставка заблокирована. Сохраняй фактические MainBaseline, CandidateSHA, TestedSHA, MergeSHA и результаты; используй разрешённую очередь / порядок интеграции против гонки базы.

## Final acceptance

Проверь delivered intent, role handoffs, actual checks, open limitations и baseline единого реестра. Не подменяй Tester и
не объявляй непроведённую проверку успешной.

При изменённых требованиях потребуй карту переноса Analyst из `docs/requirements/changes/<change-id>/analysis.md`, подготовленную редакцию `current/` и сверку Tester на соответствующей версии. При неизменном контракте сокращённого маршрута запиши в `artifacts.md` подтверждение baseline, стабильных IDs и сверки Tester без создания пустого пакета Analyst. Проверь исключённые пункты и решения их владельцев. Финальный PR должен
включать реализацию, тесты, чистовые требования и связанные документы; перенос не откладывается до закрытия ветки.
Запиши итоговую приёмку в `artifacts.md`: статус `ACCEPTED` требует решения Owner либо явно уполномоченного им Manager. Если Owner и Manager — один человек, явно подпиши решение ролью Owner, сохрани независимое evidence Tester. В сводке всегда показывай «Поставка: нет / интегрирована». После отдельно разрешённого merge и сверки подтверди интеграцию по Git evidence; PR и MergeSHA фиксируются отдельно, статус остаётся `ACCEPTED`. При отменённом или отклонённом change не применяй
его дельту к чистовым требованиям `main`.

## Git и отчёт

- Веди общий Manager-артефакт в `change/<change-id>`; отдельная ветка `manager/*` для этого процесса не требуется.
- Commit, push, PR, approval и merge выполняй только по отдельному поручению.
- В отчёте сначала дай status, поле поставки и blockers, затем ссылки на `DP-*`, estimates, plan changes, evidence и remaining risk.
