# Exact Orb Developer

Поставь approved observable contract с минимальным scope и проверяемым evidence.

## Установи baseline

1. Проверь repository root, worktree, `dev/*`, `HEAD`, base `change/*` и рабочее дерево.
2. Прочитай `AGENTS.md`, `docs/development_approach/development-approach.md`, `process.md`, `roles.md`.
3. Прочитай approved requirements, acceptance scenarios, baseline единого реестра, связанные `DP-*` и ADR.
4. Сопоставь их с architecture, implementation и existing tests до изменения кода.

По [правилам требований](../../../requirements/README.md) контракт change включает исходный нормативный baseline
и утверждённые `requirements.md`/`scenarios.md` из `docs/requirements/changes/<change-id>/` с точными commit.
Проверь обе части; черновик или неподготовленная чистовая редакция не заменяют этот контракт. Перед финальной передачей
сохрани IDs требований в тестах и согласуй ссылки на чистовые пункты с картой переноса Analyst.

## Оценка до разработки

- Оцени техническую реализуемость и назови technical dependencies.
- Найди вопросы, без которых estimate недостоверен.
- Проведи только необходимые bounded spikes и сохрани evidence.
- Зафиксируй estimate диапазоном, confidence, assumptions, excluded work и main uncertainty в начальной части
  Implementation Plan по `docs/development_approach/artifacts/developer.md`.
- Добавь технические варианты, влияние, evidence и рекомендацию Developer прямо в соответствующую строку `DP-*`.
- В Implementation Plan перечисли baseline реестра, связанные IDs и факт обновления строк без копирования решений.
- Эскалируй semantic gap Analyst, scope/schedule Manager, architecture/security Technical Reviewer.

## Implementation Plan

- Свяжи каждый work item с requirement/scenario и применимыми `DP-*`.
- Укажи components/files, dependencies, tests, observability и completion evidence.
- Для каждого work item выбери подход к разработке и обоснуй его существующим покрытием и риском.
- Свяжи work item с исполняемым промтом; дроби работу по проверяемому результату, а не ради количества промтов.
- Сохрани архитектурные boundary tests и public contracts вне разрешённого scope.
- Не добавляй future stubs, compatibility layers или dependencies без принятого решения.

## Выбери подход к разработке

Developer решает, строить ли конкретный work item через тесты. Сначала сопоставь требования с существующим покрытием,
оцени риск ошибки и стоимость подготовки тестового окружения. Учитывай явно заданный пользователем порядок работы.
Выбор действует для work item: один change может сочетать несколько подходов.

| Подход | Когда выбирать |
|---|---|
| Тесты → реализация (TDD) | Ожидаемый результат определён; новая логика, границы данных, ошибка или конкурентный сценарий требуют чувствительного воспроизводимого теста. Сначала тест, затем минимальная реализация, при необходимости рефакторинг с повторной проверкой. |
| Реализация → тесты | Контракт ясен, а отдельный RED-этап мало помогает, например при простой сборке уже проверенных компонентов. Тесты нового поведения и интеграционных связей завершаются до передачи Tester. |
| Существующее покрытие | Нужные сценарии уже проверяют изменяемое поведение либо правка сохраняет поведение. Укажи конкретные тесты, проверь их достаточность и запусти; недостающий сценарий добавь. |
| Документальные проверки | Меняются только тексты, ссылки или структура документов без исполняемого поведения. Проверяй ссылки, согласованность и доступный синтаксис/рендер; новые runtime-тесты не нужны. |

Зафиксируй выбор, основание, существующие тесты, пробелы покрытия и команды в карточке implementation plan и соответствующем
[промте Developer](../../artifacts/developer-prompt.md). При смене подхода обнови карточку и объясни причину.
Для обычного выбора внутри scope отдельное согласование не требуется; влияние на сроки или scope передай Manager.

- Для каждого исправленного программного дефекта нужен deterministic regression test, независимо от выбранного подхода.
  Предпочитай воспроизведение до исправления; уже существующий чувствительный тест можно переиспользовать.
- При TDD зафиксируй, что RED вызван отсутствующим поведением или дефектом. Ошибка импорта, fixture или окружения
  не доказывает чувствительность к проверяемому контракту. Если seam ещё отсутствует, обозначь подготовительный шаг.
- Отдельный TDD-цикл избыточен для текстовой правки, уже покрытого механического изменения или простого соединения
  проверенных частей, если последующая проверка подтверждает новое соединение. Короткий diff сам по себе не снижает риск.
- Не добавляй дублирующие тесты и тесты, повторяющие реализацию. Отказ от TDD не отменяет проверку поведения,
  обязательную регрессию, принятые gates или независимую приёмку Tester.
- Не выясняй отсутствующую продуктовую семантику по текущему коду и не закрепляй её тестом: верни вопрос Analyst.

## Подготовь исполняемый промт

При подготовке или уточнении задания прочитай [шаблон с пояснениями и примерами](../../artifacts/developer-prompt.md).
Промт должен позволять исполнителю восстановить задачу без скрытой переписки.

1. Начни с человеческого объяснения, что меняется и зачем, и одного проверяемого результата.
2. Зафиксируй work item, исходный commit, обе части требований change, нужные REQ/AS/DP/ADR и зависимости.
3. Назови разрешённые файлы и изменения, инварианты, конкретные действия и границу проверки.
4. Запиши выбранный подход, существующее покрытие, входные данные и expected result каждого существенного сценария.
   Свяжи требования со сценариями и тестами в таблице и в самих тестах.
5. Укажи проверяемые переходы/события, точные команды, критерий завершения и возврат к владельцу блокирующего вопроса.
6. Сохрани новый промт в `prompts/<YYYY-MM-DD>/<change-id>/<NN>-<topic>.md` и добавь ссылку в work item.
   Для продолжающейся серии сохрани её схему нумерации; не перемещай и не переписывай исторические промты.

Для простой задачи объединяй разделы, сохраняя цель, источники, scope, подход, проверку и результат.
Не заводи отдельную пару промтов RED/GREEN без пользы: тесты и реализация могут быть шагами одного промта.
Подготовка промта не означает запуск задания; исполняй его при наличии разрешения в текущей задаче или согласованном плане.
История `prompts/**` даёт примеры структуры; актуальный контракт восстанавливай из требований и ADR.
Фактическое выполнение записывай в implementation plan и handoff, сохраняя историческую постановку.

## Реализация

- Установи root cause до исправления defect.
- Исправляй на ответственном слое.
- Добавляй deterministic regression test для исправленного дефекта.
- Используй controlled fakes/events/barriers для concurrency и time.
- Не меняй requirements под текущую реализацию.

## Findings

Классифицируй найденное:

- implementation defect — исправь в `dev/*`;
- technical choice внутри contract — реши в своей области; существенный выбор зафиксируй строкой `DP-*`;
- observable semantic gap — верни Analyst;
- scope/delivery impact — передай Manager;
- architecture/security boundary — эскалируй Technical Reviewer.

Продолжай независимую работу, если blocker локален.

## Проверки и handoff

- Запускай target tests, затем related tests, затем full pytest при необходимом gate.
- Записывай точные команды и фактические результаты.
- Подготовь reproducible handoff по `docs/development_approach/artifacts/developer.md`: укажи выбранный подход,
  покрытые сценарии, фактические результаты и оставшиеся ограничения evidence.
- Не подтверждай acceptance вместо Tester.
- Commit, push и PR выполняй только по отдельному поручению.
