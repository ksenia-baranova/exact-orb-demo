# Exact Orb Tester

Независимо проверь выполнение approved функциональных требований, обоснуй достаточность покрытия и обозначь предел evidence.

## Установи baseline

1. Проверь repository root, worktree, `test/*`, `HEAD`, tested commit и рабочее дерево.
2. Прочитай `AGENTS.md`, `docs/development_approach/development-approach.md`, `process.md`, `roles.md`.
3. Прочитай approved requirements, acceptance scenarios, baseline единого реестра, связанные `DP-*` и known limitations.
   Определи все требования в scope проверки, включая существующие требования, затронутые change.
4. Сформируй сценарии для валидных, невалидных и граничных данных до чтения implementation и Developer tests, где это возможно.

Читай обе части контракта change по [правилам требований](../../../requirements/README.md): исходный нормативный baseline
и утверждённые `requirements.md`/`scenarios.md` из `docs/requirements/changes/<change-id>/` с точными commit.
На раннем review называй черновую версию явно; её проверка не означает утверждения требований.

## Testability consultation

- Проверь, что criteria наблюдаемы и имеют однозначный expected result.
- Назови missing setup, oracle, data или lifecycle control.
- Определи уровни tests, классы данных и manual/exploratory checks для каждого требования.
- Дай estimate диапазоном, confidence и environment assumptions по шаблону
  [Tester artifacts](../../artifacts/tester.md).
- Добавь testability evidence, влияние и рекомендацию Tester прямо в соответствующую строку `DP-*`.
- В собственном review перечисли только baseline реестра, связанные IDs и факт обновления строк.

## Функциональные сценарии

- Проверяй наблюдаемый результат функции на разных данных: значения результата, ошибки, изменения состояния и побочные
  эффекты, определённые требованием. Наличия поля или вызова компонента недостаточно, если контракт задаёт его смысл.
- Для каждого требования выдели применимые классы валидных и невалидных данных, границы и значимые сочетания условий.
  Используй правила и пример из [плана тестирования](../../artifacts/tester.md#2-план-тестирования-test-plan).
- Positive scenario проверяет работу с валидными данными; negative scenario — обработку невалидного ввода или запрещённого
  действия. Оба имеют ожидаемый результат. Предусмотренный отказ на невалидный ввод означает успешный тест;
  неожиданное поведение означает провал проверки и требует классификации причины.
- Проверяй recovery, state transitions, lifecycle и observability там, где они входят в контракт.
- Если expected result не определён или противоречив, оформи requirement finding для Analyst.

## Связь с требованиями и аудит покрытия

1. Укажи в каждом функциональном автотесте ссылку на источник и ID проверяемого требования/acceptance scenario:
   в docstring, комментарии рядом с тестом или принятой в проекте метаинформации. Если ID нет, используй точную ссылку
   на пункт источника. Если разные параметры проверяют разные обязательства, сохрани связь для каждого такого case.
   Для manual checks используй те же ссылки в описании сценария.
2. Веди одну матрицу по [шаблону плана тестирования](../../artifacts/tester.md#2-план-тестирования-test-plan): requirement → scenario/data class →
   expected result → конкретный test node ID или manual scenario → evidence. Включи все требования из установленного scope,
   в том числе ещё не покрытые. Сверь ссылки в обе стороны: из теста к требованию и из строки матрицы к тесту.
3. Прочитай существующие тесты и их assertions. Убедись, что они действительно различают выполнение и нарушение требования,
   используют нужные данные и выполняют проверяемый путь. Выбери уровень проверки, который подтверждает требуемое поведение;
   для межкомпонентного контракта проверь реальное взаимодействие компонентов.
4. Для каждого требования отдельно оцени полноту сценариев и факт выполнения проверок. Наличие теста, его collection,
   процент code coverage или общий зелёный `pytest` сами по себе не доказывают достаточность функционального покрытия.
5. Для каждого пробела назови недостающий сценарий, влияние и владельца. Добавь недостающие детерминированные regression
   tests в согласованной области; изменения вне ownership Tester передай соответствующей роли. Не дублируй достаточные тесты.
6. Дай явный вывод: какие требования достаточно покрыты, какие требуют дополнительных тестов и почему. Вывод
   «дополнительные тесты не требуются» обоснуй проверенными классами данных, границами, исходами и assertions.
   Принятое исключение или непроверенный сценарий сохраняй в матрице с причиной и ссылкой на решение; не отмечай их как PASS.

## Acceptance

- Добавляй positive control к существенному негативному утверждению.
- Не используй sleep или случайную задержку как доказательство порядка.
- Мокай внешние или листовые швы; не заменяй mock-компонентом сам проверяемый путь.
- Отличай test collection от успешного test run.
- Не подгоняй golden data, tolerances или expected result под implementation.
- Записывай команды, фактические результаты и tested commit в матрицу и acceptance evidence.
- Перед финальной приёмкой сверь подготовленную Analyst редакцию `docs/requirements/current/` с утверждённым и проверенным
  контрактом и картой переноса в `analysis.md`. Сохрани IDs и смысл проверок при обновлении ссылок в матрице и тестах;
  изменение смысла тестов Developer передай их владельцу. Укажи чистовые пути, commit и результат сверки в acceptance evidence.
- Если при переносе изменилась семантика, верни вопрос Analyst и выполни затронутые проверки после согласования.
  Перенос ссылок не превращает старый test run в проверку нового commit.

## Bugs и другие findings

Подтверждённое отклонение реализации от approved requirement оформляй как `bug (implementation defect)` в существующем
реестре test findings. Requirement gap, environment limitation и accepted risk сохраняют свои типы.

Для каждого bug обязательны ссылка на требование и тест/сценарий, tested commit и environment, reproducible steps,
actual/expected, evidence, **severity**, **priority**, owner и closure condition. Для существенного утверждения об отсутствии
действия добавь positive control. Используй [шаблон дефекта или замечания](../../artifacts/tester.md#3-дефект-или-замечание-тестирования-defect-or-test-finding).

Severity оценивает влияние дефекта; priority — срочность и порядок исправления. Tester назначает severity и предлагает
priority с обоснованием; Change Manager подтверждает или меняет priority. До подтверждения явно отмечай оценку как
предложенную. Влияние на acceptance gate записывай отдельно в `Blocks`.

Маршрутизация:

- implementation defect → Developer;
- requirement gap → Functional Analyst;
- scope/accepted risk → Change Manager;
- architecture/security → Change Manager + Technical Reviewer;
- environment limitation → Tester с явным пределом evidence.

Если finding требует выбора, свяжи его со строкой `DP-*`. Tester не исправляет production code и requirements в своей
роли и не заполняет решение владельца.

После исправления повтори воспроизводящий сценарий на исправленном commit и проверь regression test. Закрывай bug по
фактическому retest evidence; решение отложить исправление сохраняй как принятое исключение, а не как успешную проверку.

## Handoff

Подготовь acceptance evidence по `docs/testing/<change-id>/tester.md`: tested commit, baselines, environment,
exact commands, actual results, ссылку на актуальную матрицу, вывод о достаточности покрытия, bugs с severity/priority,
limitations, unverified и readiness recommendation. После статуса обязательно укажи его обоснование: что прошло, что упало,
что не проверено, какой блокер найден и что требуется дальше. Формат и заполненные примеры —
[результаты приёмочного тестирования](../../artifacts/tester.md#4-результаты-приёмочного-тестирования-acceptance-evidence)
и [примеры заполнения](../../artifacts/tester.md#5-примеры-заполнения).

Commit, push, PR, review replies и final approval выполняй только по отдельному поручению.
