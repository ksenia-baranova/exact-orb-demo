# AI-assisted specification-driven development

**Статус:** DRAFT / WORK IN PROGRESS
**Дата начала формирования:** 2026-09-05
**Дата последней редакции:** 2026-09-25
**Назначение:** описание формирующегося рабочего метода разработки `exact-orb`.

> **Этот документ находится в процессе формирования.**
>
> Он фиксирует текущий способ работы, наблюдения, инженерные гипотезы и правила,
> которые возникают в процессе реальной разработки проекта.
>
> Документ не является завершённой методологией, формальным стандартом разработки
> или источником продуктовых и архитектурных требований.
>
> Подход может изменяться по мере накопления практического опыта: появления новых
> ошибок, неудачных агентских проходов, новых способов декомпозиции задач,
> изменений моделей, инструментов и ограничений среды.
>
> Существенные выводы должны подтверждаться практикой проекта, а не только
> рассуждениями LLM.

---

## 1. Назначение

`exact-orb` разрабатывается одним владельцем с активным использованием LLM.

Модель участвует не только в написании кода. Она используется для:

* исследования архитектурных вариантов;
* выявления неизвестных и спорных решений;
* построения таблиц принятия решений;
* формализации выбранной архитектуры;
* подготовки ADR, требований и диаграмм;
* декомпозиции изменения;
* подготовки implementation prompts;
* реализации ограниченной задачи;
* генерации и анализа тестовых сценариев;
* последующего review реализации;
* проверки соответствия кода утверждённому контракту.

При этом LLM не является источником истины и не принимает архитектурные решения
вместо владельца проекта.

Короткая формула метода:

```text
свободное архитектурное обсуждение
    ↓
выявление развилок
    ↓
decision table
    ↓
решение владельца
    ↓
ADR / требования / диаграммы
    ↓
декомпозиция изменения
    ↓
approved implementation prompt
    ↓
реализация
    ↓
component tests
    ↓
integration / boundary tests
    ↓
LLM-review против контракта
    ↓
детерминированная приёмка
    ↓
решение владельца о принятии изменения
    ↓
коммит
```

Метод соединяет несколько режимов работы:

1. **dialog-driven architecture** — пространство решений исследуется в
   свободном разговоре;

2. **decision-driven specification** — существенные развилки явно выносятся
   на решение владельца;

3. **specification-driven implementation** — код пишется после фиксации
   выбранного решения;

4. **test-backed acceptance** — мнение LLM не считается достаточным
   доказательством корректности;

5. **LLM-assisted review** — отдельный проход модели используется для поиска
   нарушений контракта, а не для подтверждения уже написанного решения.

# 2. Основной принцип

Главная идея подхода:

> LLM может предлагать, исследовать, реализовывать и критиковать решение,
> но граница между предложением модели и разрешённым инженерным решением
> должна оставаться явной.

Поэтому процесс строится не как:

```text
человек написал запрос
    → LLM написала код
```

а как управляемая последовательность:

```text
проблема
    → пространство решений
    → явные развилки
    → решение
    → контракт
    → ограниченная задача
    → реализация
    → доказательства
    → принятие
```

# 3. Распределение ответственности

## 3.1. Владелец проекта

Владелец проекта:

* задаёт продуктовую цель;
* определяет поддерживаемые пользовательские сценарии;
* сообщает доменные ограничения, которых нет в коде;
* определяет архитектурные приоритеты;
* выбирает между альтернативами;
* определяет допустимый scope изменения;
* принимает решения по спорным развилкам;
* разрешает противоречия между источниками;
* утверждает implementation prompt;
* разрешает его исполнение;
* принимает или отклоняет реализацию;
* разрешает создание коммита;
* отвечает за итоговый контракт независимо от того, кем был сгенерирован
  конкретный текст кода, теста или документа.

LLM не должна самостоятельно подменять это решение своим предпочтением.

---

## 3.2. LLM

В разных проходах LLM может выполнять различные роли.

### Architecture assistant

Помогает:

* находить архитектурные альтернативы;
* искать corner cases;
* выявлять скрытые зависимости;
* анализировать последствия решения;
* сравнивать стоимость и сложность вариантов;
* находить конфликт с существующими ADR;
* выявлять новые развилки.

### Specification assistant

Помогает:

* переносить решение в требования;
* писать ADR;
* поддерживать component responsibilities;
* синхронизировать sequence diagrams;
* формировать таблицы решений;
* превращать решение в техническое задание.

### Implementation agent

Получает уже ограниченную задачу и:

* исследует указанные файлы;
* реализует изменение;
* добавляет необходимые тесты;
* выполняет только разрешённый scope.

### Judge / reviewer

Отдельным проходом:

* сравнивает фактический diff с контрактом;
* ищет контрпример;
* проверяет негативные сценарии;
* ищет нарушения архитектурных границ;
* проверяет тестовое покрытие;
* анализирует, действительно ли тестируется требуемый путь.

Эти роли могут выполняться одной и той же моделью.

Поэтому логическое разделение ролей **не означает независимость доказательств**.

---

# 4. Исполняемые проверки

Тесты, статические проверки и эталоны отвечают не за выбор архитектуры, а за
проверку наблюдаемого поведения.

Принцип:

> Там, где утверждение можно проверить механически, исполняемая проверка
> предпочтительнее мнения LLM или текстового соглашения.

Например:

```text
"handler не должен напрямую обращаться к EngineService"
```

лучше закрепить не только текстом требования, но и boundary-тестом.

А:

```text
"ошибка должна приводить к определённому ApplicationResult"
```

должно проверяться тестом наблюдаемого поведения.

# 5. Рабочий цикл

## 5.1. Свободное архитектурное обсуждение

Работа начинается не с implementation prompt.

Сначала формулируются:

* задача;
* текущее состояние;
* ограничения;
* неизвестные;
* сомнения;
* возможные варианты решения.

На этом этапе LLM может свободно исследовать пространство решений.

Полезно обсуждать:

* ответственность компонента;
* владельца состояния;
* публичный контракт;
* границы слоёв;
* happy path;
* error paths;
* concurrency;
* идемпотентность;
* отмену;
* восстановление;
* observability;
* стоимость решения;
* обратимость;
* влияние на другие компоненты;
* влияние на ADR;
* влияние на тестовую стратегию.

Архитектурный чат является рабочим материалом.

Он **не является контрактом**.

Предложение LLM не становится архитектурным решением автоматически.

# 6. Decision gate

Перед подготовкой implementation prompt для нетривиального изменения
формируется таблица принятия решений.

Это отдельный этап процесса.

Он нужен для того, чтобы спорное решение не оказалось незаметно встроено
в текст промта самим агентом.

## 6.1. Формат decision table

Типовой формат:

| №  | Развилка              | Варианты  | Рекомендация LLM                  | Решение владельца      | Последствия         |
| -- | --------------------- | --------- | --------------------------------- | ---------------------- | ------------------- |
| A1 | Что необходимо решить | a / b / c | Предпочтительный вариант и почему | Явно выбранный вариант | Что меняется дальше |

Развилки могут касаться:

* структуры компонентов;
* границ ответственности;
* API;
* Protocol;
* типов результатов;
* обработки ошибок;
* журналирования;
* структуры пакетов;
* зависимостей;
* module boundaries;
* способа тестирования;
* расположения тестов;
* использования mock / stub / fake;
* декомпозиции implementation prompts;
* документации;
* миграций;
* обратной совместимости;
* observability;
* scope.

---

## 6.2. Роль рекомендации LLM

LLM должна не просто перечислить варианты, а дать рекомендацию и аргументацию.

Например:

```text
Развилка:
handler и logging реализовывать одним изменением или разными?

Варианты:
(a) вместе
(b) отдельно

Рекомендация:
(a), потому что обработка BaseException и terminal events находятся
в одном control flow.
```

Но рекомендация остаётся только рекомендацией.

Финальная колонка:

```text
Решение владельца
```

имеет больший приоритет.

---

## 6.3. Decision table не является источником истины

Таблица используется для принятия решения.

После решения существенный долгоживущий контракт переносится в:

* ADR;
* requirements;
* component responsibilities;
* sequence diagrams;
* boundary tests;
* behavioural tests.

То есть:

```text
decision table
    ↓
решение
    ↓
authoritative artifact
```

а не:

```text
decision table
    = постоянная спецификация
```

---

# 7. Новая развилка во время исполнения

Особенно важное правило:

> Агент не должен самостоятельно разрешать новую существенную архитектурную
> развилку, обнаруженную во время реализации.

Если выясняется:

```text
для реализации текущей задачи
нужно изменить компонент вне разрешённого scope
```

исполнитель должен остановить расширение задачи.

Процесс:

```text
обнаружена новая зависимость
    ↓
STOP
    ↓
описать проблему
    ↓
сформулировать новую развилку
    ↓
решение владельца
    ↓
при необходимости отдельный prompt
```

Например:

```text
BuildNatalHandler невозможно реализовать без изменения BirthDataResolver
```

не означает:

```text
агент автоматически меняет BirthDataResolver
```

Это означает:

```text
появилась новая задача принятия решения
```

---

# 8. Фиксация решения

После decision gate выбранное решение переносится в актуальные документы.

| Характер результата                                    | Где фиксируется                                 |
| ------------------------------------------------------ | ----------------------------------------------- |
| Архитектурное решение с альтернативами и последствиями | `docs/requirements/decisions/`                  |
| Наблюдаемый контракт компонента                        | `docs/requirements/component_responsibilities/` |
| Сквозной поток взаимодействий                          | `docs/sequence_diagrams/`                       |
| Архитектурная граница                                  | requirement + boundary-test                     |
| Локальная инструкция реализации                        | implementation prompt                           |
| Regression-сценарий                                    | tests                                           |

ADR действует, пока явно не заменён.

Исторический prompt не заменяет актуальное требование.

Свободный архитектурный чат не заменяет ADR.

---

# 9. Подготовка implementation prompt

Implementation prompt появляется **после принятия решения**.

Его задача — не продолжать архитектурную дискуссию, а описать ограниченную
исполняемую работу.

## 9.1. Требование самодостаточности

Каждый prompt должен быть достаточно самодостаточным, чтобы исполнитель мог
понять задачу без восстановления всей истории разговора.

При этом:

> self-contained не означает полное копирование всех requirements.

Prompt должен содержать необходимые выдержки и одновременно ссылаться
на authoritative sources.

---

## 9.2. Типовая структура prompt

Prompt должен содержать:

1. цель;
2. исходную проблему;
3. источники истины;
4. текущее состояние;
5. предусловия;
6. разрешённый scope;
7. разрешённые файлы;
8. запрещённые файлы;
9. публичные контракты;
10. сохраняемое поведение;
11. архитектурные инварианты;
12. обработку ошибок;
13. observability;
14. позитивные сценарии;
15. негативные сценарии;
16. concurrency-сценарии, если применимо;
17. требования к тестам;
18. команды проверки;
19. требования к итоговому отчёту;
20. явно исключённые изменения.

---

# 10. Декомпозиция prompts

Количество prompts само по себе не является целью.

Нельзя оптимизировать процесс под:

```text
"сделать всё за два промта"
```

или:

```text
"обязательно должно быть четыре промта"
```

Единицей декомпозиции является **ограниченный проверяемый change-set**.

Например:

```text
contracts
→ handler
→ observability
→ module boundaries
→ documentation alignment
```

могут быть отдельными задачами, если это делает изменение:

* легче проверяемым;
* легче откатываемым;
* легче ревьюить;
* менее склонным к scope creep.

---

# 11. Код и тесты

Разделение кода и тестов также не должно быть догмой.

Используется правило:

> Тест может находиться в том же change-set, если он является частью определения
> завершённости изменения.

Но отдельный prompt оправдан, если тестирование:

* представляет другой уровень системы;
* требует отдельной инфраструктуры;
* существенно увеличивает контекст;
* должно независимо проверять готовую реализацию;
* относится к integration или end-to-end уровню.

---

# 12. Уровни тестирования

В процессе явно различаются несколько уровней.

## 12.1. Component tests

Проверяют компонент изолированно.

Например:

```text
BuildNatalHandler
```

Dependencies заменяются на controlled:

* fake;
* stub;
* test double.

Цель:

* проверить control flow;
* error mapping;
* возвращаемый результат;
* события;
* вызовы зависимостей;
* отсутствие запрещённых вызовов.

---

## 12.2. Contract tests

Проверяют совместимость публичных контрактов.

Например:

* `Protocol`;
* signature;
* обязательные kwargs;
* типовые сценарии совместимости реальной реализации с портом.

`inspect.signature` может быть дополнительным guard.

Но основное доказательство совместимости желательно получать через реальный
путь использования контракта.

---

## 12.3. Integration tests

Проверяют несколько реальных компонентов вместе.

Например:

```text
BuildNatalHandler
    → real BirthDataResolver
    → real LocalPlaceCatalog
    → real contract-compatible calculation path
```

Fake допускается на внешнем или листовом шве.

Но действует правило:

> Нельзя мокать тот компонент, интеграцию с которым данный тест должен доказать.

Иначе тест проверяет:

```text
поведение mock
```

вместо:

```text
реального пути системы
```

---

## 12.4. Boundary tests

Механически проверяют архитектурные границы.

Например:

```text
application handler
не может напрямую импортировать
calculation.engine
calculation.cache
calculation.keys
```

Такие тесты особенно полезны, потому что превращают архитектурное соглашение
в исполняемый инвариант.

---

## 12.5. Full regression

После локальных проверок выполняется полный набор тестов проекта.

Последовательность:

```text
component tests
    ↓
contract tests
    ↓
integration tests
    ↓
boundary tests
    ↓
related regression tests
    ↓
full pytest
```

---

# 13. Использование mocks, stubs и fakes

Test doubles используются осознанно.

Они нужны для:

* изоляции компонента;
* воспроизведения ошибок;
* управления временем;
* управления concurrency;
* контролируемого поведения внешнего API;
* проверки rare paths.

Но они не должны заменять весь реальный путь системы.

Поэтому тестовая стратегия должна отвечать сразу на два вопроса:

```text
Работает ли компонент отдельно?
```

и:

```text
Работают ли реальные компоненты вместе?
```

# 14. Status lifecycle implementation prompt

Создание prompt и разрешение на его исполнение — разные действия.

Рекомендуемые состояния:

```text
DRAFT
```

Prompt формируется и обсуждается.

```text
APPROVED FOR EXECUTION
```

Владелец проверил prompt и разрешил выполнение.

```text
EXECUTED
```

Работа была выполнена.

```text
ACCEPTED
```

Результат прошёл приёмку владельца.

```text
REJECTED / SUPERSEDED
```

Prompt или результат больше не должны использоваться.

Критично:

```text
prompt generated
≠
prompt approved
≠
prompt executed
≠
change accepted
```

# 15. Запрет самовольного исполнения

По умолчанию агенту запрещено:

* исполнять подготовленный prompt без команды;
* менять repository в процессе только подготовки prompt;
* создавать commit;
* push;
* менять соседние компоненты вне scope;
* «заодно» исправлять обнаруженные проблемы;
* создавать будущие архитектурные прослойки.

В prompt рекомендуется явно фиксировать:

```text
DO NOT EXECUTE WITHOUT EXPLICIT USER COMMAND.
DO NOT COMMIT.
DO NOT MODIFY COMPONENTS OUTSIDE THE ALLOWED SCOPE.
```

Даже если агент считает изменение полезным.

# 16. Реализация

Перед изменением исполнитель:

* изучает repository;
* проверяет рабочее дерево;
* сохраняет несвязанные изменения;
* читает указанные requirements;
* читает актуальные ADR;
* читает существующий код;
* читает существующие тесты;
* проверяет уже имеющееся покрытие.

При исправлении дефекта желательно сначала воспроизвести его тестом.

Реализация выполняется в минимальном объёме.

Не добавляются без необходимости:

* compatibility aliases;
* новые abstraction layers;
* будущие API;
* новые зависимости;
* крупный refactoring;
* unrelated cleanup.

---

# 17. Scope control

Каждый implementation prompt должен явно содержать:

## Allowed

Что можно изменить.

## Forbidden

Что менять запрещено.

Например:

```text
Allowed:
- exact_orb/application/handlers/build_natal.py
- tests/application/test_build_natal_handler.py

Forbidden:
- BirthDataResolver
- ChartArtifactResolver
- EngineService
- ApplicationOrchestrator
```

Это не означает, что запрещённые компоненты никогда нельзя менять.

Это означает:

> их изменение требует отдельного решения и отдельной задачи.

---

# 18. Observability как отдельный контракт

Для компонентов оркестрации observability рассматривается как часть
наблюдаемого поведения.

Например:

```text
build_natal_started
build_natal_completed
build_natal_failed
```

должны иметь определённую семантику.

Ожидаемая domain error может иметь один terminal event:

```text
build_natal_completed
outcome=calculation_error
```

а неожиданная ошибка:

```text
build_natal_failed
stage=calculate
```

Observability может быть вынесена в отдельный implementation prompt,
если её изменение достаточно самостоятельно.

---

# 19. LLM-as-judge review

После реализации выполняется отдельный review-проход.

Judge не должен переписывать решение с нуля.

Он должен сопоставить:

```text
фактический diff
```

с:

```text
утверждённым контрактом
```

Judge проверяет:

* решена ли исходная проблема;
* сохранён ли публичный API;
* не увеличен ли scope;
* не нарушены ли module boundaries;
* существует ли позитивный контроль;
* существует ли негативный сценарий;
* проверяет ли тест реальный путь;
* не проверяется ли только mock;
* корректны ли concurrency tests;
* не маскируется ли ошибка;
* синхронизированы ли затронутые документы;
* действительно ли запускались заявленные проверки.

---

# 20. Judge должен искать контрпример

Ценность judge не в утверждении:

```text
"код выглядит корректным"
```

а в возможности сформулировать:

```text
при условии X
реализация нарушает контракт Y
```

Хорошее замечание содержит:

1. конкретный контракт;
2. конкретный сценарий;
3. наблюдаемое нарушение;
4. способ воспроизведения.

Если замечание принято:

```text
review finding
    ↓
regression scenario
    ↓
ограниченная задача
    ↓
исправление
    ↓
постоянный тест
```

---

# 21. Ограничение LLM-review

LLM-review не является независимым доказательством корректности.

Если implementation и review выполняются:

* одной моделью;
* моделями одной семьи;
* с похожим контекстом;
* на основе одной исходной спецификации,

их ошибки могут быть коррелированы.

Поэтому:

```text
LLM said OK
```

не является достаточной приёмкой.

---

# 22. Детерминированная приёмка

Проверки выполняются поэтапно.

Типовая последовательность:

1. regression-test конкретного дефекта;
2. component tests;
3. contract tests;
4. integration tests;
5. boundary tests;
6. related tests;
7. полный `pytest`;
8. проверки документации;
9. `git diff --check`.

Сетевые, платные или внешние smoke tests не запускаются без отдельного решения.

Если проверка не была запущена, это указывается прямо.

Запрещено заменять:

```text
test not executed
```

на:

```text
everything is fine
```

---

# 23. Принятие изменения

Успешный запуск тестов не означает автоматического принятия реализации.

Последнее решение остаётся за владельцем.

Он оценивает:

* соответствует ли результат замыслу;
* не изменился ли scope;
* допустима ли сложность;
* понятен ли diff;
* нужен ли дополнительный review;
* были ли выполнены необходимые проверки.

---

# 24. Коммит

Агент не создаёт commit без отдельного разрешения.

Коммит создаётся после приёмки.

Он должен содержать:

* причину изменения;
* существенное изменение поведения;
* важные ограничения;
* фактически выполненные проверки.

Коммит является границей принятого изменения.

Он не является доказательством авторства каждой строки.

# 25. Источники истины

Для реализации действует следующий приоритет:

```text
текущая явная задача
    ↓
действующие ADR
    ↓
актуальные requirements
    ↓
component responsibilities
    ↓
актуальные diagrams
    ↓
исполняемые tests
    ↓
текущая implementation
    ↓
historical prompts
    ↓
decision tables
    ↓
свободное обсуждение
```

Расположение некоторых уровней может уточняться по мере формирования
методологии.

Ключевой принцип:

> Исторический conversation context не должен быть единственным местом,
> где существует важный контракт.

# 26. Prompts как журнал исполнения

Файлы:

```text
prompts/YYYY-MM-DD/
```

используются как журнал ограниченных задач.

После выполнения исторический prompt не должен редактироваться так, будто это
текущая спецификация.

Изменение требований означает:

```text
обновить актуальный requirement
    +
создать новый prompt
```

а не:

```text
переписать старый prompt
```

# 27. Documentation alignment

Изменение архитектурного контракта может затрагивать:

* requirements;
* component responsibilities;
* sequence diagrams;
* ADR;
* boundary rules.

Однако документационные изменения не обязательно смешиваются с реализацией
компонента.

При необходимости создаётся отдельный documentation alignment prompt.

Например:

```text
align BuildNatal documentation to R4
```

может включать:

```text
000-build_natal_end_to_end.puml
+
exact-orb_build_natal_components.md
```

если обе правки вызваны одним изменением контракта.

# 28. Переносимый инженерный контекст

Статусы подразделов используются в смысле раздела «Статус документа»:
наблюдение, рабочая гипотеза, повторяемая практика или принцип.

## 28.1. Принцип

**Статус: принцип метода.**

> Ни один контекст, критичный для продолжения разработки, не должен существовать
> только внутри текущей AI-сессии.

```text
AI выполняет реализацию
    ↓
решения и ограничения фиксируются вне сессии
    ↓
requirements + ADR + sequence diagrams + tests + invariants
    ↓
новый исполнитель восстанавливает намерение и сценарий
    ↓
разработка продолжается человеком или другим агентом
```

Документация достаточна для передачи работы, если новый исполнитель способен
восстановить намерение системы без реконструкции архитектуры по коду. Код
остаётся конечной реализацией, которую необходимо читать и проверять. Но по
одному коду нельзя надёжно отличить принятое решение от случайной реализации,
компромисс от недосмотра и запрет от пути, который ещё не понадобился.

«В любой момент» означает возможность передать работу с зафиксированной точки
продолжения. Для незавершённой длительной задачи должны быть доступны принятые
решения, выполненные шаги, оставшаяся работа и открытые вопросы. Не требуется
превращать каждое промежуточное рассуждение в нормативный документ.

Искомое свойство процесса — заменяемость исполнителя:

```text
human → agent
agent A → agent B
agent → human
```

Смена исполнителя не должна требовать восстановления существенных решений из
памяти предыдущего участника.

**Экономическое следствие — рабочая гипотеза.** AI может удешевить производство
кода, но не устраняет стоимость производства и сохранения инженерного знания.
Если оно остаётся только в сессии, позднее возникают затраты на повторное
исследование решений, восстановление ограничений, исправление несовместимых
изменений и зависимость от доступности конкретной модели или её контекста.
Инвестиция в переносимый контекст позволяет удержать владение разработкой у
проекта; её фактическую окупаемость необходимо проверять практикой.

## 28.2. Модель артефактов

**Статус: повторяемая практика.**

Артефакты отвечают на разные вопросы и не заменяют друг друга:

| Артефакт | Вопрос |
| --- | --- |
| Requirements и component responsibilities | WHAT — что система должна делать и кто за что отвечает? |
| ADR | WHY — почему принято решение и какие альтернативы отвергнуты? |
| Sequence diagrams | INTERACTION — как компоненты взаимодействуют во времени? |
| Явно зафиксированные инварианты | CONSTRAINTS — чего происходить не должно? |
| Code | IMPLEMENTATION — как это реализовано сейчас? |
| Tests | EXECUTABLE CONTRACT / EVIDENCE — что проверяется автоматически? |
| Зафиксированные ограничения и принятый риск | DEBT / ACCEPTED RISK — что известно и намеренно пока не исправлено? |
| Git history | EVOLUTION — как система пришла в текущее состояние? |

Инварианты и известные ограничения могут находиться в действующих requirements
или ADR; таблица не предписывает отдельный файл для каждой категории.

**Sequence diagrams.** Межкомпонентный сценарий может быть распределён между
несколькими вызовами, обработчиками исходов и инфраструктурными слоями. По коду
особенно дорого восстанавливать негативные ветви, retry, cancellation,
конкурентность и lifecycle состояния. Диаграммы фиксируют существенные
переходы и порядок взаимодействий; им не нужно изображать каждый внутренний
вызов. Текстовые исходники `.puml` доступны человеку, Git и AI-агенту.

**Инварианты.** Соблюдаемый запрет может не оставлять положительного следа в
реализации. Поэтому его нужно формулировать явно. Если запрет допускает
механическую проверку, предпочтительнее закрепить его также тестом или
статической проверкой. Остальные инварианты требуют осознанного review.

**Известные ограничения.** Намеренно отложенное исправление без явной записи
неотличимо для нового исполнителя от недавно обнаруженного дефекта. Запись
должна указывать действующее ограничение и статус решения, чтобы исполнитель
не повторял исследование и не нарушал другой контракт случайным «исправлением».

`prompts/` — исторический журнал исполнения, а не нормативный источник
текущего поведения (см. §26). Перенос знания из сессии только в старый prompt
не выполняет принцип §28.1: новый исполнитель должен понимать, какому
актуальному источнику доверять.

## 28.3. Парное правило: свежесть

**Статус: повторяемая практика; основание — наблюдавшийся дрейф документации.**

Устаревший документ может быть опаснее отсутствующего: он выглядит как готовый
ответ. При противоречии документа и реализации исполнитель должен выявить
расхождение и разрешить его по действующим решениям и проверкам, а не молча
считать любой из источников верным.

В `exact-orb` после реализации `BuildNatalHandler` 8 сентября 2026 года
(`e18ab87`, `5406306`) `overview.md` и `roadmap.md` ещё 9 сентября называли
пакет `application/` отсутствующим, а handlers — нереализованными. Коммит
`90d22d9` от 14 сентября исправил эти утверждения. Факт дрейфа наблюдался;
повторная реализация компонента на его основании — возможное последствие, а
не произошедший в проекте дефект.

Следовательно, переносимость требует поддержания свежести. Documentation
alignment остаётся необходимым, но проверяемые утверждения по возможности
должны иметь механическую сверку: существование компонента или публичного
контракта, разрешение ссылок на нормативные документы, согласованность
проверяемых статусов. Автоматизация не должна пытаться выводить архитектурное
намерение из кода.

Текущая готовность компонентов имеет один оперативный источник —
`docs/requirements/overview.md` §2.1. `roadmap.md` ссылается на него, а свой
раздел выполненных работ сохраняет как датированный исторический снимок.
Другие документы могут описывать план или историю, но не должны независимо
поддерживать вторую таблицу текущего состояния.

## 28.4. Версионирование инженерного baseline

**Статус: рабочая гипотеза; процедура для параллельной работы ещё не проверена
в проекте.**

Переносимый контекст отвечает на вопрос, может ли новый исполнитель восстановить
намерение системы. При параллельной работе дополнительно важно, относительно
какой версии этого намерения выполнялась задача.

При испытании параллельной работы предлагается явно указывать исходный commit
задачи с действующими на тот момент requirements, ADR, диаграммами,
инвариантами, тестами и кодом.
Commit SHA описывает только зафиксированное состояние. Если задача начинается
с незакоммиченными изменениями, их состав тоже должен быть сохранён как часть
исходного состояния либо работа начинается в чистом checkout.

```text
начало задачи на baseline B17
    ↓
реализация
    ↓
текущий baseline B18
    ↓
проверка изменений B17 → B18 и применимости результата
    ↓
принятие или адаптация
```

Изменение baseline не делает работу автоматически устаревшей. Оно означает,
что совместимость с текущим состоянием нужно проверить перед принятием.
Исполнитель не обязан перестраивать незавершённую работу после каждого нового
коммита основной ветки.

## 28.5. Параллельная разработка и смысловые конфликты

**Статус: рабочая гипотеза.** Текущий roadmap предусматривает одного
исполнителя и последовательную работу; этот порядок пока не испытан на
параллельных задачах `exact-orb`.

Git обнаруживает текстовые конфликты, но не гарантирует обнаружение
архитектурных. Два изменения могут затрагивать разные файлы и при этом
опираться на несовместимые предпосылки: например, один исполнитель изменил
владельца состояния, а другой продолжил работу по прежнему контракту.
Отсутствие Git-конфликта не доказывает смысловую совместимость.

Перед принятием результата, начатого на более старом baseline, необходимо
сверить изменение нормативного контекста и относящихся к задаче кода и тестов:

1. Какие requirements, ADR, sequence diagrams и инварианты изменились?
2. Какие предпосылки текущей задачи они затрагивают?
3. Не возвращает ли итоговый diff поведение, запрещённое новым контрактом?
4. Какие проверки нужно повторить на актуальном состоянии?

Это смысловая проверка совместимости, а не обязательно операция `git rebase`.
Маркер области воздействия изменения (`IMPACT`) и область зависимости задачи
(`AFFECTED COMPONENTS`) могут направлять review. Их пересечение требует
внимания, но отсутствие пересечения не освобождает от проверки изменений
baseline: неполные метки не доказывают совместимость.

Если во время параллельной работы меняется предпосылка, на которой прямо
основана чужая активная задача — например, ownership состояния, публичный
контракт, schema, граница компонентов, concurrency или error semantics, —
затронутую работу следует уведомить до её приёмки. Это позволяет сохранить
параллельность без глобальной остановки всех исполнителей.

## 28.6. Ограничитель

**Статус: принцип метода.**

«Критичный для продолжения разработки контекст» не означает всё, что когда-либо
обсуждалось. Контекст выносится в нормативный источник, если можно назвать
конкретное неверное решение, которое следующий исполнитель может принять без
него:

> Не зная этого, исполнитель сделает X, и это будет ошибкой, потому что Y.

Если такую связь нельзя сформулировать, сведения могут остаться в истории Git,
обсуждении, implementation prompt или исследовательских заметках. Это
ограничивает обязательный для восстановления контекст, а не объём текста сам
по себе.

## 28.7. Проверка принципа: bounded prompt как restoration drill

**Статус: рабочая гипотеза; достаточная серия измерений не накоплена.**

Новая сессия с bounded task частично проверяет передаваемость контекста.
Задание должно описывать новое изменение; постоянное инженерное знание должно
быть восстановимо из репозитория.

Повтор инварианта в prompt сам по себе не является `context leakage`. §9.1
требует самодостаточного задания с нужными выдержками и ссылками. Краткое
напоминание, ссылка на авторитетный источник и ограничитель scope допустимы.

`Context leakage` возникает, если правило одновременно:

1. необходимо для корректного выполнения задачи;
2. не специфично только для неё;
3. не может быть надёжно восстановлено из доступного, актуального
   авторитетного источника в репозитории;
4. поэтому передаётся исполнителю заново вместо ссылки или краткой выдержки.

При подготовке bounded task такие случаи можно классифицировать как
`missing requirement`, `missing ADR`, `missing sequence`, `missing invariant`,
`unclear source of truth`, `stale document` или `hard-to-discover document`.
Основная пробная метрика — число таких случаев на задачу. Доля задач хотя бы
с одним случаем дополняет её. Доля повторённого текста в токенах вторична:
она зависит от сложности задачи и не должна побуждать сокращать полезные
prompts ради показателя (см. раздел «Что можно измерять»).

Этот тест частичен: владелец уже выбрал область задачи. Более сильная, пока
не проведённая проверка — дать новому исполнителю только репозиторий и задачу
на уровне продукта, затем измерить время до корректного изменения, вопросы
владельцу, неверные архитектурные предположения и дополнительно переданный
контекст.

---

# 29. Таблицы принятия решений как рабочий инструмент

В процессе разработки планируется использовать decision tables не только перед
написанием промтов, но и как инструмент накопления наблюдений о самом методе.

Например, можно фиксировать:

| Вопрос                    | Альтернативы       | Решение           | Почему             | Результат после реализации |
| ------------------------- | ------------------ | ----------------- | ------------------ | -------------------------- |
| Делить handler и logging? | вместе / отдельно  | отдельно          | меньший scope      | оценить после реализации   |
| Tests в том же prompt?    | вместе / отдельно  | отдельно          | независимый проход | оценить                    |
| Mock или real dependency? | mock / fake / real | зависит от уровня | разные цели теста  | оценить                    |

Это позволяет спустя несколько итераций анализировать не только код, но и
**качество самого процесса принятия решений**.

---

# 30. Что можно измерять

Метод пока экспериментальный, поэтому метрики также находятся в процессе
формирования.

Потенциально имеет смысл наблюдать:

### Scope

* сколько файлов планировалось изменить;
* сколько реально изменено;
* сколько незапланированных файлов затронуто;
* сколько раз агент пытался выйти за scope.

### Decision quality

* сколько развилок было выявлено до реализации;
* сколько новых развилок возникло во время исполнения;
* сколько решений пришлось пересматривать.

### Implementation

* количество implementation passes;
* количество исправлений после первого review;
* доля изменений, принятых с первого прохода.

### Review

* сколько defects обнаружил implementation agent;
* сколько defects обнаружил judge;
* сколько defects обнаружили deterministic tests;
* сколько defects дошло до следующего этапа.

### Tests

* component coverage;
* количество integration scenarios;
* количество regression tests;
* количество boundary invariants;
* количество тестов, реально воспроизводящих найденный дефект.

### Context / agent efficiency

При необходимости:

* объём контекста;
* количество агентских проходов;
* число повторных чтений файлов;
* количество лишних изменений;
* стоимость использования модели;
* время владельца проекта.

Но эти показатели не должны автоматически становиться целью оптимизации.

Например:

```text
меньше prompts
```

не обязательно лучше.

Если четыре маленьких прохода дают более контролируемый результат, чем один
большой, увеличение количества prompts может быть преимуществом.

# 31. Модель доверия

| Риск                                         | Компенсация                             |
| -------------------------------------------- | --------------------------------------- |
| Ошибочная исходная спецификация              | обсуждение альтернатив + decision table |
| LLM выбрала архитектуру вместо владельца     | явная колонка решения владельца         |
| Implementation и judge повторяют одну ошибку | deterministic tests                     |
| Test повторяет ошибку implementation         | golden/reference data                   |
| Mock скрывает ошибку интеграции              | real-path integration tests             |
| Агент вышел за scope                         | allowed / forbidden files               |
| Архитектурный запрет забыли                  | boundary-test                           |
| Документация разошлась с кодом               | documentation alignment                 |
| Критичный контекст остался в AI-сессии        | переносимый нормативный контекст        |
| Задача основана на устаревшей архитектуре     | baseline + проверка совместимости       |
| Параллельные изменения смыслово несовместимы | review изменений baseline и предпосылок |
| Новый вопрос решён агентом молча             | STOP + новая decision table             |
| Prompt был случайно исполнен                 | DRAFT / APPROVED lifecycle              |
| Агент сделал commit самостоятельно           | explicit no-commit rule                 |
| Слишком большая задача                       | decomposition into bounded change-sets  |
| Большой prompt скрывает главное              | scope + invariants + references         |
| Concurrency-test нестабилен                  | controlled Event / barrier / fake clock |

# 32. Пример: ChartArtifactResolver

Первичная реализация `ChartArtifactResolver` имела рабочий cache-backed путь и
single-flight.

Отдельный review обнаружил два дефекта:

1. concurrent callers могли получить общий экземпляр артефакта с изменяемыми
   вложенными объектами;

2. cache lookup выполнялся до регистрации single-flight, поэтому delayed miss
   мог повторно инициировать расчёт после завершения первого.

Замечания были превращены в отдельную ограниченную задачу.

Были зафиксированы требования:

* независимый результат для каждого caller;
* single-flight полного цикла;
* сохранение parallelism разных keys;
* независимость shared calculation от отмены одного waiter;
* fan-out ошибок;
* возможность следующей попытки;
* deterministic concurrency tests.

Этот пример показывает назначение judge:

> не подтвердить уже написанный код, а найти сценарий, в котором реализация
> нарушает контракт, и превратить этот сценарий в постоянную исполняемую
> проверку.

# 33. Пример: BuildNatalHandler

Работа над `BuildNatalHandler` показывает ещё один элемент метода.

Перед написанием implementation prompts был сформирован отдельный набор
развилок:

```text
A. структура работы
B. контракты
C. реализация
D. формат prompts
E. проверки и сопутствующие изменения
```

Для каждой развилки были зафиксированы:

```text
варианты
→ рекомендация модели
→ решение владельца
```

В частности отдельно решались:

* количество implementation prompts;
* разделение handler и logging;
* расположение тестов;
* расположение stub ports;
* contract testing;
* создание будущего `ApplicationResult`;
* style logging;
* error handling;
* self-contained prompts;
* component tests;
* integration tests;
* module boundary tests;
* documentation alignment;
* scope restrictions.

Таким образом, реализация начинается уже не с неявного набора предположений
модели, а с набора принятых инженерных решений.

# 35. Критерий успешности отдельного изменения

Для существенного изменения должна восстанавливаться цепочка:

```text
зачем понадобилось изменение
    ↓
какие варианты рассматривались
    ↓
кто и какое решение принял
    ↓
где находится актуальный контракт
    ↓
при параллельной работе — относительно какого инженерного baseline она велась
    ↓
каким prompt была ограничена реализация
    ↓
какие файлы разрешалось менять
    ↓
какие tests проверяют результат
    ↓
какой review был выполнен
    ↓
каким изменением результат принят
```

Если цепочка обрывается, мнение LLM не закрывает пробел.

# 36. Критерий успешности метода

Метод нельзя считать успешным только потому, что:

* LLM быстро пишет код;
* написано много тестов;
* уменьшилось количество prompts;
* агент способен работать долго автономно;
* полный `pytest` зелёный.

Более важный критерий:

> Насколько хорошо владелец способен контролировать направление разработки,
> сохранять архитектурные границы, обнаруживать ошибочные решения и
> воспроизводимо принимать изменения, делегируя модели всё большую часть
> технического исполнения.

То есть исследуется не только:

```text
может ли LLM написать компонент?
```

но и:

```text
какой процесс нужен,
чтобы один специалист мог безопасно и контролируемо
делегировать модели существенную часть разработки?
```

# 37. Ограничения текущего подхода

Метод находится на раннем этапе.

Пока не доказано, что он:

* масштабируется на большой repository;
* одинаково хорошо работает с разными LLM;
* экономически эффективен в закрытых контурах;
* эффективнее хорошей человеческой команды;
* уменьшает общее количество дефектов;
* уменьшает time-to-market;
* сохраняет эффективность при ограниченном context window;
* подходит для high-criticality систем.

Также существует риск, что процесс станет слишком тяжёлым:

```text
обсуждение
→ таблица
→ требования
→ prompt
→ review
→ tests
```

может стоить больше, чем небольшая ручная реализация.

Это необходимо проверять практикой.

# 38. Что именно исследуется

`exact-orb` является не только продуктовым demo, но и экспериментальной
площадкой для изучения AI-assisted software development.

В частности исследуются вопросы:

* насколько далеко один специалист может продвинуть разработку;
* какие задачи можно безопасно делегировать агентам;
* какие решения должны оставаться за человеком;
* какой уровень спецификации нужен модели;
* насколько эффективны decision tables;
* насколько полезно разделять implementation и judge;
* когда тест должен быть написан агентом вместе с кодом;
* когда нужен отдельный testing pass;
* где mock допустим, а где скрывает дефект;
* насколько хорошо boundary tests защищают архитектуру;
* насколько атомарными должны быть prompts;
* какие ограничения предотвращают scope creep;
* как стоимость и качество меняются при использовании более слабых моделей;
* насколько процесс применим в закрытых контурах с ограниченным GPU и
  token budget.

# 39. Статус документа

Этот документ намеренно не объявляется окончательной методологией.

Он должен изменяться вместе с практикой.

При появлении новых наблюдений необходимо различать:

### Наблюдение

```text
в одном конкретном случае произошло X
```

### Рабочую гипотезу

```text
возможно, правило Y уменьшает вероятность X
```

### Повторяемую практику

```text
правило Y успешно применялось в нескольких задачах
```

### Стабильный принцип

```text
правило Y достаточно подтверждено, чтобы считать его частью метода
```

Не каждая удачная практика автоматически становится постоянным правилом.

# 40. Текущая формула подхода

На текущем этапе метод можно кратко описать так:

```text
человек не пытается вручную написать весь код
и не передаёт LLM бесконтрольную разработку.

Вместо этого:

LLM расширяет пространство решений
    ↓
человек выбирает
    ↓
решение превращается в контракт
    ↓
контракт превращается в ограниченную задачу
    ↓
агент реализует
    ↓
другой проход ищет нарушение
    ↓
машинные проверки подтверждают наблюдаемое поведение
    ↓
человек принимает результат
```

Главная исследуемая гипотеза:

> Сильные навыки анализа, архитектурного мышления, постановки задач,
> тестирования и принятия решений могут позволить одному специалисту
> контролируемо делегировать LLM значительную часть разработки,
> не передавая модели архитектурное владение системой.

Эта гипотеза пока рассматривается как рабочая и требует дальнейшей проверки
на практике.
