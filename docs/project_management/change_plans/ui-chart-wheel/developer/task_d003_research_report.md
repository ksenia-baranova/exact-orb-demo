## T003-G01 — port, outcomes и lifecycle

Существующий `session.mjs:publish()` переводит исключение всего render в `requiresReconciliation`. Это действующий общий recovery contract; будущий ожидаемый SVG-fault должен завершаться **внутри leaf renderer boundary**. `facts.mjs:readChartFacts()` сохраняет текстовые факты, но не geometry longitude; будущему controller нужен исходный readonly ChartDTO, а HTML читает опубликованные значения. `main.mjs` сейчас размещает recovery controls внутри формы — будущий collapse должен скрывать только поля, сохраняя feedback / gates.

Предложение: ResultController владеет accepted snapshot, selection / expansion / editor policy; HTML и wheel получают одну принятую карту. Wheel port имеет `mount → update → dispose`, canonical intent и tagged `rendered | svg_unavailable` outcome. При принятии B HTML B публикуется до leaf SVG; старое изображение A снимается до потенциально отказавшего paint B. Instance generation и render revision проверяются перед обработкой event/callback/async settlement; dispose идемпотентно снимает listeners. Сбой dispose не должен вернуть A или блокировать HTML B; конкретная реализация этого отказа ещё NOT RUN. Непредвиденный сбой controller / HTML сохраняет общий reconciliation; локальный SVG-fault не меняет transport gates. Детали — [DRAFT ADR](drawing_adr_draft.md), [sequence 001](sequence_diagrams/ui/001-result-renderer-lifecycle.puml).

**Реальный isolated browser control:** [lifecycle.html](evidence/task_d003_research/lifecycle.html), [followup02 records](evidence/task_d003_research/followup02/controls.json). A активирует sun; B отличается identity, sun=12.25° / Aries 12°15′, orb первой записи=2.75. При fault factory: HTML points/aspects и summary относятся к B, imageCount=0, fault hook достигнут; поздний callback A зарегистрирован `late-ignored`. Альтернативная SVG factory того же port на B получает сохранённый canonical sun и живым Enter снимает его; B input не изменён. [Fault screenshot](evidence/task_d003_research/followup02/B-fault-html.png), [alternate](evidence/task_d003_research/followup02/B-alternate.png). Это конкретная замена двух минимальных renderer одного port, не готовые две полные карты. Полные houses/angles HTML, async same-instance revision, update/dispose throw и реальное соединение с production coordinator этим control не проверены.

## T003-G03 — accepted cause и submitted snapshot

Реальный coordinator + transport/form с листовой fake сетью: один submit дал **три idle/source=build publications** после двух `clearFieldError`; POST остался один. Поэтому `source=build`, identity или очередной render не являются once token. В deferred submit форма изменена с 14:30 на 15:45: immutable submittedIntent и resultSummary сохранили 14:30, draft — 15:45. Ни sleep, ни случайные задержки не использовались.

Предложение: внутри accept-owner создать process-local монотонный `acceptanceSeq` и отдельный `attemptId`, immutable submitted snapshot / previous confirmed birth / accepted cause. Presentation применяет policy максимум один раз на seq; renderer update / повтор publish не создают нового cause. Own committed changed birth reset → 5/5, selection=null; collapse только при точном равенстве текущих полей submitted snapshot, включая edit→revert. Automatic current/reconcile обновляет факты и только исчезнувший выбор; rejected, stale/different/old recovery, failed read не становятся own-success. Модели этих ветвей явно отделены в 26 controls; enum / seam в production не добавлены. [Sequence 002](sequence_diagrams/ui/002-acceptance-selection-focus.puml).

**Конкретный новый различающий случай для Analyst / Manager → Owner, без блокировки независимого исследования:** A была показана, пользователь отправил изменённые данные B, ответ POST потерян; recovery GET fresh `birth=B`, identity=B, status=`matched`. Возможны две серверные истории: (1) завершился этот POST; (2) другой tab записал ту же B, а этот POST не победил. Публичные GET / `matched` наблюдения одинаковы; отдельного producer token нет. Actual control показывает source=current / recovery=matched; это совпадение цели, не доказательство автора server commit.

Рекомендация Developer: для presentation определить *подтверждение результата локальной pending попытки* по fresh matched recovery (однократно на attempt), без утверждения «серверный commit выполнен именно этим POST» и без нового API. Такой смысл должен адресно подтвердить Analyst / владелец наблюдаемого правила; до этого соответствующая ветвь DRAFT, не выдуманный runtime PASS. Альтернатива — сохранять current policy до недвусмысленного POST; она может нарушать ожидаемый reset после подтверждающего recovery. Истинная producer provenance потребовала бы отдельного API scope, здесь исключена. Повторный общий предстартовый review критериев не предлагается.
