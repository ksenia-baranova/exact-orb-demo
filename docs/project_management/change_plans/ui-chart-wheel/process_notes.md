# Заметки к процессу

Временные комментарии к процессу и идеи для будущих изменений и реализации.

1. После завершения каждого шага явно говорить или писать, что нужно сделать дальше.
2. В будущем при подключении таск-менеджера (например, Jira) для прохождения G0, помимо существующих критериев, должна быть создана задача для Analyst. Задание хранить в таск-менеджере, чтобы не хранить его в репозитории.

3. Дыра в процессе: начало работы роли и передача результата могут остаться незарегистрированными в общей сводке Manager.

   Основание — [комментарий Owner в ревью PR #63](https://github.com/ksenia-baranova/exact-orb-demo/pull/63#pullrequestreview-5509238539), 2026-10-13: «Дыра в процессе надо, аналитик начал работу но нигде это не отмечено».

   В TASK-A-001 Owner назначил Analyst на опубликованное задание, Analyst подтвердил STARTED в своём чате и индексе, подготовил пакет и опубликовал его на 683bdd0. После merge PR #63 в change на bc9a4fb Manager-файл всё ещё показывал DRAFT, отсутствие Analyst и неподтверждённый G0; строки TASK-A-001 / статусов пакета не было. Owner пришлось отдельно спросить про статус, а затем поручить Manager обновить сводку.

   Причина: роли разделяют ownership — Analyst пишет свои события и handoff, текущие статусы ведёт Manager. Процесс разрешает начать уже разрешённую работу без ожидания ручного переключения, но в минимальном ручном режиме не определяет обязательный способ оперативно доставить STARTED / передачу Manager и подтвердить обновление сводки. Запись события в ролевом индексе на ещё не опубликованной ветке не гарантирует, что Manager его прочитает вовремя. Описанный будущий сборщик не реализован; merge ролевого PR сам по себе не обновляет состояние. Также не был согласован срок ответа / эскалации, по которому можно заметить зависшую регистрацию.

   Влияние: реальная работа и видимый статус расходятся; непонятно, разрешён ли Analysis, начался ли он и можно ли переходить к следующему шагу. Публикация / merge и отсутствующая регистрация не должны превращаться в ложное APPROVED / DONE или скрывать реально состоявшийся STARTED.

   Что уточнить или реализовать в будущем:

   - При назначении явно фиксировать исполнителя сводки, вход, полномочия и reviewer. Для STARTED и передачи определить короткий обязательный маршрут уведомления Manager, срок обработки и подтверждение регистрации; не ждать финального merge, чтобы отметить начало.
   - В ручном режиме передавать TaskId, автора, событие, дату, входную версию и ссылку на сохранённый ролевой источник. Для передачи результата нужен точный опубликованный SHA; Manager сверяет evidence и зависимости, обновляет сводку и явно называет следующий шаг. Если событие зарегистрировано позднее, отдельно сохранять время события и время регистрации.
   - При автоматизации связать назначение / начало / передачу в таск-менеджере с событиями процесса и проверяемой версией артефакта. Определить один источник текущего состояния и подтверждение доставки; событие Jira или Git не должно обходить содержательные условия G0 / G1 и ролевые approvals.
   - Проверить процесс сценарием: Analyst начал разрешённое задание, затем опубликовал результат; Manager видит IN_PROGRESS, а после передачи — READY_FOR_REVIEW / IN_REVIEW до отдельного вопроса Owner. ALIGNMENT наступает только после полного G1.

   Это заметка для будущей правки процесса. В текущем проходе Manager восстановил подтверждённые события в manager_artifact.md; process.md и ролевые правила не изменены.
