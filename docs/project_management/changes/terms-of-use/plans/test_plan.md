## Подготовка, оракулы и оценка

- Дельта — REQ-UI-03 и REQ-TERMS-01…08. Источник каждого ожидаемого приведён в карточке. Таблицы G/R, T, D, C, L исчерпывающе распределены по карточкам; отдельная матрица не создаётся: покрытие задаёт поле req.
- Основной набор — будущие приёмочные проверки через UI и публичный HTTP-контракт. В задаче test сначала сопоставить этот уже записанный план с существующими fixtures/helpers и тестами: переиспользовать покрытие, не копировать проверки. Сведения S7 о старом покрытии принадлежат Analyst и сейчас независимо не проверялись.
- Общие тестовые данные: дата `1990-09-02`; выбранный из контролируемого каталога item `place_id="524901"`, `display_name="Москва"`; известное время `14:30`, неизвестное — выбранная отметка неизвестности. Это входы фикстуры, а не расчётный эталон. HTTP §6.4 задаёт пример этих трёх request-полей; часовой пояс/координаты определяет сервер. Название берётся из item фикстуры, не выводится из ID в UI.
- Снимок черновика D = (дата, текст места, наличие/значение выбранного place_id, подтверждённое название, строка времени, неизвестность). До перехода и после него сравнивать все компоненты по значениям; ошибки/подсказки не подменяют значения. При D2 скрытая строка времени наблюдается после снятия неизвестности. При неполном вводе сравнивать именно доступный пользовательский ввод, не записывать приватные поля.
- На каждый параметризованный пример — свежая подготовка. Наличие карты: `empty` либо заранее принятая A с зафиксированными chart_identity, birth, facts и раскрытиями; новый ответ B отличим от A. ChartDTO/BirthViewDTO готовятся независимо до прогона по публичной схеме, с количеством строк >5 для R1; числовые значения не получают из фактического UI и не пересчитывают во frontend. Для integration реальны проверяемые компоненты, моки только на внешних/листовых швах; для UI известные ответы transport задаются до действия.
- Для счётчика сетевых запросов завершить исходные bootstrap/current и записать baseline N. Далее считать прирост POST /charts/natal; допустимые GET/ bootstrap не объявлять отсутствующими. Позитивный контроль G4 использует тот же инструмент регистрации POST. Ожидание исхода/блокировки управляется Event/barrier, fake clock и readiness-сигналом; sleep и случайные задержки запрещены.
- Точный текст условий Q — только секция для публикации из конкретной отдельно утверждённой Owner редакции, с записью решения, Git SHA и hash текста. На момент TASK-T-01 Q ещё не был утверждён. Для TASK-T-02 используется секция из пакета `02cbd17e33ceffe52d465bdf6b8faf1d3c76864c`, утверждённая в TASK-O-02, SHA-256 `ee474d44cd2d8231660e3d5ab5a7d9946b72084ddabad7f22a0686281d7840a0`. Историческая шапка terms_draft.md не заменяет позднейшее решение Owner. Для сравнения видимого текста Q допускается только нормализация пробелов/переносов отображения, без удаления слов, разделов, ссылок и оговорок. Метаданные Analyst и таблица сверки в публикуемый Q не входят. Ожидаемые строки фиксировать из Q до первого запуска, а не из реализации. Отсутствие Q — предусловие будущей проверки, не новый DP о повторном утверждении адреса.
- У проверки источника кода перед запуском зафиксировать проверяемый DeploymentSHA, адрес сервиса и публичный ref полного исходного кода. Доступность внешней ссылки проверять без авторизации; в этом review сетевые проверки не выполняются и писем не отправляют.
- Оценка всей работы Tester: **24 чч / 8 мч, confidence: medium**; review и план — 6/2, подготовка независимых проверок и автоматизация — 10/3, прогоны UI/API и документирование — 6/2, один небольшой ретест — 2/1. Ожидание Owner, исправлений и стенда не включено. Допущения: один UI, доступные локальные runtime/browser, каталог/DTO фикстуры, точный коммит поставки, утверждённый Q до test. Другой объём исправлений или отсутствующее окружение требует переоценки, а не смены ожидаемого.
