Checkbox подтверждает ознакомление с условиями; значение checkbox не является юридическим согласием и не хранится как подтверждение. Переходы страницы определены REQ-TERMS-01…08; новый способ не меняет расчётный HTTP-контракт.

В таблице проверяется попытка явного построения при разрешённом действующими правилами HTTP/recovery состоянии клиента. Отказы bootstrap, admission и recovery сохраняют запреты REQ-UI-09.

Исключение закрытого M1-7, разрешавшее отсутствие страницы и текста, заменяется поставкой M1-9. DEBT-UI-001 закрывается владельцем по отдельным evidence утверждённого содержания, независимой проверки Tester на точном коммите и интеграции. Создание этого инкремента не закрывает долг.

Форма содержит дату, место и время; поля имени нет. В POST не добавляются имя, текст места, координаты, checkbox, клиентский `state_version` или иные поля. При первом показе карты в исходном виде сразу видны первые пять аспектов и первые пять рассчитанных домов; у каждой таблицы своя кнопка «Показать все» для остальных строк без нового POST. Первые пять опубликованных points видны сразу, остальные доступны через независимое «Показать все»; angles — отдельный компактный табличный блок без вымышленных значений. Условие сворачивания формы — REQ-UI-11; «Открыть чат» остаётся видимым неактивным элементом, не открывает чат и не отправляет запрос. При восстановлении `chart_ready` через GET сохраняется тот же доступ к данным; automatic current не сбрасывает выбор / раскрытие по REQ-WHEEL-08. Ошибочные ответы и запросы сверки описаны ниже и в REQ-UI-09.
- Локальная проверка препятствует очевидно неверному формату и отсутствию выбранного места, но не заменяет сервер. Для `422 INVALID_REQUEST` и `422 INPUT_REQUIRED` UI использует действующий `ErrorDTO`: `issues[].field` (`birth.date`, `birth.time`, `birth.place`, `request.body`, `request.<name>`), `code` (`MISSING`, `AMBIGUOUS`, `INVALID`, `UNSUPPORTED`), необязательные `candidates` и `constraints`; `user_message` остаётся общим сообщением. Несуществующая/двусмысленная локальная минута выбранного места показывается как ошибка `birth.time`, а не исправляется часовым поясом браузера. Ошибка у соответствующего поля имеет приоритет перед общей; неизвестный field остаётся в общей области ошибки. Schema validation предшествует проверке cookie: невалидный body без cookie даёт 422, а не 409.
- При отказе введённые дату, время/отметку и выбранный `place_id` сохраняют в клиентской форме до явного изменения. Ошибка сессии не превращает прежний текст места в подтверждённый ID. Видимое неактивное «Открыть чат» ясно обозначено как недоступное в M1-7; активное действие подробностей не обещает новой сборки.

**Добавка M1-8:** При получении карты дополнительно сразу доступно колесо. «Изменить данные» раскрывает заполненную форму по REQ-UI-11; открытие формы, таблиц и выбор не отправляют POST. При ошибке и неопределённом исходе сообщения, issues, безопасная проверка и разрешённый ручной повтор остаются доступны при ранее свёрнутой форме. Принятие новой карты после успешного build по изменённым birth data сбрасывает выбор / раскрытие к исходным первым пяти, редактирование и отказ этого не делают. После успешного явного build форма сворачивается, только если её текущие поля соответствуют отправленному снимку; более поздний отличающийся draft остаётся видим в открытой форме. Построение, восстановление карты и раскрытие редактора не выбирают checkbox; отдельное явное действие «Согласен» выбирает checkbox по REQ-TERMS-02.



Сценарии этой редакции: [AS-UI-20](#as-ui-20), [AS-UI-21](#as-ui-21), [AS-TERMS-13](#as-terms-13). Существующие AS-UI-03/04/06/12/13/14/17/22/23 и AS-WHEEL-01/12/18/19/20/21 сохраняют проверки расчёта, ответов и recovery. Их ссылки выше ведут в текущие сценарии; при transfer относительные пути заменяющей редакции отсчитываются от target.

## REQ-TERMS-04 Сохранение черновика при переходе

action: ADD
target: docs/requirements/current/ui/terms-of-use.md#req-terms-04
source: S1; S3; S6
goal: G1 — вернуться к введённым данным
priority: P1

Система должна сохранять черновик формы при текущем переходе к условиям и каждом из двух возвратов.

Сохранение означает равенство исходных и возвращённых значений даты, текста места, выбранного place_id с названием, строки времени и отметки неизвестности. Одинакового названия без выбранного place_id недостаточно. При незавершённом вводе не появляется фиктивный place_id или известное время. Отметка ознакомления изменяется отдельно по таблице T. ## Сценарии Given / When / Then

Каждый нижеуказанный сценарий является заданием проверки, а не результатом прогона. Для всех переходов счётчик POST измеряется относительно завершённого исходного открытия формы; исходные bootstrap/current не вычитаются из другого сценария. «Нет POST» дополняется позитивным контролем явного построения. Наблюдаемость новых UI-действий — страница, значения формы, focus и сетевой счётчик. Новый серверный журнал подтверждений не вводится. Если выполняется действующий business request, сохраняются X-Request-ID, парные http_message и terminal по HTTP-контракту; статические ресурсы не получают вымышленные business events.

Контроль: возврат кнопкой «Согласен» до reload сохранял черновик и выбирал отметку по T1.

## Решения, DP и границы

Приняты S1: два способа отметить checkbox; текстовая ссылка под checkbox; «Согласен» и «Вернуться к форме»; сохранение черновика; отдельное построение; новая загрузка снимает отметку. Повторное подтверждение не требуется. Для D3 сохранение неполного ввода следует из сохранения введённых данных и действующего черновика; новый пользовательский выбор не вводится. Общая доступность переносится из REQ-UI-10 без новой архитектуры.

ACCEPTED: [DP-A-01](dp/DP-A-01.md) — Owner выбрал `exact_orb@mail.ru` для публикации в условиях и личных обращений по вопросам данных и удаления. Решение применено в C6, сценариях AS-TERMS-12/15 и [черновике](terms_draft.md); повторное согласование адреса и объёма не требуется. Открытых DP нет. Полный текст условий остаётся черновиком до отдельного утверждения Owner на штатном APPROVAL. Юридическая проверка, сроки хранения журналов на стенде, отдельное согласие и прочие условия публичного запуска остаются вне scope.

REQ-UI-11 не заменяется: его правило reload и сохранение открытого черновика совместимы с возвратом T1…T4, поскольку возврат не является новой загрузкой. Отдельная страница не меняет ChartDTO, birth-time semantics, сессию, кэш, расчёт и LLM. Прямой вход на страницу без исходной формы, F5 самой страницы условий и восстановление черновика после закрытия не добавляются как новые сценарии первой версии; обязательные переходы начинаются из формы по S1. Техническую навигацию выбирает Developer в этих границах.
