# Правила размещения требований

Этот документ определяет контракт активного change, форматы требований и перенос принятого пакета в общие каталоги. Gates и допуск интеграции определены в [process.md](../development_approach/process/process.md), разделы 3.1 и 6.2.

## Размещение артефактов

Каждый новый change использует docs/project_management/change_plans/<change-id>/: Manager и материалы участвующих ролей. Полное дерево и исключение для малого варианта определены в process.md, раздел 7.

| Материал | Путь нового change | Назначение |
|---|---|---|
| Manager / DP | `change_plans/<change-id>/manager_artifact.md` относительно `docs/project_management/` | Brief, состояния, задания, единый DP-реестр, бюджет, Change Plan, approvals и поставка |
| Индекс Analyst | `change_plans/<change-id>/analyst_artifact.md` | Версии, ссылки, оценка, blockers и handoff |
| Требования change | `change_plans/<change-id>/analyst/requirements.md` | DELTA к baseline либо FULL обозначенной области |
| Сценарии change | `change_plans/<change-id>/analyst/scenarios.md` | Acceptance scenarios с устойчивыми IDs |
| Findings / карта переноса | `change_plans/<change-id>/analyst/findings.md`, `analyst/transfer_map.md` | Исходные вопросы и проверяемое соответствие принятой и чистовой редакций |
| Рабочие sequences | `change_plans/<change-id>/analyst/sequence_diagrams/<область>/` либо `developer/sequence_diagrams/<область>/` | По ownership: behavioral/API — Analyst, technical — Developer |
| Чистовые требования | `docs/requirements/current/<область>/` | Полный действующий текст требований и сценариев после переноса |
| Общие sequences | `docs/sequence_diagrams/<область>/` | Утверждённые sequences после переноса, связанные PNG при наличии |
| ADR | `docs/requirements/decisions/` | Принятые архитектурные решения по действующим правилам ADR |

Шаблоны находятся в [артефактах Analyst](../development_approach/artifacts/functional-analyst.md), а заполненные документы — внутри своего change. Исторические paths сохраняются до отдельно согласованной миграции.

## Действующая редакция и контракт активного change

[current/](current/README.md) на main содержит общий принятый baseline. До переноса прежнего тематического документа применяется его явно зафиксированный нормативный путь и commit.

Контракт активного change состоит из исходного baseline и утверждённого пакета требований / сценариев / ролевых sequences с точными версиями. DELTA меняет только перечисленные обязательства; остальные требования baseline продолжают действовать. Черновик, предложение роли или будущая чистовая редакция не заменяют утверждённый контракт.

Developer и Tester получают обе части контракта вместе, ссылки на DP и ADR. В сокращённом маршруте с неизменным контрактом используются прямые ссылки на действующие требования и сценарии; основание и проверка Tester фиксируются в `manager_artifact.md`. Четыре кратких корневых артефакта сохраняются, но пустые requirements / scenarios / подробный Analyst-пакет не создаются. Отметка участия роли не подменяет статус задания или approval.

Дельта не отменяет ADR молча. Конфликт фиксируется finding и передаётся владельцу решения; действующий архитектурный контракт определяется [реестром ADR](decisions/README.md).

## Дельта или полная спецификация

В `analyst/requirements.md` обязательны формат `DELTA` или `FULL`, область действия, исходный commit и целевые чистовые пути.

- **DELTA** — основной формат существующего поведения. Для каждого требования указываются стабильный ID, `ADD` / `MODIFY` / `REMOVE`, исходный путь / пункт @ commit, полная новая формулировка для ADD / MODIFY, сценарии, DP и целевой путь в current/.
- **FULL** — полная спецификация новой области. Для замены существующего документа перечисляются заменяемые документы и судьба каждого прежнего обязательства: сохранено, изменено или удалено с основанием. Отсутствие пункта само по себе не разрешает удаление.

Несколько областей в одном change имеют явно указанный формат для каждой. Дельта достаточна для реализации и проверки: конкретные значения, условия, expected behavior. Для REMOVE обязательны основание и последствия для сценариев, тестов и диаграмм; удалённый ID не переиспользуется. Если ID раньше не было, Analyst связывает исходный пункт с новым ID без изменения поведения.

## Диаграммы и ADR

Рабочие behavioral/API sequences создаются в `analyst/sequence_diagrams/<область>/`, технические — в `developer/sequence_diagrams/<область>/` своей папки change. У каждого изменяемого общего файла один ответственный и один целевой путь; конкурирующие рабочие копии одного sequence не создаются.

До финальных approvals общий каталог sequences сохраняет baseline. Рабочий файл ссылается на требования / сценарии принятого пакета; после approvals переносится в существующий тематический `docs/sequence_diagrams/`, ссылки обновляются на чистовые документы. При наличии tracked PNG он обновляется вместе с PUML. Исходная редакция доступна по source commit в Git; ролевой индекс получает целевой путь и ссылку на историю вместо второй действующей копии.

Архитектурная развилка получает DP с назначенным владельцем. Analyst не утверждает ADR самостоятельно. Принятые ADR сохраняют общий каталог `decisions/`; новое решение требует нового ADR, уточнение границ — явной ревизии по [правилам ADR](decisions/README.md).

## Перенос в чистовую редакцию при завершении change

Перенос изменённых требований и sequences выполняется **после финальных ролевых approvals и приёмки Owner, в том же change и до финального merge**. G5 подтверждает проверенный контракт; сверка фактического переноса — условие интеграции по process.md, раздел 6.2. При отсутствии изменений применяется подтверждение Tester на G5, описанное ниже.

1. Manager фиксирует принятую версию, scope и исключения, назначает Analyst / Developer перенос и Tester сверку. Точные approvals и source commits сохраняются; имя итогового артефакта не заменяет подтверждение каждого назначенного предмета review.
2. Analyst сверяет актуальный baseline с целевой веткой, разрешает смысловые конфликты с владельцем решения. Поздний текст не перезаписывается автоматически. Принятую дельту применяет как ADD / MODIFY / REMOVE, FULL размещает по согласованной области. В current/ получается полный действующий контракт; неизменённые обязательства сохраняются.
3. Analyst переносит действующие сценарии и behavioral/API sequences, Developer — technical sequences. IDs сохраняются, нормативные ссылки и существующие PNG обновляются. Рабочие sequences перемещаются в общие каталоги; их source versions доступны в Git. DELTA, исходные findings и approvals остаются историей change.
4. В `analyst/transfer_map.md` Analyst связывает REQ / AS / sequence, исходный путь @ SHA, действие, целевой путь / пункт, source approval, commit подготовки и результат сверки. Технический перенос Developer передаётся Analyst ссылкой и evidence. Неперенесённые / отложенные пункты имеют основания и решения владельца; они не объявляются выполненным контрактом.
5. Tester отдельно сверяет чистовые требования, сценарии и sequences с принятым и проверенным пакетом. Матрица и ссылки в тестах ведут к тем же IDs. Фактический TestedSHA сохраняется отдельно от commit документационного переноса; старый запуск не приписывается новой версии. Изменение смысла требует возврата к владельцу, согласования и затронутых проверок.
6. Manager проверяет evidence переноса и сверки как условие final PR / merge, а не как новое решение Owner при неизменном результате. Финальный PR включает реализацию, тесты, общие документы и ролевую историю. После отдельно разрешённого merge Manager фиксирует MergeSHA и сверяет поставку по Git evidence.

Если контракт и sequences не менялись, достаточно подтверждения Tester на G5 «перенос не требуется» со ссылкой на baseline; отдельное задание после приёмки не создаётся. Обновления кандидата проверяются по process.md, раздел 6.1. Ошибка применения дельты возвращает задание переноса в REWORK, сохраняя ACCEPTED и «Поставка: нет»; противоречие самого принятого контракта возвращает change в ANALYSIS по разделу 3.1.

Чисто документальный перенос требует сверки, проверки ссылок и необходимого синтаксиса / рендера. Непроверенные части сохраняют свои ограничения. Следующий change использует общий main-baseline, не применяет историческую дельту заново. CANCELLED / REJECTED не публикуют свой предложенный контракт в общую нормативную редакцию main.

## Переход существующих документов

Для новых change требования больше не создаются в `requirements/changes/<change-id>/`. Этот каталог сохраняет опубликованную историю; реальные change, исходные промты и evidence не мигрируют автоматически при обновлении процесса.

Существующие тематические требования — [overview.md](overview.md), [scenarios.md](scenarios.md), [http_api.md](http_api.md), `component_responsibilities/`, `handlers/`, `session/` — действуют по своим нормативным путям до явного переноса. Их наличие не доказывает acceptance соответствующей реализации.

При первом change, меняющем их нормативное содержание, Analyst фиксирует исходный путь @ commit, отделяет контракт от findings / исторических review и после approvals переносит затронутый документ в current/ со стабильными IDs. Обновляются актуальные ссылки в требованиях, sequences и тестах. Старый нормативный файл удаляется либо остаётся указателем без копии контракта; старые prompts и исторические отчёты не переписываются. Соответствие путей фиксируется в transfer_map.md.

Исходные findings сохраняются у обнаружившей роли, DP — одной записью в `manager_artifact.md`; reviews остаются evidence. Техдолг общий для всех change в `docs/project_management/technical_debt.md`, Roadmap — в `docs/project_management/Roadmap/`.
