# Правила размещения требований

Этот документ определяет, где лежат требования и как инкремент изменения попадает в действующую редакцию. Статусы, переходы и задачи определены в [процессе работы над изменением](../development_approach/process/change-process-v3.md), формат инкремента — в [шаблоне требований](../development_approach/artifacts/requirements.md).

## Размещение артефактов

Каждое новое изменение использует папку `docs/project_management/changes/<change-id>/`. Полное дерево папки — в процессе, раздел «Хранение и оркестратор».

| Материал | Путь | Кто ведёт |
|---|---|---|
| Инкремент требований | `changes/<change-id>/requirements.md` относительно `docs/project_management/` | Analyst |
| Поведенческие sequences изменения | `changes/<change-id>/sequences/*.puml` | Analyst |
| DP | `changes/<change-id>/dp/DP-*.md` | роль, поднявшая вопрос |
| Технические sequences | в плане реализации изменения | Developer |
| Действующие требования | `docs/requirements/current/<область>/` | Analyst при переносе |
| Общие sequences | `docs/sequence_diagrams/<область>/` | Analyst при переносе |
| ADR | `docs/requirements/decisions/` | по действующим правилам ADR |

## Действующая редакция и инкремент

[current/](current/README.md) на main содержит общий принятый baseline. До переноса прежнего тематического документа действует его нормативный путь.

Инкремент меняет только перечисленные в нём требования; остальные требования baseline продолжают действовать. У каждого требования инкремента есть action — ADD, MODIFY или REMOVE, а у MODIFY и REMOVE — base: ссылка на пункт в current/ и commit. Тихо переписать действующее требование нельзя.

Developer и Tester читают оба источника вместе: current/ как базу и инкремент как изменение, плюс ссылки на DP и ADR. Если изменение не меняет требования (например, тип refactor), инкремент не создаётся, а задачи ссылаются прямо на действующие требования.

Инкремент не отменяет ADR молча. Конфликт оформляется как DP; действующий архитектурный контракт определяется [реестром ADR](decisions/README.md).

## Диаграммы и ADR

Поведенческие sequences Analyst рисует в `sequences/` своего изменения. В шапке каждого файла указан target — путь в `docs/sequence_diagrams/<область>/`. У каждого общего файла один ответственный и один целевой путь; конкурирующие рабочие копии одного sequence не создаются.

До переноса общий каталог sequences сохраняет baseline. При переносе файл перемещается по target, ссылки обновляются на действующие требования. Если рядом лежит tracked PNG, он обновляется вместе с PUML. Исходная редакция остаётся в истории Git.

Архитектурная развилка оформляется как DP. Analyst не утверждает ADR самостоятельно. Новое решение требует нового ADR, уточнение границ — явной ревизии по [правилам ADR](decisions/README.md).

## Перенос в действующую редакцию

Перенос выполняет Analyst в задаче transfer, в статусе DONE, до приёмки owner'ом. Правила переноса по action и проверка после него — в [шаблоне требований](../development_approach/artifacts/requirements.md), раздел «Перенос в current/». Отдельной карты переноса нет: поля action, base и target в инкременте и есть карта.

- Неизменённые требования baseline сохраняются. Поздний текст в current/ не перезаписывается автоматически: смысловой конфликт — DP.
- ID сохраняются при MODIFY; удалённый ID не переиспользуется.
- Отложенные и непоставленные требования не переносятся и не объявляются выполненными.
- Если требования не менялись, задача transfer не создаётся.
- При отмене изменения откатываются все коммиты его агентов, в том числе transfer: инкремент отменённого изменения в current/ не остаётся.

Следующее изменение использует current/ на main как baseline и не применяет историческую дельту заново.

## Переход существующих документов

Папки `requirements/changes/<change-id>/` и `docs/project_management/change_plans/<change-id>/` сохраняют опубликованную историю прежних изменений. Новые изменения в них не создаются; реальные изменения, исходные промты и evidence не мигрируют автоматически.

Существующие тематические требования — [overview.md](overview.md), [scenarios.md](scenarios.md), [http_api.md](http_api.md), `component_responsibilities/`, `handlers/`, `session/` — действуют по своим нормативным путям до явного переноса. Их наличие не доказывает приёмку соответствующей реализации.

При первом изменении, которое меняет их нормативное содержание, Analyst отделяет контракт от findings и исторических review и в задаче transfer переносит затронутый документ в current/ со стабильными ID. Обновляются актуальные ссылки в требованиях, sequences и тестах. Старый нормативный файл удаляется либо остаётся указателем без копии контракта; старые промты и исторические отчёты не переписываются.

Техдолг общий для всех изменений — в `docs/project_management/technical_debt.md`, Roadmap проекта — в `docs/project_management/Roadmap/`.
