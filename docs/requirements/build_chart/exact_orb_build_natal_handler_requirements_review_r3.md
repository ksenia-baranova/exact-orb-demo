### Проверено прогоном и по коду

- `model_config = ConfigDict(frozen=True)` на `Command` наследуется:
  присваивание полю `BuildNatalCommand` даёт `ValidationError`
  (`type="frozen_instance"`). Схема §3.1 с одиночным наследованием
  `BuildNatalCommand(Command)` работает и чище прежнего маркер-класса.
- `isinstance(obj, Handler)` для Protocol без `@runtime_checkable` поднимает
  `TypeError` — тест §12.4 п.22 реализуем именно через `pytest.raises(TypeError)`.
- Разрешённые §10.1 модули действительно контрактные: `calculation/spec.py`
  импортирует только pydantic и `exact_orb.domain`, `calculation/errors.py` —
  только `typing`; оба входят в `CONTRACT_MODULES` существующего
  `tests/test_module_boundaries.py`. Native-стек это разрешение не тянет.
- Порядок проверок валидатора §5 корректен: заполненность → равенство спек →
  `chart_kind`.

## 2. Оставшиеся замечания

### R-1. §10.1: «разрешённые импорты» читаются как неполный allowlist *(внести до реализации)*

Абзац

> Для handler разрешены прямые импорты контрактных модулей:
> `exact_orb.calculation.spec`, `exact_orb.calculation.errors`

перечисляет два модуля из необходимых handler-у как минимум семи. Без
`exact_orb.outcomes` (`InputRequired`, `ResolutionUnavailable`,
`CalculationFailed`), `exact_orb.session.state` (`SessionState`, `StateDelta`),
`exact_orb.run_context` и собственных `application.commands` / `ports` /
`results` модуль просто не собирается.

Проверка §12.4 п.14 — денилист, поэтому противоречия в тесте не возникнет,
но текст §10.1 введёт в заблуждение при реализации и при следующем ревью.

**Правка.** Одна фраза: «проверка выполняется по списку запрещённых модулей;
перечисленные ниже названы явно как заведомо разрешённые контрактные, список
не является исчерпывающим» — либо дописать полный перечень.

### R-2. Края денилиста

Не хватает:

```text
exact_orb.swiss_backend        # единственный seam с native-биндингом
exact_orb.ephemeris_runtime    # runtime-конфигурация эфемерид
exact_orb.calculation.version  # отпечаток окружения, принадлежит wiring
exact_orb.birth.resolver       # конкретная реализация вместо порта (§3.2)
exact_orb.session.persistence  # session-инфраструктура наравне со store
exact_orb.session.adapters     #
```

`exact_orb.birth.resolver` тут не формальность: без него денилист запрещает
прямой импорт `calculation.artifacts` (реализация `ChartArtifactPort`), но
разрешает прямой импорт `birth.resolver` (реализация `BirthDataResolverPort`).
Порты §3.2 защищены только с одной стороны.

Мелочь там же: `exact_orb.engine.charts` избыточен при наличии
`exact_orb.engine` — при префиксном сравнении это дубль.

Отдельно не определён статус `exact_orb.calculation.types`: он не запрещён и
не разрешён. По существу он безвреден (`results.py` импортирует его в любом
случае, §10.2), но решение стоит записать, иначе оно будет приниматься заново
на code review.

### R-3. `CancelledError` не ловится `except Exception` *(внести до реализации)*

§11 требует записать `build_natal_failed` уровня `WARNING` при отмене, §12.3
п.12 это тестирует. `asyncio.CancelledError` наследуется от `BaseException`
(проверено прогоном), поэтому наивная реализация

```python
except Exception:
    log_failed(...); raise
```

отмену не поймает: событие не будет записано, а тест 12 провалится, не
показав причины. Нужен `except BaseException` (или отдельная ветка
`except asyncio.CancelledError`) с обязательным `raise`.

Это ровно та развилка, которую соседний код уже проходил осознанно:
`EngineService.calculate` использует `except Exception` **именно чтобы не
трогать отмену**. Здесь требование обратное, и умолчание будет прочитано
неверно.

**Правка.** Одна строка в §11 рядом с таблицей нештатных завершений.

### R-4. §12 не покрывает таблицу уровней §11

Тесты 11–12 закрывают только нештатное завершение, тест 18 — только
отсутствие ПДн и `tz_id`. Отображение типизированных исходов на уровни
(`INFO` / `WARNING` / `ERROR`) тестом не закреплено. Уровень `ERROR` для
`CalculationFailed("ENGINE_UNEXPECTED")` — существенная часть §8.3
(«замаскированный дефект, а не штатный исход») и заслуживает отдельного пункта.

Там же: сквозной проброс `InputRequired` с **пустым** `issues` документ
явно разрешает (контракт `InputRequired`), но тестом не фиксирует.

### R-5. Две формулировки

1. §8.3 требует алерт от «observability-слоя», которого в проекте нет, и §13
   этого критерия не содержит. Требование за границей документа — его место в
   §14 как открытого вопроса, иначе критерий готовности формально неполон.
2. BH-8 оставлен самостоятельным инвариантом, хотя выводится из BH-7 и
   `ChartArtifact._validate_identity`. Как defense-in-depth это нормально; если
   оставляете — пометьте производность одной строкой, чтобы тест 17 не
   считался покрытием независимого свойства.

## 3. Вывод

Документ готов к реализации после R-1 и R-3 — по одной фразе каждая.
R-2 (шесть строк в денилист), R-4 (два пункта в §12) и R-5 (две формулировки)
можно вносить параллельно с написанием кода.

Контракты соседних модулей перепроверены в третий раз: `birth`, `calculation`
и `session` действительно не требуют изменений, сигнатуры портов совпадают с
реализациями посимвольно.
