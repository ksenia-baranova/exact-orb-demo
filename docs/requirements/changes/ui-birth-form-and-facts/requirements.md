## Границы и нормативное наследование

M1-7 включает явное построение и чтение шести подтверждённых групп: планеты/точки, дома, аспекты, конфигурации, сила, особые градусы (`DP-UI-01`). UI берёт факты из успешного POST или восстановленного GET, не рассчитывает знаки, дома, категории, силу и флаги из `longitude`. Действующие HTTP ошибки, cookie, admission, session lifecycle и публичный whitelist сохраняются, если дельта ниже не изменяет их явно. Колесо и его геометрия — M1-8; перенос полного прототипа — M1-8.1; чат — M2. Чистовая страница условий запланирована M1-9, но действующий gate ADR-0034 остаётся обязательным для отправки UI build до решения `DP-UI-04`.

`docs/ui_ux/**` задаёт визуальное направление и идеи; числа, тексты CTA, старые `ChartDTO`/`issues` и выдуманный диапазон Луны не являются эталоном. `DP-UI-03` сохраняет публичный ключ `admin1_name` без alias: на экране его значение подписывается «регион».

### REQ-UI-01. Первое открытие и источник состояния

**Тип изменения документа:** ADD; новой нормативной UI области в `current/` нет. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-01`.

**Пользовательское действие:** открыть страницу по HTTPS или вернуться к ней после перезагрузки. Последовательность первого входа проверяет [AS-UI-01](scenarios.md#as-ui-01-первый-вход-и-пустая-сессия), восстановление — [AS-UI-10](scenarios.md#as-ui-10-восстановление-без-расчёта), состояния сохранённой карты — [AS-UI-11](scenarios.md#as-ui-11-устаревшая-и-недоступная-сохранённая-карта).

| Шаг | Запрос и ответ | Состояние экрана |
|---|---|---|
| 1. Получить или подтвердить сессию | Клиент с cookie jar отправляет `POST /session/bootstrap` с `{}`. При успехе получает `200 ready` и `state_version`; на первом входе также получает session cookie. | Ожидает чтения карты. `ready` и `state_version` сами по себе не означают, что карта есть. |
| 2. Прочитать текущее состояние | После успешного bootstrap клиент отправляет `GET /charts/current`. | Дальнейшее представление определяется только ответом GET; страница не отправляет `POST /charts/natal`. |
| 3а. Карты нет | `200 empty`, `birth:null`, `chart:null`. | Пустая форма без рассчитанных фактов и демонстрационных чисел. |
| 3б. Карта доступна | `200 chart_ready` с `birth`, `chart` (включая `chart.chart_identity`) и признаком `chart_stale`. | Сохранённые данные рождения и факты именно этой карты; stale показан по REQ-UI-08. |
| 3в. Сохранённую карту нельзя открыть | `200 chart_unavailable` с сохранённым `birth`, `chart:null`: `session_view` безопасно отверг сохранённый payload при декодировании или проверке его версии, ключа, spec либо расчётного входа. | Данные рождения доступны для повторного построения; числовые факты карты отсутствуют. Это состояние возможно после повреждения или несовместимости сохранённого артефакта, а не при обычном пустом входе или изменении текущей версии расчёта. |

После reload и возврата вкладки актуальный серверный GET остаётся источником истины: UI показывает факты только при `chart_ready` и берёт их из `chart` этого ответа. Число `state_version` из bootstrap не используется как признак наличия карты или как её `chart.chart_identity`; при `empty` и `chart_unavailable` ранее показанные факты убираются. Структурная рассинхронизация сессии и строки карты даёт `503 STATE_READ_FAILED`, а не `chart_unavailable` (`http_api.md` §6.2). Отказы запросов и сохранение черновика описаны в REQ-UI-09 и [AS-UI-12](scenarios.md#as-ui-12-утерянная-сессия-и-сохранение-черновика).

### REQ-UI-02. Дата, время и выбор места

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-02`.

**Сценарии:** выбор места — [AS-UI-02](scenarios.md#as-ui-02-префиксный-поиск-и-выбор-двух-одноимённых-мест), [AS-UI-18](scenarios.md#as-ui-18-пустой-поиск-и-отказ-каталога); время и валидация — [AS-UI-04](scenarios.md#as-ui-04-явно-неизвестное-время-и-космограмма), [AS-UI-05](scenarios.md#as-ui-05-пустое-или-противоречивое-время), [AS-UI-06](scenarios.md#as-ui-06-ошибки-даты-локального-времени-и-места).

Поля следуют в порядке дата → место → время. Дата обязательна и передаётся как календарная `YYYY-MM-DD`. Выбор места имеет отдельный поток:

| Действие пользователя | Запрос и ответ | Состояние формы |
|---|---|---|
| Ввести префикс места, например `К` → `Ки` → `Кировск` | После запуска поиска по утверждённому UX-правилу клиент отправляет `GET /places?query=…` с актуальным префиксом; полного названия не ждёт, session cookie не требуется. `200 items[]` содержит `place_id`, `display_name`, `admin1_name`, `country_code`. Допустимость `query=К` в API не обязывает UI отправлять запрос с первой буквы. | Показаны подходящие префиксу варианты с названием, «регионом» и страной. Введённый текст ещё не является выбранным `place_id`. |
| Добавить, удалить или заменить символы после запуска поиска | После изменения актуального префикса и debounce отправляется новый GET; точный порог начала поиска ожидает UX-подтверждения. Каталог ищет по нормализованному префиксу; из-за лимита выдачи состав и число показанных вариантов могут меняться, уменьшение числа строк на каждом шаге не гарантируется. | Ответ старого запроса не заменяет варианты нового текста, даже если пришёл позже. Пользователь видит подсказки только для текущего ввода. |
| Выбрать подсказку мышью либо стрелками и Enter | Дополнительного запроса нет. | Фиксируется `place_id` выбранного элемента; расчёт не запускается. |
| Изменить текст уже выбранного места | Новый GET с актуальным непустым текстом после debounce. | Прежний `place_id` немедленно сбрасывается до повторного выбора. |
| Очистить поле или оставить только пробелы | GET не отправляется; старые подсказки скрываются. | Выбранного `place_id` нет, build недоступен до нового выбора. |
| Получить `200 items:[]` | Ответ поиска не содержит вариантов. | «Место не найдено»; фиктивный ID не создаётся. |

Задержка debounce — деталь UI, не ограничение каталога. Приёмка проверяет отправку по утверждённому порогу начала поиска, актуальность префикса и отсутствие запроса для пустого поля; сам порог остаётся открытым после вопроса владельца в PR #43 (см. [Analysis](analysis.md#уточнение-по-поиску-места-из-review)). HTTP допускает односимвольный буквенно-цифровой query; без явного `limit` возвращается не более 10 предложений. Нормализация и префиксное ранжирование остаются серверными (`exact-orb_place_catalog.md` §§4.2–4.4, `http_api.md` §6.3).

**Правила времени.** Время известно только при явном корректном `HH:MM` (включая `00:00` и `12:00`). Если пользователь явно отмечает «Точное время неизвестно», отправляется JSON `birth_time:null`, а введённое время не подменяется техническим полуднем. При снятой отметке и пустом/некорректном времени интерфейс требует ясного выбора или исправления, не угадывает неизвестность молча. Переключение отметки не уничтожает дату и место. Секунды и UTC offset не вводятся.

**Граница данных места.** Координаты, часовой пояс и смещение не вводятся клиентом и определяются сервером из `place_id` и даты. Отказ поиска отдельно проверяется в [AS-UI-18](scenarios.md#as-ui-18-пустой-поиск-и-отказ-каталога).

### REQ-UI-03. Явное построение и валидация

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-03`.

**Сценарии:** успешный натал и космограмма — [AS-UI-03](scenarios.md#as-ui-03-известное-время-и-успешный-натал), [AS-UI-04](scenarios.md#as-ui-04-явно-неизвестное-время-и-космограмма); отсутствие отметки — [AS-UI-20](scenarios.md#as-ui-20-отметка-ознакомления-с-условиями-не-поставлена); ошибки ввода и transport validation — [AS-UI-06](scenarios.md#as-ui-06-ошибки-даты-локального-времени-и-места), [AS-UI-17](scenarios.md#as-ui-17-приоритет-transport-validation-и-issuedto); recovery — [AS-UI-12](scenarios.md#as-ui-12-утерянная-сессия-и-сохранение-черновика), [AS-UI-13](scenarios.md#as-ui-13-rate-и-capacity-до-запуска-build), [AS-UI-14](scenarios.md#as-ui-14-неопределённый-исход-commit-и-timeout).

Пока действует ADR-0034, перед отправкой UI build пользователь должен открыть доступную страницу «Условия использования сервиса» с минимумом ADR §2 и активно отметить ознакомление. Отметка снята по умолчанию, не передаётся в доменную команду и не сохраняется как юридическое согласие. Если страница/отметка не поставлены в M1-7, acceptance реального build-flow остаётся заблокированной до решения `DP-UI-04`; внутренний прототип без отправки не выполняет это требование.

| Действие пользователя | Запрос и ответ | Состояние экрана |
|---|---|---|
| Попытаться построить без выполненного gate ADR-0034 либо с очевидно некорректной датой, временем или без выбранного `place_id` | `POST /charts/natal` не отправляется. | Пользователь видит, что нужно открыть условия/отметить ознакомление либо исправить конкретное поле. Черновик сохраняется. |
| При разрешённом gate явно нажать построение с валидными полями | Клиент один раз отправляет `POST /charts/natal` с ровно `{birth_date,birth_time,place_id}`. Пока ответ не получен, повторное действие не создаёт второй POST. | Показано ожидание результата; дата, время/отметка и выбранное место остаются в форме. |
| Получить успешный committed result | `200 chart_ready` содержит committed `ChartDTO`. | Показаны факты полученной карты и соответствующие сохранённые данные рождения. |
| Получить `already_applied` | В **теле ответа на `POST /charts/natal`** приходит `200 {"status":"already_applied","state_version":N}` без `chart`; затем клиент отправляет `GET /charts/current`. | Показывается фактическое состояние из GET, а не предположительный результат повторного POST. |

Форма не добавляет в POST имя, текст места, координаты, checkbox, клиентский `state_version` или иные поля. Ошибочные ответы и запросы сверки описаны ниже и в REQ-UI-09.
- Локальная проверка препятствует очевидно неверному формату и отсутствию выбранного места, но не заменяет сервер. Для `422 INVALID_REQUEST` и `422 INPUT_REQUIRED` UI использует действующий `ErrorDTO`: `issues[].field` (`birth.date`, `birth.time`, `birth.place`, `request.body`, `request.<name>`), `code` (`MISSING`, `AMBIGUOUS`, `INVALID`, `UNSUPPORTED`), необязательные `candidates` и `constraints`; `user_message` остаётся общим сообщением. Несуществующая/двусмысленная локальная минута выбранного места показывается как ошибка `birth.time`, а не исправляется часовым поясом браузера. Ошибка у соответствующего поля имеет приоритет перед общей; неизвестный field остаётся в общей области ошибки. Schema validation предшествует проверке cookie: невалидный body без cookie даёт 422, а не 409.
- При любом отказе введённые дату, время/отметку и выбранный `place_id` сохраняют в клиентской форме до явного изменения. Ошибка сессии не превращает прежний текст места в подтверждённый ID. Кнопка и вспомогательные тексты M1-7 не обещают чат; окончательный состав имени/CTA ожидает `DP-UI-05`.

### REQ-UI-04. Представление общих фактов

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-04`. **Сценарии:** [AS-UI-07–09, 15](scenarios.md).
- Шесть групп имеют самостоятельные заголовки и доступные таблицы/списки. Видимый порядок внутри группы детерминирован; локализованные подписи привязаны к стабильным кодам DTO. Позиции показывают опубликованные `sign`, целые `degree` и `minute` как `ДД°ММ′` (минута всегда двумя цифрами, без секунд и длинной дроби). Край знака берётся из опубликованного `sign`, а не из вычисления браузера. `retrograde=true` обозначается видимым текстом «ретроградная» или `R` с доступной подписью; `false` не получает `R`. Орбис из API допускает только единообразное *форматирование* до градусов/минут, без пересчёта типа/категории аспекта или конфигурации.
- Для доступного рассчитанного списка `[]` означает «рассчитано, результатов нет»; `null` означает «не применимо/не рассчитано» и не изображается пустым рассчитанным результатом. Нельзя заменять `null` на `[]` или скрывать секцию так, что состояние станет неразличимо. Для `chart_unavailable` нет `ChartDTO`; показывается отказ восстановления, а не шесть пустых таблиц.
- Наличие сырых `longitude`/`cusp_longitude` в нынешнем DTO не даёт права получать из них табличные градусы/минуты или special flags. В `DP-UI-02` Analyst рекомендует сохранить эти поля для будущего M1-8 до отдельной ревизии; `degree_in_sign` в публичном DTO уже отсутствует.

### REQ-UI-05. Планеты, точки и дома

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-05`. **Сценарии:** [AS-UI-07–09, 15](scenarios.md).
- Первая группа читает `ChartDTO.points[]` в утверждённом порядке §7.2 HTTP: Sun…Pluto, Chiron, true/south node, mean apog, Selena, Pars Fortune, пропуская только отсутствующие опубликованные точки. Видимые столбцы: имя по `id`, знак, `ДД°ММ′`, номер дома при наличии, ретроградность. Лунные узлы используют публичные ID ADR-0029/0030; `south_node` виден как производная позиция, но не как самостоятельный участник аспектов/конфигураций. Натал может показывать дом; у космограммы `points[].house=null`, колонка/ячейка получает «Не определяется без времени», а не ноль или дом технического полудня. Положения космограммы являются опубликованными позициями технического якоря, не точным моментом рождения.
- Вторая группа читает `houses[]` по возрастанию `number=1…12`: номер, знак и `ДД°ММ′` куспида. Для натала обязательные `house_system`, `angles` и `houses` позволяют отдельно подписать ASC/MC/Vertex/DSC/IC, но углы не являются домами или дополнительной седьмой группой. Для космограммы `house_system`, `angles`, `houses` равны `null`; выводится «Для домов нужно время рождения», без фиктивных 12 строк.

### REQ-UI-06. Аспекты и конфигурации

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-06`. **Сценарии:** [AS-UI-07–09, 15, 16](scenarios.md).
- Третья группа читает `aspects[]`: названия концов по `from/to`, вид по `type`, категорию `exact/working/background` и опубликованный `orb`. Все аспекты доступны; краткий вид может начать с `exact`, если рядом доступен полный список и количество. Пустой полный список показывает «Аспекты не найдены». Для космограммы показываются только устойчивые опубликованные аспекты ADR-0032; `orb` означает максимальное значение по допустимым минутам, а не точный орбис полудня. UI не синтезирует `time_dependent` и не восстанавливает исключённые пары.
- Четвёртая группа после `DP-UI-02` читает типизированные `configurations[]`: тип (тау-квадрат, йод, бисекстиль, большой крест, большой тригон, трапеция), категорию, максимум орбиса, подписанные роли участников и подтверждающие публичные рёбра; вложенный T-square большого креста показывается как вложенный факт, без двойного подсчёта верхнего уровня. Ссылки обязаны указывать на опубликованные точки и аспекты; UI не выводит фигуру из геометрии или `longitude`. `[]` показывает «Конфигурации не найдены». Космограмма может иметь устойчивые конфигурации из опубликованных аспектов и не теряет их только из-за неизвестного времени.

### REQ-UI-07. Сила и особые градусы

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-07`. **Сценарии:** [AS-UI-07–09, 15](scenarios.md).
- Пятая группа после `DP-UI-02` показывает только уже рассчитанную силу натала по планетам в фиксированном порядке Sun…Pluto: имя, достоинство и применённая система, тип дома, `essential_score`, `accidental_score`, `total` и категорию `strong/moderate/weak`. Подписи категорий нейтральны: «сильная», «умеренная», «слабая», без оценочного вывода о человеке. При доступной силе и пустом наборе строк показывается «Нет данных о силе планет»; при `strength:null` — «Сила не рассчитывается без времени». Клиент не складывает scores, не выбирает систему достоинств и не вычисляет категорию. Баланс стихий/модальностей, диспозиторы, лунная фаза, рецепции и управители домов из других разделов CLI не входят автоматически в шесть таблиц M1-7; их отдельное включение требует явного scope решения.
- Шестая группа после `DP-UI-02` показывает только флаги `is_zero_degree`, `is_anaretic`, `is_critical`, которые истинны хотя бы для одного опубликованного тела, угла ASC/MC/Vertex или куспида. Строка: имя/тип объекта, знак, опубликованные целые градус и минута, понятные метки «0° знака», «анаретический», «критический» и при наличии `matched_critical_degree`. Можно показать несколько меток в одной строке. Флаги берутся из расчёта, а позиция — из согласованной публичной проекции, не из float `degree_in_sign` в браузере. `[]` для натала означает «Особые градусы не найдены»; `null` для космограммы означает «Особые градусы не рассчитываются без времени», поскольку текущий источник — `NatalStrength.degree_flags`, а strength у космограммы отсутствует.

### REQ-UI-08. Восстановление, stale и unavailable

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-08`. **Сценарии:** [AS-UI-10](scenarios.md#as-ui-10-восстановление-без-расчёта), [AS-UI-11](scenarios.md#as-ui-11-устаревшая-и-недоступная-сохранённая-карта), [AS-UI-12](scenarios.md#as-ui-12-утерянная-сессия-и-сохранение-черновика).

**Пользовательское действие:** перезагрузить страницу с живой cookie или вернуться к ней. Клиент выполняет шаги bootstrap → current из REQ-UI-01. Чтение не запускает расчёт и не меняет сохранённую карту.

| Ответ `GET /charts/current` | Состояние экрана | Следующее действие |
|---|---|---|
| `chart_ready`, `chart_stale:false` | Те же `chart_identity`, сохранённый `birth` и факты шести групп, что были в committed POST. | Не требуется. |
| `chart_ready`, `chart_stale:true` | Старая карта и её факты сохранены, версия явно помечена как устаревшая. Текущая версия расчёта не подменяет числа автоматически. | Пользователь может явно нажать «Пересчитать». |
| `chart_unavailable`, `chart:null` | Сохранённый `birth` виден; числовые факты и шесть таблиц не показаны. | Пользователь может явно нажать «Построить заново». |

Если восстановленный `birth.time_unknown=true`, в нём `birth_time:null`, `utc_offset_seconds:null`: UI может назвать `tz_id`, но не показывает offset технического полудня или выдуманный диапазон Луны.

### REQ-UI-09. Recovery и две вкладки

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-09`. **Сценарии:** [AS-UI-12](scenarios.md#as-ui-12-утерянная-сессия-и-сохранение-черновика), [AS-UI-13](scenarios.md#as-ui-13-rate-и-capacity-до-запуска-build), [AS-UI-14](scenarios.md#as-ui-14-неопределённый-исход-commit-и-timeout), [AS-UI-16](scenarios.md#as-ui-16-две-вкладки-и-superseded), [AS-UI-18](scenarios.md#as-ui-18-пустой-поиск-и-отказ-каталога).

При отказе клиент сохраняет черновик даты, времени/отметки и подтверждённого выбора места в текущей вкладке. Ответ определяет следующий запрос и показанное состояние:

| Полученный ответ | Следующий запрос клиента | Состояние экрана и действие пользователя |
|---|---|---|
| `409 SESSION_REQUIRED/EXPIRED/NOT_FOUND` | `POST /session/bootstrap {}` → `GET /charts/current`. | Показать действительное состояние новой/восстановленной сессии и сохранить черновик; новый build только по явному действию. |
| `409 RESULT_SUPERSEDED` или `200 already_applied` | `GET /charts/current`. | Показать фактическую карту из GET; не выдавать ответ POST за новую карту. |
| `429` или pre-admission `503 BUILD_CAPACITY_EXHAUSTED` | Автоматического повторного POST нет. | Показать `Retry-After`; после него предложить пользователю явное повторное действие. |
| `503 STATE_READ_FAILED` | Повторить безопасное чтение после восстановления доступности; cookie сохраняется. | Сохранить форму и сообщить о временной невозможности чтения. |
| `503 STATE_COMMIT_FAILED` | После `Retry-After` выполнить только `GET /charts/current`. | Исход build пока неопределён; показать результат сверки, не повторять POST автоматически. |
| `504 BUILD_TIMEOUT` | После `Retry-After` и подтверждённого restart/readiness выполнить bootstrap → current. | До сверки не объявлять build ни успешным, ни неуспешным и не отправлять POST автоматически. |

Если после подтверждённого restart GET возвращает `empty` или старую карту, новый POST возможен только по явному действию. Когда вкладка B явно построила карту, возврат вкладки A выполняет bootstrap → current и показывает сохранённую B карту; локальный `state_version` A не является серверным expected version.

### REQ-API-UI-01. Одинаковые факты в POST и GET

**Тип изменения документа:** MODIFY §7.2, §6.2, §6.4, AS-HTTP-11/19/28. **Цель:** `current/http-api/chart-facts.md#REQ-API-UI-01`. **Сценарии:** [AS-UI-07–11, 16](scenarios.md).
- `ApplicationCommitted` в `POST /charts/natal` и валидный `chart_ready` в `GET /charts/current` используют одну публичную схему и одну семантику `ChartDTO`. Для одного сохранённого `chart_identity` содержимое всех шести групп совпадает до/после reload, даже если изменился `state_version`. `already_applied` по-прежнему не содержит `chart`. Расширение делается явным whitelist-проектором; сырой `ChartArtifact.model_dump()` недопустим. Неопубликованный/dangling объект или нарушение связности даёт безопасный `500 INTERNAL_FAILURE`, без частичного `ChartDTO`.

### REQ-API-UI-03. Позиция special degree и сохранение координат

**Тип изменения документа:** ADD к §7.2; нынешние `longitude` и `cusp_longitude` сохраняются (`DP-UI-02`). **Цель:** `current/http-api/chart-facts.md#REQ-API-UI-03`. **Сценарии:** [AS-UI-07, 09, 15](scenarios.md).
- `PublicSpecialDegree.degree/minute/sign` публикуются с тем же округлением и знаком, что соответствующий публичный point/angle/house, после проверки `point_type` и ID. Внутренний float `degree_in_sign` и сырой `longitude` флага не публикуются. Если источник и позиция противоречат друг другу, вместо выдуманного числового результата — безопасный отказ проекции.
