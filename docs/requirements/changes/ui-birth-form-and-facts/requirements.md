## Границы и нормативное наследование

Целевой M1-7 по новому [указанию владельца](https://github.com/ksenia-baranova/exact-orb-demo/pull/43#discussion_r4179357890) включает явное построение и чтение **трёх** групп текущего `ChartDTO`: планеты/точки, дома, аспекты. Конфигурации, сила, особые градусы и оценка стихий остаются расчётными/будущими темами, но не публикуются и не показываются в M1-7; место будущих секций учитывается в композиции по REQ-UI-07. Это изменение scope ждёт обновления `DP-UI-01/02` Manager. UI берёт факты из успешного POST или восстановленного GET и не рассчитывает знак, дом или категорию из `longitude`. Действующие HTTP ошибки, cookie, admission, session lifecycle и публичный whitelist сохраняются. Колесо — M1-8; перенос полного прототипа — M1-8.1; чат — M2. Пока ADR-0034 не пересмотрен, его gate остаётся обязательным для отправки UI build.

`docs/ui_ux/**` задаёт визуальное направление и идеи; демонстрационные числа, тексты кнопок действия, старые `ChartDTO`/`issues` и выдуманный диапазон Луны не являются эталоном. `DP-UI-03` сохраняет публичный ключ `admin1_name` без alias: на экране его значение подписывается «регион».

### REQ-UI-01. Первое открытие и источник состояния

**Тип изменения документа:** ADD; новой нормативной UI области в `current/` нет. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-01`.

**Пользовательское действие:** открыть страницу по HTTPS или вернуться к ней после перезагрузки. Последовательность первого входа проверяет [AS-UI-01](scenarios.md#as-ui-01-первый-вход-и-пустая-сессия), восстановление — [AS-UI-10](scenarios.md#as-ui-10-восстановление-без-расчёта), состояния сохранённой карты — [AS-UI-11](scenarios.md#as-ui-11-устаревшая-и-недоступная-сохранённая-карта).

| Шаг | Запрос и ответ | Состояние экрана |
|---|---|---|
| 1. Получить или подтвердить сессию | Клиент с cookie jar отправляет `POST /session/bootstrap` с `{}`. При успехе получает `200 ready` и `state_version`; на первом входе также получает session cookie. | Ожидает чтения карты. `ready` и `state_version` сами по себе не означают, что карта есть. |
| 2. Прочитать текущее состояние | После успешного bootstrap клиент отправляет `GET /charts/current`. | Дальнейшее представление определяется только ответом GET; страница не отправляет `POST /charts/natal`. |
| 3а. Карты нет | `200 empty`, `birth:null`, `chart:null`. | Пустая форма без рассчитанных фактов и демонстрационных чисел. |
| 3б. Карта доступна | `200 chart_ready` с `birth`, `chart` (включая `chart.chart_identity`) и признаком `chart_stale`. | Сохранённые данные рождения и факты именно этой карты; stale показан по REQ-UI-08. |
| 3в. Сохранённую карту нельзя открыть | `200 chart_unavailable` с сохранённым `birth`, `chart:null`: `session_view` безопасно отверг сохранённый payload при декодировании или проверке его версии, ключа, spec либо расчётного входа. | Данные рождения доступны для повторного построения; числовые факты карты отсутствуют. Это состояние возможно после повреждения или несовместимости сохранённого артефакта, а не при обычном пустом входе или изменении текущей версии расчёта. |

После reload и возврата вкладки актуальный серверный GET остаётся источником истины: UI показывает факты только при `chart_ready` и берёт их из `chart` этого ответа. Число `state_version` из bootstrap не используется как признак наличия карты или как её `chart.chart_identity`; при `empty` и `chart_unavailable` ранее показанные факты убираются. Структурная рассинхронизация сессии и строки карты даёт `503 STATE_READ_FAILED`, а не `chart_unavailable` (`http_api.md` §6.2). Отказы запросов и сохранение черновика описаны в REQ-UI-09 и [AS-UI-12](scenarios.md#as-ui-12-утерянная-сессия-и-сохранение-черновика).

### REQ-UI-02. Дата, время и выбор места

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-02`.

**Сценарии:** выбор места — [AS-UI-02](scenarios.md#as-ui-02-префиксный-поиск-и-выбор-двух-одноимённых-мест), [AS-UI-18](scenarios.md#as-ui-18-пустой-поиск-и-отказ-каталога); время и валидация — [AS-UI-04](scenarios.md#as-ui-04-явно-неизвестное-время-и-космограмма), [AS-UI-05](scenarios.md#as-ui-05-пустое-или-противоречивое-время), [AS-UI-06](scenarios.md#as-ui-06-ошибки-даты-локального-времени-и-места).

Поля следуют в порядке дата → место → время. Дата обязательна и передаётся как календарная `YYYY-MM-DD`. Выбор места имеет отдельный поток:

| Действие пользователя | Запрос и ответ | Состояние формы |
|---|---|---|
| Ввести первые один или два символа места, например `К` → `Ки` | UI не отправляет GET и не показывает старые подсказки. API допускает такие запросы, но согласованный порог UI — три символа. | Текст ещё не является выбранным `place_id`; выбранный ранее ID сброшен при его редактировании. |
| Ввести третий символ, например `Кир` | После debounce клиент отправляет `GET /places?query=Кир`; полного названия не ждёт, session cookie не требуется. `200 items[]` содержит `place_id`, `display_name`, `admin1_name`, `country_code`. | Показаны подходящие префиксу варианты с названием, «регионом» и страной. Введённый текст ещё не является выбранным `place_id`. |
| Добавить, удалить или заменить символы при длине префикса от трёх, например `Кир` → `Киро` | После изменения и debounce отправляется новый GET с актуальным префиксом. Каталог ищет по нормализованному префиксу; из-за лимита выдачи состав и число показанных вариантов могут меняться, уменьшение числа строк на каждом шаге не гарантируется. | Ответ старого запроса не заменяет варианты нового текста, даже если пришёл позже. Пользователь видит подсказки только для текущего ввода. |
| Выбрать подсказку мышью либо стрелками и Enter | Дополнительного запроса нет. | Фиксируется `place_id` выбранного элемента; расчёт не запускается. |
| Изменить текст уже выбранного места | Прежний `place_id` сбрасывается немедленно; новый GET выполняется только при префиксе от трёх символов после debounce. | Выбор нужно подтвердить заново. |
| Очистить поле или оставить только пробелы | GET не отправляется; старые подсказки скрываются. | Выбранного `place_id` нет, build недоступен до нового выбора. |
| Получить `200 items:[]` | Ответ поиска не содержит вариантов. | «Место не найдено»; фиктивный ID не создаётся. |

Порог в три введённых символа [выбран владельцем](https://github.com/ksenia-baranova/exact-orb-demo/pull/43#discussion_r4179366994); задержка debounce — деталь UI. Приёмка проверяет отсутствие GET до третьего символа, запрос по третьему и последующим актуальным префиксам, подавление позднего ответа и очистку подсказок при возврате к длине меньше трёх. HTTP по-прежнему допускает односимвольный буквенно-цифровой query; без явного `limit` возвращается не более 10 предложений. Нормализация и префиксное ранжирование остаются серверными (`exact-orb_place_catalog.md` §§4.2–4.4, `http_api.md` §6.3).

**Правила времени.** Время известно только при явном корректном `HH:MM` (включая `00:00` и `12:00`). Если пользователь явно отмечает «Точное время неизвестно», отправляется JSON `birth_time:null`, а введённое время не подменяется техническим полуднем. При снятой отметке и пустом/некорректном времени интерфейс требует ясного выбора или исправления, не угадывает неизвестность молча. Переключение отметки не уничтожает дату и место. Секунды и UTC offset не вводятся.

**Граница данных места.** Координаты, часовой пояс и смещение не вводятся клиентом и определяются сервером из `place_id` и даты. Отказ поиска отдельно проверяется в [AS-UI-18](scenarios.md#as-ui-18-пустой-поиск-и-отказ-каталога).

### REQ-UI-03. Явное построение и валидация

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-03`.

**Сценарии:** успешный натал и космограмма — [AS-UI-03](scenarios.md#as-ui-03-известное-время-и-успешный-натал), [AS-UI-04](scenarios.md#as-ui-04-явно-неизвестное-время-и-космограмма); отсутствие отметки и условный закрытый стенд — [AS-UI-20](scenarios.md#as-ui-20-отметка-ознакомления-с-условиями-не-поставлена), [AS-UI-21](scenarios.md#as-ui-21-условный-закрытый-этап-без-страницы-условий); ошибки ввода и transport validation — [AS-UI-06](scenarios.md#as-ui-06-ошибки-даты-локального-времени-и-места), [AS-UI-17](scenarios.md#as-ui-17-приоритет-transport-validation-и-issuedto); recovery — [AS-UI-12](scenarios.md#as-ui-12-утерянная-сессия-и-сохранение-черновика), [AS-UI-13](scenarios.md#as-ui-13-rate-и-capacity-до-запуска-build), [AS-UI-14](scenarios.md#as-ui-14-неопределённый-исход-commit-и-timeout).

**Действующий gate:** ADR-0034 требует доступную страницу «Условия использования сервиса» с минимумом §2 и снятую по умолчанию отметку ознакомления до отправки UI build. Отметка не входит в доменную команду, не хранится и не является юридическим согласием на обработку персональных данных.

**Целевой закрытый этап по решению владельца:** [в ответе к review](https://github.com/ksenia-baranova/exact-orb-demo/pull/43#discussion_r4179344108) владелец хочет дать пройти полный сценарий на закрытом стенде до создания страницы, сохранив снятую по умолчанию отметку и ручное действие перед POST; страницу поставить до передачи ссылки другим людям. Это **предложение к изменению ADR-0034**, а не действующее исключение: до ревизии ADR и записи `DP-UI-04` build без страницы не может получить acceptance. Условный путь проверяет AS-UI-21; распространение ссылки до страницы не входит в разрешённый этап.

| Действие пользователя | Запрос и ответ | Состояние экрана |
|---|---|---|
| Попытаться построить без выполненного действующего gate ADR-0034 либо с очевидно некорректной датой, временем или без выбранного `place_id` | `POST /charts/natal` не отправляется. | Пользователь видит, что нужно выполнить действующий gate либо исправить конкретное поле. Черновик сохраняется. |
| При разрешённом gate явно нажать построение с валидными полями | Клиент один раз отправляет `POST /charts/natal` с ровно `{birth_date,birth_time,place_id}`. Пока ответ не получен, повторное действие не создаёт второй POST. После утверждённой ревизии ADR закрытый этап может использовать ручную отметку без страницы только в её согласованных пределах. | Показано ожидание результата; дата, время/отметка и выбранное место остаются в форме. |
| Получить успешный committed result | `200 chart_ready` содержит committed `ChartDTO`. | Показаны факты полученной карты и соответствующие сохранённые данные рождения. |
| Получить `already_applied` | В **теле ответа на `POST /charts/natal`** приходит `200 {"status":"already_applied","state_version":N}` без `chart`; затем клиент отправляет `GET /charts/current`. | Показывается фактическое состояние из GET, а не предположительный результат повторного POST. |

Форма не добавляет в POST имя, текст места, координаты, checkbox, клиентский `state_version` или иные поля. Ошибочные ответы и запросы сверки описаны ниже и в REQ-UI-09.
- Локальная проверка препятствует очевидно неверному формату и отсутствию выбранного места, но не заменяет сервер. Для `422 INVALID_REQUEST` и `422 INPUT_REQUIRED` UI использует действующий `ErrorDTO`: `issues[].field` (`birth.date`, `birth.time`, `birth.place`, `request.body`, `request.<name>`), `code` (`MISSING`, `AMBIGUOUS`, `INVALID`, `UNSUPPORTED`), необязательные `candidates` и `constraints`; `user_message` остаётся общим сообщением. Несуществующая/двусмысленная локальная минута выбранного места показывается как ошибка `birth.time`, а не исправляется часовым поясом браузера. Ошибка у соответствующего поля имеет приоритет перед общей; неизвестный field остаётся в общей области ошибки. Schema validation предшествует проверке cookie: невалидный body без cookie даёт 422, а не 409.
- При любом отказе введённые дату, время/отметку и выбранный `place_id` сохраняют в клиентской форме до явного изменения. Ошибка сессии не превращает прежний текст места в подтверждённый ID. Кнопка и вспомогательные тексты M1-7 не обещают чат; окончательный состав имени и кнопки действия ожидает `DP-UI-05`.

### REQ-UI-04. Представление общих фактов

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-04`. **Сценарии:** [AS-UI-07–09, 15](scenarios.md).
- Три группы имеют самостоятельные заголовки и доступные таблицы/списки. Видимый порядок внутри группы детерминирован; локализованные подписи привязаны к стабильным кодам DTO. Позиции показывают опубликованные `sign`, целые `degree` и `minute` как `ДД°ММ′` (минута всегда двумя цифрами, без секунд и длинной дроби). Край знака берётся из опубликованного `sign`, а не из вычисления браузера. `retrograde=true` обозначается видимым текстом «ретроградная» или `R` с доступной подписью; `false` не получает `R`. Орбис из API допускает только единообразное *форматирование* до градусов/минут, без пересчёта типа/категории аспекта.
- Для доступного рассчитанного списка `[]` означает «рассчитано, результатов нет»; `null` означает «не применимо» и не изображается пустым рассчитанным результатом. У космограммы `houses:null`, а `aspects:[]` означает отсутствие устойчивых аспектов. Для `chart_unavailable` нет `ChartDTO`; показывается отказ восстановления, а не три пустые таблицы.
- Наличие сырых `longitude`/`cusp_longitude` в нынешнем DTO не даёт права получать из них табличные градусы/минуты. `degree_in_sign` в публичном DTO уже отсутствует. Числовые демонстрационные значения не подставляются вместо ответа API.

### REQ-UI-05. Планеты, точки и дома

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-05`. **Сценарии:** [AS-UI-07–09, 15](scenarios.md).
- Первая группа читает `ChartDTO.points[]` в утверждённом порядке §7.2 HTTP: Sun…Pluto, Chiron, true/south node, mean apog, Selena, Pars Fortune, пропуская только отсутствующие опубликованные точки. Видимые столбцы: имя по `id`, знак, `ДД°ММ′`, номер дома при наличии, ретроградность. Лунные узлы используют публичные ID ADR-0029/0030; `south_node` виден как производная позиция, но не как самостоятельный участник аспектов. Натал может показывать дом; у космограммы `points[].house=null`, колонка/ячейка получает «Не определяется без времени», а не ноль или дом технического полудня. Положения космограммы являются опубликованными позициями технического якоря, не точным моментом рождения.
- Вторая группа читает `houses[]` по возрастанию `number=1…12`: номер, знак и `ДД°ММ′` куспида. Для натала обязательные `house_system`, `angles` и `houses` позволяют отдельно подписать ASC/MC/Vertex/DSC/IC, но углы не являются домами или дополнительной четвёртой группой. Для космограммы `house_system`, `angles`, `houses` равны `null`; выводится «Для домов нужно время рождения», без фиктивных 12 строк.

### REQ-UI-06. Аспекты

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-06`. **Сценарии:** [AS-UI-07–09, 15, 16](scenarios.md).
- Третья группа читает `aspects[]`: названия концов по `from/to`, вид по `type`, категорию `exact/working/background` и опубликованный `orb`. Все аспекты доступны; краткий вид может начать с `exact`, если рядом доступен полный список и количество. Пустой полный список показывает «Аспекты не найдены». Для космограммы показываются только устойчивые опубликованные аспекты ADR-0032; `orb` означает максимальное значение по допустимым минутам, а не точный орбис полудня. UI не синтезирует `time_dependent` и не восстанавливает исключённые пары.

### REQ-UI-08. Восстановление, stale и unavailable

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-08`. **Сценарии:** [AS-UI-10](scenarios.md#as-ui-10-восстановление-без-расчёта), [AS-UI-11](scenarios.md#as-ui-11-устаревшая-и-недоступная-сохранённая-карта), [AS-UI-12](scenarios.md#as-ui-12-утерянная-сессия-и-сохранение-черновика).

**Пользовательское действие:** перезагрузить страницу с живой cookie или вернуться к ней. Клиент выполняет шаги bootstrap → current из REQ-UI-01. Чтение не запускает расчёт и не меняет сохранённую карту.

| Ответ `GET /charts/current` | Состояние экрана | Следующее действие |
|---|---|---|
| `chart_ready`, `chart_stale:false` | Те же `chart_identity`, сохранённый `birth` и факты трёх групп, что были в committed POST. | Не требуется. |
| `chart_ready`, `chart_stale:true` | Старая карта и её факты сохранены, версия явно помечена как устаревшая. Текущая версия расчёта не подменяет числа автоматически. | Пользователь может явно нажать «Пересчитать». |
| `chart_unavailable`, `chart:null` | Сохранённый `birth` виден; числовые факты и три таблицы не показаны. | Пользователь может явно нажать «Построить заново». |

Если восстановленный `birth.time_unknown=true`, в нём `birth_time:null`, `utc_offset_seconds:null`: UI может назвать `tz_id`, но не показывает offset технического полудня или выдуманный диапазон Луны.

### REQ-UI-09. Recovery и две вкладки

**Тип изменения документа:** ADD. **Цель:** `current/ui/birth-form-and-facts.md#REQ-UI-09`. **Сценарии:** [AS-UI-12](scenarios.md#as-ui-12-утерянная-сессия-и-сохранение-черновика), [AS-UI-13](scenarios.md#as-ui-13-rate-и-capacity-до-запуска-build), [AS-UI-14](scenarios.md#as-ui-14-неопределённый-исход-commit-и-timeout), [AS-UI-16](scenarios.md#as-ui-16-две-вкладки-и-superseded), [AS-UI-18](scenarios.md#as-ui-18-пустой-поиск-и-отказ-каталога).

При отказе клиент сохраняет черновик даты, времени/отметки и подтверждённого выбора места в текущей вкладке. Ответ определяет следующий запрос и показанное состояние:

| Полученный ответ | Следующий запрос клиента | Состояние экрана и действие пользователя |
|---|---|---|
| `409 SESSION_REQUIRED/EXPIRED/NOT_FOUND` | `POST /session/bootstrap {}` → `GET /charts/current`. | Показать действительное состояние новой/восстановленной сессии и сохранить черновик; новый build только по явному действию. |
| `409 RESULT_SUPERSEDED` или `200 already_applied` | `GET /charts/current`. | Показать фактическую карту из GET; не выдавать ответ POST за новую карту. |
| `429` или pre-admission `503 BUILD_CAPACITY_EXHAUSTED` | Автоматического повторного POST нет. | Показать `Retry-After`; после него предложить пользователю явное повторное действие. |
| `503 STATE_READ_FAILED` | Повторить безопасное чтение после восстановления доступности; cookie сохраняется. | Сохранить форму и сообщить о временной невозможности чтения. |
| `503 STATE_COMMIT_FAILED` | После `Retry-After` выполнить только `GET /charts/current`. | Исход build пока неопределён; показать результат сверки, не повторять POST автоматически. |
| `504 BUILD_TIMEOUT` | После `Retry-After` и подтверждённого restart/readiness выполнить bootstrap → current. | До сверки не объявлять build ни успешным, ни неуспешным и не отправлять POST автоматически. |

Если после подтверждённого restart GET возвращает `empty` или старую карту, новый POST возможен только по явному действию. Когда вкладка B явно построила карту, возврат вкладки A выполняет bootstrap → current и показывает сохранённую B карту; локальный `state_version` A не является серверным expected version.

## Нормативный HTTP-контракт без дельты

M1-7 использует существующий `ChartDTO` из `docs/requirements/http_api.md` §7.2 без новой операции и без дополнительных полей. Для committed `POST /charts/natal` и восстановленного `GET /charts/current` у одной `chart_identity` показываются одни и те же опубликованные факты. `200 already_applied` остаётся ответом POST без `chart` и требует последующего GET.

| Группа M1-7 | Источник `ChartDTO` | Натал | Космограмма и пустое состояние |
|---|---|---|---|
| Планеты и точки | `points[]` | Позиции, ретроградность, дом при наличии. | `points[].house=null`; это отсутствие дома, а не дом технического полудня. |
| Дома | `house_system`, `angles`, `houses[]` | Двенадцать куспидов; углы подписаны отдельно. | Все три блока равны `null`; «Для домов нужно время рождения». |
| Аспекты | `aspects[]` | Опубликованные пары, тип, категория и орбис. | Только устойчивые опубликованные пары; `[]` означает «Аспекты не найдены». |

Прежние предложения `REQ-API-UI-01…03` о публикации `configurations`, `strength`, `special_degrees` **сняты с объёма M1-7** после [комментария владельца](https://github.com/ksenia-baranova/exact-orb-demo/pull/43#discussion_r4179357890) и доступны в истории commit `6187fd5` для отдельного будущего решения. Расчётные блоки существуют во внутреннем `ChartArtifact`, но текущий публичный проектор их не выдаёт; UI не создаёт их из `longitude` и не показывает как пустые рассчитанные группы. Manager должен синхронизировать `DP-UI-01/02` и roadmap до разрешения разработки по сокращённому scope.
