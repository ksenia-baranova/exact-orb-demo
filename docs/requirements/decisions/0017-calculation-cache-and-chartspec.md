# ADR-0017. Calculation Cache воспроизводим; сессия хранит `ChartSpec`

Дата: 2026-08-25.
Ревизия: 2026-09-06 — `ActiveChart.profile_version` приведён к актуальному
контракту `ChartRef.state_version` из ADR-0014; смысл хранения `ChartSpec` не
изменён.
Ревизия: 2026-09-07 — зафиксирована полнота спецификации (Т-ГРН-7): параметры,
влияющие на числа, но не выбираемые пользователем, покрываются
`CalculationVersion`, а не полями `ChartSpec`. Состав отпечатка расширен
до девяти компонент. Форма `ChartSpec` не меняется; **отменено** следствие
прошлой редакции, по которому полнота ключа оставалась открытым вопросом.
Реализация этой же ревизии уточнена без изменения решения: `ENGINE_VERSION`
является ручной константой; отпечаток не вычисляется при импорте; отсутствие
provider metadata кодируется стабильным маркером, а несколько provider'ов
дают fail-fast; каталог эфемерид обязан существовать, но может быть пустым.
Статус: принято.

## Контекст

Ранее хранилище рассчитанных карт рисовалось как `ChartRepository`
со snapshot'ами. Это делало его самостоятельным persistent-хранилищем
производных персональных данных с собственным lifecycle, что противоречит
ADR-0009 и ADR-0010.

Одновременно обнаружилось, что ссылка на карту по одному лишь ключу
невосстановима: ключ — хэш.

## Решение

**Кэш, а не репозиторий.** Любой объект в `Calculation Cache` можно удалить без
потери пользовательских данных; после eviction результат считается заново.
Операции называются `get` / `put`, а не `save`, чтобы семантика была видна
в коде.

**Источник восстановления — `ChartSpec` в сессии.** Ссылка на карту хранит
спецификацию, ключ выводится из неё чистой функцией:

```
ChartRef { state_version, spec: ChartSpec }
calculation_key = KeyFactory(CalculationInput, ChartSpec, CalculationVersion)
```

Без этого активная транзитная карта после eviction невосстановима: момент
и место транзита не входят в профиль и жили только внутри кэшированного
артефакта.

**`CalculationVersion`** — отпечаток версии расчёта: код движка, версия
числовых профилей, версия `swisseph`, имя/версия установленного биндинга,
fingerprint нативного модуля, fingerprint файлов `ephe/*.se1`, методика
Селены, набор тел по умолчанию и эффективные флаги эфемерид. Без версии
эфемерид обновление данных не инвалидирует кэш: golden tests останутся
зелёными, потому что считают заново, а пользователи будут видеть карты,
посчитанные по прежней базе.

Историческое смещение отдельной версии не требует: `tzdata` влияет
на `utc_datetime` внутри `ResolvedBirthData`, который уже входит в ключ.

`CalculationInput` — проекция из `ResolvedBirthData`, содержащая только
численно значимые поля расчёта (`utc_datetime`, `latitude`, `longitude`).
`canonical_place`, `place_id`, `tz_id` и предупреждения резолва в ключ
не входят.

**Полнота спецификации: заморозка остатка параметров.** `calculate_natal()`
принимает пятнадцать параметров, каждый из которых меняет числа. `ChartSpec`
покрывает часть; вне спеки остаются семь:

```text
selena_method          методика Селены
body_ids               набор тел
ephemeris_flags        флаги эфемерид
aspect_config          наборы орбисов
configuration_config   конфигурация фигур
strength_config        конфигурация силы
ephemeris_path         путь к каталогу эфемерид
```

Правило разделения: **параметр, который выбирает пользователь, принадлежит
спеке; параметр, зафиксированный кодом или конфигурацией процесса,
принадлежит отпечатку.** Все семь относятся ко второй категории, поэтому они
покрываются `CalculationVersion` и в `ChartSpec` не переносятся.

Покрытие по компонентам отпечатка (полный состав — §3.1.5
`exact-orb_chart_artifacts.md`):

- `selena_method`, `body_ids`, `ephemeris_flags` — отдельными компонентами;
- `aspect_config`, `configuration_config`, `strength_config` — компонентой
  «содержимое профилей расчётных конфигов»;
- содержимое файлов эфемерид — компонентой «sha256 всех `*.se1`».

**`ephemeris_path` в отпечаток не входит.** Путь — свойство развёртывания,
а не расчёта: один и тот же набор файлов, смонтированный в `/opt/ephe`
и в `/app/ephe`, обязан давать один ключ. Числа определяются содержимым
файлов, которое уже покрыто хэшами `*.se1`.

**Условие возврата к полному `ChartSpec`:** появление пользовательского выбора
любого из замороженных параметров — орбисы как настройка интерфейса, выбор
набора тел, выбор методики Селены. Тогда параметр переезжает в спеку отдельным
решением, а не правкой этого. То же условие закрывает открытый вопрос §13.1
`exact-orb_build_natal_components.md`.

**Форма значения.** Calculation Cache хранит serialized payload bytes,
а не pydantic-объекты: логическое значение — `ChartArtifact`, физическое —
gzip-6 от JSON UTF-8. Decode/validate принадлежит артефактному слою; кэш
остаётся opaque binary KV.

**Interpretation Cache** живёт по другим правилам. Для preset ключ —
`artifact keys + recipe version + topic + focus`, запись разделяема между
пользователями и детерминирована. Для free-form ключ дополнительно включает
`session_id` и хэш вопроса, а запись живёт не дольше сессии: ответ может
цитировать вопрос. Для free-form это по существу **защита от повторного
списания** при двойном клике, refresh и retry, а не экономия — попадание
случается только при точном повторе.

## Альтернативы

`ChartRepository` со snapshot'ами — отвергнуто: создаёт второй контур
персональных данных и требует lifecycle и deletion. Хранить в сессии только
`calculation_key` — отвергнуто: невосстановимо после eviction.

**Полный `ChartSpec`** — перенести все семь оставшихся параметров полями
в спеку. Отвергнуто на текущем горизонте: цена платится сейчас ради
возможности, которой в MVP не существует. Ни один из семи параметров не
является пользовательским выбором — интерфейс первой версии это кнопки
`topic + focus` (ADR-0019), настроек орбисов, набора тел и методики Селены
в нём нет. Цена:

- меняется форма спеки, значит меняется её сериализация в ключе →
  переписываются `tests/test_calculation_keys.py` и золотые эталоны;
- меняется содержимое `ChartArtifact` и записей кэша;
- `ChartSpec` сериализуется в `SessionState.base_chart.spec`, то есть в
  persisted-payload SQLite-сессии, у которого есть замороженная фикстура
  `tests/session/golden/session_sqlite_payload_v1.json`; по
  `exact-orb_session_requirements.md` §12.3 несовместимое изменение payload
  требует новой payload version и стратегии миграции;
- меняются `NatalTechniqueAdapter` и `NatalToolArgs`;
- работа обязана пройти до `BuildNatalHandler`, иначе handler переписывается
  вслед за формой спеки.

Решение пересматривается по условию возврата, названному выше, и оформляется
новым ADR.

## Последствия

- Кэш можно очищать целиком в любой момент, в том числе при деплое.
- `CalculationKeyFactory` — чистая функция без обращений к состоянию.
- Обновление эфемерид инвалидирует кэш автоматически.
- In-memory и Redis используют один формат значения: `bytes`, а не объектную
  модель в одном случае и JSON в другом.
- Calculation Cache TTL не обязан превосходить session TTL: промах восстановим.
- Free-form записи умирают вместе с сессией, что согласуется с ADR-0009
  и ADR-0010.
- Смена любого замороженного параметра инвалидирует кэш **целиком**, а не
  выборочно те карты, на которые параметр влияет. Для конфигурации,
  меняющейся при выкатке, это приемлемо.
- Два одновременных пользователя не могут иметь разные наборы орбисов, разные
  наборы тел или разные методики Селены: до переноса параметра в спеку это
  не поддерживается по построению.
- Отпечаток вычисляется до начала обслуживания. Невозможность его вычислить —
  отказ старта, а не деградация; это согласовано с fail-fast на биндинге
  (§3.1.6 `exact-orb_chart_artifacts.md`) и с тем, что `EPHEMERIS_UNAVAILABLE`
  в рантайме означает пропажу каталога уже после старта (§5.3 там же).
  До появления общей точки композиции это обязательный startup-контракт,
  а не описание текущего CLI.
- `ChartSpec` остаётся минимальным, поэтому `BuildNatalHandler` строит его
  двумя предметными полями и не переписывается вслед за расширением спеки.
