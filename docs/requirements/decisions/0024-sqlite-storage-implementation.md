# ADR-0024. SQLite как реализация хранилищ; PostgreSQL по условию, Redis только по условию пересмотра

Дата: 2026-09-04. Ревизия: 2026-09-05 — уточнены агрегатные операции
`SessionPersistence`, обязательные `BEGIN IMMEDIATE` и version guard с
проверкой `rowcount`; append/clear закреплены как атомарные write-and-renew.
Ревизия: 2026-09-06 — P4 зафиксировал per-operation connections,
component-scoped migrations, parent-only reaper и границу full-adapter
benchmark; P4.1 разделил подтверждённый transaction outcome и cleanup,
расширил однократный WAL recovery на неподтверждённый read-back и закрепил
совместимость payload v1 frozen fixture.
Ревизия: 2026-09-21 — уточнено владение запуском reaper: persistence и
process runtime предоставляют one-shot seam, периодическое расписание
принадлежит FastAPI lifespan.
Ревизия: 2026-09-24 — **отменена** безусловность запрета «Redis не вводится
ни на одной ступени». Redis по-прежнему не вводится; названо условие
пересмотра по образцу условия перехода на PostgreSQL. Данные, обязанные
пережить сбой, в Redis не переносятся ни при каком условии.
Статус: принято.

## Контекст

К этому моменту в проекте объявлены пять хранилищ: `SessionStore`,
`DialogStore`, `CalculationCache`, кэш интерпретаций и — после ADR-0023 —
`Research Corpus`. Все они описаны как `Protocol`-порты
(`build_natal_components.md` §1.3.3), но реализация есть только
in-memory, и она не переживает рестарт процесса.

Для стенда это неприемлемо по двум причинам, и вторая важнее первой.
Первая: перезапуск приложения теряет карты и переписку всех активных
пользователей. Вторая: `Research Corpus` по ADR-0023 обязан писаться с
первого дня, а in-memory реализация обесценивает его полностью — данные,
ради которых он заводится, исчезают при первом же деплое.

Ранее в обсуждении предлагалось сразу вводить PostgreSQL, поскольку
`Research Corpus` требует группировки и агрегатов, а не обхода ключей.
Требования к хранилищам, однако, различаются:

| Хранилище | Что нужно | Профиль нагрузки |
|---|---|---|
| `SessionStore` | атомарный CAS, TTL | чтение при каждой операции, запись редко |
| `DialogStore` | атомарный append с вытеснением, TTL | запись после каждой интерпретации |
| `SessionPersistence` | атомарные touch/reset/delete двух записей | lifecycle сессии |
| `CalculationCache` | opaque bytes, TTL | чтение часто, запись при промахе |
| Кэш интерпретаций | ключ → текст, TTL | то же |
| `Research Corpus` | группировка и агрегирование, бессрочно | запись всегда, чтение вручную |

Только последняя строка требует чего-то сверх key-value. Замеры первого
среза блока E (`exact-orb_session_requirements.md` §13) дают порядок
величин: пиковый темп записи системы — около 30 в секунду, расчёт одной
карты — 16 мс медианы, и он сериализован процессным `RLock`.

## Решение

Реализации хранилищ выстраиваются в **три ступени** за одними и теми же
`Protocol`-портами.

| Ступень | Где применяется | Что даёт |
|---|---|---|
| `InMemory*` | тесты | быстро, без I/O и файлов |
| `Sqlite*` | демо и стенд | переживает рестарт, ноль зависимостей в деплое |
| `Postgres*` | когда перерастём одну машину | несколько процессов, аналитика параллельно с обслуживанием |

Контракты при переходе между ступенями не меняются. Это и есть то, ради
чего порт вводился.

### SQLite закрывает все пять хранилищ

**CAS.** Операция начинается с `BEGIN IMMEDIATE` и делает precheck
актуального snapshot. Отсутствующая/истёкшая строка даёт `SessionAbsent`, а
несовпавшая версия — `VersionConflict(actual)` **до UPDATE**. После
совпавшего precheck реализация применяет `StateDelta` и выполняет guarded
`UPDATE session SET ... WHERE session_id = ? AND state_version = ?`.
Проверка `rowcount` обязательна: ранний write lock не заменяет version guard,
а commit подтверждён только при `rowcount == 1`. Иное значение после
успешного precheck — `StateWriteError`/нарушение persistence-инварианта и
rollback, а не normal conflict и не повод для второго чтения.

**Агрегатные операции.** `SessionPersistence.touch`, полный `reset` и
`delete` выполняются в одной `BEGIN IMMEDIATE … COMMIT`. `touch` продлевает
обе записи одним моментом и возвращает согласованный `SessionSnapshot`.
`reset` только делегирует фасетному CAS с `RESET_DELTA`: RESET_DELTA-aware
CAS после успешного guarded update (`rowcount == 1`) удаляет диалог в той же
транзакции. Неединичный `rowcount` откатывает reset целиком как
`StateWriteError`. `delete` атомарно удаляет обе записи. Координация двух отдельных
фасетных вызовов этому контракту не соответствует.

**Dialog write-and-renew.** `DialogStore.append` и `DialogStore.clear`
каждый выполняются в одной `BEGIN IMMEDIATE … COMMIT` вместе с продлением
parent state. Append сохраняет ограниченный dialog с тем же persisted
deadline; clear продлевает state и удаляет dialog. Предметные поля state и
`state_version` не меняются, а частичное изменение state/dialog недопустимо.
Parent `SessionState` остаётся единственным источником
live/missing/expired. Persisted dialog deadline — зеркало lifecycle и
postcondition write-and-renew: его расхождение не закрывает чтение, а
следующая записывающая lifecycle-операция синхронизирует его. Reaper этот
deadline не читает.

**TTL.** Колонка `expires_at`, проверка при чтении и периодическая чистка.
Встроенного TTL у SQLite нет. P4 предоставляет one-shot reaper, который
выбирает только истёкшие parent rows и удаляет dialog через
`ON DELETE CASCADE`. Process runtime M1-5.1 предоставляет one-shot вызов с
единым UTC clock; периодический запуск, отмена фоновой задачи и её связь с
server shutdown принадлежат FastAPI lifespan M1-6.

**Граница P4.** Первый SQLite-инкремент реализует только `SessionStore`,
`DialogStore` и `SessionPersistence`. Кэши и `Research Corpus` сохраняют ту
же стратегическую ступень SQLite, но реализуются отдельными задачами. Для
совместного файла используется component-scoped migration ledger, а не
глобальный `PRAGMA user_version`.

Concurrent first-open читает persistent journal mode до попытки переключения.
Если SQLite разрывает одновременный WAL upgrade numeric `BUSY/LOCKED` либо
`PRAGMA journal_mode = WAL` возвращает не-`wal` без исключения, проигравшее
соединение закрывается и получает одну свежую configuration attempt до начала
migration transaction. Повторный numeric BUSY не скрывается, повторный
не-`wal` является open failure; прочие PRAGMA mismatch не повторяются. Циклы,
sleep и process-global lock не используются.

**Transaction outcome и cleanup.** Подтверждённый commit и завершённое чтение
не превращаются в persistence failure из-за последующего отказа `close`:
ошибка освобождения ресурса диагностируется отдельно. `COMMIT_UNKNOWN`
означает только исключение непосредственно из `commit()`. Normal no-commit
outcome требует подтверждённого rollback либо успешного close после отказа
rollback; если оба cleanup-вызова бросили, наружу выходит typed persistence
failure. `ProgrammingError` остаётся ошибкой реализации и не типизируется.

**Payload compatibility.** State и dialog сохраняются с независимыми payload
versions. Frozen v1 fixture содержит JSON, relational metadata и действовавшие
dialog limits. Старые строки читаются через публичные порты, а публичные
create/CAS/append сверяются с той же семантической JSON-структурой. Изменения
моделей, validators, serializers или лимитов требуют явного решения об
обратной совместимости; несовместимое изменение получает новую payload version
и старый decoder либо migration.

**Путь к файлу.** Адаптер не выбирает путь и не читает environment/config.
Переданный caller относительный `db_path` канонизируется через `Path.resolve()`
в момент `open`, поэтому один relative config разрешается в разные файлы при
разном текущем рабочем каталоге процесса.

**`Research Corpus`.** Группировка и агрегаты по миллионам строк —
нормальная для SQLite работа. В режиме WAL читатели не блокируют писателей,
поэтому долгий исследовательский запрос не мешает обслуживанию.

**Ноль зависимостей в деплое:** `sqlite3` входит в стандартную библиотеку.

### Три оговорки, обязательные при реализации

1. **`synchronous=NORMAL` в режиме WAL** переживает падение процесса и
   рестарт — то есть ровно тот случай, ради которого всё затевается, — но
   при потере питания может потерять последние транзакции. `FULL`
   безопаснее и заметно медленнее из-за fsync на каждом коммите. Для демо
   берётся `NORMAL`; подтверждается при настройке стенда, когда станет
   известно, на каком диске и в какой виртуализации он живёт.
2. **`sqlite3` блокирующий.** P4 принимает `ThreadPoolExecutor` извне и не
   владеет его lifecycle; все SQLite-вызовы выполняются в нём. Решение,
   разделяет ли composition root этот executor с `EngineService` или выделяет
   отдельный, остаётся за application-слоем. `aiosqlite` не вводится.
3. **Одна машина, один файл.** Несколько процессов на одном файле в WAL
   работают, но с оговорками; несколько машин — нет. Это и есть граница
   применимости ступени.

### Граница раннего benchmark

Опубликованные в требованиях числа `median 0.016 мс`, `p95 0.084 мс` и
`61 000 записей/с` относятся только к микрозамеру SQL-примитива. Они не
включали сериализацию контрактных моделей, `BEGIN IMMEDIATE`, получение
`VersionConflict(actual)`, агрегатные операции, executor, реальный профиль
диска и конкуренцию писателей. Эти числа нельзя считать throughput будущего
`SqliteSessionPersistence` или capacity-гарантией стенда.

P4 обязан измерить публичный порт на file-backed базе с фактическими WAL и
`synchronous`, сериализацией, commit и тем же способом thread offload, что
используется приложением. Отдельно фиксируются p50/p95 для успешного CAS,
конфликта, append/clear, aggregate touch/reset/delete и конкурирующих
писателей. Показатели bare SQL нельзя приписывать полному adapter path.

Фактические machine-specific результаты не являются нормативом ADR и
хранятся отдельно в датированном
[benchmark report P4](../../benchmarks/2026-09-06-session-sqlite.md); ADR
ссылается на него, не дублируя числа.

### Условие перехода на PostgreSQL

Переход выполняется, когда наступает **одно из двух**:

* деплой перестаёт быть одномашинным;
* исследовательские запросы начинают мешать обслуживанию.

До этого PostgreSQL — вторая система в деплое без выигрыша: один бэкап,
один мониторинг и один способ восстановления для соло-разработчика дешевле,
чем два.

### Redis не вводится без условия пересмотра

Redis выигрывает микросекунды доступа там, где тратятся миллисекунды
расчёта: чтение SQLite по первичному ключу — 0.002 мс, попадание в кэш
расчётов целиком — 4.28 мс, из которых 2.49 мс уходит на глубокую копию
модели. Замена хранилища не сдвинет ни одну из этих цифр заметно, а третий
процесс в деплое появится.

Прежняя редакция запрещала Redis на любой ступени. Запрет без условия нельзя
проверить: он либо держится вопреки фактам, либо отменяется по вкусу. Поэтому,
как и для PostgreSQL, названо условие пересмотра.

Redis рассматривается только для **временного состояния, общего для
нескольких процессов**, и только когда **одновременно** выполнены три
требования:

* состояние обязано быть общим для нескольких процессов или машин — копия
  на процесс для него неверна, а не просто избыточна;
* потеря состояния допустима или оно восстанавливается: кэш, счётчик окна,
  сообщение в полёте;
* база текущей ступени не справляется — замерами, а не оценкой — с частотой
  обновления горячих ключей или с задержкой, либо не имеет нужного примитива:
  pub/sub между процессами с буфером для переподключения, вытеснение по
  памяти на уровне ключа.

Ожидаемый первый повод — несколько реплик при потоковых интерпретациях
(ADR-0012), когда отмена генерации, продолжение потока после
переподключения или учёт активных прогонов должны работать между
репликами. SQLite такого примитива не имеет, а `LISTEN/NOTIFY` в PostgreSQL
не хранит сообщения для переподключившегося клиента.

Поводом **не являются**:

* счётчики admission. Слот конкурентности привязан к процессному `RLock`
  движка и общим быть не должен; остальные счётчики при выходе за одну
  машину переходят на базу ступени за своим портом;
* `CalculationCache`: попадание 4.28 мс против 16 мс расчёта, копия на
  процесс дешевле сетевого обращения;
* single-flight расчёта между машинами: расчёт дешевле распределённой
  блокировки;
* фоновые задачи сами по себе. Durable-очередь строится на базе ступени
  (`SKIP LOCKED` в PostgreSQL); брокер на Redis допустим, только если потеря
  задачи при сбое приемлема.

Ни при каком условии в Redis не переносятся данные, обязанные пережить сбой:
состояние сессии и диалог, `Research Corpus`, учёт бюджета и дневной потолок
ADR-0013. Перед ними Redis допустим лишь как быстрый слой, источником истины
остаётся база ступени.

Выполнение условия оформляется ревизией этого ADR с замерами, а не
появлением Redis в коде.

### Что нельзя откладывать

`Research Corpus` должен писаться с первого дня работы стенда. Данные, не
записанные тогда, не восстанавливаются никогда, а именно они определяют
качество рецептов интерпретации (ADR-0023).

## Альтернативы

**PostgreSQL сразу** — отвергнуто на текущей стадии: даёт возможности, для
которых нет ни нагрузки, ни второй машины, и требует отдельного контура
эксплуатации. Решение обратимо: порты не меняются, переход описан условием
выше.

**Redis для сессий и кэшей + PostgreSQL для корпуса** — отвергнуто: два
дополнительных процесса в деплое ради выигрыша, теряющегося в шуме на фоне
16 мс расчёта.

**Остаться на in-memory до появления пользователей** — отвергнуто: теряется
`Research Corpus`, ради которого ADR-0023 и принимался, и стенд не
переживает собственный деплой.

**Файлы JSON на диске вместо базы** — отвергнуто: атомарный CAS и атомарный
append пришлось бы делать вручную через блокировки файлов, то есть
переписать заново то, что SQLite делает корректно и на два порядка быстрее
необходимого.

## Последствия

- Стратегически появляется реализация `Sqlite*` для всех пяти портов; P4
  реализует три session-порта и прогоняет их через общий
  **conformance-набор**. Остальные SQLite-адаптеры следуют отдельными
  задачами. Расхождение поведения InMemory и SQLite за одним портом — дефект.
  Набор пишется вместе с портом, до второй реализации: написанный после него
  он неизбежно подгоняется под уже существующий код.
- Появляется reaper для истёкших записей: у SQLite нет встроенного TTL.
- Состояние сессии и диалог переживают рестарт процесса — это проверяемое
  свойство, а не намерение.
- Схема миграций нужна с первого дня для `Research Corpus`: его данные
  бессрочны и переживут любую смену ступени, поэтому переносить их
  придётся, а не пересоздавать.
- Граница применимости ступени зафиксирована явно (одна машина), и её
  достижение — не авария, а известное заранее условие перехода.
- Транзиты меняют профиль нагрузки на расчёт (0.51 с на окно ±12 месяцев,
  `exact-orb_session_requirements.md` §13.4), но не на хранилища: объём
  записей от них не растёт. Настоящее решение транзитами не
  пересматривается.
- Redis остаётся вне деплоя. Условие его пересмотра названо, и его
  выполнение — повод для ревизии этого ADR, а не для молчаливого
  добавления третьего процесса.
