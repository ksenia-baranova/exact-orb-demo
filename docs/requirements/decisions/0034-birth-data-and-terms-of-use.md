# ADR-0034. Данные рождения, условия использования и граница публичного запуска

Дата: 2026-09-14.
Статус: принято.

Статус относится только к инженерным решениям этой записи. ADR не выбирает
правовое основание обработки персональных данных и не подтверждает готовность
сервиса к публичной обработке реального пользовательского трафика.

## Контекст

Ближайшая продуктовая цель M1 — как можно раньше показать на удалённом стенде
минимальный сценарий построения карты: пользователь вводит дату, опциональное
время и выбирает `place_id`, после чего сервер восстанавливает название места,
координаты, часовой пояс и UTC-момент, рассчитывает карту и возвращает её в UI.
LLM и Agent Runtime в этом сценарии не участвуют.

Данные этого пути имеют несколько независимых жизненных циклов. Их нельзя
сводить к одному утверждению о «хранении»:

| Контур | Что может содержать | Жизненный цикл в текущей системе |
|---|---|---|
| Форма и будущий HTTP request | дата, опциональное время, `place_id` | данные запроса живут в клиенте и памяти обработки; транспорт M1 ещё не реализован |
| `SessionState` | исходный `BirthInput`, `ResolvedBirthData`, `ChartSpec` | анонимная сессия со скользящим TTL 7 дней и абсолютным потолком 30 дней; reset/delete очищает session state по ADR-0009 |
| Calculation Cache | сериализованный полный `ChartArtifact` со spec, версией расчёта и картой | отдельный process-local LRU; срок задаётся конфигурацией и может не иметь TTL; удаление сессии его не очищает |
| Runtime-журнал | компактные операционные события, а в DEBUG — полные сообщения границ | файлы журнала имеют собственную ротацию и retention и не удаляются вместе с сессией |
| Research Corpus | разрешённая категориальная проекция | отдельный append-only контур без birth input, точных координат/времени, ключа, полного артефакта и текста; его retention задаёт ADR-0023 |
| Будущий LLM-flow | отобранные факты, metadata и текст запроса/ответа | в M1 отсутствует; состав получателей и retention провайдера должны быть решены до M2 |

ADR-0025 и ADR-0028 разрешают полный диагностический payload на пяти границах
Build Natal только при effective `DEBUG`. Это решение было принято для
локальной диагностики и не должно незаметно стать эксплуатационной политикой
удалённого окружения.

Страница пользовательских условий и юридическое согласие на обработку
персональных данных — разные документы и разные проверяемые факты. Согласно
[статье 9 Федерального закона № 152-ФЗ](https://ips.pravo.gov.ru/api/ips/legislation/document?baseid=None&hash=98490812b3409e2a8d78a11ca9010f434ea3d9250a11dbbdb78690cd5551bdd6),
если основанием выбрано согласие, оно должно быть конкретным, предметным,
информированным, сознательным и однозначным, оформляться отдельно от других
подтверждаемых документов; обязанность доказать получение лежит на операторе.
Настоящий ADR не заменяет юридическую проверку этих требований.

## Решение

### 1. Классификация входа

Любой поддерживаемый birth input обрабатывается как потенциально относящийся
к идентифицируемому физическому лицу. Система не пытается определить, ввёл
пользователь собственные, чужие или вымышленные сведения. Отсутствие имени,
аккаунта или проверки личности не выводит дату, время и место рождения из
защищаемой категории.

### 2. Назначение страницы условий

M1 предусматривает отдельную страницу «Условия использования сервиса» и
явный checkbox в форме, не отмеченный по умолчанию. Пока checkbox не отмечен,
UI не отправляет build request.

Страница должна сообщать как минимум:

- исследовательский характер проекта;
- отсутствие гарантий доступности и сохранности данных;
- что результат не является услугой, советом или предсказанием;
- какие входные данные нужны для расчёта и зачем;
- какие категории данных могут оказаться в session, cache и logging-контурах;
- как связаться с владельцем по вопросам данных и удаления;
- где доступен полный исходный код по ADR-0022 и AGPL §13.

ADR определяет состав и границы страницы, но не утверждает окончательный
юридический текст. Его подготовка и проверка остаются отдельной работой M1-9
и условием до публичного трафика.

### 3. Семантика checkbox

Checkbox является presentation gate и подтверждением ознакомления с
пользовательскими условиями. Он не является частью доменной команды расчёта,
`ChartSpec`, `CalculationInput`, calculation key, `SessionState`, Research
record или LLM prompt.

В первой версии отметка не отправляется отдельным persistence-событием и не
хранится после отправки формы. Не вводятся `consent_id`, timestamp, версия
текста, связь с аккаунтом или новая таблица.

Следствие этого размена явное: механизм не доказывает получение отдельного
юридического согласия на обработку персональных данных. Если после юридической
проверки будет выбрано основание, требующее подтверждаемого согласия, решение
о несохранении пересматривается новым ADR до запуска такого flow. Другие
условия пересмотра — аккаунты, сохранение карт между сессиями и отдельный
consented corpus.

### 4. Серверный logging profile

Для удалённого M1-окружения effective log level по умолчанию — `INFO`.
Сохраняется действующий контракт ADR-0025/0028:

- полный input/output `component_message` существует только при `DEBUG`;
- ниже `DEBUG` projector полного payload и JSON-сериализация не выполняются;
- на `INFO`/`WARNING` остаются компактные операционные события;
- локальный CLI сохраняет действующий default `DEBUG`;
- отдельный независимый флаг полного payload не вводится.

Это решение означает только то, что полный boundary payload ADR-0028 не
формируется при effective `INFO`. Оно не является утверждением, что после
этого персональные данные отсутствуют во всех операционных событиях или иных
контурах хранения.

Проверяемая настройка серверного профиля и guard от ошибочного `DEBUG`
относятся к будущей реализации M1-12. Настоящий ADR не объявляет их уже
реализованными. Маскирование DEBUG-payload остаётся задачей M3-8.

### 5. Удалённый стенд и публичный трафик

Различаются три режима:

1. локальная разработка с `DEBUG` и полным диагностическим контрактом
   ADR-0025/0028;
2. удалённый M1-стенд с effective `INFO` и контролируемым доступом;
3. публичный запуск с реальным пользовательским трафиком.

ADR разрешает инженерную подготовку первых двух режимов. Он не объявляет
публичный режим юридически или эксплуатационно готовым.

До публичного трафика отдельными проверяемыми решениями должны быть закрыты:

- правовое основание обработки и роль оператора;
- обязательные пользовательские документы и способ доказательства согласия,
  если оно выбрано основанием;
- retention и удаление server logs, session/cache и иных persistent данных;
- доступ к журналам и процесс обработки инцидентов;
- необходимость маскирования либо защищённой маршрутизации DEBUG;
- фактические сторонние получатели данных, включая LLM provider после M2.

Включение `DEBUG` на удалённом сервере немедленно возвращает privacy-hardening
M3-8 в обязательный ближайший объём. Открытие стенда публичному реальному
трафику до завершения перечисленных решений является stop condition, даже
если сервер работает на `INFO`.

### 6. Research и будущая интерпретация

ADR-0023 не заменяется. Always-on Research Corpus по-прежнему не получает
birth input, `calculation_key`, полный artifact, query или response text.
Будущий consented corpus требует собственного проверяемого opt-in и не
наследует checkbox пользовательских условий.

M1 не вызывает LLM Gateway. До реализации M2 отдельное решение должно описать
передаваемые провайдеру данные, получателей, retention провайдера и
соответствующий пользовательский текст. Настоящий ADR не проектирует этот
flow.

### 7. Связь с действующими решениями

- ADR-0009 сохраняет анонимную TTL-сессию и её reset/delete lifecycle.
- ADR-0012 сохраняет обычный request/response для build и отсутствие LLM и
  Agent Runtime в расчётном пути.
- ADR-0022 сохраняет требование заметной ссылки на полный исходный код.
- ADR-0023 сохраняет отдельные Research и consented boundaries.
- ADR-0025/0028 сохраняют полный локальный DEBUG-контракт; настоящий ADR
  выбирает для удалённого M1-окружения effective `INFO` и уточняет
  эксплуатационную границу этих решений.
- Privacy-hardening остаётся M3-8 либо возвращается раньше по stop condition.
- Архитектура расчёта, schema/version, session contracts и LLM Gateway не
  меняются.

## Альтернативы

**Не считать birth input персональными данными** — отклонено. Система не
умеет доказать вымышленность сведений или отсутствие их связи с физическим
лицом, а отсутствие имени не создаёт надёжную инженерную границу.

**Назвать checkbox условий юридическим согласием и не хранить факт** —
отклонено. Система не может доказать получение отдельного согласия и не должна
документировать неподтверждённое юридическое соответствие.

**Сразу хранить consent record** — отклонено для M1. Правовое основание,
оператор, версия текста, отзыв и retention ещё не определены. Nullable-таблица
или timestamp «на будущее» не создаются. Вариант возвращается после legal
review либо при появлении аккаунтов или consented flow.

**Маскировать все runtime-логи сейчас** — отклонено из объёма M1-1. Это
отдельная реализация M3-8; для контролируемого удалённого стенда выбран
effective `INFO`. Маскирование не признано ненужным и возвращается по
зафиксированным условиям.

**Оставить DEBUG на удалённом сервере** — отклонено для M1. Такой режим
переносит полный birth/chart payload из локальной диагностики в удалённое
окружение и активирует stop condition.

**Запретить любой удалённый стенд до M3** — отклонено для контролируемого
M1-стенда. Ранняя проверка карты в UI является продуктовой целью, а effective
`INFO` отключает полный boundary payload. Для публичного трафика запрет
сохраняется, пока не выполнены legal/privacy условия этого ADR.

## Последствия

- первый удалённый сценарий может разрабатываться для контролируемого стенда
  без ожидания полного Agent Runtime и маскирования M3-8;
- форма получает явный gate условий, но система не хранит доказательство
  юридического согласия;
- данные рождения остаются защищаемыми во всех затронутых контурах, а их
  retention рассматривается отдельно для session, cache, logging и Research;
- M1-12 должен задать и проверять effective `INFO` для серверного профиля;
- локальный DEBUG-контракт и default CLI не меняются;
- ошибочный `DEBUG` на сервере либо намерение открыть реальный публичный
  трафик немедленно возвращают соответствующий privacy/legal объём;
- публичный запуск остаётся заблокирован до отдельных проверяемых решений;
- этот ADR не меняет код, схемы, версии, расчётное поведение или LLM Gateway.

## Условия пересмотра

Решение пересматривается до:

- выбора consent-based правового основания;
- появления аккаунтов или хранения карт между сессиями;
- запуска consented corpus;
- передачи пользовательских данных внешнему LLM provider;
- включения `DEBUG` на удалённом окружении;
- открытия сервиса публичному реальному трафику.
