# Сквозные сценарии exact-orb

Статус документа: рабочий, версия 2.5 (2026-09-19).
Заменяет версию 1.0, где все сценарии начинались со свободного текста в чате.

Ревизия 2026-09-06: session-flow приведён к `SessionState`, `StateDelta` и
CAS по `state_version`; отменённый backend-контракт подстановки города удалён;
сценарии производных карт явно вынесены за первый MVP-срез.

Ревизия 2026-09-11: результат расчёта нормализован по ADR-0027, а полный
DEBUG-след всех компонентных границ закреплён ADR-0028.

Ревизия 2026-09-14: сценарии сверены с текущими контрактами резолва,
артефактов и сессии; добавлены семантика неизвестного времени ADR-0032,
ветви повторного сохранения, отказов, возврата в сессию и Research v1.

Ревизия 2026-09-15: routing application-команд перенесён до session load;
`RunContext` создаётся входной границей по уточнённому ADR-0006.

Ревизия 2026-09-19: application core для Build Natal, внешний
`ApplicationResult`, commit/retry/cancellation, lifecycle logging и normal
load profile сверены с реализацией; HTTP/UI и deployment остаются целевыми.

Ревизия 2026-09-21: process runtime composition отделена от FastAPI lifespan;
runtime предоставляет one-shot reaper, а M1-6 владеет его расписанием.

Контекст: вход через форму, карта сразу, затем preset-действия и — в подписке —
свободный вопрос. События потока: `status`, `input_required`, `token`, `done`, `error`.
Компоненты и готовность — по [overview](overview.md). Подробные контракты —
в [ADR](decisions/README.md) и component requirements.

**Как читать статусы.** Это целевые пользовательские и приёмочные сценарии,
а не отчёт о пройденных end-to-end тестах. Формулировка «Проверяет» указывает
проверяемое требование. `ApplicationOrchestrator` и `ApplicationResult`
реализованы и проверены через прямую application-границу. HTTP API, интерфейс,
session bootstrap и общий production startup wiring пока не реализованы.

| Сценарии | Реализованная часть | Целевая часть |
|---|---|---|
| 1–3, 5, 10–12 | Birth resolution, BuildNatalHandler, расчётный и артефактный слои, session persistence / ContextService, application lifecycle, внешний результат и CAS commit/retry | HTTP/UI, session bootstrap, client monotonicity X1, admission X2 и поиск подсказок |
| 4, 9 | интерфейсы и каркас интерпретации, transport Gateway без streaming | preset handler, Agent Runtime, общий Tool-путь, recipes, cache, budget, SSE |
| 6–8 | расчёт транзитов есть в ядре/CLI; free-form flow отсутствует | производные карты и free-form после MVP |
| 13 | Research contracts, whitelist-проекция и InMemory adapter | SQLite, producer wiring и политика application-записи |

Порядок реализации уточнён в [roadmap](../project_management/roadmap.md):
сначала сценарий 1 с UI на удалённом сервере, затем первая интерпретация
через прямой handler → InterpretationService → Gateway, затем runtime.
Прямой interpretation-путь пока запланирован и требует отдельного ADR;
сценарии 4 и 9 ниже сохраняют действующий целевой контракт с runtime/SSE.
Выполненные части и остаток отражены в таблице выше; наличие компонентного
покрытия не означает прохождение сценария через HTTP/UI.

`BuildNatalSuccess` подтверждает расчёт и подготовку дельты. Пользовательский
успех требует подтверждённого state commit либо `AlreadyApplied`.
[Sequence diagrams Build Natal](../sequence_diagrams/build_natal/README.md)
показывают ту же границу реализованного и целевого flow.

## Сценарий 1. Bootstrap: дата, время и место известны

Форма: `2 сентября 1990`, `14:30`, город выбран из подсказок → `place_id`.

1. **Session Middleware**: cookie отсутствует — transport генерирует свежий
   серверный `session_id` и создаёт анонимную сессию. Клиент ID не выбирает.
2. **AdmissionControl**: access и IP rate limit. Класс операции `calculation`,
   interpretation quota не расходуется. Действуют отдельные ограничения
   построений на сессию, IP и одновременной расчётной нагрузки (ADR-0013).
3. **Build Chart API** → **ApplicationOrchestrator**: один `RunContext`,
   точный routing по `type(command)`, затем
   `ContextService.load(session_id)` → `SessionSnapshot`. Оркестратор сохраняет
   исходную версию `0` и передаёт `BuildNatalCommand(birth_input)`, state и run
   в **BuildNatalHandler**. Agent Runtime на этом пути не вызывается.
4. **BirthDataResolver** → **PlaceCatalog.lookup(place_id)** → `LocalPlaceCatalog`:
   `place_id` → канонический город, `latitude = 55.76`, `longitude = 37.62`,
   `tz_id = Europe/Moscow`.
5. **Historical TZ**: 02.09.1990 в `Europe/Moscow` — летнее время UTC+4.
   Локальные 14:30 = **10:30 UTC**.
   Наивное «GMT+3» дало бы ошибку в час и сдвинутый асцендент.
6. `ResolvedBirthData` возвращается **в handler**; резолвер в состояние не пишет.
7. **BuildNatalHandler** формирует `ChartSpec` натальной карты
   (`chart_kind = natal`, полный `include`) и вызывает **ChartArtifactResolver**.
8. **ChartArtifactResolver** строит `CalculationInput` из resolved-данных;
   `calculation_key(input, spec, version)` даёт `eo:calc:v2:<sha256>`.
   Для известного времени `birth_time_domain_digest = None`.
   **Calculation Cache**: `get(key)` — промах.
9. **EngineService** → `calculate_natal()`: эфемериды, дома и углы, тела,
   производные точки, управители домов и интерцепции, аспекты → конфигурации → сила.
   Движок возвращает `CalculationResult(chart)`; точки каноничны, ось узлов
   имеет одного представителя в отношениях, конфигурации согласованы с аспектами,
   системы достоинств и диспозиторов совпадают (ADR-0029–0033).
10. **ChartArtifactResolver** собирает артефакт без дубликатов kind/warnings,
    проверяет chart против spec и пересчитанный из chart/spec/version ключ,
    затем кодирует и кладёт в кэш opaque `bytes` через `put(key, payload)`.
11. **BuildNatalHandler** собирает `BuildNatalSuccess` с all-set `StateDelta`.
    Валидатор связывает `birth_resolved`, spec, chart и `calculation_key`;
    новую версию состояния handler не присваивает.
12. **ApplicationOrchestrator** передаёт исходную `expected_state_version = 0`
    и дельту в `ContextService.save()`. Store выполняет CAS и возвращает версию `1`;
    ContextService классифицирует её как `Committed(state_version=1)`.
    Только после этого оркестратор формирует внешний `Success`: JSON без SSE.
13. **Chart Renderer** рисует колесо. LLM не вызывалась ни разу.

**Проверяет:** ADR-0005 (исторический пояс), ADR-0009 (сессия), ADR-0012
(построение без LLM), ADR-0017 (ключ и `ChartSpec`), ADR-0006/0020
(уровни координации), ADR-0027–0033 (согласованность и семантика результата).

### 1а. Технический отказ зависимости

- Недоступность каталога или timezone-зависимости даёт `ResolutionUnavailable`,
  без запуска расчёта и без подмены отказа на `InputRequired`.
- Типизированный отказ расчётного слоя handler отображает в `CalculationFailed`.
  `BuildNatalSuccess` и дельта для сохранения не возвращаются.
- Недоступность самого кэша не равна отказу движка: если расчёт доступен,
  resolver продолжает без кэша. Повреждённый payload пересчитывается.

Эти ветви уже разобраны в [диаграмме технических отказов](../sequence_diagrams/build_natal/005-build_natal_technical_failures.puml)
и [диаграмме деградации кэша](../sequence_diagrams/chart_artifacts/005-cache_degraded_fail_open.puml).

## Сценарий 2. Время неизвестно — космограмма, один ход

Форма: допустимая дата и город заполнены, поле времени пустое.

1. Пустое время — **не ошибка валидации**: это явное `time_unknown = true`.
   Уточняющий вопрос не задаётся (ADR-0008).
2. Birth/timezone-слой строит `BirthTimeDomain`: все валидные минуты локальной
   даты представлены каноническими UTC-диапазонами. Пропущенные минуты не входят,
   удвоенные дают оба допустимых UTC-момента. Полностью пропущенная календарная
   дата даёт `InputRequired` для `birth.date`, а не вопрос о времени.
3. `ChartSpec` содержит `chart_kind = cosmogram`,
   `include = {positions, aspects, configurations}`.
   Не рассчитываются `houses`, `angles`, `house_rulers`, `interceptions`
   и `strength` — последний требует домов.
4. Полдень используется как техническая опорная точка для долгот; аномалия
   местного полудня обрабатывается birth-слоем по ADR-0008. Опорный UTC-момент
   хранится в resolved-данных и карте, но UI не выдаёт его за введённое время:
   `BirthInput.birth_time` остаётся `None`, `time_unknown = true`.
5. `CalculationInput` включает digest домена. Resolver вычисляет key v2 до
   обращения к кэшу и передаёт готовые spec/resolved в EngineService.
6. Движок проверяет аспекты на всём домене. Публикуется только аспект,
   присутствующий с одним типом и категорией во всех допустимых моментах;
   `orb` — максимальный на домене, `applying = None`. Неустойчивые кандидаты
   попадают в `time_uncertainty.excluded_aspects`. Если аспекта нет нигде,
   нет и диагностической записи. Конфигурации строятся из устойчивых аспектов.
7. `NatalChart.chart_kind = "cosmogram"` — вид определяется полем, а не отсутствием
   домов (И-8).
8. Целевой UI визуально отличает космограмму от натала. В первом MVP переключения
   на транзиты нет. Когда оно появится, при базовой космограмме переход остаётся
   недоступным до реализации расчёта без домов и углов (сценарий 6).

**Известное невыполненное требование:** отдельные warnings ADR-0008 о смене
знака Луны или знака/направления быстрого объекта ещё не реализованы.
Аспектный `time_uncertainty` по ADR-0032 их не заменяет.

**Проверяет:** ADR-0008 (движок знает `chart_kind`, `strength` исключён),
ADR-0007 (пустое время само по себе не создаёт `input_required`), ADR-0032
(устойчивые аспекты, домен и key v2), И-8.
[Актуальная диаграмма космограммы](../sequence_diagrams/build_natal/003-build_cosmogram_time_unknown.puml).

## Сценарий 3. Выбор и проверка места

Форма: пользователь набирает название населённого пункта.

### 3а. Обычный путь — город есть в каталоге

1. **Location Dropdown** запрашивает подсказки после паузы во вводе:
   целевой `GET /places?q=Киров` возвращает ограниченный список
   `[{place_id, label}]` и имеет собственный rate limit. Поисковый endpoint
   ещё не реализован; он не является текущим `PlaceCatalog.lookup(place_id)`.
2. Пользователь выбирает вариант. Кнопка отправки разблокируется только после
   выбора: **Build API принимает `place_id` и не принимает свободный текст**,
   поэтому исход `AMBIGUOUS` **для места** на build-пути не возникает.
3. **BirthDataResolver** проверяет `place_id` через `PlaceCatalog.lookup`.
   Идентификатор пришёл
   от клиента и доверенным не является — он может устареть после обновления
   каталога, быть скопированным из другого окружения или подделанным.
   Если не разрешается:
   `InputRequired(issues=[Issue(field="birth.place", code="INVALID")])`.
4. Успешный резолв даёт канонический город, `latitude`, `longitude` и `tz_id`.
   Дальше — по сценарию 1.

### 3б. Города нет в каталоге подсказок

1. Пользователь не находит свой населённый пункт в подсказках. Форма предлагает
   указать ближайший известный ему город.
2. **Подобрать его система не может:** координат исходного места у неё нет —
   в этом и состояла проблема. Ближайший город называет человек. Формулировка
   в UI должна это отражать, иначе пользователь решит, что система что-то
   вычислила за него.
3. После выбора форма отправляет обычный `place_id`. Backend получает только
   выбранный идентификатор и не знает координат или исходного названия
   отсутствующего населённого пункта. Поэтому он не вычисляет расстояние, не
   выставляет признак подстановки и не добавляет warning по порогу расстояния.
4. Если присланный `place_id` не существует или устарел, backend возвращает
   `InputRequired(issues=[Issue(field="birth.place", code="INVALID")])`.
   Отложенный UX для устаревшего идентификатора описан в требованиях к
   BirthDataResolver; в MVP сервер не переиспользует прежние координаты молча.

### 3в. Неоднозначное или несуществующее время при выбранном городе

1. Пользователь явно вводит время из удвоенного часа осеннего перехода.
   `BirthDataResolver` возвращает `InputRequired` с `field="birth.time"`,
   `code="AMBIGUOUS"` и двумя смещениями в `candidates` (ADR-0007).
2. Явное время из пропущенного часа даёт `code="INVALID"` для `birth.time`.
   Расчёт и сохранение новой карты не выполняются.
3. Пустое время обрабатывается сценарием 2: технический полдень не порождает
   вопрос о неизвестном времени, даже если сам попал в timezone-аномалию.

Эти исходы build-пути уже реализованы и не зависят от подписки. Контракт
отдельного endpoint подсказок относится к будущему HTTP-слою.

Совет выбрать ближайший город — только текст формы, а не backend-контракт.
Отменённые поля и порог расстояния не входят ни в `BirthInput`, ни в
`ResolvedBirthData` (ревизия ADR-0005 от 2026-08-27).

**Проверяет:** ADR-0005 (frontend не источник истины, `place_id` проверяется
на сервере, backend не подбирает ближайший город), ADR-0007 (единый тип
`InputRequired`), И-11.

## Сценарий 4. Preset-интерпретация: тема и два фокуса

На странице натальной карты (`chart_kind = natal`) пользователь выбирает
`topic = natal`, `focus = [career, love]`. Весь interpretation-flow ниже
целевой; несколько фокусов предусмотрены ADR-0003.

1. **AdmissionControl**: access/rate checks для класса `preset_interpretation`.
   Новый расход LLM возникает только при промахе interpretation cache.
2. API → **ApplicationOrchestrator** → routing по типу команды →
   `ContextService.load` →
   **InterpretSelectionHandler**. **CapabilityService** разрешает demo preset.
3. **ActionContractBuilder**: `topic + focus` и ссылка на базовую карту текущего
   состояния → `ContractDraft`.
   Вероятностного шага нет — `IntentService` не вызывается (ADR-0011).
4. **ContractValidator** сверяет черновик с `SessionState` → `ResolvedContract`;
   handler передаёт его в **Agent Runtime**.
5. Внутри Agent Runtime **Planner** → **ScenarioRegistry**: сценарий `natal`,
   `tools = [natal]`, `topics = [{tool: natal, recipe: natal.focused, mode: full}]`.
   Имя recipe здесь иллюстративное; конкретные рецепты ещё предстоит реализовать.
   Два фокуса **не** порождают две темы и **не** включают `compact`:
   режим задаётся записью сценария/рецептом, а не числом выполненных tools.
6. **PolicyService** авторизует план. Пользовательского текста нет,
   `InterpretationQuery` отсутствует.
7. **ToolExecutor** → **Chart Tool** → **ChartArtifactResolver**: попадание в кэш,
   расчёт не повторяется.
8. Agent Runtime вызывает **InterpretationService**, который владеет
   DataSelector, подготовкой промпта, кэшем, бюджетом, LLM и проверкой выхода.
   **DataSelector** применяет фокусы: «карьера» — X дом и управитель, MC и его
   аспекты, Сатурн, Солнце; «личная жизнь» — VII дом и управитель, Венера,
   Луна, Марс и аспекты между ними; плюс общая база. Наборы объединяются
   с дедупликацией; `warnings` переносятся обязательно (И-7).
9. **PromptBuilder** собирает **один** `PromptBundle`; слот под пользовательский
   вопрос присутствует и пуст.
10. **InterpretationService** проверяет кэш по ключу
    `calculation_key + topic + focus + recipe_version + model` — промах.
    Представление нескольких фокусов в ключе должно быть определено в контракте
    interpretation cache при его реализации; здесь формат сериализации не вводится.
11. **AdmissionControl** атомарно резервирует бюджет с lease непосредственно
    перед вызовом модели. Отказ резервации останавливает вызов LLM.
12. **Gateway.complete_stream()**, профиль «интерпретация», потолок `max_tokens`.
    События `token` идут в канал.
13. При успешном завершении **OutputGuard** проверяет результат, ответ попадает
    в кэш, **AdmissionControl** коммитит фактический расход; канал завершается
    событием `done`. Ход сохраняется через `ContextService.append_turn` →
    `DialogStore.append`, без CAS базовой карты и изменения `state_version`
    (ADR-0014).

**Проверяет:** ADR-0003 (один промпт), ADR-0004 (темы против инструментов),
ADR-0013 (резервация и ключ кэша), ADR-0015 (capability), ADR-0017 (два кэша),
ADR-0006/0020 (разделение координации), ADR-0014 (диалог отдельно от карты).

### 4а. Повторная preset-интерпретация — cache hit

Для того же расчётного ключа, topic/focus, recipe version и model найдена
валидная запись. Проверки доступа сохраняются, но новой резервации, нового
вызова LLM и списания за генерацию нет. Клиент получает сохранённый ответ
через целевой interpretation transport. Это самостоятельная ветвь относительно
попадания в расчётный кэш: совпадение карты не гарантирует совпадение ответа.

### 4б. Preset для космограммы

Базовый артефакт имеет `chart_kind = cosmogram`; пользователь выбирает один
фокус, например `career`. Topic остаётся `natal`.
DataSelector использует доступные факты и устойчивые аспекты, сохраняет
ограничения `time_uncertainty` и warnings. Рецепт космограммы не упоминает
дома, ASC/MC и управителей и не восстанавливает исключённые аспекты.
Полуденные позиции и максимальные орбисы не выдаются за точные факты момента
рождения. Дальше действует тот же единый prompt/cache/budget flow.

Связь нескольких фокусов с Research v1 остаётся открытой — см. сценарий 13.

## Сценарий 5. Изменение данных рождения и гонка

Пользователь исправляет время в форме на странице карты.

1. Изменение через форму — явная операция `UpdateBirthData` в терминах ADR-0014.
   Текущий BuildNatalHandler принимает `BuildNatalCommand(birth_input)`;
   отдельный реализованный `UpdateBirthDataCommand` здесь не подразумевается.
2. Резолв → `ChartSpec` → `CalculationInput` и ключ → получение артефакта.
   При изменении только времени spec может остаться прежним; новый ключ
   определяется изменившимся расчётным input. Расчёт нужен при cache miss.
3. **BuildNatalHandler** формирует `StateDelta`; original
   `expected_state_version` из загруженного snapshot сохраняет ApplicationOrchestrator.
4. **ContextService** передаёт дельту в `SessionStore.compare_and_set`.
   Store атомарно обновляет `birth_input`, `birth_resolved`, `base_chart`,
   присваивает новую `state_version` и отклоняет stale-запись. Производных
   полей в первом MVP-срезе нет.
5. Старый кэш не инвалидируется: новые параметры дают другой ключ.

### 5а. Конкурентные разные намерения

Запрос A стартовал при версии 7, запрос B сохранил версию 8, A завершился позже.
`birth_resolved` и/или spec в актуальном состоянии отличаются от дельты A:

1. A не имеет права менять базовую карту: его original
   `expected_state_version = 7` больше не совпадает с актуальной версией 8.
2. Store возвращает `VersionConflict(actual)`. ContextService сравнивает actual
   с намерением A и возвращает `Superseded`; ApplicationOrchestrator передаёт
   этот исход клиенту. Артефакт A может остаться в расчётном кэше, но UI не
   показывает его как сохранённую базовую карту.

### 5б. Повторная доставка того же намерения

1. Первый save уже применил дельту, а ответ потерян или та же команда пришла
   повторно. Retry использует исходные expected и delta, без подмены версии
   свежей и без rebase.
2. Store возвращает `VersionConflict(actual)`, но actual соответствует намерению:
   ContextService возвращает `AlreadyApplied`. Повтор не увеличивает версию.
3. Если после первого save сохранено другое намерение, тот же retry даёт
   `Superseded`. Одного несовпадения версий для выбора между этими исходами
   недостаточно; сравниваются `birth_resolved` и spec по ADR-0014.

### 5в. Расчёт успешен, commit не подтверждён

1. Handler вернул `BuildNatalSuccess(artifact, delta)`, затем `ContextService.save`
   вернул `StateCommitFailed` из-за отказа или неизвестного исхода записи.
2. ApplicationOrchestrator не возвращает успешную пользовательскую операцию.
   UI не считает рассчитанную карту подтверждённо сохранённой.
3. Повторная попытка commit сохраняет исходные expected/delta. Если запись
   не произошла и версия не изменилась, retry даёт `Committed`; при конфликте
   версии — `AlreadyApplied` или `Superseded` по ветви 5б. Сам отказ записи
   не доказывает, что дельта не была применена.
4. Если к моменту commit сессия истекла, `SessionAbsent(reason="expired")`
   ведёт в сценарий 11; старый ID не используется для воскрешения сессии.

[Диаграмма отказа commit и истечения сессии](../sequence_diagrams/build_natal/007-build_natal_commit_failure_and_session_expired.puml).

**Проверяет:** ADR-0014 (CAS, `Superseded`, `AlreadyApplied`, retry без rebase),
ADR-0006 (успех только после commit), ADR-0016 (одна базовая карта), И-13.

## Сценарий 6. Транзит как производная карта — после MVP

Сценарий описывает целевую модель после снятия сужения ADR-0016. В первом
MVP-срезе `derived_chart`, `active_view` и `SetActiveView` отсутствуют.

Пользователь переключает вид на транзиты и выбирает дату.

1. `SetActiveView` / `BuildDerivedChart` — **отдельная операция состояния**,
   а не побочный эффект интерпретации (ADR-0014).
2. Момент транзита резолвится по `tz_id` **места расчёта** на дату транзита,
   не по поясу пользователя (ADR-0005).
3. `ChartSpec` транзита содержит момент, место и параметры окна.
   Кэш натала переиспользуется: `calculate_transit()` принимает готовый
   `NatalChart` (ADR-0001).
4. После расширения session-контракта `derived_chart` будет ссылаться на
   производную спецификацию с актуальной `state_version`, а `active_view`
   станет равен `derived`.
   Базовая карта не мутирует.
5. Дату транзита можно менять многократно без пересчёта натала.

**Если базовая карта — космограмма**, переход недоступен: `calculate_transit()`
требует `natal.cusps` и `natal.angles`, которых у космограммы нет. UI блокирует
действие с объяснением, а не показывает ошибку расчёта.

**Проверяет:** ADR-0016 (базовое и производное), ADR-0008 (ограничение),
ADR-0017 (переиспользование кэша).

## Сценарий 7. Свободный вопрос — подписка, после MVP

«Что в моей карте говорит о том, почему я постоянно меняю работу?»

Целевой маршрут: API → ApplicationOrchestrator → загрузка SessionSnapshot →
InterpretMessageHandler. Handler вызывает понимание запроса и затем Agent Runtime;
внешний coordinator не выбирает tools и не формирует промпт.

1. **CapabilityService**: `freeform_interpretation` разрешён тарифом.
   В demo на этом шаге операция отклоняется.
2. **InputGuard**: нормализация, **лимит длины**, детект инъекций
   → `GuardVerdict` как отдельный объект.
3. **AdmissionControl**: abuse-сигналы плюс квота.
4. **IntentService** → `UnderstandingResult`:
   `contract_fields = {topic: natal, focus: career}`,
   `interpretation_query = {normalized_text, language}`.
   Данные рождения из текста **не извлекаются** (ADR-0019) — источник один:
   `SessionState`.
5. **ContractValidator** → `ResolvedContract` → **Agent Runtime**, где
   **Planner** строит план.
   Ни тот, ни другой пользовательского текста не видят (И-1).
6. **PolicyService** авторизует план и отдельно запрос →
   `AuthorizedInterpretationQuery`. Отказ останавливает соответствующий путь.
7. **ToolExecutor** выполняет разрешённые tools через общий артефактный слой;
   Agent Runtime передаёт результаты в **InterpretationService**.
8. DataSelector отбирает Evidence; **PromptBuilder** кладёт авторизованный вопрос
   в **отдельный делимитированный слот** рядом с trusted system recipe.
   Нормализация не делает текст доверенным; модель не управляет tools,
   расчётными параметрами или пользовательским состоянием.
9. Ключ interpretation cache содержит расчётный ключ, topic/focus, recipe version,
   model, дополнительно `session_id` и хэш вопроса. Запись живёт не дольше сессии.
   При hit используются сохранённые данные без нового вызова LLM и резервации.
10. При miss выполняется атомарная резервация, затем генерация и обязательный
    **OutputGuard**. Учёт расхода и завершение — как в сценариях 4 и 9.

**Проверяет:** ADR-0018 (переформулированный И-1, `GuardVerdict` отдельно),
ADR-0015 (capability), ADR-0013 (admission), ADR-0017 (ключ free-form).

## Сценарий 8. В свободном тексте упомянута дата рождения — после MVP

«Построй карту мужу, 3 марта 1988, Киров».

Ветка будущего InterpretMessageHandler после проверки capability.

1. Rule-based **детектор** замечает дату и топоним. Резолв не выполняется —
   распознавания данных рождения в MVP нет (ADR-0019).
2. Возвращается явный отказ через существующий тип `InputRequired`:

   ```json
   {"issues": [{"field": "subject", "code": "UNSUPPORTED"}]}
   ```

   UI поясняет: «Изменение данных рождения — через форму». Необязательное
   `Issue.constraints` имеет тип объекта или `None`, а не строки; структура
   для такого сообщения здесь не вводится.
3. Молчаливый ответ про сохранённую карту недопустим: пользователь получил бы
   осмысленный текст и решил, что система его поняла. Это тихая подмена субъекта,
   а не мягкая деградация.

**Проверяет:** ADR-0019 (граница отсрочки честная, а не скрытая),
И-11 (тот же тип для другой категории).

## Сценарий 9. Ошибка после начала потока

1. Ход развивается как сценарий 4 до вызова streaming Gateway. Этот transport
   пока целевой; `complete_stream()` ещё не реализован.
2. На середине генерации провайдер обрывает соединение или превышает таймаут.
3. Поток открыт и часть `token` отдана — HTTP-код изменить нельзя.
   Ошибка доставляется событием `error` **внутри потока** (И-10).
4. **AdmissionControl** завершает резервацию с учётом фактически израсходованного.
   `cancel` освобождает неиспользованную резервацию, но не отменяет уже
   понесённый расход на выданные токены. Резервация не остаётся висеть.
5. Финализация по накопленному тексту: `ContextService.append_turn` сохраняет
   частичный ответ с `status="partial"` в диалоге сессии.
6. **Если процесс погиб между `reserve` и `commit`**, резервацию освобождает
   reaper по истечении lease. Без него краш-луп молча съедает дневной потолок,
   и снаружи это выглядит как «квота кончилась ни с того ни с сего» (ADR-0006).

**Проверяет:** И-10, ADR-0006 (lease), ADR-0013 (жизненный цикл резервации).

## Сценарий 10. Кэш вымыт, карта восстанавливается

В целевом MVP сессия ещё жива, но её артефакт вымыт из Calculation Cache.
Session persistence сохранил resolved-данные и спецификацию базовой карты.

1. ApplicationOrchestrator получает SessionSnapshot через `ContextService.load`.
   Используются `state.birth_resolved` и `state.base_chart.spec`;
   `derived_chart` и `active_view` в первом срезе отсутствуют.
2. **ChartArtifactResolver** получает spec/resolved. `calculation_input_from`
   извлекает UTC, координаты и digest домена времени для космограммы.
3. `calculation_key(input, spec, version)` вычисляет key v2, после чего
   `CalculationCache.get(key)` возвращает промах.
4. Resolver вызывает EngineService, проверяет результат, создаёт ChartArtifact
   и сохраняет его как `bytes`. Восстановление артефакта само не изменяет
   `birth_input`, spec или `state_version` сессии.
5. При неизменных расчётных входах и CalculationVersion восстанавливается
   прежний расчёт. Если после деплоя версия изменилась, будет новый ключ и
   результат по текущей методике; равенство старых чисел не обещается.

Одного spec недостаточно: он не содержит дату и координаты рождения.
Один хэш также не восстанавливает исходные данные. Для космограммы сохраняется
`birth_time_domain`, а его digest участвует в идентичности расчёта (ADR-0032).

**Проверяет:** ADR-0017 (И-12), ADR-0009 (структура `SessionState`), ADR-0032
(сохранение домена неизвестного времени).

## Сценарий 11. Истечение сессии, потеря cookie и удаление данных

### 11а. TTL истёк при открытой странице

1. Запрос к сессии получает `SessionAbsent(reason="expired")`, если запись
   ещё есть, но её sliding/hard TTL истёк. После физической очистки тот же ID
   наблюдается как `SessionAbsent(reason="not_found")`.
2. Целевой transport различает `session_expired` и `session_not_found` для
   диагностики, но пользователю даёт общую формулировку и возврат к bootstrap.
   Непригодная cookie гасится; новая сессия получает свежий серверный ID.
3. Молча восстанавливать расчётное состояние из данных клиента запрещено.
   Пользователь может заново отправить форму через обычный проверяемый build-путь.
4. Истечение логическое: запись немедленно перестаёт быть доступной. InMemory
   adapter физически её не удаляет; SQLite очищает просроченные записи reaper.
   Будущий `ApplicationRuntime` M1-5.1 предоставляет one-shot вызов reaper с
   единым UTC clock. Периодический запуск и остановка фоновой задачи относятся
   к FastAPI lifespan M1-6.

### 11б. Пользователь удалил cookie в браузере

Сервер утратил клиентскую связь с прежней сессией, но автоматический server-side
delete не произошёл. Старые записи остаются до своей очистки по lifecycle;
следующий bootstrap создаёт сессию с новым ID.

### 11в. Явное «Удалить мои данные»

Целевой `DeleteMyDataCommand` вызывает `ContextService.delete` →
`SessionPersistence.delete`: state и dialog удаляются атомарно. После подтверждения
transport гасит cookie. API команды ещё нет, операция persistence реализована.

Session lifecycle не удаляет Research Corpus: его разрешённая проекция имеет
отдельный retention по ADR-0023. Полные локальные DEBUG-логи — уже принятое
исключение по ADR-0025/0028; требования их подготовки к публичному размещению
описаны в overview §4.12.

`StateReadFailed` не является доказательством истечения или удаления сессии;
этот отказ рассматривается отдельно в сценарии 12.

**Проверяет:** ADR-0009 (TTL и отказ от восстановления с клиента),
ADR-0023 (отдельный retention корпуса), ADR-0025/0028 (граница локального журнала),
ADR-0005 (frontend не источник истины).

## Сценарий 12. Возврат в живую сессию и отказ чтения

### 12а. Повторное открытие страницы

1. Целевой `RestoreSessionQuery` не содержит `session_id`: transport получает
   его из защищённой cookie и передаёт в доверенном контексте вызова.
2. `ContextService.load` выполняет один агрегатный
   `SessionPersistence.touch(session_id, now=now)`. Он возвращает согласованный
   SessionSnapshot и продлевает TTL state/dialog с учётом hard TTL.
3. Из snapshot восстанавливаются форма (`birth_input`), диалог и описание
   базовой карты. Если карта уже задана, её артефакт получает
   ChartArtifactResolver; при промахе кэша выполняется сценарий 10.
4. Восстановление не вызывает LLM и не меняет `state_version`: продление TTL
   не является изменением содержимого состояния.

### 12б. Хранилище временно недоступно

1. Чтение или обязательное продление TTL завершается технической ошибкой.
   `ContextService.load` возвращает `StateReadFailed(error_code)`.
2. Частичный или ранее закэшированный snapshot не выдаётся как успех.
   Целевой transport отвечает `503`, UI сообщает о временной недоступности.
3. Этот outcome не доказывает утрату сессии: он не является основанием
   погасить cookie, создать новую сессию или восстановить состояние из клиента.
   Подтверждённый `SessionAbsent` обрабатывается по сценарию 11.

Контракт ContextService и persistence реализован; RestoreSessionQuery и его
HTTP/UI-композиция остаются целевыми. Потоки:
[возврат в сессию](../sequence_diagrams/session/002-session-restore-on-return.puml),
[отказ чтения](../sequence_diagrams/session/003-session-store-read-failure.puml).

**Проверяет:** ADR-0009 (серверная сессия), ADR-0017 (восстановление артефакта),
ADR-0024 (атомарный snapshot и обязательное продление TTL).

## Сценарий 13. Исследовательская запись и поздняя оценка качества

Это целевой поток для готового ответа по наталу или космограмме с одним фокусом,
например `topic=natal`, `focus=career`. Реализованы модели, whitelist-проекция
и InMemoryResearchCorpus. SQLite-адаптер и подключение producer к application
ещё не реализованы; application-политика записи и обработки её отказов
не входит в утверждённый контракт компонента.

1. Вызывающая сторона создаёт `research_id` и `created_at` один раз на
   логическую запись; время нормализовано к UTC и округлено вниз до часа.
   Повторная доставка использует те же значения.
2. Проекция `ChartArtifact` → `ChartFeatures` оставляет только разрешённые
   признаки. Вместе с selection, версиями расчёта/рецепта, моделью, задержкой
   ответа и доступными метриками расхода они образуют `ResearchRecord`.
   Исходные данные рождения,
   session ID, текст вопроса/ответа и полный artifact в запись не входят.
3. `ResearchCorpus.put_record` возвращает `ResearchStored`; повтор с тем же
   ID и digest — `ResearchAlreadyStored`. Другой payload под тем же ID даёт
   `ResearchIdConflict`, а не перезаписывает исходную запись.
4. Поздняя оценка поступает отдельным `ResearchQualityEvent` со своими стабильными
   `event_id`, `observed_at` (UTC hour) и ссылкой на `research_id`.
   `put_quality_event` добавляет событие, не изменяя ResearchRecord;
   повторная доставка также идемпотентна.
5. Новое событие для отсутствующей записи даёт `ResearchRecordAbsent`.
   Хранилище не создаёт родительскую запись из оценки. Технический отказ записи
   пересекает порт как `ResearchWriteError("RESEARCH_WRITE_FAILED")`;
   реакция application требует отдельного решения.

Корпус имеет отдельный retention и не участвует в удалении сессии (сценарий 11).
Проекция минимизирует данные, но не является доказательством анонимности.
Контракт: [Research Corpus](component_responsibilities/exact-orb_research_corpus.md);
поток: [запись и оценка](../sequence_diagrams/research/001-record-and-quality.puml).

**Открытое противоречие:** ADR-0003 разрешает несколько фокусов в одном ответе
(сценарий 4: `[career, love]`), а ADR-0023 и `ResearchSelection.focus`
предусматривают один фокус. Правило проекции такого ответа в корпус не определено.
Нельзя молча выбрать первый фокус или объявить несколько независимых записей
эквивалентом одного ответа. Для подключения этого пути нужно согласовать
границу и явно уточнить соответствующий контракт.

**Проверяет:** ADR-0023 (граница корпуса, неизменность записи и идемпотентность);
выявляет несогласованную границу с ADR-0003 для нескольких фокусов.
