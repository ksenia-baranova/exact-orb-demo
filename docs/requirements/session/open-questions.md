# Сессии — архивный лист вопросов к согласованию

**Статус: исторический материал до решений 2026-09-04; не действующий
контракт и не список открытых вопросов.** Решения перенесены в ревизии ADR и
`exact-orb_session_requirements.md`. Варианты ниже, включая предложение
оставить `BuildAttempt`, отражают ход обсуждения и могут расходиться с
принятым итогом.

Основания: ADR-0009, 0010, 0012, 0013, 0014, 0016;
`build_chart/exact_orb_negative_corner_scenarios.md` (N1…N10);
`sequence_diagrams/session/001-natal-session-lifecycle.puml`.

## A. Жизненный цикл сессии

| № | Вопрос | Что уже решено и где | Мой вариант | Ваш ответ |
|---|---|---|---|---|
| A1 | Величина sliding TTL сессии | ADR-0009: TTL есть, «продлевается любой операцией». Числа нет нигде | 7 дней: демо показывают не в один присест |  |
| A2 | Абсолютный потолок жизни сессии | Не решено. Бесконечно продлеваемое окно противоречит ADR-0010 «после истечения сессии ПДн не остаётся нигде» | 30 дней жёстко, независимо от активности |  |
| A3 | Cookie жива, записи в store уже нет | Не решено. Это `session_not_found`, а не `session_expired` | Для пользователя один исход и одна формулировка; в логах и метриках различать |  |
| A4 | Операция чтения состояния при возврате на страницу | ADR-0012: «frontend восстанавливает последнее committed состояние». Самой операции в sequence 001 нет | Ввести в MVP: без неё ветка «вернулся, карта есть» не существует, а это самый частый вход |  |
| A5 | Команда «начать заново» / карта другому человеку | Не решено. Сейчас единственный путь — `UpdateBirthData`, затирающий предыдущую карту | Ввести `ResetSession` в MVP: демо показывают друзьям, сценарий массовый |  |
| A6 | Кнопка «удалить мои данные» | Не решено. ADR-0010 строит privacy-модель на том, что данные умирают с сессией | Ввести: сброс cookie + удаление записи. Дёшево и закрывает privacy-обещание |  |

## B. Модель состояния: расхождения новой диаграммы с действующими ADR

Диаграмма 001 упростила модель. `session/README.md` это признаёт. Ниже —
что именно разошлось.

| № | Вопрос | Что уже решено и где | Мой вариант | Ваш ответ |
|---|---|---|---|---|
| B1 | Переименование `SessionProfile`/`SessionContext` → `SessionState`, `profile_version` → `state_version` | ADR-0009 и §1.1–1.2 негативных сценариев вводят старые имена | Принять новые имена, зафиксировать ревизией ADR-0009 и 0014. Косметика, но молча переименовывать нельзя |  |
| B2 | `derived_chart`, `active_view`, команда `SetActiveView` | ADR-0009, 0014, 0016. В диаграмме 001 их нет вообще | Сузить MVP до одной базовой карты, оформить ревизией ADR-0016. Транзиты и так не входят в первый срез |  |
| B3 | `BuildAttempt`, `current_build`, `build_revision` | §1.1 и §1.3 негативных сценариев. В диаграмме 001 отсутствуют | **Оставить.** На них держатся N1, N6, N7, N10 — без них нет ни идемпотентности, ни latest-accepted-build-wins |  |
| B4 | Ходы диалога в `Session Store` | ADR-0010: «живут в Session Store вместе с профилем». В новой модели их нет | Хранить: иначе после рефреша карта есть, а чат пуст, и ADR-0010 надо ревизовать |  |
| B5 | Кто владеет инкрементом версии | ADR-0009: `ProfileService` владеет инкрементом и правилом отказа stale-записи. В диаграмме handler готовит `StateDelta` сам | Версию присваивает store при compare-and-set (это и в ADR-0014). `ProfileService` как отдельный компонент в MVP не нужен — оформить ревизией ADR-0009 |  |

## C. Конкурентность за пределами build ↔ build

N6 и N10 покрывают только два одновременных построения.

| № | Вопрос | Что уже решено и где | Мой вариант | Ваш ответ |
|---|---|---|---|---|
| C1 | Интерпретация в полёте, приходит `UpdateBirthData` | Не решено. ADR-0012 фиксирует только событие `error` для технического отказа | Оборвать стрим событием `superseded` (термин уже есть в ADR-0014). Текст про карту, которой на экране нет, хуже прерванной генерации |  |
| C2 | Бюджет при обрыве наполовину сгенерированного ответа | ADR-0013: атомарная резервация с lease, затем `commit` или `cancel` | `commit` по фактически потраченному: токены израсходованы реально, `cancel` протечёт бюджетом |  |
| C3 | Нужен ли `expected_state_version` на пути интерпретации | Не решено. ADR-0014 вводит версию только для защиты записи | Не нужен для запуска, нужен в ответе: клиент должен видеть, по какой версии сгенерирован текст |  |
| C4 | Две вкладки одной сессии: в одной меняют данные, в другой жмут интерпретацию | Не решено. N6 про два build, это build ↔ interpret | Не запрещать, но ответ помечать версией (C3) и обрывать по C1, если версия сменилась во время генерации |  |
| C5 | Две интерпретации одновременно из двух вкладок | Не решено. ADR-0013 резервирует бюджет дважды | Разрешить, ограничение — общий сессионный лимит стоимости, отдельная сериализация не нужна |  |
| C6 | Блокирует ли frontend форму на время генерации | Не решено | Блокировать в UI, но backend обязан проверять сам: UI не источник истины |  |

## D. Отказы Session Store

| № | Вопрос | Что уже решено и где | Мой вариант | Ваш ответ |
|---|---|---|---|---|
| D1 | Отказ store при чтении, а не при записи | N8 покрывает только commit | Отдавать `503`. Показ пустой формы тихо уничтожает состояние, которое на самом деле цело |  |
| D2 | Круговая зависимость: `BuildAttempt` лежит в том же store, отказ которого описывает N8 | Не решено. При недоступном store не работают ни идемпотентность, ни latest-wins, ни восстановление | Признать явно: при недоступном store отказываем целиком, а не «работаем без памяти». Полудеградация даст двойные расчёты и гонки |  |
| D3 | `expected_state_version` для новой попытки после провалившегося commit | Не решено. Актуальная версия неизвестна | Перечитать состояние перед попыткой; если чтение не удалось — D1 |  |
