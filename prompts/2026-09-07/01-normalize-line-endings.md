# Политика окончаний строк: `text=auto` в `.gitattributes`

Работай в ветке:

`chore/normalize-line-endings`

Не создавай коммит, push или PR. Не выполняй `fetch` или `pull`. Сохрани все
пользовательские и несвязанные изменения рабочего дерева.

Задача инфраструктурная и однофайловая по объёму правки. Содержимое кода,
тестов и документации не изменяется: меняется только `.gitattributes` и то,
как Git обрабатывает окончания строк.

## Проблема

Окончание строки — служебный символ в конце строки текстового файла: `LF`
(`\n`, Unix) или `CRLF` (`\r\n`, Windows). Содержимое строк от этого не
зависит, но байты файлов различаются.

В рабочем дереве проекта одновременно встречаются `LF`, `CRLF` и смешанные
окончания. Само по себе это не влияет на индекс текущего клона: локальная
настройка `core.autocrlf = true` нормализует текст до `LF` при добавлении
в индекс и разворачивает его согласно локальным настройкам при checkout.

Проблема в том, что `core.autocrlf` — настройка одной машины. Она не хранится
в репозитории и не применяется автоматически в другом клоне, CI или ином
инструменте. Действующий `.gitattributes` защищает только двоичные файлы
эфемерид:

```text
*.se1 binary
```

Без репозиторной политики текстовый файл однажды может попасть в индекс с
`CRLF`. Тогда файл целиком отобразится изменённым, ухудшится `git blame`, а
параллельные ветки могут получить конфликты на строках, содержание которых
никто не менял.

## Цель

Зафиксировать политику окончаний строк в репозитории и проверить, что
существующий индекс уже нормализован.

ADR не требуется: это инфраструктурная настройка Git, а не архитектурное
решение. Новый ADR не создавай.

## Перед изменением

1. Выполни `git status --short --branch` и зафиксируй исходное состояние.
   Ничего из уже существующих изменений не удаляй, не перемещай, не
   пересохраняй и не добавляй в индекс.
2. Перейди на `chore/normalize-line-endings`, если ветка уже существует, либо
   создай её от текущего локального `main`. Не сбрасывай существующую ветку и
   не обновляй `main` по сети. Если безопасное переключение невозможно из-за
   пользовательских файлов, остановись и опиши конфликт.
3. После переключения снова выполни `git status --short` и используй этот
   вывод как baseline для проверки итогового состояния рабочего дерева.
4. Прочитай `.gitattributes` и локальное значение настройки:

   ```text
   git config --local --get core.autocrlf
   ```

   Не изменяй `.git/config`.
5. Выполни `git ls-files --eol` и сохрани исходный вывод для сравнения.

В выводе `git ls-files --eol`:

- `i/` описывает содержимое индекса;
- `w/` описывает рабочее дерево;
- `attr/` показывает действующее правило атрибутов.

Для диагностики нормализации индекса ищи текстовые файлы с `i/crlf` или
`i/mixed`. Значения `i/-text` относятся к двоичным файлам, а `i/none` означает,
что файл не содержит переводов строк; оба состояния сами по себе не требуют
нормализации.

## Реализация

Добавь в `.gitattributes` общее правило для текста перед существующим правилом
эфемерид:

```text
* text=auto
*.se1 binary
```

Порядок обязателен. В `.gitattributes` последнее совпавшее правило определяет
значение конкретного атрибута, поэтому `*.se1 binary` должно находиться ниже
`* text=auto`. Иначе общее правило переопределит `-text`, заданный макросом
`binary`, и двоичные эфемериды попадут под текстовую нормализацию.

Добавь перед `* text=auto` короткий комментарий в стиле существующего файла:
текст нормализуется до `LF` в индексе по политике репозитория, а окончания
строк рабочего дерева остаются локальной настройкой Git. Существующий
комментарий про эфемериды сохрани без смысловых изменений.

`text=auto` поручает Git определять текстовые файлы и хранить их в индексе с
`LF`. Если атрибут `eol` не задан, представление в рабочем дереве по-прежнему
определяют локальные `core.autocrlf` и `core.eol`.

Не используй `eol=lf` или `eol=crlf`: они жёстко задают представление рабочего
дерева. Цель задачи — зафиксировать нормализацию индекса, не навязывая всем
разработчикам одинаковые окончания строк на диске.

## Диагностика индекса, а не перезапись

После изменения снова выполни:

```text
git ls-files --eol
```

Сравни с исходным выводом колонки `i/`, `w/` и пути:

- `i/` и `w/` для каждого файла должны остаться прежними;
- `attr/` у обычных файлов ожидаемо изменится на `text=auto`;
- у `*.se1` должно сохраниться `attr/-text`.

Полный вывод до и после не обязан совпадать: изменение `attr/` является
ожидаемым результатом правки `.gitattributes`.

Проверь индекс по исходному и итоговому выводу:

- если текстовых файлов с `i/crlf` или `i/mixed` нет, индекс чистый и
  `git add --renormalize` не нужен;
- если такие файлы есть, не исправляй их в этой задаче. Перечисли их в отчёте
  и укажи, что нормализация требует отдельной задачи и отдельного коммита с
  `git add --renormalize .`.

Не запускай `git add --renormalize`, включая dry-run, и не приводи окончания
строк рабочего дерева вручную — ни скриптом, ни массовой заменой, ни
пересохранением файлов.

## Ограничения

- Не изменяй `.git/config`, включая `core.autocrlf`.
- Не изменяй содержимое кода, тестов и документации.
- Не изменяй `ephe/**` и не трогай правило `*.se1 binary`, кроме сохранения
  его ниже нового общего правила.
- Не добавляй `.editorconfig`.
- Не создавай и не изменяй ADR.
- Не переименовывай и не удаляй файлы.
- Не добавляй файлы в индекс.
- Не создавай коммит, push или PR.

## Проверки

1. `git ls-files --eol` до и после:
   - колонки `i/`, `w/` и пути совпадают;
   - изменение `attr/` соответствует новой политике;
   - в индексе нет `i/crlf` или `i/mixed`, либо они перечислены как отдельная
     нерешённая задача.
2. Проверь атрибуты четырёх файлов:

   ```text
   git check-attr text eol -- .gitattributes
   git check-attr text eol -- docs/requirements/overview.md
   git check-attr text eol -- src/exact_orb/birth/types.py
   git check-attr text eol -- ephe/sepl_18.se1
   ```

   Ожидаемый результат:

   - для `.gitattributes`, Markdown-файла и Python-файла — `text: auto` и
     `eol: unspecified`;
   - для `ephe/sepl_18.se1` — `text: unset` и `eol: unspecified`.

3. Выполни `git status --short` и сравни его с baseline, полученным после
   переключения ветки. Все исходные пользовательские изменения должны
   сохраниться без изменений; единственная новая запись задачи — изменение
   `.gitattributes`.
4. Выполни `git diff --check`.
5. Запусти полный `pytest`. Это общая регрессионная проверка проекта, а не
   доказательство сохранения конкретного вида окончаний строк: текстовое
   чтение в Python нормализует `CRLF` в `LF`.
6. Покажи `git diff -- .gitattributes`. Diff задачи должен состоять только из
   нескольких строк в `.gitattributes`. Дополнительно убедись по сравнению с
   baseline, что задача не создала изменений в других файлах.

## Итоговый отчёт

Начни с результата, затем укажи:

- содержимое `.gitattributes` до и после;
- результат сравнения `i/` и `w/` до и после;
- список текстовых файлов с `i/crlf` или `i/mixed`, либо явное подтверждение,
  что таких файлов нет;
- результат `git check-attr` для всех четырёх файлов, отдельно подтвердив,
  что `*.se1` осталось вне текстовой нормализации и `eol` нигде не задан;
- сравнение итогового `git status --short` с исходным baseline;
- точные команды и реальные результаты всех проверок;
- число тестов и результат полного `pytest`;
- нужен ли отдельный `git add --renormalize .`; если нужен — сколько файлов
  он предположительно затронет по результату `git ls-files --eol`;
- что не проверялось и какие ограничения остались.

Коммит не создавай: он будет подготовлен отдельной командой после проверки
результата.
