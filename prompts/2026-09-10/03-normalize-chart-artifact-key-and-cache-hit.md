# Промт 3 — нормализация `ChartArtifact`, проверка `calculation_key` и защита cache hit

## Контекст

Продолжается поэтапное устранение независимых источников истины в результате `build_natal`.

Предварительное исследование уже выполнено и сохранено отдельно. На предыдущем этапе нормализован контракт `CalculationResult`:

- `CalculationResult` содержит только `chart: NatalChart`;
- `chart_kind` и `warnings` удалены из `CalculationResult`;
- адаптер расчётного движка возвращает `CalculationResult(chart=chart)`;
- `EngineService` проверяет идентичность результата расчёта:
  - вид карты;
  - UTC datetime;
  - координаты;
  - систему домов;
  - наличие вычислительных блоков согласно `ChartSpec.include`;
- нарушение этих инвариантов преобразуется в типизированную ошибку `ChartCalculationError` с кодом `ENGINE_UNEXPECTED`.

Изменения предыдущего этапа зафиксированы коммитом:

`30eb1f3 fix(calculation): validate chart result identity`

Теперь необходимо нормализовать `ChartArtifact` и усилить проверку расчётного кэша.

## Цель

Устранить необоснованные дубликаты из `ChartArtifact` и гарантировать, что:

1. сериализованный артефакт внутренне согласован;
2. `calculation_key` действительно соответствует данным карты, спецификации и версии расчёта;
3. cache hit используется только тогда, когда артефакт соответствует текущему запросу;
4. повреждённый, устаревший или противоречивый кэш не возвращается потребителю;
5. сохранена существующая fail-open семантика кэша;
6. старые несовместимые записи безопасно приводят к пересчёту;
7. публичное вычислительное поведение вне этой задачи не меняется.

## Обязательные ограничения

Работать только с моделью расчётного артефакта, его кодеком, построением и проверкой cache hit.

В рамках этого этапа:

- не изменять документацию, ADR, requirements и диаграммы;
- не реализовывать полный сквозной инвариант `BuildNatalSuccess`;
- не изменять структуру `StateDelta`;
- не реализовывать режим полного DEBUG-логирования;
- не менять политику логирования;
- не менять алгоритм расчёта карты;
- не менять вычислительную точность;
- не менять нормализацию времени и координат;
- не менять namespace или формат `calculation_key`;
- не добавлять миграции кэша;
- не добавлять compatibility decoder;
- не добавлять новые зависимости;
- не выполнять попутный рефакторинг.

Не использовать старые файлы из `prompts/**` как действующий контракт и не редактировать существующие исторические промты.

Сохранить все несвязанные пользовательские изменения и untracked-файлы.

Не создавать коммит без отдельной команды пользователя.

## Решение о версии схемы

Не вводить поле `artifact_schema_version`.

Не добавлять константу версии схемы артефакта и не создавать параллельную систему версионирования сериализованной модели.

Актуальная Pydantic-модель `ChartArtifact` является единственным контрактом формата расчётного артефакта.

После изменения модели ранее сериализованные записи, не проходящие актуальную валидацию, считаются несовместимыми и обрабатываются по существующей fail-open семантике:

1. запись не используется как cache hit;
2. карта пересчитывается;
3. новый корректный артефакт сохраняется в кэш.

`CalculationVersion` остаётся версией вычислительного поведения.

`calculation_key`, его namespace и алгоритм построения не изменять. Версию схемы артефакта в ключ не добавлять.

## Канонические источники данных

После изменения должны действовать следующие правила.

### `chart_kind`

Сохранить:

- `ChartArtifact.spec.chart_kind` — запрошенный вид карты;
- `ChartArtifact.chart.chart_kind` — вид фактически рассчитанной карты.

Это одно значение в разных контекстах с разной ответственностью:

- `spec.chart_kind` описывает запрос;
- `chart.chart_kind` описывает результат.

Они не должны быть независимыми источниками истины: модель обязана проверять их равенство.

Удалить:

- `ChartArtifact.chart_kind`.

Потребители фактического вида карты должны читать `artifact.chart.chart_kind`.

Потребители спецификации запроса должны читать `artifact.spec.chart_kind`.

### `warnings`

Канонический источник: `ChartArtifact.chart.warnings`.

Удалить `ChartArtifact.warnings`.

Все потребители предупреждений должны читать `artifact.chart.warnings`.

### `ChartSpec`

Канонический источник спецификации артефакта: `ChartArtifact.spec`.

Спецификация сохраняется в артефакте, потому что она описывает параметры запроса и необходима для проверки происхождения результата и попадания в кэш.

### Время и координаты

Для самого сохранённого расчётного артефакта каноническими являются входные данные, содержащиеся в `ChartArtifact.chart`.

Для текущего запроса каноническими остаются разрешённые данные рождения, из которых строится `CalculationInput`.

Cache hit разрешён только при соответствии этих двух представлений после применения уже существующей нормализации `CalculationInput`.

Не вводить новую точность и не изменять правила нормализации.

### Расчётные блоки

Фактически рассчитанные позиции, аспекты, конфигурации и другие блоки хранятся только в `ChartArtifact.chart`.

`ChartArtifact.spec.include` определяет, какие блоки были запрошены.

Модель должна проверять соответствие структуры карты значениям `spec.include`.

## Целевая модель `ChartArtifact`

Привести `ChartArtifact` к следующей логической структуре:

```python
class ChartArtifact(BaseModel):
    calculation_key: str
    spec: ChartSpec
    calculation_version: CalculationVersion
    chart: ArtifactNatalChart
```

Точные типы и стиль объявления должны соответствовать существующему проекту.

В `ChartArtifact` не должно остаться полей:

- `chart_kind`;
- `warnings`;
- `artifact_schema_version`.

Для модели включить запрет неизвестных полей через `extra="forbid"`, если это не нарушает уже действующую общую базовую конфигурацию моделей.

Не добавлять aliases для удалённых полей.

Не выполнять скрытое преобразование старого payload в новый формат.

## Неизменяемость артефакта

Защитить идентификационные поля `ArtifactNatalChart` от прямого изменения после валидации.

Допускается сделать верхнеуровневую Pydantic-модель `ArtifactNatalChart` frozen.

При этом:

- не выполнять рекурсивную переработку всех вложенных моделей движка;
- не менять доменные модели, не относящиеся к артефактному слою;
- сохранить существующую изоляцию объектов между отдельными чтениями из кэша;
- не возвращать разным потребителям один общий изменяемый экземпляр.

Тестами проверить как запрет изменения идентификационного поля карты, так и отсутствие общего mutable-состояния между разными результатами чтения.

## Проекция расчётного входа из карты

Добавить одну чистую функцию артефактного или нейтрального расчётного слоя, которая строит `CalculationInput` из идентификационных полей рассчитанной карты.

Пример логического контракта:

```python
def calculation_input_from_chart(chart: NatalChart) -> CalculationInput:
    ...
```

Функция должна использовать только уже существующие правила создания и нормализации `CalculationInput`.

Она должна проецировать как минимум:

- UTC datetime карты;
- latitude;
- longitude;
- house system;
- остальные поля `CalculationInput`, если они уже являются частью действующего ключевого контракта.

Не дублировать вручную нормализацию времени и координат.

Не размещать эту функцию в слое, который создаст циклическую зависимость между движком, моделью артефакта, кодеком и построителем ключа.

## Проверка `calculation_key`

`ChartArtifact` должен проверять, что его `calculation_key` точно равен ключу, вычисленному из:

1. `CalculationInput`, восстановленного из `artifact.chart`;
2. `artifact.spec`;
3. `artifact.calculation_version`.

Использовать существующий публичный построитель `calculation_key`.

Не ограничиваться проверкой строкового префикса ключа.

Не реализовывать второй алгоритм ключа внутри валидатора.

Не менять namespace ключа, сериализацию полей ключа, порядок полей, правила нормализации, формат digest и `CalculationVersion`.

Если ключ не соответствует содержимому артефакта, модель должна отклонять артефакт.

На публичной границе не должны выходить сырые `ValidationError`, `ValueError` или runtime-исключения.

## Общие инварианты карты и спецификации

Не создавать независимые копии одной и той же проверки в `EngineService`, `ChartArtifact` и cache resolver.

Выделить минимальную чистую функцию проверки согласованности карты со спецификацией, пригодную как минимум для проверки результата движка и валидации `ChartArtifact`.

Функция должна проверять:

- `chart.chart_kind == spec.chart_kind`;
- наличие или отсутствие рассчитываемых блоков согласно `spec.include`;
- другие уже реализованные на предыдущем этапе структурные инварианты между картой и `ChartSpec`.

Проверки идентичности карты конкретному `CalculationInput` также должны переиспользоваться там, где это возможно, без изменения их внешней семантики.

`EngineService` по-прежнему обязан преобразовывать нарушение контракта движка в `ChartCalculationError(code="ENGINE_UNEXPECTED", run_id=...)`.

Не допускать утечки внутренней ошибки общей функции наружу.

## Кодек артефакта

Обновить кодек под новую модель `ChartArtifact`.

Требования:

- кэш по-прежнему хранит opaque `bytes`;
- JSON/gzip и существующий формат контейнера не менять без доказанной необходимости;
- удалённые поля не сериализуются;
- неизвестные поля не принимаются;
- отсутствие удалённых полей является нормой нового формата;
- старый payload с верхнеуровневыми `chart_kind` и `warnings` не адаптируется автоматически;
- несовместимый payload отклоняется типизированным результатом декодирования согласно существующей архитектуре;
- сырые ошибки Pydantic, JSON и gzip не выходят за границу кодека.

Не вводить несколько ветвей декодирования по версии схемы.

## Проверка cache hit

Проверка попадания в кэш должна выполняться сквозным образом.

После чтения и декодирования артефакта проверить:

1. ключ, по которому выполнялось чтение, совпадает с `artifact.calculation_key`;
2. `artifact.calculation_version` совпадает с текущей версией расчёта;
3. `artifact.spec` совпадает с текущей спецификацией;
4. `CalculationInput`, восстановленный из `artifact.chart`, совпадает с текущим разрешённым расчётным входом;
5. карта согласована со спецификацией;
6. внутренний `calculation_key` соответствует карте, спецификации и версии расчёта.

Не считать одного совпадения строкового ключа достаточным доказательством cache hit.

Сравнение входов выполнять через действующую нормализованную модель `CalculationInput`, а не через новые ручные допуски.

## Fail-open семантика кэша

Сохранить существующую fail-open семантику.

Если запись не декодируется, не проходит Pydantic-валидацию, содержит старые или неизвестные поля, имеет неправильный ключ, относится к другой версии расчёта, содержит другую спецификацию либо карту для другого времени, координат, системы домов или состава вычислительных блоков, она не должна возвращаться потребителю.

Вместо этого resolver должен:

1. классифицировать запись существующим способом как повреждённую, устаревшую или непригодную;
2. перейти к обычному cache miss;
3. вызвать движок;
4. построить новый валидный `ChartArtifact`;
5. сохранить его в кэш;
6. вернуть новый результат.

Не добавлять новый публичный код ошибки, если существующая fail-open модель не требует его.

Не превращать несовместимую запись кэша в ошибку всего `build_natal`.

Не удалять запись отдельной destructive-операцией, если существующая запись естественно заменяется через обычный `put`.

## Защита cache miss

На пути cache miss нельзя сохранять артефакт, который противоречит текущему входу.

Если fake или некорректный движок возвращает карту для другого времени, места, набора координат, вида карты, house system или состава вычислительных блоков, resolver не должен выполнять `cache.put`.

Основным ответственным слоем проверки результата движка остаётся `EngineService`.

Валидация создаваемого `ChartArtifact` должна служить дополнительной защитой сериализуемого контракта, а не заменять проверку движка.

Нарушение контракта движка должно завершаться типизированной ошибкой `ENGINE_UNEXPECTED`.

## Адаптация потребителей

Механически обновить только непосредственных потребителей удалённых полей.

Заменить `artifact.chart_kind` на `artifact.chart.chart_kind` или `artifact.spec.chart_kind` в зависимости от ответственности потребителя.

Заменить `artifact.warnings` на `artifact.chart.warnings`.

Проверить как минимум:

- сборку `BuildNatalSuccess`;
- projection/research-код;
- компонентное логирование;
- тестовые fixtures;
- кодек;
- resolver;
- другие найденные через поиск обращения к удалённым полям.

В этом этапе разрешена только механическая адаптация `BuildNatalSuccess`.

Не добавлять здесь полный инвариант согласованности `StateDelta.birth_resolved`, текущего request context, `ChartArtifact.chart` и всего результата `BuildNatalSuccess`.

Этот инвариант должен быть реализован отдельным следующим компонентным этапом.

## Логирование

Не изменять семантику логирования в этом этапе.

После удаления полей `ChartArtifact.chart_kind` и `ChartArtifact.warnings` механически обновить обращения логирования к новым каноническим путям, если такие обращения существуют.

Не реализовывать здесь настройку полного payload logging, отдельный DEBUG-флаг, изменение log level, редактирование или усечение payload и новую privacy-политику.

Полное DEBUG-логирование компонентных сообщений будет отдельным этапом.

## Golden-данные

Не вводить нумерацию формата через `v1`/`v2`, если она подразумевает несуществующий `artifact_schema_version`.

Если в проекте уже есть исторический golden старого артефакта:

- не переписывать его так, чтобы скрыть несовместимость;
- использовать его для теста отклонения старого формата, если это соответствует структуре текущих тестов.

Для актуального формата добавить или обновить отдельный golden только при наличии существующего golden-подхода.

Изменять golden разрешено только как следствие намеренного удаления полей `ChartArtifact.chart_kind` и `ChartArtifact.warnings`.

Не менять числовые результаты карты, допуски или астрономические эталоны.

## Обязательные тесты

Сначала сопоставить требование с существующими тестами и переиспользовать имеющиеся helpers и fixtures.

Добавить или обновить детерминированные тесты для следующих сценариев.

### Модель `ChartArtifact`

1. Валидный артефакт создаётся без верхнеуровневых `chart_kind` и `warnings`.
2. `artifact.chart.chart_kind` остаётся доступен.
3. `artifact.chart.warnings` остаётся доступен.
4. Неизвестные верхнеуровневые поля отклоняются.
5. Старый payload с `chart_kind` и `warnings` отклоняется.
6. Несовпадение `spec.chart_kind` и `chart.chart_kind` отклоняется.
7. Несоответствие структуры карты `spec.include` отклоняется.
8. Неправильный `calculation_key` отклоняется.
9. Правильный ключ принимается.
10. Прямое изменение идентификационного поля `ArtifactNatalChart` после создания запрещено, если модель сделана frozen.

### Кодек

1. Новый артефакт проходит encode/decode round trip.
2. После round trip удалённые поля не появляются.
3. Старый сериализованный payload безопасно отклоняется.
4. Payload с неправильным ключом безопасно отклоняется.
5. Сырые Pydantic/JSON/gzip исключения не выходят наружу.

### Cache hit

1. Валидный артефакт возвращается без вызова движка.
2. Положительный контроль доказывает, что настоящий hit действительно не вызывает движок.
3. Артефакт с картой для другого времени не используется.
4. Артефакт с картой для других координат не используется.
5. Артефакт с другой системой домов не используется.
6. Артефакт с другой спецификацией не используется.
7. Артефакт с другой версией расчёта не используется.
8. Артефакт с внутренним ключом, не соответствующим карте, не используется.
9. Непригодная запись приводит к пересчёту.
10. После пересчёта новый корректный артефакт сохраняется.
11. Потребителю возвращается пересчитанная карта, а не содержимое непригодной записи.

Для сценария внутренне противоречивого артефакта при необходимости сформировать сериализованный payload напрямую, обходя конструктор Pydantic-модели. Это допустимо только в тесте кодека или кэша для моделирования повреждённых bytes.

### Cache miss

1. Корректный результат движка сохраняется в кэш.
2. Карта от другого времени отклоняется.
3. Карта от других координат отклоняется.
4. Карта с другим `chart_kind` отклоняется.
5. Карта с другой системой домов отклоняется.
6. При нарушении контракта движка возвращается `ENGINE_UNEXPECTED`.
7. При нарушении контракта движка `cache.put` не вызывается.

### Изоляция объектов

1. Два чтения одного артефакта не возвращают общий изменяемый объект.
2. Изменение допустимого вложенного mutable-значения в одном результате не влияет на второй результат.
3. Тест не должен обходить публичный контракт произвольной мутацией внутренних приватных полей.

## Критерии готовности

Работа завершена, когда одновременно выполнены условия:

- в `ChartArtifact` нет верхнеуровневых `chart_kind` и `warnings`;
- `artifact_schema_version` не добавлен;
- фактический вид карты читается из `artifact.chart.chart_kind`;
- предупреждения читаются из `artifact.chart.warnings`;
- `spec.chart_kind` и `chart.chart_kind` проверяются на равенство;
- состав вычислительных блоков согласован с `spec.include`;
- `calculation_key` пересчитывается из содержимого карты, спецификации и версии;
- алгоритм и namespace ключа не изменены;
- старые несовместимые артефакты не адаптируются автоматически;
- несовместимый кэш приводит к безопасному пересчёту;
- cache hit проверяет соответствие карты текущему расчётному входу;
- противоречивый результат движка не сохраняется;
- кэш продолжает хранить opaque `bytes`;
- кодек остаётся ответственным за сериализацию и валидацию;
- нет утечки сырых runtime-исключений через публичные границы;
- не изменены документация, ADR и политика логирования;
- целевые, связанные и полные тесты проходят.
