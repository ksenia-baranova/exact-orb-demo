# Промт 4 — сквозные инварианты `BuildNatalSuccess`

## Контекст

Продолжается поэтапное устранение независимых источников истины в результате `build_natal`.

На предыдущих этапах:

1. `CalculationResult` нормализован до одного поля `chart: NatalChart`.
2. `EngineService` проверяет соответствие рассчитанной карты разрешённым данным рождения, `ChartSpec`, виду карты, системе домов и составу вычислительных блоков.
3. `ChartArtifact` нормализован до структуры:

   ```python
   class ChartArtifact(BaseModel):
       calculation_key: str
       spec: ChartSpec
       calculation_version: str
       chart: ArtifactNatalChart
   ```

4. Из `ChartArtifact` удалены верхнеуровневые дубликаты `chart_kind` и `warnings`.
5. `ChartArtifact` самостоятельно проверяет соответствие карты спецификации, состав вычислительных блоков и точное соответствие `calculation_key` карте, спецификации и версии расчёта.
6. Cache hit дополнительно проверяет соответствие карты текущему нормализованному `CalculationInput`.

Поле `artifact_schema_version` намеренно не вводилось.

Теперь необходимо закрыть исходный воспроизводимый дефект на уровне итогового результата `BuildNatalSuccess`.

Сейчас можно создать два по отдельности валидных объекта:

- `StateDelta`, содержащий одни разрешённые данные рождения;
- `ChartArtifact`, содержащий карту для другого времени или других координат.

Если их `ChartSpec` совпадает, текущая модель `BuildNatalSuccess` может не обнаружить противоречие.

## Цель

Сделать `BuildNatalSuccess` агрегатной границей, которая гарантирует согласованность:

1. полностью заполненного `StateDelta`;
2. `StateDelta.birth_resolved`;
3. `StateDelta.base_chart_spec`;
4. `ChartArtifact.spec`;
5. `ChartArtifact.chart`;
6. `ChartArtifact.calculation_version`;
7. `ChartArtifact.calculation_key`.

После изменения невозможно собрать формально успешный результат, в котором разрешённые данные рождения относятся к одному расчёту, а артефакт — к другому.

## Ответственный слой

Полный сквозной инвариант принадлежит `BuildNatalSuccess`.

Причина:

- `StateDelta` является общим контрактом замены состояния и не знает о расчётном артефакте;
- `ChartArtifact` проверяет внутреннюю согласованность собственного содержимого, но не знает о конкретном `StateDelta`;
- `EngineService` проверяет только непосредственный результат движка;
- cache resolver проверяет конкретный запрос, но другие реализации `ChartArtifactPort` могут возвращать самостоятельно созданные артефакты;
- только `BuildNatalSuccess` одновременно владеет итоговым `artifact` и подготовленным к фиксации `delta`.

Не переносить зависимость на `ChartArtifact` в `StateDelta`.

Не добавлять состояние сессии или application-типы в расчётный слой.

## Обязательные ограничения

В рамках этого этапа:

- не изменять структуру `StateDelta`;
- не добавлять поля в `BuildNatalSuccess`;
- не возвращать разрешённые данные рождения внутрь `ChartArtifact`;
- не добавлять `birth_resolved`, `BirthInput`, `place_id`, `tz_id` или `canonical_place` в `calculation_key`;
- не вводить `artifact_schema_version`;
- не менять алгоритм или namespace `calculation_key`;
- не менять нормализацию `CalculationInput`;
- не менять точность времени и координат;
- не менять модель `CalculationResult`;
- не менять формат сериализации артефакта;
- не менять cache hit/miss семантику;
- не реализовывать полный DEBUG-режим логирования;
- не менять политику логирования;
- не изменять ADR, requirements и диаграммы;
- не добавлять новые зависимости;
- не выполнять попутный рефакторинг.

Не редактировать старые файлы из `prompts/**` и не считать их действующим контрактом.

Сохранить несвязанные пользовательские изменения и существующие untracked-файлы.

Не создавать коммит без отдельной команды пользователя.

## Канонические представления

### Разрешённые данные рождения

В контексте результата `build_natal` каноническим источником разрешённых данных рождения является:

```python
BuildNatalSuccess.delta.birth_resolved
```

Эти данные предназначены для записи в состояние сессии.

### Расчётный вход артефакта

Каноническим представлением входа, по которому была рассчитана карта, является проекция:

```python
calculation_input_from_chart(BuildNatalSuccess.artifact.chart)
```

Карта не должна дополнительно хранить `ResolvedBirthData` целиком.

### Спецификация

Запрошенная спецификация результата хранится в `BuildNatalSuccess.delta.base_chart_spec`.

Спецификация сохранённого артефакта хранится в `BuildNatalSuccess.artifact.spec`.

Это представления в разных bounded context:

- `delta.base_chart_spec` — намерение, сохраняемое в состоянии;
- `artifact.spec` — спецификация, по которой создан расчётный артефакт.

Они сохраняются оба, но `BuildNatalSuccess` обязан проверять их точное равенство.

### Вид карты

Вид карты не должен отдельно храниться в `BuildNatalSuccess`.

Он определяется через:

- `delta.base_chart_spec.chart_kind` — запрошенный вид;
- `artifact.chart.chart_kind` — фактический вид.

Их непосредственное равенство уже следует из:

1. равенства `artifact.spec` и `delta.base_chart_spec`;
2. внутреннего инварианта `ChartArtifact`, связывающего `artifact.spec` и `artifact.chart`.

Не дублировать эту же проверку без необходимости.

Дополнительно вид карты должен соответствовать разрешённым данным рождения:

```python
expected_chart_kind = "cosmogram" if delta.birth_resolved.time_unknown else "natal"
```

### Предупреждения

Предупреждения разрешения остаются в `delta.birth_resolved.warnings`.

Предупреждения расчёта остаются в `artifact.chart.warnings`.

Это разные значения с разной ответственностью. Не объединять их и не требовать их равенства.

## Сравнение разрешённых данных с картой

Для сравнения использовать существующие проекции:

```python
calculation_input_from(delta.birth_resolved)
calculation_input_from_chart(artifact.chart)
```

`BuildNatalSuccess` должен требовать:

```python
calculation_input_from(delta.birth_resolved) == calculation_input_from_chart(
    artifact.chart
)
```

Такое сравнение должно охватывать только поля действующего расчётного входа:

- UTC datetime;
- latitude;
- longitude.

Использовать нормализацию, уже встроенную в `CalculationInput`.

Не сравнивать значения с собственными ручными округлениями или допусками.

Не менять действующую нормализацию секунд, микросекунд и координат в рамках этого этапа.

## Данные, которые нельзя ошибочно сравнивать с картой

Не добавлять в карту и не включать в расчётный ключ:

- `BirthInput.place_id`;
- `ResolvedBirthData.canonical_place`;
- `ResolvedBirthData.tz_id`;
- `ResolvedBirthData.utc_offset_seconds`;
- предупреждения разрешения;
- presentation-данные исходного ввода.

Эти поля нужны для разрешения, восстановления UI и состояния сессии, но не определяют числовой результат после получения UTC datetime и координат.

Невозможность восстановить `place_id` из `canonical_place` не является дефектом этого этапа.

Не пытаться сравнивать `place_id` и `canonical_place` строковыми эвристиками.

## Инвариант вида карты

`BuildNatalSuccess` должен проверять:

```python
expected_chart_kind = "cosmogram" if delta.birth_resolved.time_unknown else "natal"
delta.base_chart_spec.chart_kind == expected_chart_kind
```

Внутренняя модель `ChartArtifact` уже гарантирует:

```python
artifact.chart.chart_kind == artifact.spec.chart_kind
```

А `BuildNatalSuccess` должен гарантировать:

```python
artifact.spec == delta.base_chart_spec
```

В результате вид карты становится согласованным по всей цепочке без отдельного поля-дубликата.

## Инвариант `calculation_key`

После проверки разрешённых данных и спецификации пересчитать ожидаемый ключ через существующий публичный построитель:

```python
expected_key = calculation_key(
    calculation_input_from(delta.birth_resolved),
    delta.base_chart_spec,
    artifact.calculation_version,
)
```

Затем потребовать:

```python
artifact.calculation_key == expected_key
```

Не реализовывать алгоритм ключа повторно, не вычислять digest вручную и не проверять только строковый префикс.

Не добавлять в ключ новые поля.

Эта проверка является сквозной: она связывает данные, подготовленные для сохранения в состоянии, со спецификацией и версией артефакта.

Внутренняя проверка `ChartArtifact` должна остаться. Она отвечает за самосогласованность артефакта.

Проверка `BuildNatalSuccess` отвечает за согласованность артефакта с `StateDelta`.

Это разные ответственности, а не два независимых источника истины.

## Целевой валидатор `BuildNatalSuccess`

Логический порядок проверки должен быть следующим:

1. убедиться, что `StateDelta` полностью заполнен;
2. получить `birth_input`, `birth_resolved` и `base_chart_spec`;
3. проверить равенство `artifact.spec` и `base_chart_spec`;
4. проверить соответствие `base_chart_spec.chart_kind` признаку `birth_resolved.time_unknown`;
5. построить `CalculationInput` из `birth_resolved`;
6. построить `CalculationInput` из `artifact.chart`;
7. проверить равенство этих входов;
8. пересчитать ожидаемый `calculation_key`;
9. проверить равенство ожидаемого и фактического ключа.

Не обращаться к nullable-полям `StateDelta` до проверки его заполненности.

Не использовать `assert` для доменных инвариантов.

Нарушение должно приводить к ошибке Pydantic-валидации `BuildNatalSuccess`.

Сообщения ошибок должны точно указывать нарушенную связь, но не включать полный payload, координаты, дату рождения или содержимое карты.

Примеры допустимых сообщений:

```text
artifact.spec must equal delta.base_chart_spec
delta.base_chart_spec.chart_kind must match delta.birth_resolved.time_unknown
artifact.chart calculation input must equal delta.birth_resolved calculation input
artifact.calculation_key must match delta birth data, spec, and calculation version
```

## Поведение `BuildNatalHandler`

Основной успешный путь `BuildNatalHandler` менять не требуется:

1. разрешить `BirthInput`;
2. определить `chart_kind` по `resolution.time_unknown`;
3. построить `NatalChartSpec`;
4. получить `ChartArtifact`;
5. построить `StateDelta`;
6. создать `BuildNatalSuccess`.

Не дублировать все новые проверки вручную внутри handler.

`BuildNatalSuccess` остаётся последней агрегатной границей успешного результата.

Если `ChartArtifactPort` возвращает внутренне валидный, но чужой артефакт:

- `BuildNatalSuccess` должен отклонить результат;
- успешный outcome не должен быть возвращён;
- существующее логирование ошибки стадии `build_result` должно сохраниться.

В этом этапе не менять существующую классификацию такого программного нарушения на новый `CalculationFailed`.

Не вводить новый публичный error code без отдельного архитектурного решения.

Не перехватывать `ValidationError` только ради сокрытия нарушения контракта.

## `BirthInput` и `ResolvedBirthData`

`StateDelta.birth_input` и `StateDelta.birth_resolved` сохраняются одновременно, потому что имеют разные ответственности:

- `birth_input` нужен для представления исходного пользовательского ввода;
- `birth_resolved` содержит нормализованные факты для расчёта и восстановления состояния.

В рамках этого этапа не пытаться полностью доказать, что `birth_resolved` был получен именно из `birth_input`, потому что `place_id` не хранится в `ResolvedBirthData`, `canonical_place` не является обратимым представлением `place_id`, а разрешение timezone и места принадлежит `BirthDataResolver`.

Не добавлять эвристические проверки места.

Если существующий контракт однозначно гарантирует связь:

```python
(delta.birth_input.birth_time is None) == delta.birth_resolved.time_unknown
```

её можно закрепить отдельным инвариантом только после подтверждения действующими requirements, resolver-кодом и тестами.

Не вводить эту проверку только на основании предположения.

## Обязательные тесты модели

Добавить или обновить детерминированные тесты `BuildNatalSuccess`.

### Положительный контроль

1. Согласованная пара `artifact + delta` принимается.
2. Проверить, что тест использует одинаковый нормализованный расчётный вход, одинаковую спецификацию и корректный ключ.
3. Положительный контроль должен доказывать, что валидатор принимает обычный natal-результат.
4. Добавить положительный контроль для cosmogram при `time_unknown=True`.

### Полнота `StateDelta`

Сохранить тесты, проверяющие отклонение `RESET_DELTA` и частично заполненного `StateDelta`, если его возможно сформировать только через контролируемый test seam.

Не ослаблять собственный инвариант полноты `StateDelta`.

### Спецификация

Проверить отклонение результата, когда:

- `artifact.spec != delta.base_chart_spec`;
- вид карты совпадает, но отличается другой значимый параметр спецификации, например `include` или `near_interception_threshold`.

Тест не должен ограничиваться только различием `chart_kind`.

### Время

Создать внутренне валидный `ChartArtifact` для одного UTC datetime и внутренне валидный `StateDelta` для другого UTC datetime при одинаковой спецификации.

`BuildNatalSuccess` обязан отклонить такую пару.

Артефакт должен быть самосогласован и иметь корректный ключ для собственного времени, чтобы тест проверял именно сквозной инвариант результата.

### Координаты

Отдельно проверить несовпадение latitude и longitude.

Для каждого теста артефакт должен быть внутренне валиден, его ключ должен соответствовать его собственной карте, `StateDelta` должен быть внутренне валиден, а различие должно находиться между `delta.birth_resolved` и `artifact.chart`.

Не использовать различия меньше действующей точности нормализации как доказательство дефекта.

### Нормализованное равенство

Добавить положительный тест, если существующие fixtures позволяют это сделать без изменения доменного контракта: два значения, нормализующиеся в один `CalculationInput`, должны считаться согласованными.

Не вводить новые правила округления ради этого теста.

### `time_unknown` и вид карты

Проверить отклонение:

- `time_unknown=True` с `chart_kind="natal"`;
- `time_unknown=False` с `chart_kind="cosmogram"`.

Проверить принятие:

- `time_unknown=True` с `chart_kind="cosmogram"`;
- `time_unknown=False` с `chart_kind="natal"`.

### `calculation_key`

Проверить, что `BuildNatalSuccess` отклоняет объект, в котором ключ не соответствует `delta.birth_resolved`, `delta.base_chart_spec` или `artifact.calculation_version`.

Поскольку обычный конструктор `ChartArtifact` уже не позволяет создать неправильный ключ, в regression-тесте разрешено использовать контролируемый Pydantic test seam:

```python
artifact.model_copy(update={"calculation_key": foreign_key})
```

или эквивалентный способ обхода валидации.

Такой обход допустим только для моделирования противоречивого объекта, пришедшего через компонентную границу.

Положительный контроль с обычным валидным `ChartArtifact` обязателен.

## Адаптация существующих тестов

Существующие fixtures должны создавать внутренне валидные объекты.

Не исправлять новый regression-тест подгонкой `delta.birth_resolved` к чужой карте.

Не использовать один fixture одновременно как данные A и данные B, если тест должен доказать их различие.

Для каждого негативного теста явно проверить положительные предпосылки:

- артефакт самостоятельно валиден;
- его ключ соответствует его собственной карте;
- спецификации совпадают там, где проверяется именно различие входов;
- карта действительно содержит отличающееся время или координаты.

## Архитектурные границы

Сохранить следующие зависимости:

- `session.state` не импортирует `calculation.types`;
- `StateDelta` не знает о `ChartArtifact`;
- расчётный слой не импортирует `application.results`;
- `BuildNatalSuccess` может использовать публичные расчётные проекции и построитель ключа;
- `calculation_key` остаётся чистой функцией;
- кэш продолжает хранить opaque `bytes`;
- LLM и пользовательский сырой текст не входят в расчётный путь.

Не ослаблять `tests/test_module_boundaries.py`.

Если новый допустимый импорт меняет точный import upper bound, обновить тест только для явно добавленного модуля. Не расширять разрешения до целого слоя.

## Логирование

Не реализовывать в этом этапе полный DEBUG payload mode, конфигурационный флаг полного логирования, новые уровни логирования, редактирование или усечение сообщений и новую privacy-политику.
