## 2. Сохрани принятые границы R3.2

Зафиксируй их в плане без возврата к отменённым предложениям исходной R3:

1. Новый внешний union живёт в `application/application_results.py` и сразу
   использует `handler_status`. Миграции существующего `build_status` нет.
2. `application/results.py`, общий `outcomes.py` и agent-каркас не изменяются.
   Calculation error codes сохраняют `str` и fallback для неизвестного кода.
3. RunContext создаётся входной границей; Orchestrator не заменяет объект и
   не создаёт fallback. Новое поле deadline не требует изменения сигнатуры
   `RunContext.new()`.
4. Политика отказов — чистая функция/таблица в application. Она не пишет логи;
   предупреждение о неизвестном коде пишет вызывающий код. Модели результата
   сохраняют собственную валидацию согласованных полей.
5. События пишутся штатным logger. Отдельный telemetry port, no-op recorder,
   registry активных run_id и общие counters Orchestrator не вводятся.
6. Средства записи событий готовятся заранее. Каждый реализуемый путь сразу
   получает свои lifecycle-события; группа 8 проверяет их полноту и порядок.
7. Первая реализация commit уже содержит защищённую единицу исполнения,
   сильную ссылку на задачу, ожидание после отмены и отложенный проброс
   CancelledError. Одного `asyncio.shield()` недостаточно. Retry добавляется
   внутрь этой же структуры.
8. Запреты проверяются тестами до реализации: нет save после non-success,
   нет rebase, нет второго load между save, нет retry после Superseded,
   максимум два save. Проверяется журнал вызовов и публичный результат;
   каждый отрицательный сценарий имеет положительный контроль прохождения
   нужной ветки.
9. Session bootstrap/restore, HTTP/cookie и клиентское применение версий
   относятся к внешним срезам. Резервирование Idempotency-Key удалено;
   полноценная идемпотентность и BuildAttempt отложены.
10. Нагрузочный профиль 1 не зависит от admission controller. Профиль 2
    требует конечного admission limit и политики очереди/отказа.

## 4. Построй зависимости и контрольные точки

Для каждой карточки запиши:

```text
ID и единственный проверяемый результат.
Зависимости: какие результаты должны существовать до начала.
Закрывает: номера AC/FR и конкретный аспект каждого составного требования.
Разрешено менять: точные пути.
Запрещено менять: соседние контракты, компоненты, ранее принятые проверки.
Проверка готовности: команда и наблюдаемое свидетельство успеха.
```

Не считай порядковую нумерацию достаточной картой зависимостей:

- 1.4 подготавливает реальные функции logging, но ещё не доказывает ровно
  один terminal event на execute; это проверяется после сборки Orchestrator;
- 2.2 должен быть готов до использующих его моделей и обработчиков отказов;
- тестовые задания 3–6 опираются на ещё собираемый публичный execute;
  укажи, какие проверки смогут пройти только после 6.4;
- 6.2 содержит основной cancellation contract сразу, без no-op или «пустой»
  семантики; 7.2 расширяет его retry, 9.1 проверяет дополнительные гонки;
- 8.1–8.2 проверяют уже встроенные события, а не переносят всю
  инструментализацию на конец реализации;
- 10.4 зависит от рабочего retry и реального ContextService;
- 10.6 можно выполнять без готового HTTP-приложения;
- 10.7 имеет отдельную внешнюю предпосылку admission controller.

Группы 3–6 образуют первый собираемый application-flow. До 6.4 не подключай
его к transport и не объявляй готовым Orchestrator. Не планируй фиктивные
ответы, no-op save, skip/xfail или заглушки ради промежуточного зелёного CI.
Небольшой промт не обязан быть отдельным готовым к выпуску коммитом.

Различай «написан тест», «ожидаемо падает», «не может быть исполнен до сборки
API» и «прошёл». Ошибка импорта отсутствующего API сама по себе не доказывает
чувствительность всех негативных проверок. Укажи первый этап, где требование
можно проверить через законченный публичный execute.

Если найденный дефект относится к прошлому implementation-этапу, отметь
возврат в этот этап. Не превращай тестовый промт в разрешение менять весь код.

## 5. Составь матрицу приёмки

Возьми актуальный §15 R3.2 непосредственно из рабочего файла. Создай ровно
36 основных строк: AC-1–AC-36, без пропусков, дубликатов и перенумерации.
В каждой строке укажи:

| Поле | Содержание |
|---|---|
| ID и требование | Номер с обозначением R3.2 и точная формулировка AC |
| Реализация | Промт-владелец; для составного AC — аспект каждого владельца |
| Проверка | Промт с тестом и первая контрольная точка его полного прохождения |
| Test evidence | Существующий node id либо явно помеченный планируемый файл/сценарий |
| Текущее покрытие | Что уже проверяет соседний компонент и чего ещё не доказывает |
| Статус / зависимости | Целевой, частично покрытый соседними тестами или внешний срез |

Отдельно добавь строки для требований без собственного AC: FR-05 о полноте
и неизменяемости registry, FR-21 и §11.1 о deadline, session P3-AC-11/12.
Не придумывай новые номера AC внутри R3.2.

Обязательно отрази:

- **AC-28** — отдельная проверка отсутствия общего mutable request state с
  контролируемым чередованием через Event/barrier;
- **AC-32** — порядок последнего stage/attempt event, terminal event и
  возврата/CancelledError; это не номер теста изоляции;
- **AC-34** — клиентский срез, не выполнен тестами Orchestrator;
- **AC-35** — application load profile без обязательного admission controller;
- **AC-36** — profile с конечным admission limit и отдельной зависимостью;
- отрицательные требования — spy/recording fake и положительный контроль,
  без проверки случайных private fields и без sleep.

### Обязательный сценарий 10.4

Опиши его явно, со ссылкой на session requirements §8.4, пункт 12:

1. Реальные Handler и ContextService обслуживают Orchestrator; за
   ContextService находится persistence с настоящим сохранением состояния.
2. Тестовая обёртка в первой попытке применяет реальный CAS, а затем
   однократно выбрасывает типизированный SessionPersistenceError.
3. ContextService возвращает StateCommitFailed; Orchestrator сам начинает
   повтор с original expected и тем же объектом delta.
4. При отсутствии конкурирующей записи повтор получает AlreadyApplied;
   внешний результат — ApplicationAlreadyApplied.
5. Версия за обе попытки растёт на единицу, save вызван дважды, Handler один
   раз; нет промежуточного load и rebase.

Сверь существующий
`tests/session/test_context.py::test_sequential_retry_keeps_original_expected_and_commits_once`.
Он проверяет последовательность Committed → AlreadyApplied на уровне
ContextService; сам по себе не доказывает потерю подтверждения и автоматический
retry Orchestrator. Не заменяй новый сценарий мокированным ответом ContextService.
Конкурентное другое намерение и Superseded относятся к отдельному сценарию.

## Проверки этапа 0.1

До работы получи read-only baseline:

```powershell
git branch --show-current
git rev-parse HEAD
git status --short
```

После записи документа проверь:

- перечислены все 36 рабочих ID и все AC-1–AC-36;
- каждой карточке назначены зависимости, AC/FR, точный allowlist, запреты и
  проверка готовности;
- все ссылки на существующие файлы разрешаются; планируемые пути выделены
  отдельно и не выдаются за существующие тесты;
- 10.6 и 10.7 не имеют общей ложной блокировки admission controller;
- AC-34 и внешняя предпосылка AC-36 не объявлены выполненными;
- новый план не разрешает изменение outcomes.py, legacy orchestration,
  добавление telemetry port или резервирование Idempotency-Key;
- конечный diff относительно исходного рабочего дерева ограничен одним
  разрешённым документом.

```powershell
git diff --check
git diff -- docs/project_management/application_orchestrator_implementation_plan.md
git status --short
```

Если документ новый и untracked, дополнительно прочитай его целиком и проверь
пробелы, code fences и ссылки: обычный `git diff` не показывает untracked-файл.
Не добавляй его в index ради проверки.

На этапе 0.1 pytest, нагрузочные и сетевые smoke-тесты не запускай: здесь
проверяется документ плана. В нём укажи будущие прогоны точными командами с
проектным `.venv\Scripts\python.exe`, целевые → связанные → полный pytest.
Используй `-B` и `-p no:cacheprovider`, как в существующем процессе проекта.
Наличие этих команд в плане не означает их выполнения.
