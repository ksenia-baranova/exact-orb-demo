## Требуемое покрытие

Добавь небольшие самостоятельные тесты; одинаковые случаи параметризуй.
Все новые имена содержат `deadline`, чтобы отделить их точным pytest-фильтром.

| Сценарий | Проверка публичного поведения |
|---|---|
| Поле не передано | `RunContext(run_id=..., started_at=...).deadline is None` |
| Передано `deadline=None` | Создание успешно; `run.deadline is None` |
| Передан aware UTC deadline | Значение сохранено и равно переданному; UTC offset равен нулю |
| Передан naive datetime | Конструктор поднимает `pydantic.ValidationError`, относящийся к полю `deadline` |
| Передан ненулевой UTC offset | Положительный и отрицательный offset отклоняются как ошибка `deadline` |
| Deadline раньше started_at | Создание успешно; значение не отброшено и не заменено |
| Deadline равен started_at | Создание успешно; дополнительного ограничения порядка дат нет |
| Вызван `RunContext.new()` без аргументов | Вызов сохраняется; новый `deadline` равен `None` |

Для UTC используй правило текущего `started_at`: `tzinfo` задан и
`utcoffset() == timedelta(0)`. Не требуй identity `tzinfo is timezone.utc`.
Положительный UTC-сценарий служит контролем для негативных случаев.

Во всех прямых конструкторах передавай заведомо валидные `run_id` и UTC
`started_at`. В проверках исключения анализируй `ValidationError.errors()`:
ошибка должна относиться к `deadline`, а не к ошибочному соседнему полю.
Не привязывайся к полному тексту сообщения или имени приватного валидатора.

В тестах сохранения явного deadline дополнительно проверь, что переданные
`run_id` и `started_at` не изменились. Старые тесты UUID/new() не дублируй:
новая проверка `new()` добавляет только обязанность `deadline is None`.

Используй фиксированные UUID/время и существующие test helpers/константы,
где они подходят. Для сравнения deadline со started_at не читай реальные
часы и не используй `sleep`. Вызов реального `new()` нужен только для
проверки прежнего способа создания; его timestamp с текущим временем не
сравнивай.

## Границы и защита от ложного успеха

- Измени только `tests/test_run_context.py`: новые тесты и необходимые им
  импорты/локальные helpers. Не рефактори существующие тесты и их logging setup.
- Создавай настоящую модель `RunContext`. Не мокай её, не добавляй поле через
  monkeypatch, subclass, `model_construct` или `model_copy(update=...)`.
- Проверяй `run.deadline` напрямую. `getattr(run, "deadline", None)` скрывает
  отсутствие поля и для этих тестов не подходит.
- Не перехватывай `AttributeError` как ожидаемое успешное поведение теста.
  Целевой контракт требует существующего поля; сейчас отсутствие поля должно
  проявиться падением assertion/доступа.
- Не используй `skip`, `xfail` или ветвление по наличию поля для зелёного прогона.
- Не меняй `src/exact_orb/run_context.py` ради прохождения новых тестов.
- Не добавляй тесты исполнения Orchestrator, injected clock, retry или
  принудительного timeout. Эти обязанности находятся в следующих этапах.

## Проверки при выполнении

Из корня репозитория зафиксируй исходное состояние:

```powershell
git branch --show-current
git status --short
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_run_context.py -q
```

После добавления тестов запусти весь целевой файл:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_run_context.py -q
```

При отсутствии реализации ожидаются падения новых тестов из-за отсутствующего
поля либо отсутствующей UTC-валидации. Проверь реальную причину каждого
падения. Import/collection error, отсутствующая зависимость или ошибка fixture
не доказывают проверку нового контракта. Не исправляй окружение изменением
чужих файлов в рамках этого задания.

Если есть ожидаемые падения новых тестов, отдельно подтверди старое покрытие:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_run_context.py -k "not deadline" -q
```

В этом случае зафиксируй red и закончи этап 1.1. Связанный и полный прогоны
переходят к этапу 1.2 после реализации поля. Ожидаемый red не даёт разрешения
самостоятельно выполнить 1.2. Прежние тесты должны сохранять baseline;
неожиданные изменения их результатов разбери и отрази отдельно.

Если целевой файл уже полностью зелёный на текущем checkout, проверь, что
новые тесты действительно собраны и проверяют требования. Затем выполни
связанный набор R и полный набор F из плана:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_run_context.py tests/application tests/session tests/test_module_boundaries.py -q
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider -q
```

Полный набор запускается только после успешного связанного. Никаких
дополнительных сетевых/платных smoke или новых quality gates.

Заверши проверкой границ изменения:

```powershell
git diff --check
git diff -- tests/test_run_context.py
git status --short
```

Сопоставь итоговое дерево с исходным: задача должна добавить изменения только
в разрешённый тестовый файл, сохранив все предшествующие правки.
