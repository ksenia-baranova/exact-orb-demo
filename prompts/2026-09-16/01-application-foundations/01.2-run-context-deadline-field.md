## Требуемое изменение

1. Добавь поле:

   ```python
   deadline: datetime | None = None
   ```

   Пропущенное значение и явно переданный `None` означают отсутствие
   application deadline. Поле должно существовать в обоих случаях.

2. Добавь отдельную валидацию поля `deadline` средствами используемого
   Pydantic. Для `None` верни `None`. Для datetime примени то же UTC-правило,
   которое сейчас используется для `started_at`:

   ```text
   value.tzinfo is not None
   value.utcoffset() == timedelta(0)
   ```

   Naive datetime и aware datetime с ненулевым offset должны отвергаться.
   Нарушение выражается обычным `ValueError` внутри field validator и
   становится `pydantic.ValidationError` с location `deadline`.
   Сообщение должно объяснять требование timezone-aware UTC.

3. Сохраняй валидное значение deadline. Не требуй identity
   `tzinfo is timezone.utc`: именованная зона с нулевым offset тоже допустима.
   Не превращай недопустимый offset в UTC через `astimezone()` и не подставляй
   timezone для naive datetime — это скрыло бы некорректный вход.

4. Не сравнивай deadline со `started_at` или текущим временем. Значения раньше,
   равные и позже `started_at` допустимы. Этот модуль хранит бюджет операции,
   а решение о повторе commit будет принимать Orchestrator.

5. Сохрани сигнатуру и существующее поведение `RunContext.new()` без новых
   параметров. Вызов без аргументов продолжает создавать UUID и UTC
   `started_at`; `deadline=None` получается из default нового поля.

## Границы реализации

- Существующий validator `started_at`, его поведение и сообщение не меняются.
- Не рефактори общую валидацию времени и не переноси её в другой модуль.
- Не меняй конфигурацию модели: frozen, extra, strict, assignment validation
  и прочие настройки не относятся к этому срезу.
- Не добавляй новые зависимости, clock, таймеры, автоматическую отмену,
  timeout-result, fallback RunContext или логи.
- Не меняй Handler, resolver, ContextService, Orchestrator и способы передачи
  RunContext между ними.
- Не переписывай и не ослабляй тесты 1.1, не добавляй skip/xfail. Они описывают
  согласованный контракт, а не текущую реализацию.
- Документация уже задаёт целевой контракт. Её статус и матрица плана
  синхронизируются отдельным этапом; этот промт их менять не разрешает.

## Проверки после изменения

Выполняй последовательно, из корня репозитория.

### 1. Целевой файл

```powershell

```

Должны пройти и новые случаи deadline, и прежние проверки RunContext/resolver.
Ожидаемый состав при неизменном тестовом файле — 21 случай; отчитай фактическое
число, а не предполагаемое. Ошибка collection/setup не считается проверкой
контракта.

### 2. Связанный набор R — после успешного целевого

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_run_context.py tests/application tests/session tests/test_module_boundaries.py -q
```

### 3. Полный набор F — после успешного связанного

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider -q
```

Если обнаружится падение, установи причину. Исправляй только дефект текущего
изменения в разрешённом файле. Несвязанные дефекты и проблемы окружения
зафиксируй отдельно, не меняя соседние файлы или тесты ради зелёного результата.
Без фактического успешного прогона не объявляй соответствующий набор пройденным.
Новые quality gates, сетевые и платные smoke-тесты не запускай.

### 4. Объём изменения


Сопоставь содержимое файлов с baseline, а не только список modified:
