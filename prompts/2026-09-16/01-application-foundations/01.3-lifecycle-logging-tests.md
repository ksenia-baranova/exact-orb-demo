## Задача

Напиши тесты компактных функций записи lifecycle-событий будущего
`ApplicationOrchestrator`. Проверяй настоящие записи штатного Python logger
через `caplog`: вид события, поля, значения и уровень.

Это тестовый этап перед реализацией `operation_logging.py` в промте 1.4.
Реализацию функций, сам Orchestrator и подключение событий к application-flow
сейчас не добавляй. Не вводи telemetry port, recorder или реестр операций.

Работай в текущем checkout, сохрани все предшествующие изменения, включая
`RunContext.deadline` и его тесты. Не создавай ветку, коммит, push или PR.
Не выполняй следующие карточки плана автоматически.

## Проверяемый интерфейс

Целевой модуль — `exact_orb.application.operation_logging`.
Зафиксируй в тестах следующий небольшой внутренний API для парного этапа 1.4.
Это функции логирования, а не новый внешний application-контракт.

Все аргументы — keyword-only. Все функции синхронные, возвращают `None`.
Logger модуля: `exact_orb.application.operation_logging`.

| Функция | Аргументы |
|---|---|
| `log_operation_started` | `run_id`, `command_type` |
| `log_stage_finished` | `run_id`, `stage`, `outcome`, `duration_ms`, `state_version=None` |
| `log_commit_attempt_finished` | `run_id`, `attempt`, `outcome`, `detail_code`, `duration_ms`, `state_version=None` |
| `log_operation_finished` | `run_id`, `orch_status`, `handler_status`, `context_status`, `code`, `detail_code`, `state_version`, `load_duration_ms`, `handler_duration_ms`, `commit_duration_ms`, `commit_attempts`, `commit_error_codes`, `delivery_cancelled` |
| `log_operation_cancelled` | `run_id`, `cancelled_stage`, `load_duration_ms`, `handler_duration_ms` |

Типы значений: `run_id: UUID`; версии — `int | None`; длительности — `float`
для завершённых stage/attempt и `float | None` для terminal; `attempt: 1 | 2`;
`commit_attempts: 0 | 1 | 2`; `commit_error_codes: tuple[str, ...]`;
`delivery_cancelled: bool`. Остальные значения — нормализованные строки,
`detail_code` также допускает `None`.

Две последние функции записывают один и тот же вид события
`application_operation_finished`, но с разными наборами полей. Значения
`terminal_kind` и `commit_attempts=0` для отмены задаёт функция, а не вызывающий.

Функции получают уже подготовленные компактные значения. Не передавай им
`ApplicationResult`, command, snapshot, outcome-объекты, исключения или payload.
Модели `ApplicationResult` появятся на этапе 2; зависимости от них здесь нет.
Подсчёт попыток, накопление ошибок, измерение времени и сумма длительностей
принадлежат будущему `execute()`.

## Обязательные проверки

### 1. Общие свойства записей

- Каждый вызов функции создаёт ровно одну запись соответствующего lifecycle
  event. Это утверждение о функции, не о целом `execute()`.
- Запись содержит имя события и переданный `run_id`. Используй `RUN_ID` и
  `RUN_ID_B` из fixtures, чтобы проверить сохранение разных входных значений.
- Захватывай реальный logger; не подменяй функции записи, `Logger.log`,
  `Logger.info` или `Logger.warning` моками. `caplog` собирает настоящие записи
  logging: тест проверяет их содержимое и уровень. Проверки одного факта
  «вызвали logger.info» для этого недостаточно.
- Проверяй поля в выводимом сообщении, как в существующем logging-контракте
  проекта. Одних `LogRecord.extra`, невидимых штатному formatter, недостаточно.
  Не требуй нового JSON formatter и не меняй `logging_setup.py`.
- Не фиксируй несущественные пробелы, порядок полей и количество знаков после
  запятой. Сопоставляй полные значения полей, а не неоднозначные подстроки.

### 2. Начало операции

`log_operation_started(run_id=..., command_type="BuildNatalCommand")` создаёт
`application_operation_started` уровня `INFO` с `command_type` и `run_id`.
В прикладном наборе полей нет состояния сессии, результата или payload команды.

### 3. Завершение load и Handler

Параметризуй допустимые примеры:

| Стадия | Нормализованные `outcome` | Уровень |
|---|---|---|
| `load` | `loaded`, `session_absent`, `state_read_failed` | `DEBUG` |
| `handler` | `success`, `input_required`, `resolution_unavailable`, `calculation_failed` | `DEBUG` |
| `load` или `handler` | `invalid_outcome`, `unexpected_failure` | `WARNING` |

Для каждой записи обязательны `stage`, `outcome`, `duration_ms`, `run_id`.
При переданной достоверной версии проверь её значение; при `None` опциональное
поле `state_version` отсутствует. Примеры версий должны включать `0`.

Названия `invalid_outcome` и `unexpected_failure` здесь фиксируют нормализацию
внутреннего logging API. Это не новые application-level коды ошибок.

Отдельная exception-запись со stack trace по FR-25 — обязанность вызывающего
exception-пути. Эти функции не получают исключение и не создают такую запись.
Не моделируй отменённую стадию как `stage_finished(outcome="cancelled")`.

### 4. Завершение попытки commit

Проверь поля `attempt`, `outcome`, `detail_code`, `duration_ms`, `run_id` и
опциональную достоверную `state_version`.

- Первая подтверждённая попытка: `committed` и `already_applied` — `DEBUG`.
- `state_commit_failed` и `unexpected_failure` — `WARNING`, включая attempt 1.
- Вторая попытка — `WARNING` для всех результатов:
  `committed`, `already_applied`, `superseded`, `session_absent`,
  `state_commit_failed`, `unexpected_failure`.
- Для одного успешного outcome сравни attempt 1 и attempt 2: это позитивный
  контроль выбора уровня по номеру попытки.
- `detail_code` присутствует и при `None`; версия отсутствует, если не передана.
  Проверяй безопасный synthetic error code, а не текст runtime-исключения.

Не выводи из этих unit-тестов, что retry разрешён, выполнен или ограничен:
здесь номер попытки передаёт вызывающий. Соответствующее поведение проверяется
на этапах 6–9.

### 5. Terminal event с результатом

`log_operation_finished` записывает `terminal_kind=result` и все поля result
из §11.5, включая nullable `detail_code` и `state_version`.

Параметризуй согласованные примеры статусов из §8 R3.2:

- `SUCCESS / SUCCESS / COMMITTED` — `INFO`;
- `INPUT_REQUIRED / INPUT_REQUIRED / LOADED` — `INFO`;
- `SUPERSEDED / SUCCESS / SUPERSEDED` — `INFO`;
- `SESSION_ABSENT / NOT_STARTED / SESSION_ABSENT` — `INFO`;
- `FAILURE / SUCCESS / COMMIT_FAILED` — `WARNING`.

Передавай соответствующие `code`, `detail_code` и версии. Проверяй сохранение
всех трёх статусов. Валидацию недопустимых комбинаций оставь моделям этапа 2.

Проверь передачу `commit_attempts` для 0, 1 и 2, пустого списка ошибок,
одного кода при успешном retry и двух кодов при двух отказах. Разные коды
сохраняют порядок; одинаковые не схлопываются. Logger не восстанавливает эту
историю из событий и не делает выводов из последнего `detail_code`.

Оба значения `delivery_cancelled` сохраняются. При `True` событие остаётся
result-вида; успешный результат не превращается в `FAILURE` или в
`terminal_kind=cancelled`. Поля `cancelled_stage` в result-виде нет.

### 6. Terminal event отмены до commit

`log_operation_cancelled` пишет `application_operation_finished` уровня `INFO`:

```text
terminal_kind=cancelled
run_id
cancelled_stage
load_duration_ms
handler_duration_ms
commit_attempts=0
```

Проверь отмену на `load` и на `handler`. В первом примере обе длительности
равны `None`; во втором load завершён, а `handler_duration_ms=None`.

Запись не содержит `orch_status`, `handler_status`, `context_status`, `code`,
`detail_code`, `state_version`, `commit_duration_ms`, `commit_error_codes`,
`delivery_cancelled`. Позитивный контроль — result-событие из предыдущего
пункта, где эти поля действительно присутствуют.

Реальный `CancelledError` здесь не вызывай: правило его проброса и отсутствие
ложного stage event проверяются в тестах Orchestrator.

### 7. Длительности и компактный набор полей

- Используй заранее заданные длительности, например `0.0`, `1.25`, `2.5` мс.
  Проверяй единицы и сохранение значений; опубликованные числа конечны и
  неотрицательны. `None` для неначатой/незавершённой стадии не превращается в 0.
- Для примера retry передай итог `commit_duration_ms=3.75` и проверь, что он
  записан. Это проверка передачи значения; вычисление суммы в `execute()`
  этим тестом не доказано.
- Не добавляй неоговорённую политику обработки неверных аргументов logger:
  исключение, clamp или подмена `NaN`/отрицательного числа нулём не заданы
  R3.2. Этот срез проверяет формат при корректных входных значениях; расчёт
  допустимых длительностей реального flow проверяется на этапе 8.2.
- Для каждого вида записи проверяй разрешённый прикладной набор полей и
  позитивные значения обязательных полей. Не сравнивай весь
  `LogRecord.__dict__`: штатные метаданные logging не являются payload события.
- API не принимает `session_id`, `birth_input`, `command`, `delta`, `artifact`
  или произвольный payload. Можно параметризованно проверить `TypeError` на
  лишний такой keyword рядом с корректным вызовом той же функции. Не добавляй
  приём payload ради последующего теста его очистки.
- Эти проверки ограничивают новый компактный формат. Они не доказывают
  отсутствие PII во всём application-flow и не меняют ранее принятые правила
  boundary DEBUG logging.

## Организация тестов

- Один разрешённый файл, небольшие параметризованные тесты по поведению.
- Допустимы локальные helpers для захвата и чтения записи. Не реализуй в них
  production-функции, выбор уровня или ожидаемую логику вместо предмета теста.
- Настрой захват так, чтобы существующие file handlers не мешали `caplog`.
  Если приходится менять handlers/propagate/level, восстанови их в `finally`
  или fixture teardown. Не перенастраивай весь проект через `basicConfig`.
- Общие UUID бери из fixtures. Не создавай новые fixtures-файлы или зависимости.
- Не импортируй будущие Orchestrator и ApplicationResult. Не используй
  `importorskip`, `xfail`, `skip`, fallback-реализацию или подмену модуля в
  `sys.modules`, чтобы скрыть отсутствие `operation_logging.py`.
- Тесты синхронные; реальное время, `sleep`, файловые логи и внешние сервисы
  не нужны.

## Проверки при выполнении промта

### Целевой набор

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/application/test_orchestrator_logging.py -q
```

До этапа 1.4 ожидается ошибка импорта отсутствующего production-модуля.
Зафиксируй реальный результат и exit code. Это означает, что тесты пока нельзя
исполнить; это не доказательство чувствительности assertions и не успешный
прогон. Не добавляй реализацию ради зелёного результата в этом промте.

При import error отдельно проверь синтаксис нового тестового файла через
`ast.parse`, не создавая `__pycache__`. Статическая проверка не заменяет pytest.

### Связанный и полный наборы — только после зелёного целевого

Если реализация к моменту выполнения уже существует и целевые тесты прошли,
выполни последовательно R и F из плана:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_run_context.py tests/application tests/session tests/test_module_boundaries.py -q
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider -q
```

При ожидаемом падении из-за отсутствующей реализации связанные и полные
проверки откладываются до этапа 1.4.
Не добавляй новые quality gates и не запускай сетевые или платные smoke-тесты.

### Проверка границ изменения

```powershell
git diff --check
git diff -- tests/application/test_orchestrator_logging.py

```

Новый untracked файл не входит в обычный `git diff`: прочитай и проверь его
отдельно. Сопоставь содержимое остальных файлов с исходным baseline.
Production-код и прежние изменения должны остаться нетронутыми.
