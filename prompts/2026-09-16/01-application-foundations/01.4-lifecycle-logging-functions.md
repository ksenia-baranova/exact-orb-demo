**Дата:** 2026-09-16.
**Статус при подготовке:** промт подготовлен; результаты выполнения — в журнале плана.
**План:** [карточки 1.3–1.4](../../../docs/project_management/application_orchestrator_implementation_plan.md).
**Зависимости:** тесты 1.3 и выполненная корректировка 1.R1.
**Требования:** [ApplicationOrchestrator R3.2](../../../docs/requirements/component_responsibilities/exact-orb_application_orchestrator_requirements.md), FR-26–27, §11.5; связанное требование FR-25 определяет ответственность за exception-запись.
**Результат:** работающие функции логирования, проверенные существующими тестами, и фактические результаты связанных и общих проверок.

## 1. Что получит проект — простыми словами

Появятся функции, с помощью которых Orchestrator сможет записывать в журнал
приложения начало запроса, завершение загрузки сессии и работы Handler,
результат каждой попытки сохранения, окончательный результат или отмену.

Все записи содержат `run_id`. По нему можно собрать историю одного запроса
и понять, на каком этапе возникла проблема. Если первое сохранение завершилось
ошибкой, а повтор прошёл успешно, журнал сохранит оба факта.

Это технические записи в логах приложения. Функции не создают записи
в пользовательской сессии и не хранят состояние операций между вызовами.

После этапа будут готовы пять небольших функций. Существующие тесты смогут
проверить их поведение; отсутствие модуля перестанет блокировать общий набор
application. Подключение к `execute()`, управление сохранением и обработка
отмены остаются последующим этапам.

## 4. Интерфейс функций

Все функции синхронные, принимают только явно перечисленные keyword-only
аргументы, возвращают `None` и используют logger
`exact_orb.application.operation_logging`.

| Функция | Аргументы |
|---|---|
| `log_operation_started` | `run_id`, `command_type` |
| `log_stage_finished` | `run_id`, `stage`, `outcome`, `duration_ms`, `state_version=None` |
| `log_commit_attempt_finished` | `run_id`, `attempt`, `outcome`, `detail_code`, `duration_ms`, `state_version=None` |
| `log_operation_finished` | `run_id`, `orch_status`, `handler_status`, `context_status`, `code`, `detail_code`, `state_version`, `load_duration_ms`, `handler_duration_ms`, `commit_duration_ms`, `commit_attempts`, `commit_error_codes`, `delivery_cancelled` |
| `log_operation_cancelled` | `run_id`, `cancelled_stage`, `load_duration_ms`, `handler_duration_ms` |

Типы: `run_id: UUID`, версии `int | None`, `duration_ms: float`, длительности
итоговых событий `float | None`, `attempt: Literal[1, 2]`,
`commit_attempts: Literal[0, 1, 2]`, `commit_error_codes: tuple[str, ...]`,
`delivery_cancelled: bool`, `detail_code: str | None`.
Остальные значения — нормализованные строки.

Функции получают подготовленные значения. Они не принимают ApplicationResult,
RunContext, команды, snapshot, outcome-объекты или исключения.

## 5. Поведение функций

### 5.1. Начало операции

`log_operation_started` пишет `application_operation_started` уровня INFO
с полями `run_id`, `command_type`.

### 5.2. Завершение загрузки или Handler

`log_stage_finished` пишет `application_stage_finished` с полями
`run_id`, `stage`, `outcome`, `duration_ms`.

`state_version` добавляется только при значении, отличном от None; версия 0
сохраняется. Ожидаемые типизированные исходы load/Handler имеют уровень DEBUG;
`invalid_outcome` и `unexpected_failure` — WARNING.

Отдельная exception-запись со stack trace по FR-25 принадлежит вызывающему коду.
Отменённая незавершённая стадия не должна моделироваться фиктивным finished:
решение о вызове этой функции будет принимать будущий Orchestrator.

### 5.3. Завершение попытки сохранения

`log_commit_attempt_finished` пишет `application_commit_attempt_finished`
с полями `run_id`, `attempt`, `outcome`, `detail_code`, `duration_ms`.

`detail_code` присутствует и при None. `state_version` добавляется только
при известном значении, включая 0.

- Вторая попытка всегда имеет уровень WARNING.
- `state_commit_failed` и `unexpected_failure` — WARNING при любой попытке.
- Остальные типизированные исходы первой попытки — DEBUG.

Функция использует переданный номер попытки; решение о повторе и вызов save
в этот этап не входят.

### 5.4. Завершение операции с результатом

`log_operation_finished` пишет `application_operation_finished`:

```text
terminal_kind=result
run_id
orch_status, handler_status, context_status
code, detail_code, state_version
load_duration_ms, handler_duration_ms, commit_duration_ms
commit_attempts, commit_error_codes
delivery_cancelled
```

Все поля присутствуют, включая nullable. Уровень WARNING при
`orch_status=FAILURE`; в остальных случаях INFO.

Сохраняй порядок и повторяющиеся коды `commit_error_codes`, число попыток,
длительности и признак отменённой доставки. При `delivery_cancelled=True`
сохраняются `terminal_kind=result` и переданные статусы.
Поля `cancelled_stage` здесь нет.

### 5.5. Отмена до начала сохранения

`log_operation_cancelled` пишет `application_operation_finished` уровня INFO:

```text
terminal_kind=cancelled
run_id
cancelled_stage
load_duration_ms, handler_duration_ms
commit_attempts=0
```

`terminal_kind` и `commit_attempts=0` задаёт функция. В записи отсутствуют
три статуса, `code`, `detail_code`, `state_version`, `commit_duration_ms`,
`commit_error_codes`, `delivery_cancelled`.
Обработку настоящего CancelledError сейчас не реализуй.

## 6. Формат и ограничения реализации

Каждая функция делает один вызов logger. При включённом уровне тест получает
ровно одну запись. Имя события и поля находятся в самом сообщении `msg`/`args`,
возвращаемом `LogRecord.getMessage()`. Одних атрибутов `extra` недостаточно.
Formatter, handlers и конфигурация logging не меняются.

Контракт текстового представления:

- Формат `<event> key=value key=value ...`; перед первым полем после имени
  события нет иных фрагментов. Порядок полей и несущественные пробелы не фиксируются.
- Ключи уникальны, значения не пустые.
- `commit_error_codes` рендерится литералом кортежа или списка строк,
  например `()`, `[]`, `('A', 'B')`. Соединение кодов через запятую без скобок
  не подходит; пустая коллекция не превращается в пустое значение.
- Числа остаются числами после разбора: `state_version=0`, а не `state_version='0'`.
- UUID после разбора равен `str(run_id)`; обычная строка UUID допустима
  и без кавычек, и в строковом литерале, но без префикса `UUID(...)`.
- Для None допустимы `None`, `null` или `-`; для bool — `True/False`
  либо `true/false`. Значения должны сохранять тип и смысл.

Общее ограничение всех пяти функций: у записей `exc_info is None`
и `stack_info is None`. Не используй `logger.exception` и не передавай
параметры `exc_info` или `stack_info`.

Готового общего compact-helper для этих событий нет. Приватные
`_log_started`, `_log_completed`, `_log_failed` в `handlers/build_natal.py`
показывают стиль записи через штатный logger. Их уровни не копируются:
уровни Orchestrator заданы §5 и существующими тестами.
Полный `component_message` DEBUG-gated и payload-ориентирован; его не используй.

Передавай исходный run_id, не создавай UUID. Не принимай произвольные kwargs,
session_id, birth_input, command, delta, artifact или payload в публичном API.
Не сохраняй аргументы между вызовами, не вычисляй время, попытки или ошибки.
Не превращай неизвестную длительность None в 0.

Не добавляй неоговорённую политику обработки отрицательных длительностей,
NaN или бесконечности. Контракт здесь проверяется при корректных входах;
их подготовка принадлежит будущему execute(). Не вводи telemetry port,
recorder, metrics backend или общий сервис логирования для проекта.

## 7. Порядок реализации и связь тестов с требованиями

Сначала реализуй модуль и добейся успешного целевого прогона на неизменённом
тестовом файле. Затем проведи оба эксперимента §8.2 и восстанови исправный код.
До добавления docstring сохрани список собранных node IDs через collect-only.

Только после этого добавь короткие русские docstring в десять существующих
тестовых функций: номер требования, проверяемое поведение и граница проверки.
Например:

```python
"""R3.2 FR-26, §11.5, AC-31 частично.

Проверяет поля и уровень события попытки сохранения.
Связь события с фактическим save проверяется в тестах Orchestrator.
"""
```

| Проверка | Связь с требованиями |
|---|---|
| Переданный run_id | FR-26; AC-26 частично |
| Формат начала и завершения | §11.5; AC-29 частично |
| Формат load/Handler | §11.5; AC-30 частично |
| Номер, поля и уровень commit attempt | §11.5; AC-31 частично |
| Длительности и история ошибок | FR-26; §11.5 |
| Различие результата и отмены | FR-26; §11.5 |
| Разрешённые поля и отказ от payload | FR-27; §11.5; AC-33 частично |

Указывай только проверяемые данным тестом требования. AC-32 о порядке событий
и возврата управления здесь не доказывается; единичность событий на execute
также остаётся последующим этапам.

Проверь неизменность тестов объективно: AST до и после должен совпасть после
исключения docstring. Diff должен содержать только добавленные docstring
и комментарии. Список node IDs collect-only до и после должен совпасть.
Совпадение одного количества тестов не заменяет проверку AST.

### 8.2. Две разовые проверки чувствительности

После успешного целевого прогона сохрани точные байты исправного модуля.
Каждый эксперимент отдельно защищай try/finally с восстановлением этих байтов.
Проверь точность восстановления; не используй git restore для нового файла.

**Эксперимент A — запрещённый аргумент.** Временно разреши
`log_operation_started` дополнительный keyword-only `payload=None`,
при передаче добавляй его в сообщение. Запусти:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/application/test_orchestrator_logging.py::test_payload_keywords_are_rejected_after_valid_call_positive_control -q
```

Случай передачи payload в log_operation_started должен упасть потому,
что ожидаемый TypeError не возник. Ошибка импорта/синтаксиса не подходит.
Восстанови модуль и повтори команду: она должна пройти.

**Эксперимент B — лишнее поле записи.** От исправной версии, сохраняя сигнатуру,
временно добавь в started-сообщение постоянное поле `payload` с синтетической
строкой. Запусти:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/application/test_orchestrator_logging.py::test_started_records_command_type_and_run_id_at_info -q
```

Проверка должна упасть на `actual.keys() == expected.keys()`.
Восстанови модуль и повтори команду: она должна пройти.

Не меняй тесты для экспериментов, не оставляй намеренные ошибки и резервные
файлы в репозитории, не добавляй mutation-testing зависимости или quality gate.
Запиши реальные количества failed/passed и причины обоих падений.
Это подтверждает чувствительность двух конкретных проверок, но не доказывает
отсутствие персональных данных во всём application-flow.
