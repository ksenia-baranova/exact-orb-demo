поведение модели и не вводит новый контракт неизменяемости.

## 1. Независимые константы для тестов

Создай маленький `tests/fixtures/telemetry.py`, импортирующий только стандартную
библиотеку. В нём нужны:

- `STARTED_AT` — фиксированный aware UTC datetime;
- `RUN_ID` и `RUN_ID_B` — два разных фиксированных UUID;
- `FORBIDDEN_PAYLOAD` — синтетическая строка-маркер для проверки запрещённых
  аргументов logging API.

Эти значения описывают только тестовый correlation context. Выбери отдельные
детерминированные значения, например UTC-дату 2026-09-16 и UUID, созданные через
`UUID(int=1, version=4)` / `UUID(int=2, version=4)`. Это не эталоны расчётного
домена: не переноси дату рождения и domain fixture builders из calculation.
Маркер не должен содержать реальные пользовательские данные.

В `tests/test_run_context.py` используй `STARTED_AT` вместо расчётного
`BASE_UTC`, а UUID импортируй из нового модуля. В logging-тестах используй
его UUID и `FORBIDDEN_PAYLOAD` вместо `SENSITIVE_WARNING`.

Сохрани смысл существующих assertions и имена тестов. Значения в ожидаемых
логах должны по-прежнему сопоставляться с переданным идентификатором.
Не изменяй расчётные fixtures, их потребителей, golden-данные или вычисления.
Не добавляй proxy-import из `tests.fixtures.calculation`: это сохранит проблему.

В двух затронутых тестовых файлах больше не должно быть импорта
`tests.fixtures.calculation`. Новый fixture-модуль не должен загружать
`exact_orb`, calculation/engine, pytest или сторонние зависимости.

Это устраняет добавленную зависимость от расчётного стека. Не объявляй весь
`tests/test_run_context.py` изолированным листовым тестом: в нём остаются
существующие проверки BirthDataResolver и действует общий conftest.
Не разделяй файл и не меняй autouse fixtures в этой карточке.

## 2. Проверки существующего контракта started_at

Сохрани прежний тест отказа для naive `started_at` и все тесты deadline.
Добавь небольшие параметризованные проверки:

1. Принимаются и сохраняются `started_at` с `timezone.utc` и с именованной
   timezone, имеющей нулевой offset.
2. Отвергаются aware значения с offset `+03:00` и `-04:00`.
3. Для отказов проверь `ValidationError` и множество locations
   `{("started_at",)}`, чтобы не принять ошибку другого поля за нужный отказ.

Во всех случаях остальные входы должны быть корректными. Используй новые
детерминированные константы; не читай текущее время ради этих сценариев.
Сравнивай `utcoffset()` с нулём, не identity объекта timezone.

Не меняй модель, её сообщения об ошибках или правила преобразования типов.
Не добавляй проверки frozen/extra/model_fields в этот срез.
Это дополнительные проверки уже реализованного поведения: ожидается их
прохождение сразу; искусственно создавать падение не нужно.

Обнови docstring файла так, чтобы он называл обе его обязанности:
контракт модели RunContext и correlation logging при birth resolution.

### 3.2. Исторические свидетельства этой сессии

Следующие результаты взяты из предыдущих отчётов выполнения. При переносе

```powershell

.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_run_context.py -q
```

## 4. Проверки при выполнении

### 4.1. Baseline и целевые проверки RunContext

До изменения и после него выполни T из раздела 3.2. Сравни результат,
сохрани старые случаи и укажи фактическое число новых проверок.
Прежнее прохождение 21 теста — историческое свидетельство, не замена baseline.

После успешного целевого набора проверь соседние архитектурные ограничения:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_run_context.py tests/test_module_boundaries.py -q
```

### 4.2. Изоляция fixture-модуля

В новом процессе проверь, что его импорт не загружает пакет exact_orb:

```powershell
.\.venv\Scripts\python.exe -B -c "import sys; import tests.fixtures.telemetry; assert not any(n == 'exact_orb' or n.startswith('exact_orb.') for n in sys.modules); print('telemetry fixtures: isolated import OK')"
```

Дополнительно проверь исходные импорты: у нового модуля только стандартная
библиотека, в двух тестовых файлах отсутствует calculation fixtures import.
Не добавляй отдельный постоянный framework проверки импортов ради этой правки.

### 4.3. Logging и граница доступной проверки

Выполни L из раздела 3.2 и зафиксируй точный исход:

- если `operation_logging.py` всё ещё отсутствует, ожидается тот же
  ModuleNotFoundError при collection. Проверь синтаксис двух изменённых
  тестов и нового fixture-модуля через `ast.parse`; не добавляй заглушку;
- при этой известной ошибке сборки R/F отложены до 1.4. Не исключай тест
  через `--ignore`, skip/xfail или importorskip ради зелёного полного набора;
- если модуль к моменту выполнения уже реализован, целевой L должен пройти,
  после чего последовательно выполни R и F. Любое другое падение исследуй
  отдельно и не списывай на отсутствие будущей реализации.

Даже если L остановился до импорта telemetry fixtures, их независимость
должна быть подтверждена отдельной командой из 4.2.

### 4.4. Объём и документация

- Выполни `git diff --check`; отдельно проверь новые untracked файлы.
- Проверь Markdown-ссылки добавленного раздела и соответствие команд журналу.
- Сравни хеши с baseline: все файлы вне allowlist должны остаться неизменными,
  особенно `src/exact_orb/run_context.py` и прежние пользовательские правки.
- Проверь, что в logging-тесте изменились только импорты и ссылки на константы;
  формат событий, уровни, assertions и количество тестовых функций сохранены.
- Не запускай сетевые/платные smoke-тесты и не вводи новые quality gates.

## Критерий завершения и отчёт

Готовность этой карточки означает: лишние импорты устранены, новые проверки
started_at проходят, описание тестового файла точно, журнал различает историю,
текущее выполнение и отложенные проверки. Наличие известной ошибки импорта L
не позволяет объявить текущий полный набор успешным, но не требует выполнять
production-этап 1.4 внутри этой задачи.

В отчёте укажи:

1. Изменённые файлы и четыре устранённых замечания.
2. Фактические команды, результаты и exit codes до/после изменения.
3. Статус L, что именно не было проверено из-за отсутствия реализации,
   и выполнялись ли R/F.
4. Сохранность production-кода и предыдущих изменений.
5. Следующий основной шаг — 1.4; неизменяемость RunContext и extra не
   реализованы этой карточкой.
