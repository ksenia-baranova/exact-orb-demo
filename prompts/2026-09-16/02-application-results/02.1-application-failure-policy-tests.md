## Внутренний API пары 2.1–2.2

Зафиксируй одну синхронную функцию `describe_failure` в модуле
`exact_orb.application.failure_policy`. Все аргументы — keyword-only:

```python
describe_failure(
    *,
    kind,
    error_code=None,
    retryable=None,
    stage=None,
    reason=None,
)
```

Это небольшой внутренний API чистой политики, не внешний transport-контракт.
Допустимые входы этого среза:

| `kind` | Дополнительные аргументы |
|---|---|
| `input_required` | Нет |
| `resolution_unavailable` | `error_code: str`, `retryable: bool` — оба обязательны для этого случая |
| `calculation_failed` | `error_code: str` |
| `state_read_failed` | `error_code: str` |
| `state_commit_failed` | `error_code: str` — причина окончательного отказа, выбранная вызывающим |
| `session_absent` | `stage: "load" или "commit"`, `reason: "expired" или "not_found"` |
| `superseded` | Нет |
| `handler_not_registered` | Нет |
| `internal_failure` | Нет |

Неиспользуемые аргументы опускаются. Политика не принимает command, session
state, `ApplicationResult`, outcome-объекты, исключения, birth data или
session ID. Для внутреннего отказа достаточно `kind="internal_failure"`:
исключение обрабатывает вызывающий, а политика выбирает статический текст.

Результат предоставляет четыре именованных атрибута:

```text
code: str
detail_code: str | None
user_message: str
retryable: bool
```

Сравнивай эти поля по значениям; для bool проверяй настоящий `True`/`False`.
Не закрепляй конкретный класс, способ хранения таблицы, приватные helpers,
identity возвращаемого объекта или использование Pydantic/dataclass.
Внешние модели и валидация их связок появятся в 2.3–2.6.

Поведение для неизвестного `kind`, отсутствующих обязательных аргументов
конкретного случая или противоречивых комбинаций аргументов здесь не задаётся.
Не изобретай для них fallback, coercion или отдельные ошибки. Это не относится
к неизвестному `error_code`: его допустимость и fallback заданы требованиями.

## Обязательные проверки

### 1. Каждая строка политики

Параметризуй следующие случаи. В каждой строке проверяй все четыре поля,
включая точный текст и явный `None`. Ожидаемые значения возьми из §9–10 R3.2;
не импортируй ожидаемые тексты или таблицу из production-модуля.

| Вход | `code` | `detail_code` | `retryable` | Точный `user_message` |
|---|---|---|---:|---|
| `input_required` | `INPUT_REQUIRED` | `None` | false | `Проверьте введённые данные и исправьте отмеченные поля.` |
| `resolution_unavailable`, `TZ_DATA_UNAVAILABLE`, true | `RESOLUTION_UNAVAILABLE` | `TZ_DATA_UNAVAILABLE` | true | `Не удалось определить данные места и времени. Попробуйте ещё раз.` |
| `resolution_unavailable`, `TZ_DATA_UNAVAILABLE`, false | `RESOLUTION_UNAVAILABLE` | `TZ_DATA_UNAVAILABLE` | false | `Не удалось определить данные места и времени для указанного ввода.` |
| `calculation_failed`, `EPHEMERIS_UNAVAILABLE` | `CALCULATION_FAILED` | `EPHEMERIS_UNAVAILABLE` | true | `Расчёт временно недоступен. Попробуйте ещё раз.` |
| `calculation_failed`, `HOUSES_DEGENERATE` | `CALCULATION_FAILED` | `HOUSES_DEGENERATE` | false | `Для выбранных данных невозможно рассчитать дома в текущей системе домов.` |
| `calculation_failed`, `SPEC_INVALID` | `CALCULATION_FAILED` | `SPEC_INVALID` | false | `Не удалось подготовить параметры расчёта карты.` |
| `calculation_failed`, `GEOGRAPHY_INVALID` | `CALCULATION_FAILED` | `GEOGRAPHY_INVALID` | false | `Не удалось выполнить расчёт карты для выбранного места.` |
| `calculation_failed`, `ENGINE_UNEXPECTED` | `CALCULATION_FAILED` | `ENGINE_UNEXPECTED` | false | `Не удалось рассчитать карту из-за внутренней ошибки.` |
| `calculation_failed`, `SYNTHETIC_CALC_FAILURE` | `CALCULATION_FAILED` | `SYNTHETIC_CALC_FAILURE` | false | `Не удалось рассчитать карту.` |
| `state_read_failed`, `SQLITE_BUSY` | `STATE_READ_FAILED` | `SQLITE_BUSY` | true | `Не удалось загрузить данные сессии. Попробуйте ещё раз.` |
| `state_commit_failed`, `SQLITE_BUSY` | `STATE_COMMIT_FAILED` | `SQLITE_BUSY` | true | `Не удалось подтвердить сохранение карты. Обновите страницу, чтобы проверить актуальное состояние.` |
| `session_absent`, load, expired | `SESSION_EXPIRED` | `None` | false | `Сессия истекла. Введите данные рождения заново.` |
| `session_absent`, load, not_found | `SESSION_NOT_FOUND` | `None` | false | `Сессия не найдена. Начните заново.` |
| `session_absent`, commit, expired | `SESSION_LOST_DURING_OPERATION` | `None` | false | `Сессия была потеряна до сохранения карты. Введите данные рождения заново.` |
| `session_absent`, commit, not_found | `SESSION_LOST_DURING_OPERATION` | `None` | false | `Сессия была потеряна до сохранения карты. Введите данные рождения заново.` |
| `superseded` | `RESULT_SUPERSEDED` | `None` | false | `Результат этого запроса уже не актуален. Текущая карта не изменена.` |
| `handler_not_registered` | `HANDLER_NOT_REGISTERED` | `None` | false | `Не удалось выполнить запрос из-за внутренней ошибки.` |
| `internal_failure` | `INTERNAL_FAILURE` | `None` | false | `Произошла внутренняя ошибка.` |

`Superseded` требует пользовательской реакции, поэтому включён в эту политику;
это не превращает его в инфраструктурный failure. Статусы политика не выбирает.

### 2. Открытые технические коды

- Неизвестный calculation-код принимается обычным вызовом функции, сохраняется
  без изменения в `detail_code`, даёт fallback и `retryable=False`.
  Используй два разных синтетических кода, чтобы не закрепить частный случай.
  Положительный контроль — известный `EPHEMERIS_UNAVAILABLE` с другим текстом
  и `retryable=True` из основной таблицы.
- Для resolution проверь неизвестный `SYNTHETIC_RESOLVER_FAILURE` с обоими
  значениями `retryable`. Текст зависит от bool, `detail_code` сохраняется.
- Для чтения и окончательного commit проверь `SYNTHETIC_STORAGE_FAILURE`:
  сохраняется технический код, используется общий текст соответствующей строки.
- В `user_message` не подставляется технический код. Сопоставление выполняется
  по четырём полям; одного утверждения «не поднялся exception» недостаточно.
- Не закрывай `CalculationFailed.error_code` через Literal и не конструируй
  невалидные модели через обход валидации. По действующему контракту код — str.
- Фактический WARN для неизвестного calculation-кода принадлежит Orchestrator
  и проверяется в 5.2/8.2. Чистая политика сама не пишет предупреждение.

### 3. Тексты, повтор и независимость вызовов

- Все строки с `retryable=False` должны совпадать с заданными текстами.
  Не добавляй эвристический поиск слов как замену точному сравнению:
  исправить поля или начать новую сессию — допустимые действия по FR-23.
- `internal_failure` возвращает именно `Произошла внутренняя ошибка.`,
  без прежнего приглашения «Попробуйте позже». Объект исключения не передаётся.
- Выполни несколько чередующихся вызовов: неизвестный calculation-код A,
  известный код, неизвестный код B, снова A. Проверь соответствующие четыре
  поля и сохранность ранее полученного описания. Identity объектов не проверяй.
- При обычном захвате штатного logger через `caplog` вызовы политики не должны
  создавать записей, включая неизвестный код. Не подменяй саму функцию или её
  будущие внутренние helpers и не меняй настройки logging проекта.

Эти проверки фиксируют безопасные статические сообщения. Проброс/нормализация
реальных исключений, отсутствие birth data во всём flow, частоты событий,
выбор последнего commit error и разрешение retry здесь не проверяются.
Пустые `InputRequired.issues` и конфликт K3 остаются вне этого среза:
политика не получает и не валидирует issues.

## Организация тестов

- Один файл, небольшие параметризованные тесты с понятными case IDs.
- Допустим helper, извлекающий четыре именованных поля; в нём не должно быть
  копии алгоритма выбора текста, retryable или кода.
- Строки ожидаемых сообщений заданы в тестовой таблице независимо от
  production. Не читай requirements/README во время выполнения pytest.
- Не подключай расчётные fixtures, Handler, ContextService или session state
  ради строковых примеров: входы этой функции не требуют расчётного стека.
- Импортируй будущую функцию непосредственно из целевого модуля. Не используй
  `importorskip`, `skip`, `xfail`, fallback-реализацию или подмену `sys.modules`,
  чтобы скрыть отсутствие `failure_policy.py`.
- Без сети, файловых логов, реальных часов, sleep и новых зависимостей.

## Проверки при выполнении промта

### Целевой набор

Из корня репозитория:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/application/test_application_failure_policy.py -q
```

До 2.2 ожидается ошибка импорта отсутствующего production-модуля.
Запиши фактическую причину и exit code. Ошибка сборки означает, что assertions
ещё не исполнялись; это не успешная проверка политики и не доказательство
чувствительности тестов. Не добавляй реализацию в тестовом этапе.

Если импорт блокирует pytest, отдельно проверь синтаксис:

```powershell
.\.venv\Scripts\python.exe -B -c "import ast,pathlib; p=pathlib.Path('tests/application/test_application_failure_policy.py'); ast.parse(p.read_text(encoding='utf-8'), filename=str(p)); print('AST OK')"
```

Статическая проверка не заменяет выполнение assertions.

### Связанный и полный наборы

Если к моменту выполнения политика уже реализована и целевой набор прошёл,
запусти R из плана:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_run_context.py tests/application tests/session tests/test_module_boundaries.py -q
```

Только после успешного R запусти F:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider -q
```

При ошибке целевого импорта R/F откладываются до 2.2. Если после зелёного
целевого R остановится на отсутствующем `operation_logging.py`, зафиксируй
отдельную причину из незавершённой 1.4; F до её устранения не запускай.
Не исключай logging-тесты из набора и не объявляй полный прогон успешным.
