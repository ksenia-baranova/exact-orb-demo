## 1. Сохрани согласованный внутренний API

Одна синхронная функция, все аргументы keyword-only:

```python
def describe_failure(
    *,
    kind: FailureKind,
    error_code: str | None = None,
    retryable: bool | None = None,
    stage: Literal["load", "commit"] | None = None,
    reason: Literal["expired", "not_found"] | None = None,
) -> FailureDescription:
    ...
```

`FailureKind` — локальный Literal из девяти нормализованных значений:

```text
input_required
resolution_unavailable
calculation_failed
state_read_failed
state_commit_failed
session_absent
superseded
handler_not_registered
internal_failure
```

`FailureDescription` — небольшой immutable value object с четырьмя полями:

```text
code: str
detail_code: str | None
user_message: str
retryable: bool
```

Для него достаточно frozen dataclass или NamedTuple стандартной библиотеки.
Это внутреннее описание реакции, не одна из будущих моделей ApplicationResult.
Не добавляй статусы, run_id, state_version, payload, HTTP-код или поле для
накопления observability-данных. Не возвращай всем вызовам один объект,
чьи поля перезаписываются при следующем запросе.

Функция принимает только компактные аргументы. Не передавай ей исключения,
outcome-объекты, command, snapshot, artifact, birth data или session ID.
Не вводи `**kwargs`, positional fallback или дополнительный аргумент logger.

Допустимые сочетания входов уже зафиксированы в 2.1. Политика обработки
неизвестного `kind` и противоречивых сочетаний там не задана: не превращай
их в новые application outcomes и не объявляй их валидацию проверенной.
Не смешивай такие ошибки вызова с допустимым неизвестным `error_code`.

## 2. Реализуй единую политику реакции

Точные тексты берутся из **§10 R3.2**, поля detail_code — из §9.
Сверяй с независимыми ожиданиями тестов 2.1. Не читай документацию или тесты
из production во время импорта/вызова и не импортируй тестовые константы.

| `kind` | Правило |
|---|---|
| `input_required` | `INPUT_REQUIRED`, detail_code=None, retryable=False |
| `resolution_unavailable` | `RESOLUTION_UNAVAILABLE`; error_code сохраняется; оба значения retryable берутся из входа и выбирают соответствующий текст |
| `calculation_failed` | `CALCULATION_FAILED`; error_code сохраняется; текст и retryable определяются таблицей расчётных кодов |
| `state_read_failed` | `STATE_READ_FAILED`, detail_code=error_code, retryable=True |
| `state_commit_failed` | `STATE_COMMIT_FAILED`, detail_code=error_code, retryable=True; текст о неподтверждённом сохранении и проверке актуального состояния |
| `session_absent` при load | expired → `SESSION_EXPIRED`; not_found → `SESSION_NOT_FOUND`; detail_code=None, retryable=False |
| `session_absent` при commit | Обе причины → `SESSION_LOST_DURING_OPERATION`, detail_code=None, retryable=False |
| `superseded` | `RESULT_SUPERSEDED`, detail_code=None, retryable=False |
| `handler_not_registered` | `HANDLER_NOT_REGISTERED`, detail_code=None, retryable=False |
| `internal_failure` | `INTERNAL_FAILURE`, detail_code=None, retryable=False; сообщение `Произошла внутренняя ошибка.` |

Известные calculation-коды:

- `EPHEMERIS_UNAVAILABLE` — retryable=True, временная недоступность расчёта;
- `HOUSES_DEGENERATE`, `SPEC_INVALID`, `GEOGRAPHY_INVALID`,
  `ENGINE_UNEXPECTED` — retryable=False, отдельные точные тексты §10.

Для **любого другого calculation-кода** возвращай
`CALCULATION_FAILED`, исходный код в detail_code, retryable=False и
`Не удалось рассчитать карту.`. Не распознавай специально синтетические
значения из тестов: fallback работает для всего открытого множества str.

Resolution и persistence также сохраняют неизвестный код и используют
общий текст своего вида отказа. Не обрезай, не переименовывай и не подменяй
detail_code. Не вставляй его в user_message. `retryable=False` у resolution
должен сохраняться как False, без выражений вроде `retryable or True`.

Тексты остаются в application как принятый долг. Не добавляй локализацию,
шаблонизацию произвольного payload или очистку raw exception вместо заданных
статических сообщений. При retryable=False не дописывай приглашение повторить
тот же запрос; исправить ввод или начать новую сессию допустимо по FR-23.

## 3. Сохрани чистоту и границы

- Одинаковый вход даёт одинаковые четыре поля. Другие вызовы не меняют уже
  полученные описания. Статические таблицы не мутируют при вызове функции.
- Нет logging, warnings, print, файлов, сети, чтения окружения или часов.
  WARN для неизвестного calculation-кода запишет Orchestrator в 5.2/8.2.
- Нет импорта Handler, ContextService, calculation/engine, transport или
  будущих ApplicationResult. Для этого модуля достаточно стандартной библиотеки.
- Общий `CalculationFailed.error_code` остаётся str: Literal применяется к
  локальному `kind`, а не закрывает множество технических error_code.
- Выбор окончательного commit error, количество попыток, deadline, save,
  обработка отмены и нормализация реального исключения принадлежат вызывающему.
- Не превращай Superseded в инфраструктурный failure. Функция формирует
  пользовательскую реакцию, но не выбирает тройку application-статусов.
- Не разрешай конфликт K3 о пустых InputRequired.issues: функция не получает
  issues и не должна их валидировать.
