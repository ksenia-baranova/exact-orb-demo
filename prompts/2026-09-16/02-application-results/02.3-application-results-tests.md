### 1. Проверяемый интерфейс

Импортируй три класса напрямую:

```python
from exact_orb.application.application_results import (
    ApplicationAlreadyApplied,
    ApplicationCommitted,
    ApplicationSuperseded,
)
```

Все три — Pydantic-модели с `ConfigDict(frozen=True)`.

Общие поля:

```text
orch_status
handler_status
context_status
code
detail_code
user_message
retryable
run_id
state_version
```

Контракт этого среза:

| Модель | Тройка статусов | `code` | `detail_code` | `retryable` | `state_version` | Payload |
|---|---|---|---|---|---|---|
| `ApplicationCommitted` | `SUCCESS / SUCCESS / COMMITTED` | `OK` | `None` | `False` | `int >= 1` | обязательный `artifact: ChartArtifact` |
| `ApplicationAlreadyApplied` | `SUCCESS / SUCCESS / ALREADY_APPLIED` | `OK` | `None` | `False` | `int >= 0` | обязательный `artifact: ChartArtifact` |
| `ApplicationSuperseded` | `SUPERSEDED / SUCCESS / SUPERSEDED` | `RESULT_SUPERSEDED` | `None` | `False` | `int >= 0` | отсутствует |

Для двух успешных моделей `user_message=None`.

Для `ApplicationSuperseded` используется текст §10:

```text
Результат этого запроса уже не актуален. Текущая карта не изменена.
```

Фиксированные статусы, `code` и `retryable` задаются через `Literal` согласно требованиям. Тесты должны проверять их фактическое поведение, а не только аннотации.

В валидных образцах передавай поля явно. Не устанавливай дополнительный контракт на значения по умолчанию фиксированных полей.

### 2. Валидные образцы и сохранение значений

Для каждой модели создай корректный экземпляр и проверь:

- точную тройку статусов;
- `code`, `detail_code`, `user_message`, `retryable`;
- переданные `run_id` и `state_version`;
- наличие предусмотренного payload.

UUID бери из `tests.fixtures.telemetry`: используй и `RUN_ID`, и `RUN_ID_B`, чтобы проверить сохранение входного значения.

Для успешных моделей используй настоящий валидный `ChartArtifact` из helper `artifact()` в `tests.fixtures.calculation`.

Проверь равенство полученного артефакта переданному. Identity артефакта не является требованием: не закрепляй `result.artifact is artifact`.

Для `Superseded` допустимо формировать поля реакции через уже реализованный `describe_failure(kind="superseded")`. Ожидаемые значения проверяй независимо по таблице требований; не получай и фактический, и ожидаемый результат из одной production-функции.

### 3. Противоречивые поля отклоняются

Каждый негативный случай начинай с валидного набора аргументов. Меняй **одно поле**, чтобы причина отказа была однозначной.

Для каждой модели проверь отклонение:

- неверного `orch_status`;
- неверного `handler_status`;
- неверного `context_status`;
- чужого application-level `code`;
- ненулевого `detail_code`, например `"SYNTHETIC_ERROR"`;
- `retryable=True`.

Для статусов используй альтернативы из §7–8 и неизвестное строковое значение. В частности:

- `ApplicationCommitted` не принимает `ALREADY_APPLIED` или `COMMIT_FAILED` как `context_status`;
- `ApplicationAlreadyApplied` не принимает `COMMITTED`;
- `ApplicationSuperseded` не принимает `orch_status="SUCCESS"` или `"FAILURE"`;
- ни одна из трёх моделей не принимает `handler_status="NOT_STARTED"`.

Проверяй `pydantic.ValidationError`, а не произвольное исключение.

Не проверяй точный английский текст ошибки Pydantic. Там, где отказ относится непосредственно к полю, проверяй его расположение в `errors()`. Если реализация использует проверку согласованности модели, не навязывай ей имя валидатора или точный формат сообщения.

### 4. Границы `state_version`

Параметризуй:

| Модель | Принимает | Отклоняет |
|---|---|---|
| `ApplicationCommitted` | `1`, положительное значение больше единицы | `0`, `-1`, `None`, отсутствие поля |
| `ApplicationAlreadyApplied` | `0`, положительное значение | `-1`, `None`, отсутствие поля |
| `ApplicationSuperseded` | `0`, положительное значение | `-1`, `None`, отсутствие поля |

Принятая версия сохраняется без изменения. Модель не вычисляет следующую версию и не прибавляет единицу.

Не вводи дополнительную политику strict/coercion для строк, bool или дробных значений: она этим срезом не определена.

### 5. Обязательный `run_id`

Для каждой модели проверь:

- сохранение обоих корректных UUID;
- отклонение отсутствующего `run_id`;
- отклонение `None`;
- отклонение явно некорректной UUID-строки.

Не требуй, чтобы корректная строковая форма UUID обязательно отвергалась: запрет преобразования строки в UUID не установлен.

Эти тесты проверяют поле модели. Совпадение с `run.run_id` в реальном `execute()` будет проверяться позже.

### 6. Payload и сообщение

**Для `ApplicationCommitted` и `ApplicationAlreadyApplied`:**

- валидный `ChartArtifact` принимается;
- отсутствие `artifact`, `artifact=None` и явно невалидный объект, например `{}`, отклоняются;
- `user_message=None` сохраняется;
- произвольный текст вместо `None` отклоняется.

Не повторяй весь набор проверок внутренней согласованности `ChartArtifact`: его собственный контракт уже существует.

**Для `ApplicationSuperseded`:**

- корректная модель создаётся без `artifact`;
- `artifact` отсутствует в обычном `model_dump()`;
- попытка передать настоящий валидный `artifact` отклоняется;
- попытка передать `artifact=None` также отклоняется.

Простого молчаливого удаления переданного `artifact` недостаточно: карточка 2.3 требует, чтобы модель его **не принимала**.

Позитивный контроль — тот же валидный артефакт принимается успешной моделью.

Проверь точный текст `Superseded` в корректном образце и отклонение `user_message=None`. Не навязывай моделям автоматическую генерацию текста или конкретный способ вызова `failure_policy`.

Не расширяй этот этап до общей политики всех неизвестных полей.

### 7. Неизменяемость после создания

Для всех трёх моделей проверь:

- `model_config.get("frozen") is True`;
- присваивание существующему полю вызывает `ValidationError` с типом ошибки `frozen_instance`;
- после отказа исходный экземпляр сохранил прежние значения.

Обязательно включи попытки:

- заменить `run_id` на другой валидный UUID;
- заменить `state_version` на другую допустимую версию;
- присвоить статусу его текущее допустимое значение.

Для успешных моделей также проверь запрет замены `artifact` на другой валидный артефакт.

Используй допустимые значения при попытках изменения: тест должен доказывать заморозку, а не срабатывать из-за невалидного нового значения.

Не используй `model_copy(update=...)` или `model_construct()` для проверки валидации. Не добавляй защиту от обхода Pydantic через `object.__setattr__` и не объявляй рекурсивную неизменяемость всего вложенного артефакта доказанной.

### 8. Проверка публичного набора полей

Для валидных экземпляров проверь обычный `model_dump()`:

- все девять общих полей присутствуют;
- поля со значением `None` сохраняются без `exclude_none=True`;
- у успешных моделей дополнительно присутствует `artifact`;
- у `Superseded` payload отсутствует.

Не закрепляй порядок ключей. Не сравнивай полный большой артефакт с новым вручную написанным JSON.

Этот тест относится к публичным полям модели. HTTP serialization и транспортный контракт остаются за пределами этапа.

### Организация тестов

- Один файл, небольшие параметризованные тесты с понятными идентификаторами случаев.
- Ожидаемые таблицы берутся из требований, а не из production-констант.
- Допустимы локальные helpers для подготовки валидных аргументов; они не реализуют валидацию вместо моделей.
- Используй существующие fixtures. Не создавай новые fixture-файлы.
- Для отключения автоматической настройки эфемерид допустим существующий маркер:

  ```python
  pytestmark = pytest.mark.no_ephemeris_autoinit
  ```

  Он отключает ненужную инициализацию runtime, а не выполнение тестов.

- Не вызывай Handler, resolver, ContextService или реальный расчёт.
- Не импортируй будущий полный `ApplicationResult` union.
- Не используй `importorskip`, `skip`, `xfail`, fallback-классы или подмену модуля в `sys.modules`.
- Не добавляй новые зависимости и quality gates.
