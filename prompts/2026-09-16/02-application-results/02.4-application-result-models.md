## Что реализует этот этап

Создаём три стандартных вида ответа приложения на запрос построения карты:

1. **«Карта сохранена».** Приложение возвращает карту и номер версии состояния, в котором она сохранена.

2. **«Нужный результат уже сохранён».** Например, другой одновременно выполнявшийся запрос уже сохранил тот же результат. Пользователь получает успешный ответ с картой; дополнительная запись не требуется.

3. **«Результат запроса устарел».** За время выполнения запроса состояние сессии изменилось. Приложение сообщает, что результат этого запроса не применён, и передаёт актуальную на момент проверки версию состояния. Саму неприменённую карту этот ответ не содержит.

Каждый ответ содержит идентификатор запроса, чтобы его можно было найти в журнале работы приложения.

**Зачем это нужно:** интерфейс должен однозначно понимать, что произошло, какую карту можно показать и к какой версии состояния относится ответ. Противоречивый ответ — например, «карта сохранена» без карты — должен отклоняться при создании.

**Граница этапа:** здесь создаём и проверяем структуру этих ответов. Построение карты, сохранение сессии и выбор нужного ответа во время выполнения запроса подключаются на следующих этапах.

**Результат работы:** три модели ответов проходят ранее написанные тесты. После создания поля ответа нельзя изменить, чтобы его статус и содержимое оставались согласованными.

## 1. Реализуй точный контракт моделей

Все три модели наследуются от Pydantic `BaseModel` и используют `ConfigDict(frozen=True)`.

| Поле | `ApplicationCommitted` | `ApplicationAlreadyApplied` | `ApplicationSuperseded` |
|---|---|---|---|
| `orch_status` | `Literal["SUCCESS"]` | `Literal["SUCCESS"]` | `Literal["SUPERSEDED"]` |
| `handler_status` | `Literal["SUCCESS"]` | `Literal["SUCCESS"]` | `Literal["SUCCESS"]` |
| `context_status` | `Literal["COMMITTED"]` | `Literal["ALREADY_APPLIED"]` | `Literal["SUPERSEDED"]` |
| `code` | `Literal["OK"]` | `Literal["OK"]` | `Literal["RESULT_SUPERSEDED"]` |
| `detail_code` | только `None` | только `None` | только `None` |
| `user_message` | только `None` | только `None` | обязательный `str` |
| `retryable` | `Literal[False]` | `Literal[False]` | `Literal[False]` |
| `run_id` | обязательный `UUID` | обязательный `UUID` | обязательный `UUID` |
| `state_version` | обязательный `int >= 1` | обязательный `int >= 0` | обязательный `int >= 0` |
| `artifact` | обязательный `ChartArtifact` | обязательный `ChartArtifact` | поля нет |

### Фиксированные поля

Фиксированным полям допустимо задать соответствующие значения по умолчанию. Явно переданное противоречивое значение должно отклоняться, а не заменяться правильным.

Не используй три независимых enum, допускающих произвольные сочетания статусов.

Для этих моделей достаточно декларативных ограничений полей. Не добавляй общий механизм классификации результатов или универсальный валидатор будущего union.

### Обязательные данные

У `run_id`, `state_version` и предусмотренного `artifact` нет fallback-значений или генераторов:

- не создавай UUID;
- не подставляй версию `0`;
- не вычисляй следующую версию;
- не создавай и не рассчитывай артефакт.

Для границ версии используй обычные средства Pydantic, например `Field(ge=1)` и `Field(ge=0)`.

Не вводи глобальный strict mode или дополнительную политику преобразования строк, bool и дробных чисел: тестовый этап 2.3 её не устанавливал.

## 2. Сохрани границу payload

У успешных моделей:

- `artifact` имеет существующий тип `ChartArtifact`;
- отсутствие поля, `None` и невалидное содержимое отклоняются;
- переданный валидный артефакт сохраняет своё содержимое.

Не дублируй внутри application-моделей расчёт `calculation_key` и проверки согласованности артефакта. Это ответственность `ChartArtifact`.

У `ApplicationSuperseded`:

- поля `artifact` нет;
- передача `artifact=<валидный артефакт>` вызывает ошибку валидации;
- передача `artifact=None` также вызывает ошибку.

Молчаливое игнорирование `artifact` не выполняет контракт. Для этой модели используй `extra="forbid"`, чтобы лишний payload отклонялся обычной валидацией Pydantic.

Не добавляй в модели `delta`, snapshot, session ID или внутренний commit outcome.

## 3. Сообщение Superseded

`ApplicationSuperseded.user_message` — обязательная строка, передаваемая вызывающим кодом.

Источник согласованного текста уже существует:

```python
describe_failure(kind="superseded")
```

Ожидаемый текст:

```text
Результат этого запроса уже не актуален. Текущая карта не изменена.
```

В тестах 2.3 поля этой реакции передаются модели явно. Сохрани такой способ создания.

Не копируй таблицу сообщений в новый модуль, не меняй `failure_policy.py` и не добавляй автоматическую генерацию сообщения внутри модели. Здесь проверяется наличие строкового поля и сохранение переданного текста; выбор реакции остаётся в политике отказов.

Для двух успешных моделей `user_message` допускает только `None`.

## 4. Неизменяемость и публичные поля

После создания модели нельзя присвоить существующему полю новое значение — даже если оно само по себе допустимо.

Используй штатную заморозку Pydantic. Не реализуй собственный `__setattr__` и не обходи валидацию через `model_construct()`.

Обычный `model_dump()` должен сохранять:

- все девять общих полей;
- `detail_code=None`;
- `user_message=None` для успеха;
- `artifact` только у успешных моделей.

Не переопределяй `model_dump()` ради удаления полей и не добавляй собственную JSON serialization.

Не обещай рекурсивную неизменяемость всего вложенного графа артефакта: этот этап проверяет заморозку application-моделей.

## 5. Архитектурные границы

- Новый модуль содержит только три текущие модели и необходимые для них определения.
- Используй настоящий `ChartArtifact`, не подменяй его `Any`, словарём или локальным дублем.
- Не импортируй Handler, ContextService, transport или будущий Orchestrator.
- Не выполняй I/O, логирование, чтение часов или окружения.
- Не классифицируй session outcomes и не выполняй CAS.
- `BuildNatalSuccess` остаётся в `application/results.py`.
- Не экспортируй новые классы через соседние `__init__.py`.
- Не объявляй union из трёх моделей под именем `ApplicationResult`: полный контракт появится в 2.6.
- Не решай вопрос K3 о пустых `InputRequired.issues`: эти модели с ним не связаны.
