## Что реализует этот этап

На предыдущем этапе появились три ответа приложения: **карта сохранена**, **нужный результат уже сохранён**, **результат запроса устарел**.

Теперь готовим автоматические проверки для остальных ситуаций:

1. **Нужно исправить введённые данные.** Ответ должен объяснять, какие поля требуют внимания.
2. **Не удалось определить место или время.** Приложение должно сообщить о проблеме и указать, имеет ли смысл повторить запрос.
3. **Не удалось рассчитать карту.** Ответ должен отличать временную недоступность расчёта от случая, когда расчёт невозможен для выбранных данных.
4. **Сессия отсутствует или потеряна.** Нужно различать ситуацию, когда сессии не было уже в начале, и ситуацию, когда она исчезла во время выполнения запроса.
5. **Не удалось загрузить состояние сессии.** Такой сбой сам по себе не означает, что данные потеряны.
6. **Сохранение не подтверждено.** Приложение не должно сообщать об успешном сохранении, если подтверждения нет. При этом утверждать, что запись точно не произошла, тоже нельзя.
7. **Произошла внутренняя ошибка.** Пользователь получает понятное сообщение, а технические подробности не должны подставляться в этот текст.

Также проверяем, что все десять видов ответа образуют единый согласованный набор. Например, нельзя создать ответ, который одновременно сообщает об ошибке расчёта и об успешном сохранении карты.

**Зачем это нужно:** интерфейс должен понимать, что показать пользователю и какое действие предложить. Ошибка в структуре ответа не должна превращаться в ложное сообщение об успехе, потере данных или возможности повторить запрос.

**Граница этапа:** сейчас пишем проверки этих правил. Реализация оставшихся моделей будет в **2.6**. Расчёт карты, сохранение сессии и обработка реальных запросов здесь не выполняются.

**Результат работы:** подготовлен набор тестов для всех десяти видов ответа. До реализации 2.6 новые проверки ещё не смогут успешно выполниться; это состояние нужно явно записать в журнал.

## 2. Контракт семи моделей

Общие поля остаются прежними:

```text
orch_status, handler_status, context_status
code, detail_code, user_message, retryable
run_id, state_version
```

| Модель | Статусы: orch / handler / context | `code` | `detail_code` | `retryable` | `state_version` | Дополнительные поля |
|---|---|---|---|---|---|---|
| `ApplicationInputRequired` | INPUT_REQUIRED / INPUT_REQUIRED / LOADED | INPUT_REQUIRED | None | False | прочитанная, ≥ 0 | непустой `issues` |
| `ApplicationResolutionFailure` | FAILURE / RESOLUTION_UNAVAILABLE / LOADED | RESOLUTION_UNAVAILABLE | строка Handler | переданный bool | прочитанная, ≥ 0 | нет |
| `ApplicationCalculationFailure` | FAILURE / CALCULATION_FAILED / LOADED | CALCULATION_FAILED | строка Handler | зависит от кода | прочитанная, ≥ 0 | нет |
| `ApplicationSessionAbsent` | по таблице ниже | по стадии и причине | None | False | None | `reason` |
| `ApplicationStateReadFailure` | FAILURE / NOT_STARTED / READ_FAILED | STATE_READ_FAILED | строка persistence | True | None | нет |
| `ApplicationStateCommitFailure` | FAILURE / SUCCESS / COMMIT_FAILED | STATE_COMMIT_FAILED | строка persistence | True | None | нет |
| `ApplicationInternalFailure` | по таблице ниже | INTERNAL_FAILURE или HANDLER_NOT_REGISTERED | None | False | по стадии | нет |

Для каждой модели:

- `run_id` — обязательный UUID;
- `user_message` — строка, `None` не допускается;
- модель заморожена;
- фиксированные статусы, коды и значения `retryable` не принимают противоречивые значения.

В валидных образцах передавай поля явно. Не устанавливай новые требования к defaults фиксированных полей или общей политике преобразования типов.

## 4. Технические отказы и политика повторения

### ResolutionFailure

Проверь оба значения `retryable` для одного и того же технического кода.

Модель сохраняет переданный bool. Она не должна самостоятельно решать по названию кода, допустим ли повтор.

Неизвестный строковый код принимается и сохраняется в `detail_code`.

### CalculationFailure

Проверь согласованность `detail_code` и `retryable`:

| `detail_code` | Допустимый `retryable` |
|---|---|
| EPHEMERIS_UNAVAILABLE | True |
| HOUSES_DEGENERATE | False |
| SPEC_INVALID | False |
| GEOGRAPHY_INVALID | False |
| ENGINE_UNEXPECTED | False |
| неизвестный строковый код | False |

Для каждой строки:

1. Согласованный образец принимается.
2. Противоположное значение `retryable` отклоняется.
3. Код сохраняется без изменения.

Используй не менее двух разных неизвестных calculation-кодов. Множество кодов остаётся открытым: не закрепляй `Literal` из пяти известных значений.

### ReadFailure и CommitFailure

Проверь:

- `retryable=True`;
- отклонение `retryable=False`;
- сохранение неизвестного строкового `detail_code`;
- `state_version=None`;
- отклонение версии `0` и положительной версии.

Проверка модели `CommitFailure` не доказывает, что повтор commit состоялся или что выбран код последней попытки. Здесь модель сохраняет уже переданный код.

### Общая граница технического кода

Для четырёх технических failure-моделей проверь обязательность строкового `detail_code`: отсутствие и `None` отклоняются.

Не вводи ограничений на длину, список допустимых значений или непустоту строки, которых нет в требованиях.

## 5. SessionAbsent: причина и стадия связаны

Проверь все четыре допустимых случая:

| `handler_status` | `reason` | `code` |
|---|---|---|
| NOT_STARTED | expired | SESSION_EXPIRED |
| NOT_STARTED | not_found | SESSION_NOT_FOUND |
| SUCCESS | expired | SESSION_LOST_DURING_OPERATION |
| SUCCESS | not_found | SESSION_LOST_DURING_OPERATION |

Во всех случаях:

```text
orch_status = SESSION_ABSENT
context_status = SESSION_ABSENT
detail_code = None
retryable = False
state_version = None
```

Для каждого валидного случая проверь отклонение противоречий:

- код не соответствует причине;
- код относится к другой стадии;
- неизвестная причина;
- отсутствующая или `None` причина;
- ненулевой `detail_code`;
- числовая `state_version`;
- неверные статусы или `retryable=True`.

Не добавляй отдельное поле `stage`: в действующем контракте стадия выражена через `handler_status`.

## 6. InternalFailure: полная разрешённая запись

Проверь четыре допустимые записи:

| `code` | `handler_status` | `context_status` | `state_version` |
|---|---|---|---|
| HANDLER_NOT_REGISTERED | NOT_STARTED | NOT_ACCESSED | None |
| INTERNAL_FAILURE | NOT_STARTED | NOT_ACCESSED | None |
| INTERNAL_FAILURE | UNEXPECTED_FAILURE | LOADED | прочитанная, ≥ 0 |
| INTERNAL_FAILURE | SUCCESS | COMMIT_FAILED | None |

Общие значения:

```text
orch_status = FAILURE
detail_code = None
retryable = False
```

Проверяй связи между полями, а не только принадлежность каждого поля списку допустимых значений.

Обязательно отклоняются:

- `HANDLER_NOT_REGISTERED` со стадией Handler или commit;
- `UNEXPECTED_FAILURE / COMMIT_FAILED`;
- `SUCCESS / LOADED`;
- `NOT_STARTED / LOADED`;
- `None` вместо прочитанной версии в Handler-варианте;
- числовая версия до загрузки или при неподтверждённом commit;
- ненулевой `detail_code`;
- `retryable=True`.

Для Handler-варианта проверь принятие версии `0`, положительной версии и отклонение отрицательной.

Не передавай модели реальное исключение и не добавляй в неё обработку исключений.

## 7. Сообщения и общие проверки

### Сообщения

Для корректных образцов допустимо получать поля реакции через `describe_failure`.

Ожидаемые значения проверяй независимо по §10 требований. Не вычисляй фактический и ожидаемый результат одной production-функцией.

Существующие тесты политики уже проверяют таблицу текстов. Здесь проверяется, что корректная реакция принимается моделью и сохраняется вместе с остальными полями.

Следуй границе, принятой в 2.4:

- сообщение передаёт вызывающий;
- модель принимает строку и сохраняет её;
- автоматическая генерация, очистка или семантическая проверка произвольного текста моделью не вводится.

Не выдавай эти тесты за доказательство отсутствия raw exception text во всём application-flow. Это будет проверяться на реальном пути нормализации ошибок.

### Версии и UUID

Для всех новых моделей проверь:

- сохранение `RUN_ID` и `RUN_ID_B` из telemetry fixtures;
- отклонение отсутствующего UUID, `None` и некорректной UUID-строки;
- сохранение допустимой версии без изменения;
- обязательность версии там, где требуется прочитанное состояние;
- запрет числовой версии там, где контракт требует `None`.

### Payload

Проверь точный публичный набор полей через обычный `model_dump()`:

- девять общих полей;
- дополнительно `issues` только у `ApplicationInputRequired`;
- дополнительно `reason` только у `ApplicationSessionAbsent`.

Поля со значением `None` присутствуют.

Все семь моделей отклоняют переданный `artifact`, включая `artifact=None`. Положительный контроль — тот же валидный артефакт принимается существующей успешной моделью.

Не требуй нового формата сериализации или порядка ключей.

### Frozen

Для каждой новой модели:

- проверь `model_config.get("frozen") is True`;
- попробуй заменить `run_id` другим корректным UUID;
- проверь ошибку `frozen_instance`;
- убедись, что экземпляр сохранил исходные значения.

Для `InputRequired` и `SessionAbsent` также проверь запрет замены их дополнительных полей допустимыми значениями. Для смены причины сессии используй commit-вариант, где обе причины допустимы при одном коде.

Не проверяй глубокую заморозку вложенного `Issue`: это отдельный контракт, который данный этап не меняет.
