## Что реализует этот этап

Завершаем **единый формат ответов приложения**.

Три ответа уже реализованы: карта сохранена, нужный результат уже сохранён, результат запроса устарел. Теперь добавляем остальные семь:

| Ситуация | Что должен сообщать ответ |
|---|---|
| Введённых данных недостаточно или они требуют исправления | Какие поля нужно проверить |
| Не удалось определить место или время | Что произошло и допустим ли повтор |
| Не удалось рассчитать карту | Какая причина возникла и может ли повтор помочь |
| Сессия отсутствует | Не было ли её уже в начале запроса или она потеряна во время выполнения |
| Не удалось загрузить состояние | Что загрузка не удалась; это само по себе не означает потерю данных |
| Сохранение не подтверждено | Что успешное сохранение подтвердить нельзя |
| Произошла внутренняя ошибка | Понятное сообщение для пользователя и согласованные сведения о стадии ошибки |

**Зачем это нужно:** интерфейс должен однозначно понимать ответ приложения. Например, при временной недоступности расчёта можно разрешить повтор, а при неподтверждённом сохранении нельзя показать сообщение «карта успешно сохранена».

Модели будут проверять согласованность ответа при его создании. Противоречивый ответ — например, ошибка загрузки с подтверждённой версией сохранённой карты — должен отклоняться.

После создания основные поля ответа нельзя изменить. Это защищает от ситуации, когда один участок программы поменял статус, а остальные сведения остались прежними.

### Что будет готово после этапа

- Все десять видов ответа определены в одном модуле.
- Для каждого ответа проверяются обязательные поля и допустимые сочетания значений.
- Все десять моделей объединены под общим именем `ApplicationResult`.
- Ранее подготовленные тесты моделей исполняются и проходят.

**Граница этапа:** создаём структуры ответов и правила их проверки. Выбор ответа во время реального запроса, расчёт карты, чтение сессии, сохранение и повтор сохранения подключаются позже.

## 2. Общие правила новых моделей

У всех семи моделей есть девять общих полей:

```text
orch_status
handler_status
context_status
code
detail_code
user_message
retryable
run_id
state_version
```

Используй:

```python
model_config = ConfigDict(frozen=True, extra="forbid")
```

Правила:

- `run_id` — обязательный `UUID`;
- `user_message` — обязательная строка, `None` не допускается;
- фиксированные статусы и application-коды закрепляются через `Literal`;
- фиксированный `retryable` закрепляется через `Literal[True]` или `Literal[False]`;
- версия прочитанного состояния — обязательное целое число `>= 0`;
- там, где достоверная версия неизвестна, допускается только `None`;
- дополнительные поля разрешены только соответствующему варианту ответа;
- все семь моделей отклоняют `artifact`, включая `artifact=None`.

Не вводи новую общую политику строгого преобразования типов, ограничения длины строк или дополнительные ограничения UUID.

### Сообщение передаёт вызывающий

Модель принимает `user_message` и сохраняет его.

Она не генерирует текст автоматически, не очищает произвольную строку и не проверяет её смысл. Выбор сообщения уже принадлежит `failure_policy.py`, а безопасное преобразование реального исключения будет обязанностью Orchestrator.

Не дублируй таблицу пользовательских текстов в моделях.

## 3. ApplicationInputRequired — данные требуют исправления

Этот ответ должен давать интерфейсу конкретные сведения о полях, требующих внимания.

```text
orch_status    = INPUT_REQUIRED
handler_status = INPUT_REQUIRED
context_status = LOADED
code           = INPUT_REQUIRED
detail_code    = None
retryable      = False
state_version  = обязательная прочитанная версия >= 0
```

Дополнительное поле:

```python
issues: tuple[Issue, ...]
```

Используй существующий `Issue` из `exact_orb.outcomes`.

Требования:

- tuple непустой;
- отсутствие `issues`, `None`, пустой tuple и невалидный элемент отклоняются;
- порядок и содержимое issues сохраняются;
- `candidates` и `constraints` сохраняются по существующему контракту `Issue`;
- присваивание нового значения `issues` после создания модели запрещено.

Не меняй сам `Issue` и не вводи глубокую заморозку вложенных значений.

### Открытый вопрос K3

Handler сейчас допускает `InputRequired(issues=())`, а внешний ответ требует непустой список.

На этом этапе реализуй действующее внешнее ограничение: пустой список отклоняется.

Не подставляй фиктивную ошибку, не меняй Handler и не выбирай автоматически `InternalFailure`. Решение о преобразовании такого Handler outcome остаётся открытым перед этапами 5.1–5.2.

## 4. Технические отказы

| Модель | `orch_status` | `handler_status` | `context_status` | `code` | `retryable` | `state_version` |
|---|---|---|---|---|---|---|
| `ApplicationResolutionFailure` | FAILURE | RESOLUTION_UNAVAILABLE | LOADED | RESOLUTION_UNAVAILABLE | Переданный bool | Обязательная, `>= 0` |
| `ApplicationCalculationFailure` | FAILURE | CALCULATION_FAILED | LOADED | CALCULATION_FAILED | По политике расчётных ошибок | Обязательная, `>= 0` |
| `ApplicationStateReadFailure` | FAILURE | NOT_STARTED | READ_FAILED | STATE_READ_FAILED | True | None |
| `ApplicationStateCommitFailure` | FAILURE | SUCCESS | COMMIT_FAILED | STATE_COMMIT_FAILED | True | None |

Для всех четырёх моделей:

```python
detail_code: str
```

Поле обязательно. Отсутствие и `None` отклоняются.

Неизвестные строковые коды принимаются и сохраняются. Не ограничивай их закрытым списком, длиной или непустотой строки.

### ResolutionFailure

Сохраняй переданное значение `retryable`.

Для одного и того же `detail_code` допустимы и `True`, и `False`: решение уже принято Handler. Модель не должна выводить возможность повторения из названия кода.

### CalculationFailure

Здесь возможность повторения зависит от причины отказа:

| `detail_code` | Допустимый `retryable` |
|---|---:|
| `EPHEMERIS_UNAVAILABLE` | True |
| `HOUSES_DEGENERATE` | False |
| `SPEC_INVALID` | False |
| `GEOGRAPHY_INVALID` | False |
| `ENGINE_UNEXPECTED` | False |
| Любой неизвестный строковый код | False |

Используй существующую политику:

```python
describe_failure(
    kind="calculation_failed",
    error_code=self.detail_code,
)
```

Валидатор сравнивает переданный `retryable` с результатом политики.

**Противоречие нужно отклонить**, а не молча исправить. Переданные `detail_code` и `user_message` сохраняются.

Не создавай второй список известных calculation-кодов в модели. Не меняй `CalculationFailed.error_code` в общем `outcomes.py`: он остаётся строкой.

### ReadFailure и CommitFailure

Обе модели требуют:

```text
retryable = True
state_version = None
```

Числовая версия, включая `0`, отклоняется.

Модель `CommitFailure` сохраняет уже переданный технический код. Она не выполняет повтор сохранения и не определяет, какая попытка была последней.

## 5. ApplicationSessionAbsent — различаем причину и стадию

Потеря сессии во время выполнения запроса отличается от отсутствия сессии в самом начале. Ответ должен сохранять это различие.

Общие поля:

```text
orch_status    = SESSION_ABSENT
context_status = SESSION_ABSENT
detail_code    = None
retryable      = False
state_version  = None
```

Дополнительное обязательное поле:

```python
reason: Literal["expired", "not_found"]
```

Допустимы только четыре сочетания:

| `handler_status` | `reason` | `code` |
|---|---|---|
| NOT_STARTED | expired | SESSION_EXPIRED |
| NOT_STARTED | not_found | SESSION_NOT_FOUND |
| SUCCESS | expired | SESSION_LOST_DURING_OPERATION |
| SUCCESS | not_found | SESSION_LOST_DURING_OPERATION |

Проверь эту связь валидатором модели. Это **проверка согласованности полей**: статус, код ошибки и причина должны соответствовать друг другу.

Недостаточно разрешить каждому полю отдельный список значений: сочетание `NOT_STARTED / expired / SESSION_NOT_FOUND` должно отклоняться.

Не добавляй поле `stage`. Стадия уже выражена через `handler_status`.

Не меняй причину или код автоматически ради согласования входных данных.

## 6. ApplicationInternalFailure — согласованный ответ внутренней ошибки

Ответ должен показывать, до какой стадии дошла операция, без ложного подтверждения сохранения.

Общие поля:

```text
orch_status = FAILURE
detail_code = None
retryable   = False
```

Допустимы только четыре полные записи:

| `code` | `handler_status` | `context_status` | `state_version` |
|---|---|---|---|
| HANDLER_NOT_REGISTERED | NOT_STARTED | NOT_ACCESSED | None |
| INTERNAL_FAILURE | NOT_STARTED | NOT_ACCESSED | None |
| INTERNAL_FAILURE | UNEXPECTED_FAILURE | LOADED | Обязательная прочитанная версия `>= 0` |
| INTERNAL_FAILURE | SUCCESS | COMMIT_FAILED | None |

Валидатор должен проверять связанные поля вместе.

В частности, отклоняются:

- `HANDLER_NOT_REGISTERED` после выполнения Handler или на commit;
- `UNEXPECTED_FAILURE / COMMIT_FAILED`;
- `SUCCESS / LOADED`;
- `NOT_STARTED / LOADED`;
- `None` вместо прочитанной версии в Handler-варианте;
- числовая версия до получения состояния или при неподтверждённом commit;
- ненулевой `detail_code`;
- `retryable=True`.

Используй обычные ошибки валидации Pydantic. Внутри валидатора допустим `ValueError`, который становится `ValidationError` при создании модели.

Модель не получает реальное исключение, не обрабатывает `CancelledError` и не пишет лог.

## 7. Полный ApplicationResult

Объяви обычное объединение десяти конкретных моделей:

```python
ApplicationResult = (
    ApplicationCommitted
    | ApplicationAlreadyApplied
    | ApplicationInputRequired
    | ApplicationResolutionFailure
    | ApplicationCalculationFailure
    | ApplicationSessionAbsent
    | ApplicationStateReadFailure
    | ApplicationStateCommitFailure
    | ApplicationSuperseded
    | ApplicationInternalFailure
)
```

Добавь новые модели и `ApplicationResult` в существующий `__all__`.

Не добавляй в union `Any`, `None`, общий `BaseModel`, Handler outcomes или запасной вариант для неизвестного ответа.

Не вводи дополнительное поле-дискриминатор или обёртку вокруг результата.

Существующие тесты используют:

```python
get_args(ApplicationResult)
TypeAdapter(ApplicationResult)
```

Они должны видеть десять конкретных типов и выбирать правильную модель по полной записи.

Особенно важно различать:

- `ApplicationCommitted` и `ApplicationAlreadyApplied`;
- `ApplicationStateCommitFailure` и `ApplicationInternalFailure` на commit.

Последние два варианта имеют одинаковые статусы, но разные `code`, `detail_code` и `retryable`.

Множество допустимых троек статусов должно точно соответствовать **12 уникальным комбинациям** §8 требований.

## 9. Связь тестов с требованиями

У каждого теста должно быть понятно, какое требование он проверяет, какое поведение подтверждает и какая часть требования ещё не проверена.

**Зачем это нужно:** при изменении требования можно быстро найти соответствующие тесты, а при приёмке — увидеть, чем подтверждено выполнение требования.

Ссылки на требования должны находиться **внутри самого теста, в docstring**. На момент сохранения промта они уже добавлены ко всем 39 тестовым функциям. Сохрани их, включая пояснения к частичному покрытию. Например:

```python
def test_failure_models_are_frozen_for_valid_field_assignments(case):
    """Созданные модели запрещают замену run_id другим корректным UUID.

    Требования: R3.2, FR-22, §9; AC-24.
    """
    # Далее остаются существующие assertions теста.
```

Не назначай всем тестам общий диапазон AC-19–27. Описание должно соответствовать реальным assertions.

В журнал 2.6 добавь таблицу:

| Требование | Что проверяется | Тесты | Результат запуска | Что остаётся проверить |
|---|---|---|---|---|

Основные соответствия:

- состав моделей и допустимые статусы — FR-22, §8–9, AC-22;
- отклонение противоречивых полей — FR-22, §9, AC-23;
- неизменяемость созданной модели — FR-22, AC-24;
- различение отсутствия сессии до и после Handler — §9, модельная часть AC-20;
- наличие или отсутствие версии — §12, модельная часть AC-27;
- сохранение переданного run_id — §12, модельная часть AC-26;
- сохранение корректной реакции — FR-23, §10, часть AC-25 о полях ответа.

Укажи точные имена тестов и результат фактического запуска. Сохранение UUID в модели не доказывает его передачу через все компоненты. Принятие безопасного сообщения не доказывает отсутствие текста реального исключения. Проверка неизвестного calculation-кода не подтверждает WARN, а CommitFailure — выполнение повтора.

Исполняемый код тестов сохраняется. Если пришлось дополнить docstrings, сравни AST до и после изменения, исключив только docstrings; fixtures, decorators, параметризации и assertions должны совпасть. Если описания уже готовы, сохрани весь тестовый файл без изменений.
