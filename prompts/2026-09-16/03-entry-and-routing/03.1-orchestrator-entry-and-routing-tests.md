## Что реализует этот этап

Приложение уже умеет описывать результаты операции и записывать события её выполнения. Теперь готовим проверки того, **как запрос попадает к нужному обработчику**.

ApplicationOrchestrator — координатор запроса. Он получает готовую команду, выбирает ответственный за неё обработчик, а затем организует чтение сессии, выполнение работы и сохранение результата. На этом этапе проверяем вход и выбор обработчика — routing.

Проверяем пять правил:

1. **Запрос приходит с готовым контекстом операции.** В нём уже есть идентификатор, связывающий ответ и записи журнала. Координатор не должен создавать другой идентификатор и терять связь с исходным запросом.
2. **Каждая команда направляется только явно назначенному обработчику.** Похожая команда или её расширенная версия не должны автоматически попасть в старый обработчик: он может не понимать новые данные или правила.
3. **Если обработчик не назначен, запрос завершается до чтения сессии.** Ошибка настройки должна быть видна сразу. Она не должна маскироваться сообщением об истёкшей сессии или запускать ненужную работу с данными.
4. **Настройки маршрутизации фиксируются при создании координатора.** Если внешний код позже изменит исходный словарь настроек, уже созданный координатор продолжит работать с прежними назначениями.
5. **Отказ можно проследить в журнале.** У него должны быть один старт, одно завершение и тот же идентификатор, что у входного запроса и ответа.

**Зачем это нужно:** эти проверки защищают от отправки запроса не тому обработчику, скрытых изменений конфигурации и вводящих в заблуждение ошибок. Они также помогают найти конкретную неудачную операцию в журнале.

Обязательно добавляем положительный контроль: зарегистрированная команда действительно доходит до своего обработчика. Иначе проверка «неизвестная команда никого не вызывает» могла бы пройти у системы, которая вообще ничего не выполняет.

**Граница этапа:** сейчас пишем тесты и небольшие тестовые компоненты, которые записывают обращения к ним. Сам координатор будет появляться начиная с **3.2**. Чтение сессии, вызов обработчика и сохранение собираются последовательно в группах **4–6**.

**Результат работы:** подготовлен проверяемый набор правил входа и маршрутизации с явным указанием, когда каждый тест сможет пройти. Наличие тестов ещё не означает, что обработка запросов реализована.

## 1. Проверяемый публичный API

Тесты должны использовать контракт R3.2:

```python
orchestrator = ApplicationOrchestrator(
    context=context,
    handlers=handlers,
    clock=clock,
)

result = await orchestrator.execute(
    command,
    session_id=session_id,
    run=run,
)
```

Конструктор получает только `context`, `handlers`, `clock`. Не требуй отдельного telemetry port, recorder или параметра для тестирования. Журнал вызовов принадлежит fake-компонентам теста.

### Обязательный run

В тесте с фрагментом имени `requires_run` проверь:

- `run` — обязательный keyword-only параметр `execute`, без значения по умолчанию;
- вызов без `run` даёт `TypeError` на привязке аргументов, до выполнения операции;
- `context.load`, Handler и `context.save` не вызывались.

Проверь сигнатуру и реальный вызов без аргумента. Не ограничивайся анализом аннотации. Не привязывайся к точному тексту Python `TypeError`.

Вызов без обязательного аргумента ещё не является начатым `execute`: не требуй для него lifecycle-событий. Корректный вызов с явно переданным `run` проверяется в остальных сценариях.

Не добавляй новый контракт runtime-валидации для `run=None` или произвольного объекта. Не проверяй здесь frozen/extra модели `RunContext` и не дублируй её UTC-тесты.

## 2. Неизвестная команда: отказ до чтения сессии

Создай небольшой локальный тип команды, наследующий настоящий `Command`, и не регистрируй его. В реестре при этом должен быть обработчик другой команды: это дополнительно обнаруживает ошибочный fallback «возьмём любой Handler».

Fake context заранее настрой на валидный ответ `load`, например `SessionAbsent(reason="not_found")`. Вызов всё равно не должен состояться: существование или состояние сессии не меняет ошибку маршрутизации.

Проверь настоящий результат `execute`:

| Поле | Ожидаемое значение |
|---|---|
| Тип | `ApplicationInternalFailure` |
| `orch_status` | `FAILURE` |
| `handler_status` | `NOT_STARTED` |
| `context_status` | `NOT_ACCESSED` |
| `code` | `HANDLER_NOT_REGISTERED` |
| `detail_code` | `None` |
| `user_message` | `Не удалось выполнить запрос из-за внутренней ошибки.` |
| `retryable` | `False` |
| `run_id` | UUID переданного `run` |
| `state_version` | `None` |

Журнал обращений к context и Handler должен быть пустым; `load`, `handle` и `save` не вызваны.

Ожидания задай по требованиям, независимо от production `describe_failure`. Вызов той же функции для построения ожидаемого ответа может скрыть ошибку реализации.

Не подменяй `execute`, его результат или внутренний выбор Handler. Имена этих тестов должны содержать `unknown_command`.

## 3. Точный тип команды и положительный контроль

Используй два связанных типа: базовую команду и её подкласс. Наследование нужно только в тестах; новые production-команды не добавляются.

Подготовь самостоятельные сценарии:

1. **Базовый тип зарегистрирован.** Его экземпляр проходит `load`, затем вызывается назначенный Handler.
2. **Зарегистрирован только базовый тип, пришёл подкласс.** Получаем тот же отказ `HANDLER_NOT_REGISTERED` до `load`. Базовый Handler не вызывается. Имя теста содержит `subclass`.
3. **Оба типа явно зарегистрированы за разными Handler.** Экземпляр дочернего типа вызывает только свой Handler, экземпляр базового — только базовый. Это проверяет, что подклассы допустимы при собственной точной регистрации.

Для первых положительных сценариев достаточно `SessionSnapshot` и настоящего `InputRequired` с **непустым** набором `Issue`. Проверь `ApplicationInputRequired` и фактические обращения. Пустой `issues` не используй: вопрос K3 остаётся вне этой карточки.

В едином журнале должно быть видно `load → handle`; переданный `session_id` сохранён. У выбранного Handler проверь аргументы `command`, `snapshot.state` и `run` по identity. Другие Handler не вызывались. Детальная матрица load/Handler outcomes относится к группам 4–5.

Дополнительно подготовь **один** положительный сценарий полного пути:

```text
зарегистрированная команда → SessionSnapshot → BuildNatalSuccess
→ один context.save → Committed → ApplicationCommitted
```

Используй согласованные `artifact` и `delta`, собранные из существующих fixtures. Fake `save` возвращает заранее заданный `Committed`; проверяются порядок `load → handle → save`, исходная версия и переданная delta, а также успешный application-ответ.

Это unit-контроль того, что координатор продолжает обработку известной команды. Он не доказывает реальную запись в хранилище, CAS или работу расчётного движка.

## 4. Защитная копия реестра

Реестр — внешний mapping «тип команды → Handler», переданный конструктору. Проверяй его фиксацию через поведение публичного `execute`, без чтения `_handlers` и других приватных полей.

Нужны три изменения исходного словаря **после** создания координатора:

| Изменение внешнего словаря | Поведение уже созданного координатора |
|---|---|
| Добавлен новый тип | Для него по-прежнему `HANDLER_NOT_REGISTERED`, `load` не вызывается |
| Удалено прежнее назначение | Прежняя команда по-прежнему вызывает первоначальный Handler |
| Прежний Handler заменён другим | Вызывается первоначальный Handler; новый не вызван |

Для добавления сделай положительный контроль: **новый** координатор, созданный уже из изменённого mapping, принимает добавленный тип и вызывает назначенный Handler. Иначе отрицательный тест мог бы пройти при полном игнорировании входного реестра.

Проверяется копирование состава назначений, а не глубокое копирование объектов Handler. Не требуй конкретного контейнера, `MappingProxyType` или дублирования зависимостей.

Конфигурация поступает только через конструктор. Не вводи для тестов runtime registration/replacement и не обращайся к придуманным методам регистрации. Полнота реестра поддерживаемых production-команд проверяется отдельно в 10.1–10.2.

## 5. События отказа маршрутизации

Через `caplog` наблюдай реальные записи существующего `operation_logging`. Уровень захвата — `DEBUG`, чтобы случайное событие стадии не оказалось скрыто фильтром.

Для одного корректно вызванного `execute` с неизвестной командой проверь:

- ровно один `application_operation_started`, уровень `INFO`, с типом фактической команды;
- ровно один `application_operation_finished`, уровень `WARNING`, `terminal_kind=result`;
- started предшествует terminal; terminal уже записан к моменту возврата ответа;
- UUID обоих событий совпадает с входным `run.run_id` и `result.run_id`;
- статусы, `code`, `detail_code` и `state_version` terminal совпадают с возвращённым отказом;
- нет `application_stage_finished` и `application_commit_attempt_finished`;
- `commit_attempts=0`, `commit_error_codes=()`, `delivery_cancelled=False`;
- длительности не начатых стадий равны `None`.

Ограничь выборку application lifecycle-событиями этой операции. Не запрещай сторонние диагностические записи одним assertion на размер всего `caplog.records`.

Ожидания проверяются по публичному содержимому записей; не замыкай проверку на точном шаблоне строки или `LogRecord.args`. Учти существующий формат `key=value`, в котором значения могут содержать пробелы. Не импортируй приватные helpers из другого тестового модуля и не переноси сюда весь набор тестов logging-функций.

Не меняй глобальную конфигурацию логирования. Временные настройки теста восстанавливай. События после load, Handler, commit и отмены остаются группам 4–9; здесь проверяется только полностью определённая ветка routing failure.

## 6. Минимальные recording fake-компоненты

В `orchestrator_fakes.py` нужны только зависимости для перечисленных сценариев:

- context с асинхронными `load(session_id)` и `save(session_id, expected_state_version, delta)`;
- Handler с асинхронным `handle(command, state, run)`;
- простой callable clock, возвращающий фиксированное timezone-aware UTC значение, если это удобно вынести из теста.

Каждый fake сохраняет аргументы без копирования и записывает вызов в общий для **одного теста** журнал. У разных экземпляров нет общего изменяемого состояния. Возвращаемый outcome задаётся тестом явно; отсутствие настроенного ответа не должно автоматически означать успех.

Используй настоящие модели `SessionSnapshot`, `SessionState`, Handler outcomes и commit outcomes. Не реализуй в fake вычисление версии, применение delta, CAS, retry или маршрутизацию. Не создавай собственный вариант `ContextService` или расчётного движка.

Для UUID и времени используй `tests/fixtures/telemetry.py`. Расчётный `artifact` нужен только полному положительному сценарию: не загружай расчётные fixtures исключительно ради времени/UUID. Переиспользуй доступные helpers; не импортируй приватные функции из `test_*.py` и не меняй существующий `tests/application/stubs.py`.

Применяй существующий маркер `no_ephemeris_autoinit`: эти unit-тесты не вызывают Swiss Ephemeris. Не добавляй зависимости, I/O, `sleep`, случайные задержки, фоновые задачи и инфраструктуру будущих concurrency-тестов.

## 7. Когда проверки смогут пройти

План вводит координатор постепенно. Раздели тесты так, чтобы ранняя проверка 3.2 не требовала ещё не реализованных стадий:

| Проверка | Устойчивое имя или фрагмент имени | Первая точка проверки |
|---|---|---|
| Обязательный `run` | `requires_run` | 3.2 |
| Неизвестная команда и её события | `unknown_command` | 3.2 |
| Подкласс без собственного назначения | `subclass` | 3.2 |
| Внешнее добавление не меняет старый реестр | `registry` | 3.2; положительная пара — 5.2 |
| Зарегистрированный тип доходит до Handler | `test_exact_type_reaches_handler` | 5.2 после 4.2 |
| Дочерний тип с явной регистрацией | `test_explicit_child_registration_selects_own_handler` | 5.2 |
| Удаление/замена внешнего назначения не меняет старый Handler | `test_external_mapping_removal_keeps_original_handler`, `test_external_mapping_replacement_keeps_original_handler` | 5.2 |
| Новый экземпляр принимает добавленный тип | `test_new_instance_accepts_added_type` | 5.2 |
| Полный успешный путь | `test_known_command_completes_with_commit` | 6.4 |

Поздние положительные тесты не должны содержать `requires_run`, `unknown_command`, `subclass` или `registry` в имени функции, параметризованного случая либо родительского класса: эти фрагменты использует `-k` карточки 3.2.

Отрицательные и соответствующие положительные сценарии остаются в одном файле. В docstring укажи связь между ними. Частичный успех раннего набора не закрывает полностью exact routing, защитную копию и порядок стадий.

Не используй `skip`, `xfail`, `importorskip`, условные импорты, проверки наличия метода с тихим выходом, временные классы или подмену модуля ради успешного прогона. Не перехватывай произвольное исключение как доказательство, что нужная ветка «достаточно далеко дошла».

## 8. Связь тестов с требованиями

В docstring **каждого теста** напиши по-русски: что проверяем, зачем это нужно и на какие пункты требований опираемся. Укажи границу доказательства, если проверяется только часть AC.

Пример:

```python
async def test_unknown_command_returns_failure_before_load(...):
    """Неизвестная команда завершается до обращения к сессии.

    Это сохраняет причину отказа: отсутствие Handler не маскируется
    состоянием сессии. Положительная пара — test_exact_type_reaches_handler.

    Требования: R3.2, UC-11, FR-03–04; AC-4, routing-часть AC-5.
    """
```

Основные соответствия:

- обязательный `run` — §1.3, FR-01, AC-1;
- точный тип и подкласс — FR-04, AC-3;
- отказ до `load` — FR-03, UC-11, AC-4, часть AC-5;
