## Что реализует этот этап

Создаём **вход в координатор пользовательской операции** — `ApplicationOrchestrator`.

На предыдущем этапе мы записали правила в виде тестов. Сейчас появляется код, который принимает команду, проверяет наличие ответственного обработчика и корректно завершает запрос, если обработчик не назначен.

Делаем четыре вещи:

1. **Принимаем готовый контекст запроса.** Идентификатор операции уже создан на входе в приложение. Координатор использует его в ответе и журнале, чтобы запрос можно было проследить целиком.
2. **Фиксируем назначения обработчиков.** При создании координатор получает таблицу «тип команды → обработчик» и сохраняет собственную копию назначений. Последующие изменения исходного словаря не должны незаметно менять работу уже созданного объекта.
3. **Выбираем обработчик по точному типу команды.** Похожая команда или подкласс без отдельного назначения не отправляются к чужому обработчику.
4. **Возвращаем понятный отказ до чтения сессии, если назначения нет.** Ответ сообщает о внутренней ошибке настройки, а журнал содержит старт и завершение с исходным идентификатором операции.

**Зачем это нужно:** ошибочная конфигурация должна обнаруживаться сразу. Например, если обработчик команды не подключён, проверка сессии не должна скрыть эту причину сообщением «сессия истекла». Также нельзя автоматически отправлять неизвестный запрос первому доступному обработчику.

**Что будет готово:** тесты обязательного контекста и отказа маршрутизации смогут исполниться и пройти. Вместо ошибки импорта появится проверенная работа конкретной ветки координатора.

**Граница этапа:** запрос с найденным обработчиком ещё не выполняет полезную работу. Загрузка сессии появится в 4.2, вызов обработчика — в 5.2, полный путь с сохранением — в 6.4. До этого координатор не подключается к пользовательскому интерфейсу или транспорту. Прохождение ранних тестов не означает готовность всего построения карты.

## 1. Конструктор и обязательный вход

Используй публичный контракт R3.2:

```python
class ApplicationOrchestrator:
    def __init__(
        self,
        *,
        context: ContextService,
        handlers: Mapping[type[Command], Handler],
        clock: Callable[[], datetime],
    ) -> None:
        ...

    async def execute(
        self,
        command: Command,
        *,
        session_id: str,
        run: RunContext,
    ) -> ApplicationResult:
        ...
```

Все параметры обязательны. `run` и `session_id` — keyword-only. `execute` остаётся обычным асинхронным методом с явной сигнатурой.

Сохрани зависимости `context` и `clock`. Реестр скопируй при создании, например через `dict(handlers)`. Копируются назначения, а не сами объекты Handler. Не вводи отдельный неизменяемый контейнер, если для соблюдения контракта достаточно приватного словаря без методов изменения.

У класса нет публичных методов регистрации, замены или удаления Handler и нет свойства, выдающего наружу изменяемый внутренний реестр. Полнота production-реестра будет проверяться в composition в 10.1–10.2; конструктор не должен сам добавлять `BuildNatalHandler`.

Не проверяй зависимости через runtime `isinstance(..., ContextService)`: тесты передают recording fake с тем же публичным API. Не создавай новые правила runtime-валидации зависимостей или аргументов, не заданные требованиями.

`clock` будет нужен перед retry в 7.2. На этом этапе его не вызывай и не сравнивай deadline. Он не создаёт `started_at` и не подменяет часы `ContextService`.

Вызов без `run` должен отклоняться самой сигнатурой с `TypeError` до входа в тело метода. Не добавляй `run=None`, fallback `RunContext.new()`, генерацию UUID, копирование или восстановление `run` из других аргументов.

## 2. Точное назначение Handler

Для корректно вызванного `execute` порядок такой:

```text
started event → lookup по type(command) → ветка результата routing
```

Используй точный поиск в собственной копии реестра:

```python
handler = self._handlers.get(type(command))
```

Отсутствие Handler проверяется как `handler is None`. Не используй `isinstance`, MRO, строки имён, перебор похожих классов, LLM или запасной обработчик. Не превращай зарегистрированный Handler с ложным bool-значением в отсутствующий.

Подкласс команды принимается только при собственной точной регистрации. Нельзя запретить все подклассы ради прохождения отрицательного теста или всегда возвращать отказ независимо от реестра.

Все значения текущего запроса — command, session_id, run, выбранный Handler и результат — остаются локальными переменными `execute`. В полях экземпляра хранятся только зависимости и конфигурация. Не добавляй общий список операций, счётчики, последний результат или реестр активных run_id.

На этом этапе не вызывай `load`, Handler или `save` ни в одной ветке.

## 3. Отказ при отсутствии Handler

Когда точного назначения нет, используй существующую политику:

```python
reaction = describe_failure(kind="handler_not_registered")
```

Создай настоящий `ApplicationInternalFailure` из `application_results.py`:

| Поле | Значение |
|---|---|
| `orch_status` | `FAILURE` |
| `handler_status` | `NOT_STARTED` |
| `context_status` | `NOT_ACCESSED` |
| `code` | `reaction.code`, то есть `HANDLER_NOT_REGISTERED` |
| `detail_code` | `reaction.detail_code`, то есть `None` |
| `user_message` | `reaction.user_message`: `Не удалось выполнить запрос из-за внутренней ошибки.` |
| `retryable` | `reaction.retryable`, то есть `False` |
| `run_id` | исходный `run.run_id` |
| `state_version` | `None` |

Не дублируй таблицу сообщений в координаторе и не возвращай произвольный dict. Не вычисляй версию сессии и не подставляй `0` вместо неизвестной версии.

Отсутствие назначения — ожидаемая ветка конфигурационного отказа. Не создавай искусственное исключение, чтобы получить этот ответ через общий обработчик ошибок.

## 4. События завершённой ветки

Используй существующие `log_operation_started` и `log_operation_finished` из `application/operation_logging.py`. Не создавай свой logger с другим форматом, telemetry port или копию этих функций.

Перед lookup один раз вызови:

```python
log_operation_started(
    run_id=run.run_id,
    command_type=type(command).__name__,
)
```

После создания отказа и **до возврата** результата один раз вызови `log_operation_finished`. Передай статусы, code, detail_code, state_version и run_id из сформированного результата. Остальные поля:

```text
load_duration_ms    = None
handler_duration_ms = None
commit_duration_ms  = None
commit_attempts     = 0
commit_error_codes  = ()
delivery_cancelled  = False
```

Функции сами назначают уровни: started — `INFO`, этот terminal — `WARNING`, поскольку `orch_status=FAILURE`. Не меняй helpers ради coordinator-тестов.

Не записывай события завершения load, Handler или commit: эти стадии не начинались. Не создавай фиктивную отмену, попытку сохранения или длительность `0.0` вместо отсутствующей стадии.

В lifecycle-события передаются только предусмотренные поля. В них не передаются payload команды, artifact, delta или полный session_id. Существующие правила DEBUG boundary logging соседних компонентов не меняются.

Порядок «старт → завершение → возврат» обеспечивается прямыми вызовами функций. Здесь не нужны задачи asyncio, callback, shield, блокировки, таймеры или `finally`, который мог бы продублировать terminal.

## 5. Явная граница ещё не собранного положительного пути

Здесь есть техническая особенность разбиения плана: публичный метод уже появляется в 3.2, а действия после успешного routing предусмотрены только в следующих карточках. §4.1 плана допускает неполный flow и ожидаемые падения положительных тестов до 6.4.

**Для этого промежуточного модуля явно задай временную границу:** если Handler найден, останови исполнение через `NotImplementedError` с техническим пояснением, что обработка зарегистрированной команды будет добавлена в этапах 4–6. Помести её непосредственно после успешного lookup, без отдельного будущего метода или сервисной заглушки.

Это явно обозначенная незавершённость разработки, **не новый вариант публичного application-ответа и не целевое поведение R3.2**. Она противоречила бы правилам готовой границы компонента, если бы такой модуль подключили к транспорту. Поэтому:

- модуль не подключается к CLI, HTTP, UI или production composition;
- эта ветка не получает ложный `HANDLER_NOT_REGISTERED`, фиктивный `InternalFailure`, `SUCCESS`, `None` или `NotImplemented` как возвращаемое значение;
- временное исключение не маскируется обработчиком ошибок, чтобы незавершённый путь оставался виден в отложенных тестах;
- для неё не изобретается новый terminal_kind или ложное событие успешного/отменённого завершения;
- в docstring модуля и журнале явно указано: реализована только unknown-command ветка, полный lifecycle-контракт для известной команды ещё не выполнен;
- при реализации 4.2 эту точку продолжения заменяет настоящий load; оставшаяся сборка идёт по плану.

Требование временной остановки ограничено этим промежуточным этапом. Не добавляй другие заглушки будущих функций, коды ошибок, outcome-модели или fallback-поведение. Не считай наличие такого исключения реализацией FR-25 или нарушением Handler: Handler ещё не вызывался.

Положительные тесты сохраняются без изменений и пока падают. Их нельзя «починить» возвратом поддельного результата, отключением assertions, `skip`/`xfail` или реализацией 4.2–6.4 в этой карточке.
