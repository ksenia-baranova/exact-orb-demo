# Промт 3.R2 — Закрепить согласованные гарантии перед продолжением координатора

**Дата:** 2026-09-17.  
**Основание:** поручение написать промт и исправить согласованные замечания ревью.  
**Тип:** корректирующая карточка; основные номера плана сохраняются.  
**Контракт:** [ApplicationOrchestrator R3.2](../../../docs/requirements/component_responsibilities/exact-orb_application_orchestrator_requirements.md), FR-02/22/23/26, §9–12; уточнение ADR-0006.

## Что делаем и зачем

Закрепляем гарантии, на которые будут опираться следующие этапы координатора.
Идентификатор запроса и его срок нельзя будет переписать после создания.
Ответ приложения будет проверять версию состояния и точный текст сообщения,
а итоговая запись журнала будет брать поля непосредственно из этого ответа.
Строка ошибки больше не сможет превратиться в дополнительные поля или новую
строку события при разборе журнала.

Сейчас тесты подтверждают корректные входы, но не обнаруживают все способы
нарушить эти гарантии. Выполняем работу последовательными небольшими частями
с отдельными проверками. Следующие основные карточки не реализуем.

## Границы

Разрешены `run_context.py`, `application/failure_policy.py`,
`application/application_results.py`, `application/operation_logging.py`,
terminal-вызов в `application/orchestrator.py`, соответствующие пять тестовых
файлов RunContext/policy/results/logging/routing, требования Orchestrator,
ADR-0006, observability diagram 010, журнал плана и README серии.

Не менять расчёты, baseline/hash, retryable чтения сессии, discriminator,
политику extra RunContext, старые промты, Git index и несвязанные файлы.
Не реализовывать load/Handler/commit: семь известных положительных routing
случаев остаются отложенными группам 4–6. Веток, коммитов, push и PR не создавать.

Глубокую неизменяемость Issue/ChartArtifact выделить в отдельную карточку
2.R2: artifact-контракт допускает вложенные mutable-значения при обязательной
глубокой копии на выходе resolver. Не замораживать общие модели попутно и
не объявлять глубокую часть AC-24 закрытой.

## 1. RunContext

Добавить `ConfigDict(frozen=True)`, сохранив поля, new(), default deadline,
UTC-валидацию и политику extra. Проверить запрет присваивания каждому полю,
включая корректный другой UUID и naive deadline, сохранность исходного
объекта после отказа и создание нового корректного контекста.

## 2. Политика и модели

- Версия ApplicationResult — строгий int в прежних границах: bool, строка
  и float отклоняются; None остаётся только там, где разрешён.
- Persistence detail_code непустой, как у исходных session outcomes.
  Открытые коды и calculation fallback сохраняются.
- user_message failure-модели совпадает с describe_failure для её кода,
  стадии, причины и retryable. Тексты не менять; эвристический фильтр слов
  Traceback/путей не вводить.
- describe_failure отклоняет нерелевантные для kind аргументы со значением
  не None. Публичная сигнатура сохраняется.
- Обновить тест, ранее допускавший произвольное сообщение. Сохранить
  независимые таблицы ожидаемых текстов и проверки выбора реакции.

## 3. События

log_operation_finished принимает `result: ApplicationResult` вместо отдельных
run_id/status/code/version и извлекает только прежний разрешённый набор полей.
artifact, issues, user_message и полный model_dump не записывать. Длительности,
история попыток и delivery_cancelled остаются отдельными аргументами.

Формат: прежнее имя события, пробел, один JSON object с прежними именами полей.
UUID — строка; tuple кодов — массив. Управляющие символы экранируются, исходные
строки сохраняются. Использовать стандартный json и текущий logger без нового
backend или изменения общего formatter. Тесты разбирают реальный JSON сообщения.

Длительности конечные и неотрицательные, номера попыток 1/2, количество 0/1/2;
bool не подменяет числа. committed требует версии >=1, already_applied и
superseded — >=0; остальные commit outcomes не публикуют версию. Невалидные
аргументы отклоняются типизированной ошибкой контракта до записи. Не заменять
плохие значения нулями и не создавать фиктивный terminal. Измерение и связь
истории с реальным save остаются ответственностью будущего execute.

Ошибка подготовки события не отменяет состоявшийся commit и не может
превращаться в ложный ответ о неуспешном сохранении. Закрепить это требование
для будущей commit-ветки; саму ветку здесь не создавать.

Регрессии: строки с кавычками, обратными слешами, поддельными key=value и
переводами строк сохраняются при round-trip; один LogRecord и одна физическая
строка. Для запретов нужны положительные контроли.

## 4. Документы и проверки

Синхронизировать требования, ADR и diagram 010. Исторический F: 2152 passed
обозначить результатом локального Windows-окружения. Linux-результат ревью
не выдавать за свой запуск и не объявлять ОС доказанной причиной различия.

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_run_context.py tests/application/test_application_failure_policy.py tests/application/test_application_results.py tests/application/test_orchestrator_logging.py -q
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/application/test_orchestrator_routing.py -k "requires_run or unknown_command or subclass or registry" -q
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_run_context.py tests/application tests/session tests/test_module_boundaries.py -q
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider -q
git diff --check
```

Целевые части проверять последовательно, затем ранний routing и R. Полный
pytest выполнить после классификации R даже при семи известных NotImplementedError:
RunContext используется за пределами R. Не исключать эти случаи и не называть
R/F успешными. Сетевые/платные smoke не запускать. Проверить локальные ссылки,
сохранность файлов вне области и Git index по исходным хешам. Записать реальные
результаты и оставшиеся ограничения в журнал; старые записи сохранить.
