# Промт 4.1 — Тесты загрузки сессии и исходной версии

**Статус:** подготовлен; выполнение отдельно.
**Зависимость:** 3.2; корректировки 3.R1 и 3.R2 выполнены, результаты — §1.3.18 плана.
**Основание:** ApplicationOrchestrator R3.2, FR-06–08, FR-11, FR-25–26, §7–12.
**Покрытие:** часть AC-5–7, AC-19–21, AC-26–27, AC-29–30. Полная приёмка остаётся последующим карточкам.

## Что делаем и зачем

Координатор запроса уже умеет выбирать обработчик команды. Следующий шаг — проверить, **с какими данными сессии он начинает работу и как объясняет невозможность их загрузить**.

Сессия хранит состояние работы пользователя. Перед запуском обработчика координатор должен один раз получить это состояние. Если сессия истекла или отсутствует, пользователь получает понятное предложение начать заново. Если хранилище не смогло прочитать данные, ответ должен сообщать об ошибке загрузки: это другая ситуация, которая не означает потерю сессии. Во всех этих случаях обработчик не запускается и сохранение не начинается.

Вместе с данными координатор запоминает их **исходную версию**. Например, запрос начал работу с версией 7, а параллельный запрос уже изменил данные до версии 9. При сохранении первого результата система должна помнить, что он подготовлен на основе версии 7. Подмена исходной версии новой могла бы скрыть конфликт и позволить затереть более свежие изменения. Решение о допустимости записи принимает сессионный сервис; координатор передаёт ему правильную исходную версию.

**Зачем нужны проверки:** они защищают от работы без пригодных данных, неверных сообщений пользователю и потери связи между прочитанным состоянием и последующим сохранением. События журнала должны точно показывать, на каком шаге остановился запрос.

**Результат этапа:** тесты загрузки, её отказов и передачи исходной версии, с понятной границей готовности каждого сценария. Сейчас создаём проверки. Реализация загрузки — карточка **4.2**, вызова обработчика — **5.2**, полного пути до сохранения — **6.4**. Наличие тестов само по себе не подтверждает, что эти пути уже работают.

## 1. Общая организация тестов

Вызывай настоящий `ApplicationOrchestrator.execute(command, session_id=..., run=...)` с зарегистрированным точным типом команды. Конструктор получает только `context`, `handlers`, `clock`; тестовый журнал принадлежит зависимостям, отдельный recorder в production API не нужен.

Переиспользуй `Call`, `RecordingContext`, `RecordingHandler` и общие telemetry fixtures. Fake-компоненты фиксируют реальные вызовы и исходные объекты аргументов. Для исключения, неверного результата load или замены доступного snapshot достаточно маленьких специализированных fakes; не создавай универсальный сценарный движок.

Не импортируй helpers из другого `test_*.py` и не копируй целиком routing-набор. Его проверки выбора Handler остаются прежними. Новые тесты должны добавлять свидетельство о загрузке, её исходах и исходной версии.

Используй валидные `SessionState`/`SessionSnapshot`. Не обходи frozen через `object.__setattr__` и не создавай заведомо невалидные модели с `model_construct`, чтобы имитировать изменение версии.

## 2. Отказы load

Для каждого сценария проверяй ровно один `context.load` с переданным `session_id`. В общем журнале нет `handle` и `save`. Отсутствие повторной загрузки существенно: координатор не повторяет чтение и не создаёт сессию вместо отказа.

| Сценарий | Возвращаемая модель | Статусы `orch / handler / context` | Остальные поля |
|---|---|---|---|
| `SessionAbsent(reason="expired")` | `ApplicationSessionAbsent` | `SESSION_ABSENT / NOT_STARTED / SESSION_ABSENT` | `code=SESSION_EXPIRED`, исходный reason, `retryable=False` |
| `SessionAbsent(reason="not_found")` | `ApplicationSessionAbsent` | `SESSION_ABSENT / NOT_STARTED / SESSION_ABSENT` | `code=SESSION_NOT_FOUND`, исходный reason, `retryable=False` |
| `StateReadFailed(error_code=...)` | `ApplicationStateReadFailure` | `FAILURE / NOT_STARTED / READ_FAILED` | `code=STATE_READ_FAILED`, исходный error_code в detail_code, `retryable=True` |
| `load` выбрасывает обычный `Exception` | `ApplicationInternalFailure` | `FAILURE / NOT_STARTED / NOT_ACCESSED` | `code=INTERNAL_FAILURE`, `retryable=False` |
| `load` возвращает `None` или чужой тип вместо typed outcome | `ApplicationInternalFailure` | `FAILURE / NOT_STARTED / NOT_ACCESSED` | `code=INTERNAL_FAILURE`, `retryable=False` |

Во всех строках `state_version=None`, `run_id` совпадает с входным. Кроме `StateReadFailed`, `detail_code=None`. Отсутствие сессии при load не должно превращаться в `SESSION_LOST_DURING_OPERATION`: этот код предназначен для исчезновения сессии после Handler и проверяется в commit-карточках.

Проверяй точные сообщения из §10 требований независимо от вызова production-политики в ожидаемом значении:

- expired: `Сессия истекла. Введите данные рождения заново.`;
- not_found: `Сессия не найдена. Начните заново.`;
- read failure: `Не удалось загрузить данные сессии. Попробуйте ещё раз.`;
- internal failure: `Произошла внутренняя ошибка.`.

Для `StateReadFailed` достаточно нескольких разных непустых кодов, чтобы подтвердить передачу исходного значения и отсутствие жёстко заданной замены. Не меняй `retryable` в зависимости от кода: текущее правило R3.2 для чтения сохранено.

Для unexpected exception используй заранее созданное исключение с отличимым текстом. Техническая exception-запись должна содержать исходное исключение и traceback; наружу возвращается фиксированное сообщение без этого текста. Для неверного outcome проверь классификацию нарушения контракта и предусмотренную §11.5 техническую запись, не закрепляя конкретный класс внутреннего диагностического исключения.

Имена тестов отказов должны содержать `absent`, `read_failed` или `unexpected`, включая сценарий `unexpected_invalid_outcome`. Это сохраняет исполнимость выборки из карточки 4.2.

Отмену load и исключения, не наследующиеся от `Exception`, здесь не добавляй: их отдельные сценарии и безопасный test harness предусмотрены в 5.3–5.4. Этот промт не подтверждает соответствующую часть AC-30.

## 3. Положительный контроль загрузки

Подготовь сценарий, где load возвращает валидный snapshot, Handler возвращает `InputRequired` с непустым `issues`, а `execute` завершается `ApplicationInputRequired`.

Проверь наблюдаемую последовательность `load → handle`, единственный load с исходным `session_id`, передачу именно `snapshot.state` по identity, исходных command/run и отсутствие save. Версия результата и load-stage event равны версии snapshot. Используй версии 0 и ненулевую, например 7: обе допустимы, ответ не должен всегда содержать 0 или терять версию.

Это положительная пара к проверкам «Handler не запускается при отказе». В отличие от routing-тестов, здесь существенно подтверждаются обе границы версии и событие успешного load. Непустой `InputRequired` не решает K3.

Сценарий должен в итоге пройти через обычный возврат результата. Не считай `pytest.raises(NotImplementedError)` доказательством корректной загрузки. После 4.2 этот полный контроль ещё может падать; завершение ожидается после 5.2.

## 4. Исходная версия на реальном вызове save

Подготовь отдельный unit-тест наблюдаемого вызова `context.save`. Он должен обнаруживать повторное чтение или подмену исходной версии после Handler:

1. Первый и единственный load возвращает snapshot версии N. Проверь N=0 и N=7.
2. Handler получает исходный state и готовит валидный `BuildNatalSuccess` с согласованными artifact/delta на основе существующих calculation fixtures.
3. Во время Handler fake-контекст начинает предоставлять другой валидный snapshot с версией N+2. Это замена ссылки в тестовой зависимости, а не изменение frozen исходного state и не дополнительный вызов load.
4. Fake save возвращает `Superseded(actual=<новое состояние>)`, соответствующий сценарию более свежих несовместимых данных. Тест не реализует CAS и не выдаёт fake за реальное хранилище.
5. В журнале ровно `load → handle → save`. Save получает исходный `session_id`, **N**, а не N+2, и тот же `outcome.delta` по identity. Handler вызван один раз; повторного load/save и rebase нет. Ответ — `ApplicationSuperseded` с версией N+2.

До начала execute сохрани ожидаемое N в тесте. Не выводи ожидаемый аргумент из уже изменившегося fake. Проверь также, что подмена доступного snapshot действительно произошла, а исходный state сохранён.

Не читай приватную локальную переменную `original_expected_state_version`. Её название не является публичным контрактом. Доказательство — аргумент реального вызова save на публичной границе зависимости.

Для успешного Handler переиспользуй `tests/fixtures/calculation.py`. Учитывай существующий пример подготовки согласованных birth input/resolved/artifact/delta в routing-тесте и продуктовую точность времени до минуты; общие fixtures и эталоны не меняй.

Этот тест ожидает 6.4, когда появится нормальная commit-классификация. Он подтверждает передачу исходной версии, но не работу реального CAS, конкурентного хранилища или retry. Такие проверки принадлежат последующим карточкам.

## 5. События загрузки и завершения

Проверяй настоящие отрендеренные записи штатного logger. Не подменяй `log_operation_finished`, политику или модели результата моками. Выделяй имя события и разбирай JSON-часть через `json.loads`; не используй regex по `key=value`.

Фикстура должна читать `caplog.records` в фазе вызова после `await execute`. Не сохраняй список records из setup: в 3.R1 уже исправлялась именно эта ошибка. Временные настройки logger восстанавливай в `finally`; глобальную конфигурацию не меняй.

Для завершившихся отказов load:

- ровно один `application_operation_started` на INFO;
- ровно один `application_stage_finished(stage="load")`: `session_absent`/`state_read_failed` на DEBUG, `unexpected_failure`/`invalid_outcome` на WARNING;
- ровно один `application_operation_finished` до возврата результата: absence на INFO, failure на WARNING;
- один входной `run_id` во всех событиях; нет Handler-stage и commit-attempt events;
- terminal имеет `terminal_kind="result"`; статусы, code, detail_code, state_version совпадают с реально возвращённой моделью;
- `load_duration_ms` конечна и неотрицательна, равна duration завершённой load-стадии; `handler_duration_ms` и `commit_duration_ms` — `None`, `commit_attempts=0`, `commit_error_codes=[]` в JSON, `delivery_cancelled=False`;
- load-stage при отсутствии достоверной версии не содержит `state_version`. На положительном snapshot-контроле поле присутствует и равно N.

Техническая exception-запись является отдельной диагностикой и не считается вторым terminal. Фильтруй lifecycle-события по точному имени; наличие дополнительных диагностических записей не должно ломать проверку их порядка.

Для положительного snapshot-контроля проверь `started → load finished → handler finished → terminal`. Отсутствие стадий при отказе сопоставь с их присутствием в соответствующем положительном сценарии, включая save-контроль из предыдущего раздела.

Проверяй набор разрешённых полей lifecycle-сообщений по §11.5, без command/state/artifact payload и полного session_id. Не расширяй это до ревью всех логов проекта. Формат и числовые валидаторы самих logging-функций уже покрыты; здесь проверяем их подключение к execute.

Не добавляй `sleep`, реальную задержку или новый параметр конструктора для измерения времени. Не привязывай длительность к UTC `clock`, предназначенному для deadline. Точные миллисекунды и полный lifecycle всех веток относятся к группе 8; здесь достаточно корректных значений и их соответствия событию стадии.
