**Граница приёмки:** отказы load и их события; части AC-5–7, AC-19–21, AC-26–27, AC-29–30. Передача state Handler и original expected на save проверяются позднее.

## Что делаем и зачем

Координатор уже умеет выбирать обработчик команды. Теперь добавляем следующий шаг: **получение данных сессии перед началом работы**. Без этих данных нельзя корректно продолжать запрос.

Для пользователя важны разные причины остановки:

- **Сессия истекла или не найдена.** Нужно предложить начать заново; выполнять расчёт и сохранять результат пока не на чем.
- **Не удалось прочитать данные.** Это техническая ошибка загрузки. Она сама по себе не означает, что сессия потеряна, поэтому сообщение пользователю должно быть другим.
- **Во время загрузки произошла непредвиденная ошибка.** Пользователь получает понятный общий ответ, а разработчики — диагностическую запись для разбора причины.

Когда загрузка успешна, координатор сохраняет полученный снимок данных и его исходную версию. Например, если работа началась с версии 7, последующее сохранение должно учитывать именно её, даже если другой запрос уже изменил сессию. Это позволит сессионному сервису обнаружить конфликт и защитить более свежие данные.

**Зачем этот этап:** прекращать запрос с правильной причиной, не запускать обработчик без пригодной сессии и подготовить данные для безопасного продолжения. В журнале должно быть видно, что загрузка действительно завершилась и каким исходом.

**Результат работы:** все отказы загрузки завершаются готовым ответом приложения и корректными событиями. Успешный snapshot и его версия подготовлены для следующего шага. Вызов обработчика появится в **5.2**, полный путь до сохранения — в **6.4**. Этот этап ещё не делает весь пользовательский сценарий готовым.

## 1. Вызов load и локальные данные

Сохрани публичную сигнатуру конструктора и execute, обязательный RunContext, defensive copy mapping и exact routing. Неизвестная команда по-прежнему завершается до любого load, с прежними результатом и событиями.

После найденного Handler выполни ровно один:

```python
loaded = await self._context.load(session_id)
```

Передавай исходный `session_id`. Не создавай новый RunContext, не заменяй его UUID и не проверяй deadline как основание отказаться от load: внедрённый `clock` предназначен для решения о будущем commit retry.

Snapshot, исходная версия, длительность, outcome и возвращаемый результат принадлежат локальным переменным текущего execute. Не сохраняй их в полях экземпляра, глобальном реестре или общей mutable-структуре.

Измеряй длительность load монотонным источником времени, например `time.perf_counter()`. Переводи разницу в миллисекунды. Не используй для этого UTC clock конструктора, фиксированное значение, sleep или ограничение отрицательного результата через max(0, ...). Измеренное значение должно быть конечным и неотрицательным; в stage и terminal передаётся одно и то же значение.

## 2. Классификация исходов

Используй реальные типы исходов, готовые модели `ApplicationResult` и существующую `describe_failure`. Не собирай внешний ответ произвольным dict и не дублируй таблицу сообщений в координаторе.

| Исход load | Результат / действие | Статусы `orch / handler / context` | Политика |
|---|---|---|---|
| `SessionSnapshot` | Сохранить snapshot и исходную версию, записать завершение load | Внешний результат пока не возвращается | Отказа нет |
| `SessionAbsent(reason="expired")` | `ApplicationSessionAbsent`, `SESSION_EXPIRED` | `SESSION_ABSENT / NOT_STARTED / SESSION_ABSENT` | `kind="session_absent", stage="load", reason=loaded.reason` |
| `SessionAbsent(reason="not_found")` | `ApplicationSessionAbsent`, `SESSION_NOT_FOUND` | `SESSION_ABSENT / NOT_STARTED / SESSION_ABSENT` | Та же политика с исходным reason |
| `StateReadFailed` | `ApplicationStateReadFailure`, `STATE_READ_FAILED` | `FAILURE / NOT_STARTED / READ_FAILED` | `kind="state_read_failed", error_code=loaded.error_code` |
| Обычный `Exception` из load | `ApplicationInternalFailure`, `INTERNAL_FAILURE` | `FAILURE / NOT_STARTED / NOT_ACCESSED` | `kind="internal_failure"` |
| `None` или иной тип вместо трёх допустимых outcomes | `ApplicationInternalFailure`, `INTERNAL_FAILURE` | `FAILURE / NOT_STARTED / NOT_ACCESSED` | `kind="internal_failure"` |

Для всех отказов `state_version=None`, `run_id=run.run_id`. Absence сохраняет исходный reason. Только read failure получает исходный error_code в detail_code и `retryable=True`; у остальных отказов `detail_code=None`, `retryable=False`.

Сообщения берутся из политики без изменения:

- expired — `Сессия истекла. Введите данные рождения заново.`;
- not_found — `Сессия не найдена. Начните заново.`;
- read failure — `Не удалось загрузить данные сессии. Попробуйте ещё раз.`;
- internal failure — `Произошла внутренняя ошибка.`.

Не передавай политике нерелевантные аргументы: после 3.R2 такие вызовы отклоняются. Не меняй retryable по частным persistence-кодам и не используй `SESSION_LOST_DURING_OPERATION` при load. Handler и save при любом отказе не вызываются; повторного load нет.

## 3. Исключения и нарушение контракта

Ограничь обработку обычных исключений самой загрузкой. Исходное исключение load должно попасть в отдельную техническую запись штатного logger с traceback и исходным run_id. Во внешний результат его текст не попадает.

Неверный возвращённый тип — отдельный путь `invalid_outcome`. Подготовь диагностическую exception-запись с traceback о нарушении контракта, затем нормализованный InternalFailure. Не сериализуй неверный объект в пользовательское сообщение или compact lifecycle-событие. Конкретный класс внутреннего диагностического исключения публичным контрактом не является.

Не оборачивай весь оставшийся execute в один `except Exception`: ошибки формирования результата или logging не должны маскироваться под отказ ContextService. В частности, временная граница следующего этапа после успешного snapshot должна оставаться снаружи обработчика ошибок load.

Не перехватывай BaseException как application failure. `CancelledError`, `KeyboardInterrupt` и `SystemExit` должны проходить наружу. Прерванный отменой load не получает фиктивного stage finished или result terminal. Полный cancelled-terminal и его проверки остаются отдельным этапам 5.3–5.4; не объявляй их реализованными в 4.2.

## 4. События и готовый ответ при отказе

Используй `log_operation_started`, `log_stage_finished` и `log_operation_finished`. Не меняй их API, формат JSON, уровни logger или общую конфигурацию.

Для каждого завершившегося load записывается ровно один `application_stage_finished(stage="load")`:

| Исход | Поле outcome | Уровень | state_version в stage |
|---|---|---|---|
| Snapshot | `loaded` | DEBUG | Прочитанная версия, включая 0 |
| SessionAbsent | `session_absent` | DEBUG | Отсутствует |
| StateReadFailed | `state_read_failed` | DEBUG | Отсутствует |
| Исключение load | `unexpected_failure` | WARNING | Отсутствует |
| Неверный тип результата | `invalid_outcome` | WARNING | Отсутствует |

У каждого завершённого отказа порядок lifecycle-записей: **started → load finished → terminal**. Техническая exception-запись идёт отдельно и не заменяет ни stage, ни terminal. Нет событий незапущенных Handler и commit.

Сначала создай модель результата, затем передай именно её в `log_operation_finished(result=result, ...)`, после записи верни тот же результат. Terminal должен содержать:

- `load_duration_ms` — длительность завершённого load;
- `handler_duration_ms=None`, `commit_duration_ms=None`;
- `commit_attempts=0`, `commit_error_codes=()`, `delivery_cancelled=False`.

Статусы, code/detail_code, run_id и версия извлекаются logging-функцией из результата. Absence завершается на INFO, application failure — на WARNING. Во всех событиях остаётся входной UUID. Не добавляй в lifecycle payload команды, snapshot, полный session_id, artifact или raw exception text.

## 5. Успешный snapshot и граница следующего этапа

Для `SessionSnapshot` сохрани сам исходный объект в локальном `snapshot` и один раз выполни:

```python
original_expected_state_version = snapshot.state.state_version
```

Не копируй и не изменяй state, не вычисляй следующую версию, не перечитывай сессию и не выполняй rebase. Версия 0 допустима. После фиксации запиши `load/loaded` с этой версией.

На этом граница 4.2 заканчивается. Перенеси существующий явный `NotImplementedError` на продолжение **после успешного load**, обновив пояснение о недостающих Handler/commit. Не превращай его в InternalFailure, не возвращай фиктивный InputRequired/Success и не добавляй no-op save ради тестов.

Успешная загрузка ещё не означает завершённую пользовательскую операцию: для этой незавершённой ветки не создавай ложный result terminal. Обнови docstring модуля/execute, чтобы они точно описывали реализованные отказы и оставшуюся границу. К транспорту частичный flow не подключается.
