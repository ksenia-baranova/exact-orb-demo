# Промт 5.1 — Тесты вызова Handler и его штатных исходов

**Статус:** подготовлен; выполнение отдельно.
**Зависимость:** 4.2 и 2.6 выполнены; K3 о пустом `issues` остаётся открытым.
**Основание:** ApplicationOrchestrator R3.2, FR-02, FR-05–10, FR-25–26, §7–12; карточка 5.1 плана.
**Граница приёмки:** тесты вызова Handler и трёх штатных исходов без сохранения. Реализация обычных веток — 5.2, завершение успешного commit-контроля — 6.4; полное AC-8 зависит от K3.

## Что делаем и зачем

Координатор уже выбирает обработчик команды и загружает данные сессии. Следующий шаг — проверить, что обработчик получает **именно ту команду, то состояние и тот контекст запроса**, с которыми операция началась. Если подменить хотя бы один из них, ответ может относиться к чужому запросу или к другой версии данных.

Обработчик не всегда возвращает готовую карту. Он может сообщить, что пользователю нужно исправить ввод, что сервис определения места и времени временно недоступен или что расчёт карты не удался. Для пользователя это разные ситуации: при ошибке ввода нужны конкретные поля для исправления; при технической недоступности нельзя выдавать её за ошибку пользователя. Во всех трёх случаях сохранять новое состояние сессии нельзя.

**Зачем тесты сейчас:** они закрепят смысл ответов и запрет преждевременного сохранения до реализации 5.2. Отдельный положительный контроль нужен, чтобы проверка «save не вызван» не проходила только потому, что координатор вообще не умеет доходить до сохранения. Журнал должен показывать завершённую работу Handler и ровно один итог операции.

Есть открытая граница **K3**: существующий Handler вправе вернуть `InputRequired(issues=())`, а внешний `ApplicationInputRequired` требует непустые `issues`. Тесты с непустыми проблемами можно подготовить без нового решения. Они **не закрывают** пустой случай и AC-8 целиком. Не придумывай фиктивную проблему и не назначай пустому исходу `InternalFailure` без согласованного решения.

**Результат этапа:** новый тестовый файл с проверками передачи данных, понятных ответов и событий для штатных исходов Handler. До 5.2 эти сценарии ожидаемо остановятся после успешного load; до 6.4 положительный контроль save остаётся незавершённым. Эта карточка не делает полный пользовательский путь готовым.

## 1. Передача исходных объектов и порядок

Для зарегистрированной команды настрой `RecordingContext` с настоящим `SessionSnapshot` и `RecordingHandler` с типизированным результатом. Проверь наблюдаемый журнал вызовов:

```text
context.load(original_session_id) ровно один раз
handler.handle(original_command, snapshot.state, original_run) ровно один раз
```

Проверяй `is`, а не только равенство, для command, `snapshot.state` и `RunContext`; `run_id` остаётся входным. Версия снимка, включая 0, остаётся прочитанной версией. Handler не получает `SessionSnapshot`, исходный `expected_state_version`, persistence-порт или новый `RunContext`. Повторного load и отдельного get/touch нет. Не проверяй приватные поля координатора вместо публичного вызова.

Проверка no-save должна иметь положительный контроль существующего пути: `test_orchestrator_routing.py::test_known_command_completes_with_commit` и `test_orchestrator_load.py::test_save_uses_original_version_when_available_snapshot_changes`. Не копируй их сценарии целиком в новый файл. Если нужен дополнительный позитивный случай именно для наблюдения Handler stage, добавь только отличающееся утверждение и объясни его необходимость.

## 2. Штатные исходы без save

Проверь реальный результат `execute` для каждого исхода Handler. Фиксируй ожидаемые значения независимо от вызова `describe_failure` в тесте: иначе одинаковая ошибка в policy и координаторе останется незамеченной.

| Исход Handler | Внешняя модель и статусы `orch / handler / context` | Что проверить |
|---|---|---|
| `InputRequired` с непустыми структурированными `issues` | `ApplicationInputRequired`; `INPUT_REQUIRED / INPUT_REQUIRED / LOADED` | Точный текст, `code=INPUT_REQUIRED`, порядок и содержимое issues, `retryable=False`, исходная версия и run_id |
| `ResolutionUnavailable(error_code, retryable=True/False)` | `ApplicationResolutionFailure`; `FAILURE / RESOLUTION_UNAVAILABLE / LOADED` | Оба текста policy, сохранение открытого `error_code` в `detail_code`, исходный `retryable`, версия и run_id |
| `CalculationFailed(error_code)` с известным кодом | `ApplicationCalculationFailure`; `FAILURE / CALCULATION_FAILED / LOADED` | Известные варианты policy, точный текст и `retryable`, исходный `detail_code`, версия и run_id |
| `CalculationFailed` с неизвестным непустым кодом | Та же модель и тройка | Безопасный fallback-текст, `retryable=False`, неизменённый `detail_code`, отдельный WARN с кодом; известный код — позитивный контроль отсутствия такого WARN |

Для всех этих исходов проверь `load → handle` и отсутствие `save` и commit-attempt event. Не трактуй `ResolutionUnavailable` или `CalculationFailed` как `InputRequired`. Не меняй исходный snapshot или outcome ради построения результата. Не требуй identity вложенных `Issue`, если публичный контракт гарантирует только их содержимое и порядок.

Используй минимум независимых примеров для известных calculation-кодов, достаточный для проверки различий `retryable` и текстов; если таблица R3.2 покрывается параметризацией без повторения уже имеющихся тестов policy, укажи, что здесь проверяется именно преобразование Handler → ApplicationResult.

## 3. Lifecycle и граница следующих карточек

Разбирай реальные JSON-сообщения штатного logger через `caplog` после `execute`. Для завершившегося non-success пути ожидаются `application_operation_started → load/loaded → handler/<outcome> → application_operation_finished`. В итоговом событии поля должны соответствовать **тому же возвращённому результату**: статусы, code/detail_code, исходные run_id/state_version, `load_duration_ms` и `handler_duration_ms`. Обе длительности конечны и неотрицательны; commit duration отсутствует, attempts равно 0, error codes пусты, `delivery_cancelled=False`.

Typed Handler outcome даёт один `application_stage_finished(stage="handler")` на DEBUG. Для неизвестного calculation-кода проверь отдельный WARN с фактическим кодом, без сырого пользовательского payload; общий terminal для failure остаётся WARNING. Не объявляй факт WARN доказанным только по terminal: нужен отдельный диагностический record. Для InputRequired terminal имеет INFO. Не записывай в compact events command payload, полный session_id, `issues` или artifact.

Текущий `NotImplementedError` после load означает, что новые assertions после `execute` до 5.2 ещё не исполнятся. Не ослабляй их, не добавляй `skip`/`xfail` и не подставляй фиктивный результат. Успешный `BuildNatalSuccess` должен в будущем доходить до save; полный result, attempt и terminal для него подтверждаются в 6.4 существующими положительными контролями. Ошибки и отмена Handler, включая отменённый load и его cancelled terminal, относятся к 5.3–5.4 и здесь не проверяются как готовые.

## 4. Открытое решение K3

Перед **полной приёмкой** карточек 5.1–5.2 нужно согласовать преобразование допустимого `InputRequired(issues=())`: [план §3](../../../docs/project_management/application_orchestrator_implementation_plan.md) фиксирует противоречие с non-empty внешней моделью. Если решение принято до выполнения 5.1, добавь отдельный тест ровно на согласованную реакцию и свяжи его с решением. Если решения нет, подготовь независимые проверки из разделов 1–3, явно отметь 5.1 как частично выполненную и не объявляй AC-8 закрытым. Не выбирай за владельца контракта новую публичную семантику.

Если тесты остановились на ожидаемом `NotImplementedError` после load, укажи, какие assertions ещё не исполнились и какие случаи ждут 5.2 либо 6.4. Ошибка импорта, fixture, тестовых данных или регрессия существующих тестов — не ожидаемый red; исправь причину в разрешённых файлах. ```powershell
