# Промт 5.3 — Тесты нарушений Handler и отмены до сохранения

**Статус:** подготовлен; не выполнялся.
**Зависимость:** сначала 5.2 — вызов Handler и штатные исходы. В текущем checkout 5.2 ещё не выполнена: после успешного load стоит `NotImplementedError`. Пустые `issues` остаются открытым K3 и не получают решения в этой карточке.
**Основание:** ApplicationOrchestrator R3.2, UC-12/14, FR-25/26, §8–12, AC-9/17/21/26/29/30/32/33; карточки 5.3–5.4 [плана](../../../docs/project_management/application_orchestrator_implementation_plan.md).
**Граница приёмки:** тесты через настоящий `ApplicationOrchestrator.execute` для невалидного ответа, исключения и отмены во время load/Handler. Обработка в production принадлежит 5.4; отмена после начала save — группе 6 и далее.

## Что делаем и зачем

После загрузки сессии координатор доверяет Handler выполнить предметную работу. Но Handler может нарушить свой контракт: вернуть `None` или объект чужого типа, а также выбросить неожиданное исключение. Такие сбои нельзя выдавать пользователю как ошибку его данных и нельзя превращать в запись нового состояния. Пользователь должен получить безопасный ответ о внутренней ошибке, а технический журнал — достаточно сведений для диагностики без переноса сырого текста исключения в пользовательское сообщение.

Отмена запроса — другая ситуация. Если клиент перестал ждать, пока ещё идёт загрузка сессии или работа Handler, операция должна завершиться отменой **до сохранения**. Нам важно видеть один итог в журнале для каждого начатого запроса: иначе по событиям получится «вечная активная операция». При этом нельзя записывать ложное событие о завершении той стадии, которая была прервана. Стадия load требует отдельного теста: сейчас именно её отмена оставляет `started` без terminal.

**Результат этапа:** воспроизводимые тесты показывают правильный ответ при дефекте Handler и правильную последовательность событий при ранней отмене. Тесты фиксируют будущую реализацию 5.4 и не объявляют её готовой. Положительный путь Handler из 5.1/5.2 остаётся контролем, что проверки «нет save» не проходят просто из-за недостижимого Handler. Полный успешный save подтвердится только в 6.4.

## 1. Нарушение контракта Handler

Запускай настоящий `execute` с зарегистрированной командой и валидным `SessionSnapshot`. Двумя независимыми случаями проверь `None` и чужой тип результата, например typed session outcome, который не является `BuildNatalOutcome`. Отдельно настрой Handler на `RuntimeError` с узнаваемым техническим текстом и приватным маркером. Не подменяй `execute` или функцию классификации.

Для каждого случая проверь:

- Ровно один `load` и один `handle` с исходными command/state/run; `save` не вызывается, commit-attempt event отсутствует.
- Возвращается **`ApplicationInternalFailure`** с полной связкой `FAILURE / UNEXPECTED_FAILURE / LOADED`, `code=INTERNAL_FAILURE`, `detail_code=None`, `retryable=False`, исходными `run_id` и загруженной `state_version` (включая 0 хотя бы в одном случае), точным безопасным `user_message="Произошла внутренняя ошибка."`.
- Сырой текст исключения и приватный маркер отсутствуют в `user_message` и compact lifecycle events. Отдельная техническая запись для настоящего исключения содержит исходный `run_id` и **реальный traceback**; в ней сырой текст допустим для диагностики в рамках действующего logging-контракта.
- Для чужого результата есть отдельная диагностическая запись с `run_id`, но тест не требует искусственно созданного исключения и поддельного `exc_info`. Проверяй наблюдаемую диагностику; `stack_info` допустим, если реализация выберет этот способ.
- События идут `started → load/loaded → handler/invalid_outcome` либо `handler/unexpected_failure → finished(result)`; Handler stage и terminal имеют `WARNING`. Поля terminal равны **возвращённой модели**, load/handler duration конечны и неотрицательны, commit duration отсутствует, attempts равно 0, error codes пусты, `delivery_cancelled=False`.

Текущие helper-тесты уже проверяют формат `handler/invalid_outcome` и `handler/unexpected_failure` на `WARNING`, а модельные тесты — допустимость status triple. Здесь требуется реальное преобразование исхода Handler в `execute`, порядок событий и отсутствие save. Не копируй их проверки без новой наблюдаемой границы.

## 2. Отмена во время load и Handler

Сделай два отдельных сценария с управляемыми `asyncio.Event`. В fake-зависимости сначала запиши факт входа в `load` или `handle`, установи `entered`, затем жди `release`. Запусти `execute` отдельной `asyncio.Task`; дождись `entered`, вызови `task.cancel()` и наблюдай `CancelledError` у вызывающего. `sleep` и случайная задержка не доказывают порядок; timeout допустим лишь как страховка от зависания и требует корректной уборки задачи.

Для **отменённого load** проверь, что Handler и save не начинались; нет `application_stage_finished(stage=load)` и commit-attempt event. Для **отменённого Handler** проверь, что load завершился и имеет один `load/loaded` stage event, Handler действительно начался, но `application_stage_finished(stage=handler)` отсутствует; save и commit-attempt event отсутствуют. В обоих случаях `CancelledError` пробрасывается, а не превращается в `ApplicationInternalFailure` и не возвращает `ApplicationResult`.

Из реальных `LogRecord.getMessage()` разбери однострочные JSON lifecycle-события. Для каждого вызова требуй ровно один `application_operation_started` и **ровно один** `application_operation_finished(terminal_kind="cancelled")` с исходным `run_id` и правильным `cancelled_stage="load"` или `"handler"`. Terminal обязан существовать уже к моменту, когда вызывающий наблюдает `CancelledError`. Он имеет `INFO`, `commit_attempts=0`, `load_duration_ms`/`handler_duration_ms` соответствуют завершённым стадиям; для незавершённой стадии допускай `None` либо конечное неотрицательное измерение по §11.5. Полей `orch_status`, `handler_status`, `context_status`, `code`, `state_version` и `delivery_cancelled` у cancelled terminal нет. Не допускай второго terminal или ложного result-terminal.

Проверь отсутствие command payload и полного session ID в compact events. Для отрицательных утверждений используй позитивные контроли уже имеющихся завершённых load и Handler веток. Если добавляешь прямой `CancelledError` из Handler как отдельный случай, он должен подтверждать ту же отменённую форму и отсутствие нормализации; не повторяй весь внешний `task.cancel()` сценарий. Не запускай `KeyboardInterrupt` или `SystemExit` внутри основного pytest runner; их запрет на нормализацию остаётся требованием 5.4, но не поводом рисковать остановкой всего набора в 5.3.
