# Промт 5.4 — Ошибки Handler и отмена до commit

**Статус:** подготовлен; реализация отдельно.
**Зависимость:** тесты 5.3 написаны, но 5.2 ещё не реализована в текущем checkout. Полная приёмка Handler-веток 5.4 возможна только после 5.2. Исправление отмены во время load независимо и может быть проверено раньше, но не делает всю карточку выполненной.
**Основание:** [ApplicationOrchestrator R3.2](../../../docs/requirements/component_responsibilities/exact-orb_application_orchestrator_requirements.md), UC-12/14, FR-25/26, §8–12, AC-9/21/26/29/30/32/33; [план](../../../docs/project_management/application_orchestrator_implementation_plan.md), карточки 5.2–5.4.
**Граница приёмки:** production-обработка неверного результата/исключения Handler и отмены до начала сохранения. Защищённый commit, его отмена, retry и итоговый success относятся к группе 6–7.

## Что делаем и зачем

Координатор должен завершать пользовательский запрос предсказуемо, даже если Handler вернул не тот тип ответа или аварийно завершился. Такой сбой означает внутреннюю техническую проблему. Пользователь получает одинаковое безопасное сообщение, а разработчик — отдельную диагностическую запись с причиной. Новое состояние сессии в этой ситуации сохранять нельзя.

При отмене во время загрузки сессии или работы Handler запрос тоже должен получить итоговое событие. Сейчас тест 5.3 воспроизводит конкретную дыру: `load` отменяется, `CancelledError` доходит до вызывающего, но в журнале остаётся только `application_operation_started`. Операция выглядит незавершённой для метрик. Мы должны записать **один cancelled terminal до проброса отмены**, не утверждая, будто прерванная стадия успешно закончилась, и не начинать сохранение.

**Результат этапа:** для невалидного outcome и настоящего исключения Handler возвращается `ApplicationInternalFailure` с известной версией загруженной сессии; для отмены load/Handler наружу выходит исходный `CancelledError` без `ApplicationResult`. Во всех этих ветках нет save. Штатные исходы Handler и их тексты остаются собственностью 5.2; успешный commit не объявляется готовым до 6.4.

## 1. Отмена во время load

Обработай `asyncio.CancelledError` **вокруг `await context.load(session_id)`**. Когда запрос отменён на этой незавершённой стадии, вызови существующий `log_operation_cancelled` с исходным `run.run_id`, `cancelled_stage="load"`, `handler_duration_ms=None` и допустимой длительностью load по §11.5 (`None` либо конечное неотрицательное измерение). Затем пробрось тот же `CancelledError`. Не создавай `ApplicationResult`, не вызывай Handler/save и не записывай ложный `application_stage_finished(stage="load")`. После уже записанного `started` должен остаться ровно один terminal `terminal_kind="cancelled"` до того, как отмену увидит вызывающий.

Сохрани существующую обработку typed `SessionAbsent`, `StateReadFailed`, невалидного load outcome и настоящего `Exception`. Не превращай отмену в `InternalFailure` через общий `except Exception` или `BaseException`; не расширяй область перехвата так, чтобы ошибки формирования результата либо журнала стали ошибками load. Переустройство диагностики невалидного **load** outcome из 4.2 не входит в эту карточку.

## 2. Нарушение контракта и исключение Handler

Этот раздел выполняй, когда 5.2 уже передаёт Handler исходные `command`, `snapshot.state` и `run` и классифицирует его штатные исходы. Ограничь `try/except` самим `await handler.handle(...)`: исключение при построении модели или записи события не должно маскироваться как «ошибка Handler».

Для `None` и любого объекта вне `BuildNatalOutcome`:

- Не вызывай save и не делай повторного load/Handler.
- Запиши отдельную техническую диагностику с исходным `run_id`. Это нарушение возвращённого контракта, а не реально пойманное исключение: не создавай искусственный `raise` только ради `logger.exception`/`exc_info`. Допустима обычная error-запись со `stack_info=True`.
- Запиши один `application_stage_finished(stage="handler", outcome="invalid_outcome")` на `WARNING`, с конечной неотрицательной длительностью и, если указываешь версию, с исходной загруженной версией.
- Верни `ApplicationInternalFailure`: `FAILURE / UNEXPECTED_FAILURE / LOADED`, `code=INTERNAL_FAILURE`, `detail_code=None`, `retryable=False`, точный текст `Произошла внутренняя ошибка.`, исходные `run_id` и `state_version` (включая 0). Затем запиши ровно один result-terminal на `WARNING` из **того же объекта результата**.

Для неожиданного `Exception` из `handler.handle` результат и порядок те же, но `outcome="unexpected_failure"`. Отдельная запись должна использовать **настоящий traceback пойманного исключения** и `run_id`. Сырой текст исключения остаётся в технической диагностике; в `user_message` и compact lifecycle events его нет. Обычный `except Exception` не перехватывает `KeyboardInterrupt`/`SystemExit`, их нельзя нормализовать в application failure. Тесты не должны прерывать pytest runner ради этих двух классов.

Для обоих завершённых ошибкой путей порядок lifecycle: `started → load/loaded → handler/<исход> → finished(result)`. Значения terminal соответствуют возвращённой модели; `load_duration_ms` и `handler_duration_ms` конечны и неотрицательны, `commit_duration_ms=None`, `commit_attempts=0`, `commit_error_codes=()`, `delivery_cancelled=False`. Не передавай в compact события payload команды, полный session ID, `issues`, artifact или сырой текст исключения.

## 3. Отмена во время Handler

Обработай `asyncio.CancelledError` отдельно от `Exception` вокруг **ожидания Handler**. Запиши один `log_operation_cancelled` с `cancelled_stage="handler"`, исходным `run_id`, длительностью уже завершённого load и допустимой длительностью незавершённого Handler, затем пробрось исходную отмену. Нет `ApplicationResult`, save, commit-attempt event и ложного `application_stage_finished(stage="handler")`; завершённый `load/loaded` остаётся в журнале. У cancelled terminal нет фиктивных статусов результата или `delivery_cancelled` — этот флаг относится к отмене **после начала commit** и здесь не используется.

Именно такой порядок проверяет Event-тест 5.3: он ждёт фактического входа в Handler, затем отменяет задачу и после наблюдения `CancelledError` требует terminal. Не подменяй это `sleep` или перехватом отмены только вокруг тела после Handler. Отмена после старта save, включая shield, strong reference и ожидание inner task, принадлежит 6.1–6.4; текущая ветка не должна её затрагивать.

## 4. Проверки и отчёт при выполнении

Если 5.2 отсутствует, сначала запусти узкий сценарий отмены load:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/application/test_orchestrator_handler.py::test_cancel_during_load_writes_one_cancelled_terminal -q
```

После правки докажи его прохождение и отдельно запусти уже работающие отказы load. Весь Handler-набор в таком состоянии остаётся красным на `NotImplementedError`; запиши точные причины без `skip`/`xfail` и не запускай F вместо отсутствующей 5.2.

Когда 5.2 есть, проверь сначала пять случаев 5.3 (node IDs из журнала §1.3.26), затем целевой набор карточки:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/application/test_orchestrator_handler.py -k "invalid_handler or handler_exception or cancel_during" -q
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/application/test_orchestrator_handler.py tests/application/test_orchestrator_logging.py -q
```

Сохрани положительные контроли 5.1: штатные `InputRequired` с непустыми issues, `ResolutionUnavailable` и `CalculationFailed` должны по-прежнему проходить без save. Сверь ранний routing и отказы load. После зелёного целевого набора выполни R, затем F по §4.2 плана; если R содержит только заранее отложенный success/commit до 6.4, зафиксируй реальные node IDs и не объявляй его зелёным. При красном R полный F не запускай. Выполни `git diff --check`; не добавляй Ruff/mypy/coverage как обязательные gates.

В §1.3 плана и README запиши команды и их реальные exit codes, таблицу «требование → node ID → прошло/ожидает 5.2 или 6.4», число started/terminal и точную границу оставшегося red. K3 о пустом `issues` не решай молча и не объявляй AC-8 закрытым. Отличай реализованную отмену до commit от защищённой отмены commit. Не выполняй следующий промт автоматически.
