# Промт 5.R1 — Непустой `InputRequired` у источника

**Статус:** подготовлен к выполнению.
**Решение владельца:** K3 закрыт 2026-09-19: пустой `InputRequired` запрещён у источника.
**Основание:** требования к `BuildNatalHandler` §7.1 и §12.2, требования к `ApplicationOrchestrator` AC-8/AC-23, план реализации K3.
**Граница приёмки:** общий outcome `InputRequired`, его `Issue` и существующая обработка исключения Handler в `ApplicationOrchestrator`. Интеграция 10.3 остаётся следующим отдельным этапом.

## Что делаем и зачем

`InputRequired` означает, что пользователь должен исправить конкретные поля. Пустой список проблем не даёт пользователю ни причины, ни следующего действия, а на границе application такой объект всё равно невозможно превратить в корректный `ApplicationInputRequired`. Поэтому источник обязан создавать `InputRequired` минимум с одной содержательной проблемой, а каждая проблема обязана указывать непустой путь поля.

Закрепи это правило в общей доменной модели. `InputRequired(issues=())` и `Issue(field="", code="MISSING")` должны отклоняться Pydantic при построении. Handler не добавляет фиктивные проблемы и не нормализует пустой результат. `ApplicationInputRequired` сохраняет действующее требование непустого `issues`.

Если ошибочный resolver всё же пытается построить пустой `InputRequired` во время реального вызова Handler, созданный Pydantic `ValidationError` должен пройти через уже существующую границу ошибок: Handler повторно поднимает исключение, а `ApplicationOrchestrator` возвращает безопасный `ApplicationInternalFailure`. Для менеджера это означает предсказуемое завершение операции: пользователь видит обычное сообщение о внутренней ошибке, состояние не сохраняется, а разработчики получают traceback для диагностики.

## Сначала тесты

В `tests/application/test_build_natal_handler.py` замени `test_empty_input_required_passes_through_unchanged` на проверку двух недопустимых конструкций:

```python
InputRequired(issues=())
Issue(field="", code="MISSING")
```

Обе конструкции должны поднимать `pydantic.ValidationError`. Существующий положительный контроль с непустым `issues` должен сохраниться.

Добавь regression-тест с resolver, который пытается вернуть `InputRequired(issues=())`. Собери реальный `BuildNatalHandler`, реальный `ApplicationOrchestrator` и recording context с загруженной сессией. До production-правки тест должен воспроизводить дефект. После правки проверь:

- результат `ApplicationInternalFailure` со связкой `FAILURE / UNEXPECTED_FAILURE / LOADED`;
- `code=INTERNAL_FAILURE`, `detail_code=None`, `retryable=False` и точный текст `Произошла внутренняя ошибка.`;
- исходные `run_id` и `state_version`;
- отсутствие `save` и вызова artifact port;
- один terminal event после `handler/unexpected_failure`;
- диагностическую запись Orchestrator с настоящим traceback `ValidationError`.

## Реализация

Импортируй `Field` из Pydantic и задай:

```python
field: str = Field(min_length=1)
issues: tuple[Issue, ...] = Field(min_length=1)
```

Не добавляй проверку в Orchestrator: после усиления модели обычный runtime не может получить пустой типизированный outcome. Попытка ошибочного producer создать его является исключением Handler и уже имеет согласованную безопасную обработку.
