# Промт 6.1 — Тесты одной защищённой попытки сохранения

**Статус:** подготовлен 2026-09-18; не выполнялся.
**Зависимость:** 5.4, включая реализованные штатные Handler-ветки 5.2. По §1.3.29 плана ранние ветки завершены; текущий код после `BuildNatalSuccess` останавливается на `NotImplementedError` перед commit. Перед исполнением сверить состояние заново.
**Основание:** ApplicationOrchestrator R3.2, UC-01/15, FR-10–13/17/20/26, §11.4–11.5 и §12; AC-7/10/16/17/19/26/27/31/32, связанные AC-29/30; карточки 6.1–6.4 [плана](../../../docs/project_management/application_orchestrator_implementation_plan.md).
**Граница приёмки:** unit-тесты настоящего `ApplicationOrchestrator.execute` для одного save с исходом `Committed`, без отмены и с одной отменой после фактического входа в save. Реализация защиты принадлежит отдельному этапу 6.2.

## Что делаем и зачем

Расчёт карты и сохранение результата в сессии — два разных шага. Готовая карта ещё не означает, что новое состояние сохранено. Поэтому координатор может сообщить об успехе только после подтверждения от компонента, который отвечает за хранение. В этом этапе мы подготовим автоматические проверки: результат расчёта передаётся на сохранение один раз, в нужную сессию и с той версией состояния, с которой началась работа.

Есть важная ситуация: запрос уже дошёл до записи, но пользователь перестал ждать, например закрыл страницу. Запись в этот момент может продолжаться. Координатор должен дождаться её исхода и оставить в техническом журнале достоверный итог. Только после этого выполнение запроса завершается отменой. Иначе система будет считать запрос законченным, пока его запись ещё работает, а по журналу нельзя будет понять, сохранился ли результат.

Проверим это управляемым сценарием. Тест останавливает сохранение в известной точке, отменяет запрос и убеждается, что запись продолжает ждать разрешения, а запрос ещё не завершён. Затем тест разрешает сохранение и проверяет порядок: подтверждение записи → запись итоговых событий → передача отмены вызывающему. Отмена доставки ответа не должна превращать уже подтверждённое сохранение в ошибку или отменённую запись.

**Результат этапа:** воспроизводимые тесты для обычного сохранения и этого сценария отмены. Сам механизм сохранения здесь не реализуется: тесты задают проверку для следующего промта 6.2. Они проверяют координацию внутри работающего процесса; сохранность при падении процесса, реальная база данных, повторные попытки и остальные исходы сохранения проверяются другими этапами.

## 1. Общий управляемый сценарий

Используй валидные `SessionSnapshot`, `BuildNatalCommand` и согласованный `BuildNatalSuccess(artifact, delta)` из существующих factories. Время рождения нормализуй до минут по примеру текущих тестов; не создавай отдельный набор расчётных данных или golden-файл. Исходная версия должна включать `0` хотя бы в одном случае и ненулевое значение в другом.

Fake Handler возвращает подготовленный `BuildNatalSuccess`. Fake ContextService возвращает исходный snapshot из load, а внутри save записывает реальный вход и аргументы через `Call`, устанавливает `save_entered`, затем ждёт `allow_save_finish`. Оба сигнала — `asyncio.Event`. После разрешения fake фиксирует нормальное завершение и возвращает настроенный `Committed(state_version=...)`.

Если в save приходит `CancelledError`, fake отмечает это и пробрасывает исключение. Он не должен самостоятельно защищать себя через shield, подавлять отмену или возвращать успех из `finally`: иначе тест скроет отсутствие защиты у Orchestrator. Допустимо сохранить `asyncio.current_task()` при входе в save для наблюдения lifecycle и уборки; не привязывай тест к приватному имени или месту хранения задачи в Orchestrator.

Запускай caller отдельной задачей. Ожидание `save_entered` должно одновременно замечать раннее завершение caller: например, через `asyncio.wait(..., return_when=FIRST_COMPLETED)` с ограничением времени. Если caller упал на текущем `NotImplementedError`, извлеки исходное исключение, а не жди timeout и не объявляй его дефектом синхронизации. Создание commit-task само по себе не доказывает, что save начался.

Все вспомогательные задачи и event waiters убирай в `finally`: освободи ворота, дождись начатых задач, извлеки их результаты/исключения. Cleanup не должен создавать события, которые затем используются как доказательство правильного порядка основной операции. Timeout служит только защитой от зависания.

## 2. Обычное сохранение и подтверждённый успех

В `test_orchestrator_commit.py` проверь путь без отмены. До разрешения save должны быть наблюдаемы ровно один load, один handle и вход в один save; caller ещё не завершён, commit-attempt-finished и terminal отсутствуют. Это доказывает, что успех Handler не выдан за завершённую application-операцию.

После разрешения save проверь:

- Последовательность вызовов строго `load → handle → save`; повторных load/Handler/save нет. Handler получил исходные command, `snapshot.state` и run по identity.
- Save получил точный `session_id`, original expected из загруженного snapshot и именно `outcome.delta` по identity. Сравнения delta только по равенству недостаточно.
- Возвращается `ApplicationCommitted`: `SUCCESS / SUCCESS / COMMITTED`, `code="OK"`, `detail_code=None`, `user_message=None`, `retryable=False`, исходный `run_id`, версия из typed `Committed` и artifact Handler. Не требуй новой гарантии глубокой identity/immutability artifact сверх текущего контракта.
- Хотя бы в одном unit-случае настрой валидную версию typed `Committed`, отличную от локально вычисленного `loaded_version + 1`. Это проверка прозрачной передачи ответа зависимости: Orchestrator не назначает версию сам. Не описывай такой fake как сценарий реального CAS — его инкремент проверяется в session/integration.
- До передачи результата вызывающему записана вся последовательность lifecycle из раздела 4; `delivery_cancelled=False`.

Наблюдение «до возврата» делай в caller сразу после `await execute`, сохраняя состояние журнала в этот момент, либо через единый упорядоченный журнал вызовов и реальных LogRecord. Проверка только после общего teardown недостаточна.

## 3. Одна отмена после входа в save

В `test_orchestrator_cancellation.py` используй тот же управляемый путь с `Committed`. Дождись `save_entered` из тела save, затем вызови `caller_task.cancel()` **один раз**, пока `allow_save_finish` закрыт.

Проверка `not caller_task.done()` сразу после `cancel()` ничего не доказывает: отмена ещё могла не обработаться. Дай циклу событий обработать запрос отмены через явную синхронизацию, например Event-checkpoint, поставленный `loop.call_soon` после `cancel()`, и объясни порядок в helper/docstring. Не используй `sleep`, повтор фиксированного числа проходов цикла, случайную задержку или истечение timeout как доказательство ожидания.

После этой точки и до открытия ворот проверь:

- Caller не вернул `ApplicationResult` и не доставил `CancelledError`; его задача остаётся незавершённой.
- Начатый save не получил отмену и не завершился; он по-прежнему ждёт `allow_save_finish`.
- Нет commit-attempt-finished и terminal, второго save, повторного load или Handler. Завершённые load/Handler уже имеют свои stage events.

Затем разреши save и дождись caller. Fake должен нормально закончить save и вернуть `Committed`; вызывающий должен получить **`asyncio.CancelledError`**, а не `ApplicationCommitted`, `ApplicationInternalFailure` или выдуманный статус отмены.

Сними журнал непосредственно в момент, когда caller наблюдает `CancelledError`, до cleanup. К этому моменту уже обязаны существовать один commit-attempt event с подтверждённой версией и один result-terminal с `SUCCESS / SUCCESS / COMMITTED`, `code="OK"`, `delivery_cancelled=True`. Форма `terminal_kind="cancelled"`/`cancelled_stage` относится только к отмене до commit и здесь недопустима. Не требуй проверки identity экземпляра исключения через приватные поля asyncio.

Докажи наблюдаемый порядок:

```text
вход в save
→ запрос отмены caller
→ контроль незавершённого caller при закрытых воротах
→ разрешение и нормальное завершение save
→ application_commit_attempt_finished(attempt=1, outcome=committed)
→ application_operation_finished(terminal_kind=result, delivery_cancelled=true)
→ CancelledError у вызывающего
```

Проверка должна обнаруживать и прямое отменяемое ожидание save, и вариант «shield защищает запись, но caller сразу выходит с отменой». Не подменяй тестируемый Orchestrator или его logging-функции ради получения нужных событий. Способ хранения strong reference и структура защищённой стадии остаются выбором реализации 6.2; после завершения caller не должно оставаться незавершённой работы этого save.

## 4. События и связь с реальными действиями

Захватывай настоящий logger `exact_orb.application` по образцу существующих fixtures с восстановлением handlers, propagate, level и disabled. Разбирай `LogRecord.getMessage()` как имя события и следующий за ним JSON object. Старый разбор `key=value` к текущему контракту не подходит. Не вызывай logging helpers вручную вместо исполнения пути.

Для обоих сценариев требуй ровно пять lifecycle-событий в порядке:

```text
application_operation_started                                      INFO
application_stage_finished(stage=load, outcome=loaded)              DEBUG
application_stage_finished(stage=handler, outcome=success)          DEBUG
application_commit_attempt_finished(attempt=1, outcome=committed)    DEBUG
application_operation_finished(terminal_kind=result)                INFO
```

Во всех событиях один входной `run_id`; отдельного `stage=commit` нет. Stage events содержат загруженную версию, attempt и terminal — подтверждённую версию из `Committed`. У attempt `detail_code=None`, номер строго 1 и конечная неотрицательная длительность. У terminal `commit_attempts=1`, `commit_error_codes=[]`, правильная тройка статусов, `code="OK"`, `detail_code=None` и корректный признак доставки. Его длительности load/Handler совпадают с соответствующими stage events, а `commit_duration_ms` — с единственной attempt; конкретное число миллисекунд не фиксируй.

Нормальный terminal сверяй с реально возвращённым `ApplicationCommitted`. При отмене проверяй ту же классификацию по настроенному typed outcome и фактическим событиям, хотя результат вызывающему уже не доставляется. Terminal обязан предшествовать возврату либо пробросу отмены, а attempt — следовать за нормальным завершением save. Формат helper уже покрыт другими тестами; здесь проверяется его использование в живом execute.

Компактные события не должны получать command/StateDelta/ChartArtifact payload или полный session ID. Не меняй существующую политику DEBUG boundary logging. Изолируй события одной операции, чтобы чужая запись не могла послужить положительным контролем.

## 5. Проверки и отчёт о выполнении

В docstring каждой новой тестовой функции укажи соответствующие FR/AC и наблюдаемое поведение. Не копируй весь перечень AC в каждый тест; AC-19 здесь покрывается только для `Committed`, AC-16/17 — для одной отмены первого save, AC-31/32 — для одной попытки. Retry, повторная отмена, другие outcomes и persistence-интеграция остаются своим карточкам. Ошибка подготовки lifecycle-события после подтверждённого commit не считается проверенной нормальными сценариями; обязанность §11.5 остаётся для последующего среза групп 6/8.

Запусти точную целевую команду из карточки 6.1:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/application/test_orchestrator_commit.py tests/application/test_orchestrator_cancellation.py -q
```

До реализации 6.2 ожидается падение на отсутствующей commit-ветке. Зафиксируй настоящие node IDs, причины и exit code. Ошибка импорта, невалидная fixture, пропущенный logger, зависание helper или недетерминированный порядок — не подтверждение чувствительности теста к отсутствующему commit. Исправь тестовую причину в allowlist; дефект production верни этапу-владельцу. Не используй `skip`, `xfail`, перехват `NotImplementedError` как успешную проверку или ослабление assertions. Collection не равна прохождению тестов.

После успешного целевого набора запусти R, затем F только при успешном R:
