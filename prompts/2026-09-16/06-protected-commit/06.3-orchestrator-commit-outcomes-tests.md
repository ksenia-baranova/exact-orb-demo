# Промт 6.3 — Тесты остальных исходов сохранения

**Статус:** подготовлен 2026-09-18; не выполнялся.
**Зависимость:** выполнена 6.2: первая защищённая попытка с `Committed` и отменой после входа в `save` прошла в трёх случаях. Остальные ответы `save` пока доходят до явного `NotImplementedError`; фактический результат — §1.3.33 [плана](../../../docs/project_management/application_orchestrator_implementation_plan.md).
**Основание:** [ApplicationOrchestrator R3.2](../../../docs/requirements/component_responsibilities/exact-orb_application_orchestrator_requirements.md), UC-01/07–09, FR-10–18/25–26, §8, §11.4–11.5, §12 и AC-10/19–21/26/27/31/32; [ADR-0006](../../../docs/requirements/decisions/0006-application-orchestrator.md); карточки 6.3–6.4 и 7.1–7.2 плана.
**Результат:** детерминированные тесты всех оставшихся исходов первой попытки `ContextService.save`, включая результат для пользователя, отсутствие лишних вызовов и порядок lifecycle-событий. Реализация mapping остаётся отдельной карточкой 6.4.

## Что делаем и зачем

После расчёта сохранение может ответить по-разному. Карта уже могла быть применена другим запросом, результат мог устареть, сессия могла исчезнуть, а сама запись — завершиться отказом или непредвиденной ошибкой. Если показать все эти случаи как обычный успех или спрятать их за общей ошибкой, пользователь не поймёт, сохранена ли карта и что делать дальше. Менеджерам и сопровождению также нужна однозначная запись о том, чем закончилась попытка.

На этом шаге описываем проверками ожидаемое поведение для каждого исхода. Тесты должны показать, какой ответ получит пользователь, какая версия состояния достоверна, сколько раз действительно вызвали сохранение и какие события появились **до** ответа. Отдельно закрепляем, что координатор не запускает расчёт заново при уже окончательном исходе и не выдаёт успешную карту, когда запись не подтверждена.

**Результат этапа для менеджеров:** готова проверяемая матрица решений после первой попытки сохранения. Сама система на этом шаге ещё не начинает возвращать все эти ответы: тесты должны показать незавершённую реализацию, которую закроет 6.4. Повтор записи после временного отказа проектируется и проверяется отдельно в группе 7.

## 1. Общий сценарий и граница попытки

Используй существующие валидные command, snapshot, `BuildNatalSuccess(artifact, delta)`, `RunContext` и расчётные fixtures из тестов 6.1. Собирай реальный `ApplicationOrchestrator` с записывающими fake ContextService и Handler. Для каждого нового случая настрой один конкретный ответ либо исключение из `save`. Журнал вызовов должен подтвердить ровно `load → handle → save`: исходный `session_id`, original `snapshot.state.state_version` (включая 0 хотя бы в одном новом случае) и **ту же delta по identity**. Не делай вывод о реальной работе CAS по искусственной версии fake.

Захватывай настоящие `LogRecord` logger `exact_orb.application`, извлекай JSON из `record.getMessage()` и восстанавливай состояние logger после теста. Не создавай lifecycle-события вручную. Фиксируй состояние событий непосредственно при возврате `execute`, чтобы terminal, записанный позже во время cleanup, не засчитывался. В каждом тесте нужен позитивный контроль достигнутого `save`; простое утверждение «второго save нет» при недостигнутой первой попытке не годится.

Сохрани существующий `test_one_confirmed_save_waits_and_returns_committed` как положительный контроль: он должен входить в целевой запуск файла и оставаться зелёным. Новые сценарии после 6.2 ожидаемо падают на незавершённой ветке, но должны доходить до `save`; ошибка импорта, fixture или logger не подтверждает чувствительность теста.

## 2. Матрица ответов после одного save

Для каждого исхода проверь класс `ApplicationResult`, всю тройку `orch_status / handler_status / context_status`, `code`, `detail_code`, `user_message`, `retryable`, исходный `run_id`, `state_version` и наличие либо отсутствие artifact. Сообщение сравнивай с действующей `describe_failure`, не дублируя её таблицу в тестовом helper.

| Ответ `save` | Ожидаемый application-результат | Существенная проверка |
|---|---|---|
| `AlreadyApplied(state_version=N)` | `ApplicationAlreadyApplied`: `SUCCESS / SUCCESS / ALREADY_APPLIED`, `OK`, `detail_code=None`, `retryable=False` | Версия именно N, включая допустимый 0; artifact результата Handler доступен; нет повторного save, load или Handler. |
| `Superseded(actual=state)` | `ApplicationSuperseded`: `SUPERSEDED / SUCCESS / SUPERSEDED`, `RESULT_SUPERSEDED`, `detail_code=None`, `retryable=False` | Версия из `actual.state_version`, включая 0; artifact не публикуется; нет retry и rebase. |
| `SessionAbsent(reason="expired")` и `SessionAbsent(reason="not_found")` из **save** | `ApplicationSessionAbsent`: `SESSION_ABSENT / SUCCESS / SESSION_ABSENT`, `SESSION_LOST_DURING_OPERATION`, `detail_code=None`, `retryable=False` | Для обоих reason сохранены их значения; это commit-stage, а не load-stage код; `state_version=None`, artifact нет. |
| `StateCommitFailed(error_code=E)` как окончательный исход | `ApplicationStateCommitFailure`: `FAILURE / SUCCESS / COMMIT_FAILED`, `STATE_COMMIT_FAILED`, `detail_code=E`, `retryable=True` | `state_version=None`, artifact нет; один save при запрете повтора; safe user message без сырых данных. |
| Непредвиденный `Exception` из save | `ApplicationInternalFailure`: `FAILURE / SUCCESS / COMMIT_FAILED`, `INTERNAL_FAILURE`, `detail_code=None`, `retryable=False` | `state_version=None`, artifact нет; текст исключения отсутствует в `user_message` и compact events; отдельная exception-запись содержит `run_id` и traceback. |

У `StateCommitFailed` задавай `RunContext.deadline` **раньше** времени injected clock, например `STARTED_AT - timedelta(seconds=1)` при `clock=lambda: STARTED_AT`. Первая попытка всё равно обязана состояться; истёкший deadline запрещает лишь вторую. Это делает ожидание одного save совместимым с будущей 7.2. Не объявляй `StateCommitFailed` с открытым deadline окончательным: там положительный контроль retry появится в 7.1. В тесте unexpected Exception используй уникальный sentinel текста ошибки и не пытайся нормализовать `CancelledError`, `KeyboardInterrupt` или `SystemExit`.

## 3. Наблюдаемый порядок и поля событий

Для каждого случая ожидай ровно пять lifecycle-событий одного `run_id`:

```text
application_operation_started
application_stage_finished(stage=load, outcome=loaded)
application_stage_finished(stage=handler, outcome=success)
application_commit_attempt_finished(attempt=1, outcome=<реальный исход>)
application_operation_finished(terminal_kind=result)
```

Attempt появляется после завершённого save, terminal — после attempt и до возврата результата. У всех `commit_attempts=1`, `delivery_cancelled=false`; `commit_duration_ms` terminal равна длительности этой attempt, а load/Handler durations — соответствующим stage events. Длительности конечны и неотрицательны; не фиксируй число миллисекунд. Все terminal status/code/detail/version поля совпадают с фактически возвращённым результатом. Никаких `attempt=2`, второго terminal или отдельного commit-stage event.

Для `AlreadyApplied` и `Superseded` attempt outcome — `already_applied`/`superseded`, его `state_version` берётся из typed outcome, уровень `DEBUG`; terminal `INFO`. Для обоих `SessionAbsent` attempt — `session_absent`, без `state_version` и detail code, `DEBUG`; terminal `INFO`. Для окончательного `StateCommitFailed` attempt — `state_commit_failed`, `detail_code=E`, без версии, `WARNING`; terminal `WARNING` с `commit_error_codes=[E]`. Для unexpected Exception attempt — `unexpected_failure`, без detail code и версии, `WARNING`; terminal `WARNING`, без выдуманного persistence error code (`commit_error_codes=[]`). У остальных исходов `commit_error_codes=[]`.

Компактные lifecycle-сообщения не должны содержать raw exception sentinel, command, delta, artifact или полный `session_id`; проверяй их отдельно от разрешённой exception-записи с traceback. Не считай отдельную exception-запись шестым lifecycle-событием. Точный формат JSON уже проверен в `test_orchestrator_logging.py`; здесь проверяй связь записанных событий с фактически исполненным `save` и возвращённым результатом.
