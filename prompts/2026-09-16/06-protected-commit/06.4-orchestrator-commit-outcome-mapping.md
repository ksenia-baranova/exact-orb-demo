# Промт 6.4 — Полные ответы после первой попытки сохранения

**Статус:** подготовлен 2026-09-18 перед выполнением.
**Зависимость:** карточка 6.3 написала тесты остальных ответов `save`; последний целевой прогон — 2 passed и 8 ожидаемых failed, см. §1.3.35 [плана](../../../docs/project_management/application_orchestrator_implementation_plan.md).
**Основание:** [ApplicationOrchestrator R3.2](../../../docs/requirements/component_responsibilities/exact-orb_application_orchestrator_requirements.md), UC-01/07–09/15, FR-10–18/20/25–26, §8, §11.4–11.5, §12 и AC-5–10/16/19–21/26/27/29–32; [ADR-0006](../../../docs/requirements/decisions/0006-application-orchestrator.md); карточки 6.1–6.4 и 7.1–7.2 плана.
**Результат:** `execute` классифицирует все ответы первой защищённой попытки `save`, записывает attempt и terminal, затем возвращает соответствующий `ApplicationResult` либо передаёт ранее полученный `CancelledError`.

## Что делаем и зачем

Расчёт карты и сохранение — разные события. Сейчас координатор уже умеет дождаться подтверждённой записи, но другие реальные ответы сохранения ещё заканчиваются технической заглушкой. Пользователь из-за этого не узнаёт, что карта уже была применена, что результат устарел, что сессия исчезла или что запись не удалось подтвердить.

На этом шаге превращаем каждый из этих ответов в понятный результат. Если намерение уже применено, пользователь получает карту и подтверждённую версию. Если другая операция успела изменить сессию, старый результат не выдаётся за сохранённый. При исчезнувшей сессии система объясняет, что начать нужно с новой сессии. При неясном исходе записи она предлагает проверить актуальное состояние; непредвиденная ошибка получает безопасное сообщение. Журнал фиксирует ровно ту попытку, которая действительно состоялась, до выдачи ответа.

**Результат этапа для менеджеров:** система завершает первый полный путь построения карты с корректным ответом для каждого исхода одной попытки сохранения. Автоматический повтор после отказа записи ещё не включён: его правила, deadline и отмена проверяются и реализуются отдельно в группе 7.

## 1. Классификация одной попытки

Оставь вызов `save(session_id, original_expected_state_version, handled.delta)` и локальную защищённую задачу. После завершения первого `save` используй только его typed outcome:

| Ответ `save` | Внешний ответ |
|---|---|
| `Committed(N)` | Уже действующий `ApplicationCommitted`: подтверждённая версия N, artifact Handler. |
| `AlreadyApplied(N)` | `ApplicationAlreadyApplied`: `SUCCESS / SUCCESS / ALREADY_APPLIED`, `OK`, версия N (включая 0), artifact Handler; без новой записи. |
| `Superseded(actual)` | `ApplicationSuperseded`: `SUPERSEDED / SUCCESS / SUPERSEDED`, `RESULT_SUPERSEDED`, версия `actual.state_version` (включая 0), без artifact, без retry/rebase. |
| `SessionAbsent(reason)` | `ApplicationSessionAbsent`: `SESSION_ABSENT / SUCCESS / SESSION_ABSENT`, `SESSION_LOST_DURING_OPERATION` для обоих reason, `state_version=None`, без artifact. |
| окончательный `StateCommitFailed(E)` | `ApplicationStateCommitFailure`: `FAILURE / SUCCESS / COMMIT_FAILED`, `STATE_COMMIT_FAILED`, `detail_code=E`, `retryable=True`, `state_version=None`, без artifact. |
| непредвиденный `Exception` из save | `ApplicationInternalFailure`: `FAILURE / SUCCESS / COMMIT_FAILED`, `INTERNAL_FAILURE`, `detail_code=None`, `retryable=False`, `state_version=None`, без artifact; raw текст только в отдельной exception-записи. |

Для пользовательских сообщений `Superseded`, `SessionAbsent`, `StateCommitFailed` и internal failure вызывай существующую `describe_failure` с относящимися к исходу аргументами. Не создавай вторую таблицу сообщений. Типизированный `StateCommitFailed` не превращай в успех без другого typed результата. В 6.4 нет повтора: тест 6.3 задаёт истёкший deadline для окончательного однопопыточного отказа; при открытом бюджете retry будет добавлен 7.2. Не делай проверку deadline перед первой попыткой и не вводи частичный retry попутно.

Неожиданное исключение журналируй со stack trace и `run_id`, затем нормализуй по достигнутой commit-стадии. Не включай raw текст исключения в `user_message` или compact lifecycle. Перехватывай только `Exception`; `CancelledError`, `KeyboardInterrupt` и `SystemExit` не становятся application failure. Если исключение из inner save встретилось после внешней отмены, сначала доведи классификацию и terminal до конца, затем пробрось исходный `CancelledError`.

## 2. События, порядок и отмена

Для каждой реально завершённой первой попытки после `save` запиши ровно один `application_commit_attempt_finished(attempt=1)`, затем один result-terminal через готовые logging helpers. Outcome attempt: `committed`, `already_applied`, `superseded`, `session_absent`, `state_commit_failed` либо `unexpected_failure`. Передавай версию только для первых трёх; `detail_code` — только typed persistence error. У `StateCommitFailed` и unexpected Exception attempt и terminal имеют `WARNING`; остальные ожидаемые исходы — attempt `DEBUG`, terminal `INFO`.

Terminal строится из готового `ApplicationResult`, содержит исходный `run_id`, `commit_attempts=1`, действительные длительности load/Handler/одного save и `delivery_cancelled` по наблюдённой внешней отмене. `commit_error_codes=(E,)` только для typed `StateCommitFailed`; у остальных без typed persistence error — пустой tuple. Не сериализуй command, delta, artifact, полный session ID или персональные данные в lifecycle. Сохрани порядок «завершённый save → attempt → terminal → результат или исходный `CancelledError`» и ожидание inner task без fire-and-forget. Повторную отмену как отдельную гонку по-прежнему проверяет 9.1.
