## Что делаем и зачем

Сохранение рассчитанной карты иногда отвечает, что подтверждение записи не
получено. Это не позволяет сразу сообщить пользователю ни об успехе, ни о том,
что запись точно не произошла. Координатору разрешён один повтор того же
намерения: хранилище сможет подтвердить запись или сообщить, что она уже
применена. Если же повторить изменённые данные или выполнить расчёт заново,
ответ перестанет относиться к исходному запросу.

Этот этап проверяет именно поведение координатора. Тесты должны показать,
что он делает не более двух попыток с одними и теми же данными, правильно
объясняет любой второй ответ и не начинает повтор после наблюдённой отмены
или истечения выделенного времени. Журнал событий должен соответствовать
фактическим попыткам: это помогает поддержке отличить один отказ от двух,
не раскрывая персональные данные в кратких lifecycle-событиях.

**Результат для менеджеров:** временный отказ записи получает один
контролируемый шанс подтверждения, а отменённый или просроченный запрос не
создаёт лишнюю запись. Автоматические проверки воспроизводят эти варианты
без случайных задержек. Реальная потеря подтверждения после применённой
записи проверяется отдельно в 10.4: два заданных ответа fake-хранилища не
доказывают отсутствие двойного CAS.

`docs/project_management/application_orchestrator_implementation_plan.md` и
`prompts/2026-09-16/README.md`.

Не меняй production, модели, Handler, ContextService, persistence, прежние
тесты, требования, ADR, диаграммы или сохранённый [промт 7.2](07.2-orchestrator-exact-retry.md).
Не создавай второй расчёт, load, Handler, rebase, новую expected-version,
копию delta, третий save или тест с реальным ожиданием deadline. Не добавляй
дублирующие сценарии, зависимости, сетевые smoke, коммит, ветку, push или PR.
Посторонние файлы рабочего дерева оставь нетронутыми.

## Проверки контракта

Вызови настоящий `ApplicationOrchestrator.execute` с валидными command,
snapshot, `BuildNatalSuccess` и локальным управляемым fake `ContextService`.
Записывай реальные вызовы `load`, Handler и `save`. Первый save возвращает
`StateCommitFailed`; следующий ответ задаётся сценарием. Проверь точный порядок
`load → handle → save → save`, один вызов первых двух компонентов, одинаковые
`session_id` и исходную expected-version у обеих попыток, а также **identity
того же объекта delta**. При запрете повтора ожидается ровно один save.

Покрой второй `Committed`, `AlreadyApplied`, `Superseded`, `SessionAbsent`
с причинами `expired` и `not_found`, ещё один `StateCommitFailed` с другим
`error_code`, а также неожиданное `Exception`. Сверь полную публичную модель
результата: версия берётся из достоверного typed outcome, artifact есть
только при подтверждённом успехе, после двух отказов `detail_code` относится
ко второй попытке. Исключение даёт безопасный `ApplicationInternalFailure`
и отдельный traceback; третьей попытки нет.

Используй fake UTC clock для четырёх границ: deadline отсутствует, находится
в будущем, равен текущему времени и уже прошёл. Первые два случая разрешают
повтор, два последних запрещают. Истёкший deadline не отменяет уже допустимый
первый save. Реальное время, `sleep` и timeout как доказательство порядка
запрещены.

Для отмены останови первый save через `asyncio.Event`. После входа в save
отмени caller, дай event loop обработать отмену через явный checkpoint,
убедись, что caller ещё ждёт внутреннюю задачу, и лишь затем разреши первый
`StateCommitFailed`. Должны появиться один attempt и один result-terminal
с `delivery_cancelled=true`, после чего вызывающий получает исходный
`CancelledError`. Второго save нет; timeout допускается только как защита от
зависания теста.

Во всех сценариях захватывай настоящие lifecycle `LogRecord`. Сверяй порядок
с завершением save и возвратом caller, номера попыток, уровни, версии,
упорядоченные `commit_error_codes`, число `commit_attempts` и сумму
длительностей попыток. Краткие события не должны содержать command, delta,
artifact, полный session ID или текст приватного исключения. Это проверка
наблюдаемого поведения `execute`, а не ручной вызов logging helpers.

## Исполнение и готовность

Сначала проверь состав уже созданной матрицы и её соответствие указанным
контрактам. Исторический запуск до production-правки уже записан в §1.3.37:
**11 failed, 1 passed** из-за отсутствовавшего тогда повтора; повторять его
откатом рабочего кода нельзя. Не добавляй тесты только ради нового diff.

Запусти целевой файл:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/application/test_orchestrator_retry.py -q
```

Если тестовый или production-код потребует исправления по установленному
дефекту, соблюдай отдельные границы соответствующей карточки и затем запускай
связанный R и полный F из §4.2 плана. Зафиксируй точные результаты, состав
файлов и остающиеся 9.1/10.4, K3, 2.R2 в журнале и README. Проверки
структуры Markdown, `git diff --check` и пустого staged index обязательны;
коммит по этой задаче не создаётся.
