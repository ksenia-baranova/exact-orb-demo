# Промт 8.1 — Сквозная последовательность событий операции

**Статус:** подготовлен 2026-09-18 перед исполнением.
**Зависимости:** 1.4 и 7.2 реализованы; текущий HEAD содержит точный commit retry.
**Основание:** [ApplicationOrchestrator R3.2](../../../docs/requirements/component_responsibilities/exact-orb_application_orchestrator_requirements.md),
FR-26, §11.5, AC-26/29–32; [ADR-0006](../../../docs/requirements/decisions/0006-application-orchestrator.md),
[диаграмма событий 010](../../../docs/sequence_diagrams/build_natal/010-build_natal_application_observability.puml),
[карточка 8.1 плана](../../../docs/project_management/application_orchestrator_implementation_plan.md).
**Результат:** тесты реального `execute()` подтверждают последовательность
lifecycle-событий для каждой операции, включая ранние отказы, сохранение,
повтор и отмену.

## Что делаем и зачем

По журналу сопровождение должно видеть начало и достоверный конец каждого
запроса. Между ними нужны только события тех шагов, которые действительно
завершились. Иначе запрос, прерванный при загрузке, может выглядеть как
законченный расчёт; лишнее событие сохранения создаст ложное впечатление,
что запись уже выполнялась. Для одного запроса в журнале должно быть ровно
одно начало и одно завершение, а завершение появляется до того, как результат
или отмена переданы вызывающему.

`run_id` связывает события, но не является счётчиком вызовов. Даже если два
последовательных вызова используют один и тот же идентификатор, тесты должны
проверять границы каждого вызова отдельно. Это защищает от ситуации, когда
лишний terminal одного вызова компенсирует отсутствующий terminal другого.
При уровне INFO начало и конец должны оставаться видимыми: из этих событий
считают завершённые операции без включения подробного DEBUG-журнала.

**Результат для менеджеров:** операцию можно проследить от входа до выхода
без вымышленных стадий и потерянных завершений. Эта карточка проверяет
порядок событий; точный состав полей, числовые длительности и отсутствие
чувствительных данных подробно проверяются в 8.2.

## Границы работы

Разрешено менять:

- `tests/application/test_orchestrator_logging.py` — только сквозные проверки
  через настоящий `ApplicationOrchestrator.execute` и узкие локальные fake
  зависимости;
- §1.3 `docs/project_management/application_orchestrator_implementation_plan.md`
  и `prompts/2026-09-16/README.md` — статус и фактические проверки.

Не меняй production, общие fakes, уже сохранённые промты, другие тесты,
requirements, ADR и диаграммы. Если новый тест выявит дефект, сначала
покажи воспроизводимый сценарий и верни исправление в карточку владельца
3.2–7.2 отдельным обоснованным срезом; не внедряй всю instrumentation здесь.
Не добавляй counters/registry по `run_id`, telemetry-port, глобальную
logging policy, зависимость или сетевой smoke. Сохрани посторонние файлы;
коммит, ветка, push и PR требуют отдельного указания.

## Перед изменением

Сверь ветку, HEAD, рабочее дерево и index. Прочитай FR-26, §11.5 и AC-26/29–32,
ADR-0006, диаграмму 010, карточки 8.1–8.2/9.1 и текущий
`orchestrator.py`/`operation_logging.py`. Сопоставь с имеющимися тестами
routing, load, Handler, commit, retry и cancellation: они уже проверяют
частные ветки, поэтому не копируй их полные assertions. Новый результат —
сквозная граница каждого вызова, в том числе при одинаковом `run_id`, и
видимость terminal при effective INFO.

## Проверка через execute

В `test_orchestrator_logging.py` вызывай настоящий координатор, подменяя
только ContextService и Handler управляемыми fake-компонентами. Захватывай
настоящие `LogRecord` logger `exact_orb.application.operation_logging`.
Для каждого вызова сохраняй отдельный диапазон записей до выхода caller;
проверяй имена lifecycle-событий, порядок, `run_id`, число `started`/`finished`,
стадии и номера попыток. Подсчёт всех записей по одному `run_id` без границ
вызовов не принимается.

Проверь матрицу достижимых путей: отказ routing до load; отказ load до
Handler; non-success Handler без save; обычный подтверждённый save; отказ
commit с разрешённым точным повтором; отмена при незавершённом load и
незавершённом Handler. Для каждого сценария сопоставь реальные вызовы
зависимостей с событиями: load/Handler event только после завершения стадии,
commit-attempt event только для начатого и законченного save. Никаких
фиктивных stage/attempt при раннем выходе и никаких событий после terminal.
При повторе увидь attempt 1 и 2; при отмене до commit —
`terminal_kind=cancelled` без вымышленного результата.

Для отмены используй `asyncio.Event` и явный handshake входа в стадию;
timeout служит только защитой от зависания. События незавершённой стадии
должны отсутствовать, terminal должен существовать до наблюдения
`CancelledError` у caller. Не используй `sleep` или случайное ожидание.

Сделай отдельную проверку при effective INFO: каждый вызов по-прежнему
даёт ровно одно начало и одно завершение, DEBUG stage/успешная первая
commit-attempt скрыты, WARNING-попытки остаются видимыми. Не меняй
производственный уровень логирования глобально; локальную настройку logger
восстанови после теста.
