# Промт 9.R1 — Terminal-гарантия при внутренних ошибках commit-flow

**Статус:** подготовлен 2026-09-19 перед исполнением.
**Зависимости:** реализованы 7.2, 8.1, 9.1 и 9.2.
**Основание:** [зафиксированные дефекты ручного ревью](../../../docs/development_approach/problems_detected_by_human/004-application-orchestrator-internal-failures-lose-terminal-event.md), UC-13, FR-25/26 и AC-29/31/32 [требований ApplicationOrchestrator](../../../docs/requirements/component_responsibilities/exact-orb_application_orchestrator_requirements.md).

## Что делаем и зачем

Операция уже может записать начало, успешные load и Handler, а затем исчезнуть
из lifecycle-журнала, если координатор не смог создать задачу сохранения или
получил некорректное время при решении о повторе. Для пользователя это сырое
техническое исключение, а для эксплуатации — операция без terminal-события,
которая выглядит в метриках как навсегда активная.

Закроем две воспроизведённые дыры commit-flow. Ошибку вызова `save` или
создания `asyncio.Task` классифицируем как внутренний отказ первой попытки.
Ошибку clock после первого `StateCommitFailed` завершим как внутренний отказ,
не создавая второй save. Оба пути должны вернуть безопасный типизированный
ответ и ровно один terminal.

**Результат для менеджеров:** даже ошибка конфигурации внутренней зависимости
не оставляет запрос без результата и завершения в журнале. При этом система
не сообщает о повторном сохранении, если оно фактически не начиналось.

## Границы работы

Разрешено:

- создать `tests/application/test_orchestrator_internal_failures.py`;
- изменить `src/exact_orb/application/orchestrator.py`;
- обновить запись дефекта 004, §1.3 и карточку 9.R1 плана, а также README серии.

Не выполняй полный рефакторинг `_route/_load/_handler/_commit`, не меняй
ApplicationResult, ContextService, Handler, failure policy, operation logging,
requirements, ADR, диаграммы, composition или transport. Не добавляй общий
`except Exception`, который может переклассифицировать подтверждённый
`Committed`/`AlreadyApplied`. Не меняй cancellation/retry policy, число
попыток, CAS-аргументы или публичные API. Посторонние файлы рабочего дерева
сохраняй. Коммит, push и PR требуют отдельного указания.

## Реализация и проверки

Добавь детерминированные regression-тесты через настоящий
`ApplicationOrchestrator.execute`:

1. Синхронный callable `save` бросает до создания coroutine.
2. `save` возвращает не-awaitable значение, отклоняемое `create_task`.
3. После первого `StateCommitFailed` clock бросает, возвращает naive datetime
   или значение другого типа.

В первых двух случаях докажи один вызов `save`, один attempt с
`unexpected_failure`, `ApplicationInternalFailure` на commit-стадии и один
terminal. В clock-случаях докажи ровно один save/attempt, сохранение error code
первой попытки, отсутствие attempt 2 и terminal с `INTERNAL_FAILURE`.
Проверь безопасный `user_message`, исходный `run_id`, отсутствие artifact и
техническую exception-запись. Timeout и `sleep` не нужны.

В production защити вычисление `save(...)` вместе с созданием task. При
ошибке используй ту же commit-stage internal classification, что и при
исключении из работающей task. Перед сравнением deadline проверь, что clock
вернул timezone-aware UTC datetime; исключение или некорректное значение
нормализуй без запуска второй попытки. Реально завершённый первый
`StateCommitFailed` остаётся в attempt event и `commit_error_codes`.
