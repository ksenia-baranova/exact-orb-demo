## Что делаем и зачем

Компоненты Build Natal уже существуют, но вызывающая сторона пока должна
вручную знать, какой Handler связать с какой командой. Добавим одну точку
сборки application-слоя. Она получает готовые зависимости, создаёт настоящий
`BuildNatalHandler`, формирует registry и передаёт его координатору.

Перед возвратом координатора сборка проверяет, что все поддерживаемые команды
имеют точное назначение. Сейчас продукт поддерживает одну такую команду —
`BuildNatalCommand`. Если позднее команда появится в supported-set, но её
забудут подключить, запуск завершится понятной ошибкой до первого запроса.

**Результат для менеджеров:** приложение получает явную и проверяемую точку
подключения Build Natal. Ошибка комплектации обнаруживается при запуске, а
корректная сборка использует существующие расчётные и сессионные компоненты
без скрытых глобальных объектов.

посторонние файлы рабочего дерева сохраняй.

## Реализация

В новом модуле объяви локальный неизменяемый набор:

```python
_SUPPORTED_COMMAND_TYPES = frozenset({BuildNatalCommand})
```

Локальная `_validate_handler_registry(handlers)` сравнивает этот набор с
точными ключами mapping. Если тип отсутствует, выбрасывает `ValueError` и
перечисляет имена недостающих команд в стабильном порядке. Регистрация
базового `Command` или любого другого типа не покрывает `BuildNatalCommand`.
Дополнительный ключ не является fallback и сам по себе не отменяет полноту
обязательных назначений.

Публичная keyword-only функция имеет контракт:

```python
build_application_orchestrator(
    *,
    context: ContextService,
    clock: Callable[[], datetime],
    resolver: BirthDataResolverPort,
    artifacts: ChartArtifactPort,
) -> ApplicationOrchestrator
```

Создай `BuildNatalHandler(resolver=resolver, artifacts=artifacts)`, положи его
в новый локальный mapping под точным ключом `BuildNatalCommand`, проверь
mapping и передай `context`, mapping и `clock` в существующий конструктор
`ApplicationOrchestrator`. Не сохраняй registry или зависимости в глобальном
изменяемом состоянии и не предоставляй runtime registration/replacement.
Экспортируй через `__all__` только публичную функцию сборки.

## Проверки и отчёт

Сначала запусти неизменённый тест 10.1. Все четыре функции должны реально
исполниться и пройти:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/application/test_application_composition.py -q
```

После зелёного результата запусти связанный набор R и полный F по §4.2 плана:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_run_context.py tests/application tests/session tests/test_module_boundaries.py -q
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider -q
```

Если проверка падает, установи точный node ID и исправляй только
`composition.py`; не меняй тесты и соседние контракты. Затем проверь Python
AST нового production-файла, `git diff --check`, локальные Markdown-ссылки,
code fences, trailing whitespace, состав изменений и пустой staged index.
Запиши точные команды, результаты и границу доказанного в §1.3 плана и README.

Этот этап подтверждает startup-комплектацию и FR-05, но ещё не доказывает
реальный session/Handler flow, cache hit/miss или persistence: это область
10.3–10.5. Полную приёмку R3.2 не объявляй.
