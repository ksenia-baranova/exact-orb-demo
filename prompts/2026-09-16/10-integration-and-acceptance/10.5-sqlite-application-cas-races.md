[карточка 10.5 плана](../../../docs/project_management/application_orchestrator_implementation_plan.md).

## Что делаем и зачем

Проверяем, как две одновременно выполняющиеся пользовательские операции
делят одну SQLite-сессию. Обе успевают прочитать одну исходную версию, затем
независимо рассчитывают карту и пытаются сохранить результат. SQLite должна
атомарно принять только одну запись, а application-слой обязан правильно
объяснить исход второй операции.

Для одинаковых данных вторая операция должна вернуть `AlreadyApplied`: нужное
состояние уже записано первой операцией, поэтому ошибка пользователю не нужна.
Для разных данных вторая операция должна вернуть `Superseded`: её результат
устарел и не может затереть победившую запись. В обоих случаях версия сессии
увеличивается ровно один раз.

**Результат для менеджеров:** двойной клик или повтор одного запроса безопасен,
а два конкурирующих изменения не перезаписывают друг друга. Пользователь
получает результат, соответствующий реально сохранённому состоянию, даже если
запросы обслуживаются разными SQLite handles.

## Границы работы

Разрешено менять только:

- `tests/application/test_orchestrator_sqlite_integration.py` — новый
  integration-файл и локальные test-only wrappers;
- §1.3 плана и README серии — фактический статус и результаты;
- этот промт.

Не меняй production-код, SQLite adapter, `ContextService`, Orchestrator,
Handler, общие fixtures, requirements, ADR, диаграммы, session conformance и
прежние промты. Не используй один InMemory store вместо SQLite-файла, один
SQLite handle вместо двух независимых `open`, заранее заданные commit outcomes,
глобальную блокировку, `sleep` или случайные задержки. Timeout допустим только
как защита теста от зависания. Коммит, push и PR требуют отдельного указания;
несвязанные файлы рабочего дерева сохраняй.

## Реальный стенд

Создай временный SQLite-файл и последовательно открой над ним два независимых
`SqliteSessionPersistence` с общим ограниченным `ThreadPoolExecutor`. Для
каждого handle создай собственный реальный `ContextService` и
`ApplicationOrchestrator`; resolver, artifact resolver, calculation engine и
cache возьми из реального стенда 10.3.

Локальная test-only обёртка aggregate должна:

- делегировать `touch` настоящему SQLite persistence;
- после завершения реального `touch` дождаться общей `asyncio.Barrier(2)`,
  чтобы оба `execute` получили исходный snapshot версии `N` до первого CAS;
- обернуть только sessions facet для записи аргументов и настоящих результатов
  `compare_and_set`, не подменяя их;
- делегировать остальные операции исходному aggregate.

Setup сессии и verification read выполняются вне измеряемой пары `execute`.
Параллельную пару запускай через `asyncio.gather` с bounded timeout только для
защиты от зависания.

## Обязательные сценарии

1. **Одинаковое намерение.** Две отдельные, но равные `BuildNatalCommand`
   используют разные `RunContext` и один `session_id`. Обе загрузки возвращают
   версию `N`; каждый Handler выполняется один раз, каждый ContextService делает
   один CAS с expected `N`. Настоящие store outcomes — один `N+1` и один
   `VersionConflict(actual=N+1)`. Application outcomes — один
   `ApplicationCommitted` и один `ApplicationAlreadyApplied`, оба с версией
   `N+1`, своими `run_id` и одинаковым расчётным намерением.
2. **Разные намерения.** Команды отличаются поддерживаемыми birth data и дают
   разные delta. Настоящий SQLite снова принимает ровно один CAS. Победитель
   получает `ApplicationCommitted(N+1)`, проигравший —
   `ApplicationSuperseded(N+1)` без artifact и без retry. Итоговое состояние
   равно birth data и chart spec победившей операции.

В каждом сценарии отдельным чтением подтверди версию `N+1`, целостную тройку
`birth_input/birth_resolved/base_chart` и отсутствие второй мутации. Проверь,
что оба recorded CAS использовали original expected `N`, а два wrapper-touch
получили snapshot версии `N` до выхода из barrier.
