# Промт 10.6 — Штатный application load profile

**Статус:** подготовлен 2026-09-19 перед исполнением.
**Зависимости:** 10.2–10.5 реализованы.
**Основание:** AC-35 и нагрузочное подтверждение AC-26, AC-28, AC-29,
§6.3/§6.5
[требований ApplicationOrchestrator](../../../docs/requirements/component_responsibilities/exact-orb_application_orchestrator_requirements.md)
и [карточка 10.6 плана](../../../docs/project_management/application_orchestrator_implementation_plan.md).

## Что делаем и зачем

Проверяем, что собранный application-flow способен не только принять, но и
полностью завершить штатный поток построения карт. В течение не менее 60 секунд
harness подаёт 5 операций в секунду, после прекращения подачи дожидается всех
результатов и проверяет сохранённые версии сессий.

В прогоне участвуют реальные `ApplicationOrchestrator`, `BuildNatalHandler`,
`ContextService`, SQLite persistence, resolver, calculation engine и cache.
HTTP заменён прямым вызовом `execute`, потому что transport ещё не реализован и
не должен искажать измерение application-ядра.

**Результат для менеджеров:** отчёт показывает, выдерживает ли готовое ядро
целевой поток 5 операций в секунду, сколько запросов завершилось полезными
результатами, образуется ли хвост после подачи, сколько операций одновременно
активно и не теряются ли изменения при работе с общими сессиями.

## Границы работы

Разрешено менять только:

- `scripts/bench_application_orchestrator.py` — отдельный локальный harness;
- `docs/project_management/application_orchestrator_load_profile_1.md` —
  автоматически сформированный фактический отчёт;
- §1.3 плана и README серии — статус и результаты;
- этот промт.

Не меняй production-код, session benchmark, admission controller, тесты,
requirements, ADR, диаграммы и прежние промты. Не добавляй HTTP, сеть, новые
зависимости или latency SLA. Не используй fake Handler/ContextService и не
считай 300 быстрых infrastructure failures успешным throughput. Коммит, push и
PR требуют отдельного указания; несвязанные файлы рабочего дерева сохраняй.

## Harness и профиль

Реализуй CLI:

```powershell
.\.venv\Scripts\python.exe -B scripts/bench_application_orchestrator.py --profile normal --rate 5 --duration 60 --operations 300 --log-level INFO --report docs/project_management/application_orchestrator_load_profile_1.md
```

Harness должен:

1. Собрать calculation-компоненты и тестовые данные из стенда 10.3, но для
   измеряемой session/application цепочки открыть реальный временный SQLite и
   построить новый `ContextService` и Orchestrator.
2. До измерения создать сессии, выполнить отдельный warm-up расчёта и сохранить
   исходные cache counters. Setup, прогрев и dialog measurement не входят во
   время подачи.
3. Подать не менее 300 операций средним темпом 5 RPS в течение не менее 60
   секунд. Использовать детерминированные пары операций: часть работает с
   отдельными сессиями, часть — с общими сессиями и одинаковыми либо разными
   намерениями.
4. Для общих пар разрешена test-only обёртка persistence: оба настоящих SQLite
   `touch` завершаются до выхода через `asyncio.Barrier(2)`. Обёртка не меняет
   ответы, CAS, время или данные и должна быть явно описана в отчёте. Таймер
   задаёт только скорость подачи; barrier доказывает CAS-пересечение.
5. Удерживать ссылки на все задачи, после окончания окна подачи выполнить drain
   и посчитать submitted, completed at stop, completed after drain, unhandled
   exceptions, текущую и максимальную активность.
6. При effective `INFO` собирать реальные
   `application_operation_started`/`application_operation_finished`, проверять
   по одному событию каждого вида на `run_id` и совпадение множества ID с
   поданными операциями.
7. Сохранить распределение `ApplicationResult`, status triples, cache hit/miss,
   результаты по типам сессий и observed CAS outcomes. Полезными допустимыми
   исходами валидного профиля считать `Committed`, `AlreadyApplied` и
   `Superseded`; остальные typed outcomes делают профиль непрошедшим.
8. После drain прочитать каждую измеряемую сессию. Итоговая версия должна
   совпасть с числом `Committed` для неё, а state — с последним победившим
   command/artifact. Это проверяет отсутствие lost update без дополнительной
   мутации внутри `execute`.
9. Закрыть executor и временную базу после drain и verification.

Допускается отдельный `--allow-short` режим только для локальной проверки
harness. Он обязан маркировать отчёт как diagnostic и не может дать PASS
профилю 1.

## Dialog snapshot overhead

После load profile создай две одинаково заполненные chart-сессии. В одну добавь
20 реальных `DialogTurn` по 1000 символов, вторую оставь с пустым dialog.
Выполни не менее 100 чередующихся `SessionPersistence.touch` для каждого
варианта.

В отчёте укажи:

- число turns и символов;
- размер сериализованных state и dialog и долю dialog в их сумме;
- число измерений, среднее, минимум, максимум и разброс touch для пустого и
  заполненного dialog;
- сравнительную оценку времени и явное ограничение: общий таймер touch не
  позволяет приписать разницу только dialog.

Это измерение не меняет контракт и не обходит `SessionPersistence.touch`.

## Проверки и отчёт

До полноценной нагрузки запусти R и F:

```powershell
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider tests/test_run_context.py tests/application tests/session tests/test_module_boundaries.py -q
.\.venv\Scripts\python.exe -B -m pytest -p no:cacheprovider -q
```

После них выполни точную normal-команду. Отчёт обязан содержать environment и
HEAD, dirty-state, команду, состав реальных компонентов и wrappers, timings,
counts, outcomes, cache, CAS/state integrity, dialog overhead, критерии PASS и
ограничения. Admission profile 10.7, HTTP/client и deployment не проверяются.

Дополнительно проверь `--help`, AST harness, локальные Markdown-ссылки, code
fences, trailing whitespace, `git diff --check`, точный состав изменений и
пустой staged index. Запиши реальные команды и результаты в §1.3 плана и
README.
