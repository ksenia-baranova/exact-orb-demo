# Промт 2.1 — детерминированный GeoNames → SQLite builder

## Что делаем и зачем

Перевести `scripts/build_place_catalog.py` с production JSONL на один
воспроизводимый `places.sqlite`. Builder должен собрать из трёх локальных
GeoNames-источников данные, достаточные для будущих `PlaceSearch.search()` и
существующего `PlaceCatalog.lookup()`, не выполняя сетевых запросов и не
реализуя runtime adapter.

Единственный production-результат — проверенный SQLite-файл, который появляется
на целевом пути только после успешного чтения, записи и валидации. Предыдущий
целевой файл должен остаться неизменным при любом отказе.

## Реализация

### 1. CLI и поток чтения

Сохранить CLI-аргументы `--cities`, `--admin1`, `--out`,
`--full-countries`, `--other-min-population`, сделать `--admin1` обязательным и
добавить обязательный `--alternate-names`. Все три входа должны существовать и
быть обычными файлами до создания временной базы.

Порядок единственного содержательного прохода:

1. `admin1CodesASCII.txt`: связать `country.admin1` с ASCII-name и GeoNames ID
   региона;
2. `cities1000.txt`: отфильтровать места и собрать нужные place/admin1 IDs;
3. `alternateNamesV2.txt`: сохранить в памяти только `ru`-имена нужных IDs;
4. записать строки в SQLite в стабильном порядке.

SHA-256 считать по исходным bytes внутри соответствующего прохода. Полный
`alternateNamesV2.txt` или все его строки в память не загружать. Некорректная
структура обязательной строки, дубликат выбранного `place_id`, неверное число,
координата или обязательный идентификатор должны явно завершать сборку.

### 2. Фильтры и нормализация данных

Включать только:

- feature class `P`;
- feature code вне `PPLX`, `PPLH`, `PPLW`;
- запись с непустым `tz_id`, присутствующим в `tzdata/zones` установленного
  Python distribution `tzdata`;
- все города стран `RU, UA, BY, KZ, MD, AM, GE, AZ, KG, UZ, TJ, TM, LT, LV,
  EE`, остальные — при population `>= 100000`;
- один уникальный GeoNames `place_id`.

Не использовать системную timezone database или `zoneinfo.available_timezones`
для состава каталога. Версию брать через `importlib.metadata.version("tzdata")`,
список keys — через `importlib.resources` из файла `tzdata/zones`.

Координаты читать как `Decimal`, применять `quantize(Decimal("0.01"),
rounding=ROUND_HALF_UP)` и хранить целые сотые. Проверять диапазоны latitude и
longitude. Binary float и `round()` в builder не использовать.

Builder обязан импортировать объект `normalize_place_query` и singleton
`ALLOWED_ALTERNATE_LANGUAGES` из `exact_orb.birth.places`. Локальную копию
normalizer не создавать. Имя, для которого canonical normalizer вернул
`InvalidPlaceQuery`, не индексировать и учитывать в статистике отклонённых имён.

### 3. Русские имена и aliases

Из `alternateNamesV2.txt` принимать только точный language code `ru` из
singleton allow-list. Пустые языки, `Məskeү`, псевдоязыки и все прочие языки не
индексировать.

Имя актуально, если `isHistoric != 1` и колонка `to` пуста. `historic=1`, если
`isHistoric == 1` или `to` непусто; колонку `from` с часами сборки не сравнивать.

`display_name` места выбирать в порядке:

1. актуальное preferred `ru`;
2. другое актуальное `ru`;
3. source `name`;
4. `name_ascii`.

Внутри одного уровня выбирать минимальный числовой `alternateNameId`. Для
`admin1_name` применять те же первые два уровня по GeoNames ID региона, затем
ASCII fallback из `admin1CodesASCII.txt`.

В `place_names` записывать source name, ASCII name, текущие и исторические
русские aliases. Одинаковые строки одного класса дедуплицировать до вставки.
Историческое имя не может стать display-name.

### 4. SQLite schema v1

Зафиксировать `SCHEMA_VERSION = 1`, `PRAGMA user_version = 1` и три таблицы:

```text
places
  place_id TEXT PRIMARY KEY
  display_name TEXT NOT NULL
  name_ascii TEXT NOT NULL
  country_code TEXT NOT NULL
  admin1_code TEXT NOT NULL
  admin1_name TEXT NULL
  latitude_e2 INTEGER NOT NULL
  longitude_e2 INTEGER NOT NULL
  tz_id TEXT NOT NULL
  population INTEGER NOT NULL

place_names
  place_name_id INTEGER PRIMARY KEY
  place_id TEXT NOT NULL REFERENCES places(place_id)
  name TEXT NOT NULL
  search_key TEXT COLLATE BINARY NOT NULL
  language TEXT NULL
  preferred INTEGER NOT NULL CHECK IN (0, 1)
  historic INTEGER NOT NULL CHECK IN (0, 1)

catalog_metadata
  singleton INTEGER PRIMARY KEY CHECK = 1
  schema_version INTEGER NOT NULL
  source_checksums TEXT NOT NULL
  build_parameters TEXT NOT NULL
```

Создать стабильные индексы `idx_place_names_search_key` на
`(search_key COLLATE BINARY, place_id)` и `idx_place_names_place_id` на
`place_id`. Foreign keys включить и проверить.

Metadata хранить каноническим JSON (`sort_keys=True`, compact separators):

- `source_checksums`: SHA-256 с фиксированными ключами `cities`, `admin1`,
  `alternate_names`;
- `build_parameters`: отсортированные full countries, population threshold,
  `tzdata_version`, singleton language allow-list, feature class и исключённые
  feature codes.

Не записывать timestamp, mtime, абсолютные пути, случайные IDs или другие
недетерминированные значения.

### 5. Атомарность и самопроверка

Создавать temp-файл через `tempfile.mkstemp` в каталоге рядом с целью. Включить
foreign keys, создать schema, вставить metadata и данные в детерминированном
порядке, выполнить commit и проверить:

- `PRAGMA integrity_check == "ok"` и пустой `foreign_key_check`;
- schema/user version, единственную metadata-строку и parseable JSON;
- наличие обязательных таблиц, колонок и двух индексов;
- количество записанных places/names и наличие хотя бы одного search-name для
  каждого места;
- отсутствие неразрешимых относительно зафиксированного `tzdata/zones` зон.

Закрыть connection до `os.replace`. При любой ошибке закрыть connection,
удалить temp и не менять прежнюю цель. Не оставлять temp активным выпуском.

Печатать статистику в фиксированном порядке: прочитанные строки каждого
источника, записанные places/names, причины фильтрации, включая отдельный
`filtered_timezone`, и `rejected_names`.

### 6. Synthetic data-only fixtures

Создать только три текстовых файла в `tests/fixtures/place_catalog/`:

- `cities1000.txt`;
- `admin1CodesASCII.txt`;
- `alternateNamesV2.txt`.

Минимальный набор обязан содержать: Москву `524901`, `Москва`, `Məskeү`, второй
non-preferred русский вариант, два равных preferred-кандидата с разными IDs,
псевдоязык, историческое имя, строку с непустым `to`, admin1 GeoNames ID и
русский регион, `Nowhere/Fake`, координаты на half-boundary, места внутри и вне
country/population filters, исключённый feature code, другой feature class и
пустой timezone. Это data-only fixtures; исполняемые тесты добавляет 2.2.
Для synthetic-строк `alternateNamesV2` разрешено опустить конечные пустые
`from/to`, чтобы data-файл не содержал trailing tabs; parser дополняет такие
строки до логических 10 колонок. Реальный десятиколоночный формат сохраняется.

## Проверка ranking schema без runtime search

После реализации одним локальным SQL-запросом на synthetic in-memory SQLite
подтвердить, что schema выражает порядок:

1. exact match;
2. current preferred;
3. current перед historic;
4. population DESC;
5. `place_id` как стабильный tie-breaker;

и выполняет `GROUP BY place_id` до `LIMIT`. Запрос является разовой проверкой
schema карточки 2.1; публичный `search()` и adapter не добавлять. Команду,
полученный порядок IDs и доказательство отсутствия дублей записать в журнал
плана.
