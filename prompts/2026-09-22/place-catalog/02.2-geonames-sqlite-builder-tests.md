# Промт 2.2 — тесты детерминированного GeoNames → SQLite builder

## Что делаем и зачем

Добавить исполняемую приёмку для builder, реализованного карточкой 2.1.
Synthetic GeoNames fixtures должны доказать правила отбора и имён,
воспроизводимость логического SQLite-содержимого, полноту metadata и
атомарность публикации. Production-код и входные fixtures в этой карточке не
меняются.

## Единственный исполняемый результат

Создать `tests/test_place_catalog_builder.py`. Тесты загружают script через
`runpy.run_path`, вызывают реальный `build()`/`main()` и читают полученный
SQLite через stdlib `sqlite3`. Не копировать алгоритм builder в тесты и не
вводить отдельную production-обёртку только ради тестирования.

## Обязательные доказательства

### 1. Fixtures имеют позитивные контроли

До проверки отсутствия отфильтрованных значений подтвердить, что исходные
fixtures действительно содержат:

- Москву `524901`, `Москва`, `Məskeү`, второй актуальный non-preferred `ru`
  alias и два preferred `ru`-кандидата с разными числовыми IDs;
- псевдоязык, историческое имя по `isHistoric` и отдельную строку с непустым
  `to`;
- GeoNames ID admin1, русское имя региона и регион без русского alias для
  ASCII fallback;
- `Nowhere/Fake`, пустую timezone, half-boundary `12.345/-45.675`, PPLX,
  другой feature class, внешние места на и ниже population threshold и место
  полного country coverage с малым population.

Проверять поля по tab-separated колонкам. Конечные пустые `from/to` могут быть
физически опущены согласно prompt 2.1.

### 2. Реальная synthetic-сборка и data rules

Собрать SQLite в `tmp_path` настоящим `build()` и проверить:

- статистику всех трёх проходов, записанных places/names и каждой причины
  фильтрации;
- ровно ожидаемые place IDs; присутствие включённых граничных случаев и
  отсутствие `Nowhere/Fake`, пустой timezone, PPLX, другого feature class и
  места ниже внешнего population threshold;
- Москву: `display_name="Москва"`, `admin1_name="Москва"`, координаты
  `5575/3762`, `Europe/Moscow`; `Məskeү` и псевдоязык отсутствуют в индексе;
- минимальный `alternateNameId` побеждает среди preferred-кандидатов, а
  non-preferred актуальный alias остаётся доступен для поиска;
- historical flag выставлен как по `isHistoric`, так и по непустому `to`, но
  исторические имена не становятся display-name;
- русский admin1 выбирается по GeoNames ID, а при отсутствии русского alias
  используется ASCII fallback;
- half-boundary округляется через `ROUND_HALF_UP` до `1235/-4568`;
- source и ASCII aliases дедуплицированы в одном классе, invalid normalized
  name не индексируется и учитывается в `rejected_names`.

Отрицательные проверки всегда связывать с позитивным контролем из исходной
fixture или со счётчиком реально выполненного фильтра.

### 3. Schema и metadata

Для готовой базы проверить:

- `PRAGMA integrity_check`, `foreign_key_check` и `user_version=1`;
- таблицы `places`, `place_names`, `catalog_metadata` и обязательные индексы;
- `BINARY` collation первого поля `idx_place_names_search_key`;
- единственную metadata-строку, `schema_version=1`, parseable canonical JSON;
- SHA-256 фактических bytes трёх fixtures;
- точные country/population filters, singleton language allow-list, feature
  filters и текущую версию project `.venv` distribution `tzdata`;
- отсутствие timestamp, mtime и путей в metadata.

### 4. Логическая воспроизводимость

В одном тесте выполнить две независимые сборки из одинаковых входов. Сравнить
результаты упорядоченными `SELECT` по всем трём таблицам, включая metadata и
нормативные идентификаторы строк. Байты SQLite-файлов не сравнивать и не
утверждать их равенство или различие.

### 5. Атомарная публикация и обязательные входы

- Для каждого отсутствующего обязательного input проверить явный
  `CatalogBuildError` до появления output.
- Для отказа непосредственно при публикации использовать управляемый leaf
  seam `os.replace`: дать builder полностью создать и проверить временную
  базу, затем выбросить `OSError`.
- Подтвердить, что прежние bytes target не изменились, temp был создан рядом с
  целью, после отказа удалён, а target не стал частично готовой SQLite-базой.

Не мокать чтение, parsing, SQLite, валидацию или сам `build()`.

### 6. Canonical normalizer и CLI

- AST-проверка должна находить импорт `normalize_place_query` и
  `ALLOWED_ALTERNATE_LANGUAGES` именно из `exact_orb.birth.places` и запрещать
  локальное определение функции `normalize_place_query`.
- Runtime-проверка должна подтверждать identity обоих импортированных объектов
  соответствующим canonical-объектам.
- Один вызов реального `main()` должен подтвердить exit code `0`, фиксированный
  порядок JSON-статистики и отсутствие tracebacks/ошибок в stderr.

## Запреты

Не менять `src/**`, `scripts/build_place_catalog.py`, fixtures карточки 2.1,
существующие tests, реальные `cities/**`, JSONL/goldens, requirements, ADR,
diagrams или зависимости. Не загружать данные по сети, не запускать полный
real-data build и не тестировать будущий runtime adapter/search.

Если новый тест обнаруживает дефект production builder или fixture, не
исправлять его скрыто в тестовой карточке: зафиксировать точный сценарий и
вернуть работу в 2.1 отдельным решением.

Не создавать commit, push или PR без отдельного указания владельца.

whitespace, отсутствие generated SQLite в Git и изменение только разрешённых
файлов.
