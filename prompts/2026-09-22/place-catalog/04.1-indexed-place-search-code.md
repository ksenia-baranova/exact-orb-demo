## Единственный production-результат

Изменить только `src/exact_orb/birth/adapters/sqlite.py`: тот же
`SqlitePlaceCatalog` получает метод

```python
async def search(
    self,
    query: str,
    *,
    limit: int = 10,
) -> PlaceSearchOutcome: ...
```

Не менять contracts и публичные реэкспорты: `PlaceSearch`, outcomes и модели
уже определены в `exact_orb.birth.places`; concrete adapter по-прежнему
импортируется только из leaf-модуля.

## Валидация и lifecycle

До SQL:

1. non-`str` query отклонять `TypeError` как нарушение Python-контракта;
2. принимать только `type(limit) is int` и диапазон `1..20`; `bool`, `0`,
   отрицательные значения и `21+` отклонять `ValueError`;
3. подтвердить открытый lifecycle тем же `_require_open_connection()`;
4. вызвать импортированный объект `normalize_place_query` без локальной копии;
5. при `InvalidPlaceQuery` вернуть этот fresh outcome без executor/SQL.

Корректный неизвестный query обязан дойти до worker/SQL и вернуть
`PlaceSuggestions(items=())`. Default `limit` равен `10`.

## Индексный SQL и ranking

Вычислить `upper = lower + "\U0010FFFF"` и выполнить один параметризованный
read query на том же injected `ThreadPoolExecutor(max_workers=1)` и том же
thread-bound connection, что lookup/open/close.

Диапазон обязан иметь BINARY-семантику:

```sql
search_key >= :lower COLLATE BINARY
AND search_key < :upper COLLATE BINARY
```

Не использовать `LIKE`, интерполяцию query в SQL, substring/fuzzy search,
accent folding или новые aliases. `%`, `_` и `'` остаются обычными символами.
Query plan должен использовать существующий
`idx_place_names_search_key`; schema и индексы не менять.

Сначала по всем совпавшим `place_names` вычислить один минимальный rank для
каждого `place_id`:

1. `0` — точное `search_key == lower`;
2. `1` — prefix match текущего `preferred=1, historic=0` имени;
3. `2` — прочее текущее `historic=0` имя;
4. `3` — historical имя.

После `GROUP BY place_id` присоединить `places`, отсортировать по
`match_rank ASC, population DESC, place_id ASC` и только затем применить
параметризованный `LIMIT`. Один ID возвращается не больше одного раза даже при
нескольких совпавших aliases.

## Результат и ошибки

Каждую SQL-строку преобразовать в новый immutable `PlaceSuggestion` только с
полями `place_id`, `display_name`, `admin1_name`, `country_code`. Координаты,
`tz_id`, population и matched alias наружу не возвращать; alias не подменяет
canonical `display_name`.

Каждый вызов создаёт новый `PlaceSuggestions` и новые item-модели. Любой ID из
выдачи остаётся разрешим прежним `lookup()` того же экземпляра.

Cancellation ожидания worker распространять как `CancelledError` без
преобразования. Технический отказ планирования/чтения/model construction после
успешной валидации преобразовать в `PlaceCatalogUnavailableError` с сохранённой
причиной. Ошибки query/limit и `InvalidPlaceQuery` не преобразовывать в
ошибку доступности.

## Ручная приёмка

На catalog, собранном из существующих synthetic fixtures, проверить реальный
executor и один экземпляр adapter:

- `Москва`, `москва`, `МОСКВА` и `Moscow` возвращают `524901` с
  `display_name="Москва"`, регионом `Москва` и `country_code="RU"`;
- prefix `Моск` дедуплицирует несколько aliases Москвы;
- `Санкт` возвращает `498817`, historical `Ленинград` также разрешает его;
- корректный неизвестный query возвращает пустой успешный outcome;
- `###@@@` возвращает `InvalidPlaceQuery` без worker submission;
- invalid limits дают `ValueError` без worker submission, default равен 10;
- `%`, `_` и `'` не получают wildcard/SQL-семантику;
- каждый выданный ID успешно разрешается прежним `lookup()`;
- повторный search возвращает равные, но не тождественные модели;
- `EXPLAIN QUERY PLAN` для того же диапазона показывает
  `idx_place_names_search_key`.
