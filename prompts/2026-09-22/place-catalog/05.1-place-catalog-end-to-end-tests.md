# Промт 5.1 — сквозная приёмка каталога мест

## Что делаем и зачем

Добавить исполняемую сквозную приёмку уже реализованной цепочки
builder → `SqlitePlaceCatalog.search()` → `lookup()` → `BirthDataResolver` →
существующий application flow. Тест должен доказать, что подсказка из одного
выпуска SQLite-каталога пригодна для повторной проверки и расчёта, а ошибки
lookup сохраняют принятую типизированную семантику до границы приложения.

Это тестовая карточка после завершения 1.1–4.2. Production-код не меняется.
Если приёмка обнаруживает дефект, зафиксировать точное расхождение и вынести
исправление в отдельную узкую correction-карточку.

## Единственный результат

Создать `tests/application/test_place_catalog_integration.py`. Для каждого
сценария строить реальный schema v1 SQLite catalog из существующих synthetic
GeoNames fixtures настоящим builder-ом, открывать его через
`SqlitePlaceCatalog` на caller-owned `ThreadPoolExecutor(max_workers=1)` и
закрывать adapter до shutdown executor.

Переиспользовать `application_test_stand` без изменения: передать ему тот же
экземпляр `SqlitePlaceCatalog`, который обслуживает search и lookup. Не
копировать production SQL, schema, нормализацию, resolver или application
composition в тест.

## Search → lookup → resolver

Прямой `search("Москва")` должен:

- вернуть suggestion `place_id="524901"`;
- не обращаться к `ApplicationOrchestrator` и `ContextService`;
- для каждого ID выдачи успешно выполнить `lookup()` того же экземпляра;
- разрешить Москву как `Москва`, `55.75/37.62`, `Europe/Moscow`;
- после передачи выбранного ID в `BirthDataResolver` для 02.09.1990 14:30
  вернуть `utc_offset_seconds=14400` и `1990-09-02T10:30:00Z`.

Так тест даёт сквозное подтверждение AC-P4, AC-L1 и AC-L3, не дублируя
полную матрицу ranking/search карточки 4.2.

## Application flow

С выбранным через search ID создать реальную сессию и выполнить
`BuildNatalCommand` через существующий
`ApplicationOrchestrator → BuildNatalHandler → BirthDataResolver`.

Проверить:

- реальный SQLite `lookup()` получает выбранный ID;
- результат — `ApplicationCommitted` версии 1;
- сохранённый snapshot содержит исходный `BirthInput`, московские resolved
  coordinates/timezone, `utc_offset_seconds=14400`, `10:30Z` и базовую карту;
- используется тот же catalog instance; отдельный production composition root
  или новое bootstrap ownership не вводятся.

## Негативные исходы

Для неизвестного числового ID через тот же реальный application flow доказать:

- `ApplicationInputRequired` содержит ровно
  `Issue(field="birth.place", code="INVALID")`;
- historical timezone resolver не вызывается;
- calculation/cache не запускаются;
- session state остаётся на версии 0 без birth/calculation данных, то есть
  commit не выполнялся.

После успешного startup детерминированно закрыть underlying SQLite connection
на его owning worker и выполнить Build path. Реальный read failure должен дать
`ApplicationResolutionFailure` с
`detail_code="PLACE_CATALOG_UNAVAILABLE"` и `retryable=True`, а не input
failure. Timezone, calculation и commit при этом также не выполняются.
