# Промт 04. Чистая проекция сохранённой карты

**Дата:** 2026-09-27.
**Ветка:** `feat/session-stored-chart`.
**План:** [M1-5.2](../../../docs/project_management/implementation_plans/session_stored_chart_implementation_plan.md), карточка 04.
**Статус:** выполнен 2026-09-27.

## Человеческое описание: что и зачем мы делаем

После повторного входа приложение получает готовый снимок сессии с байтами
ранее построенной карты. Нужно вернуть пользователю эту карту и заполненную
форму без нового расчёта. Если байты повреждены или сохранённая карта не
соответствует состоянию, приложение должно сохранить данные для формы и
сообщить безопасную причину недоступности карты. Изменение версии расчёта
лишь помечает корректную старую карту как устаревшую: пересчёт остаётся
явным действием пользователя.

Для этого создаём чистую проекцию: она читает переданный снимок, проверяет
формат и целостность карты и возвращает один из трёх внутренних результатов.
Она ничего не загружает и не сохраняет, не обращается к resolver, cache или
engine. Будущий HTTP transport отдельно решит, как показать результат и
записать ERROR при недоступной карте.

## Задача

Выполни только карточку 04 плана. Сверь ADR-0040, §4 спецификации
`stored-chart-session-behavior.md`, sequence 002/003, текущие модели, кодек и
существующие тесты. Сохрани несвязанные изменения рабочего дерева. Не
создавай коммит, ветку, push или PR.

1. Добавь `application/session_view.py` с типизированными неизменяемыми
   вариантами `empty`, `chart_ready` и `chart_unavailable`. На входе — готовый
   `SessionSnapshot` и текущая версия расчёта; на выходе — только компонентное
   представление, без I/O или изменения snapshot.
2. Для карты проверяй строго по порядку: поддерживаемый формат, строгий
   decode, ключ и версию envelope, spec и расчётный вход состояния. Возвращай
   первый соответствующий `safe_reason`. Только полностью проверенную карту
   сравнивай с текущей версией для `chart_stale`.
3. Проверь пустую, корректную и устаревшую карту; каждый достижимый
   `safe_reason`; приоритет причин при нескольких ошибках; сохранение
   `birth_input`, `canonical_place` и `state_version`; отсутствие мутации и
   ERROR-лога. Структурно неверный snapshot остаётся ошибкой чтения агрегата.
4. В `tests/test_module_boundaries.py` закрепи прямые импорты проекции с
   положительным контролем: кодек, ключи и `calculation.types` допустимы;
   concrete resolver/cache/engine, session I/O, adapters и transport — нет.
   Не ослабляй существующие архитектурные тесты.

## Приёмка и отчёт

Запусти целевые тесты проекции и границ, затем связанные тесты кодека и
application-контрактов. Проверь `git diff --check`. Запиши в план точные
команды, результаты и предел их свидетельства; отметь выполненной только
карточку 04. Сквозное сохранение InMemory/SQLite и transport относятся к
последующим карточкам.

## Фактическое выполнение

Добавлена чистая `session_view` с неизменяемыми типизированными вариантами.
Корректная карта возвращается из сохранённых байтов; при расхождении с
текущей версией она помечается `chart_stale` без пересчёта. Все восемь
`safe_reason` и их приоритет проверены. Проекция сохраняет данные формы и
`state_version`, не пишет ERROR и не меняет snapshot. Проверка прямых импортов
разрешает контракт snapshot и расчётные pure-модули, но отвергает concrete
I/O/движок; временный импорт `calculation.engine` вызвал ожидаемое падение
теста и удалён из итогового кода.

Первый целевой запуск: **57 passed, 5 failed** из-за ошибочного тестового
`house_system="K"`: контракт разрешает для natal только Placidus. После
замены на валидное отличие `near_interception_threshold`: **62 passed**.
Финальный связанный набор после усиления boundary-теста: **262 passed**.
`git diff --check` прошёл; новые файлы дополнительно проверены на хвостовые
пробелы. Полный `pytest`, InMemory/SQLite aggregate, restart и HTTP transport
не проверялись в этой карточке. Точные команды и предел свидетельства
записаны в журнал плана.
