# Промт 06. Схема SQLite v2 и миграция сессий

**Дата:** 2026-09-27.
**Ветка:** `feat/session-stored-chart`.
**План:** [M1-5.2](../../../docs/project_management/implementation_plans/session_stored_chart_implementation_plan.md), карточка 06.
**Статус:** выполнен 2026-09-27.

## Человеческое описание: что и зачем мы делаем

Прежняя база хранит состояние сессии и диалог, но не содержит построенную
карту. После изменения контракта такую старую сессию нельзя безопасно считать
готовой к восстановлению: у неё нет обязательной сохранённой карты. Добавляем
дочернюю таблицу для карты и при переходе на новую версию удаляем старые
сессии вместе с диалогами. Это разовая очистка только session component;
данные других компонентов базы сохраняются.

Переход должен быть атомарным: либо новая таблица, очистка и запись версии
появляются вместе, либо база остаётся в прежнем состоянии. При каждом новом
открытии проверяем, что таблица действительно соответствует контракту, а
запись о миграции согласована с ней. Так следующий этап сможет записывать
состояние и карту вместе без неопределённой старой схемы.

## Задача

Выполни только карточку 06 плана. Сверь ADR-0040, требования к сессии и
§9 `stored-chart-session-behavior.md`, текущую схему, мигратор и тесты SQLite.
Сохрани несвязанные изменения дерева. Не создавай коммит, ветку, push или PR.

1. Добавь `session_charts` точно по SQL из §9: один BLOB на сессию,
   `ON DELETE CASCADE`, ограничения `payload_format`, `calculation_key`,
   `calculation_version` и длины `payload`; без собственного TTL, версии и
   дополнительного индекса.
2. Добавь session migration v2 в существующий `BEGIN IMMEDIATE`: создание
   таблицы, удаление всех прежних `session_states` с каскадной очисткой
   диалогов, запись v2 в компонентный ledger. Отказ любого шага должен
   откатить схему, данные и запись версии. Чужие таблицы и ledger не меняй.
3. Перед миграцией проверь известную v1-схему. После миграции и при каждом
   открытии v2 проверь точные столбцы, типы, `NOT NULL`, PK, обязательные
   `CHECK`, единственный FK и согласованность таблицы с ledger. Несовпадение
   верни как `SESSION_SQLITE_SCHEMA_INCOMPATIBLE` до обслуживания сессий.
4. Проверь новую базу, переход v1→v2 с очисткой старых сессий, rollback
   после удаления, сохранение чужого компонента, повторное открытие и
   отклонение испорченной схемы/ledger. Обнови прежние ожидания версии ledger.
   `_STATE_PAYLOAD_VERSION=2` и frozen payload v1/v2 оставь без изменений.

## Приёмка и отчёт

Запусти целевые schema/migration-тесты, затем применимые связанные SQLite
проверки. Общие CAS/touch-тесты могут оставаться красными до карточки 07;
отдели их от результата миграции. Проверь `git diff --check`, внеси точные
команды, результаты и пределы свидетельства в план. Отметь выполненной
только карточку 06; полный `pytest` после сборки всех срезов.

## Фактическое выполнение

Session migration v2 создаёт `session_charts`, удаляет прежние родительские
сессии с каскадной очисткой диалогов и записывает v2 в компонентный ledger
в одной существующей `BEGIN IMMEDIATE` транзакции. До удаления проверяется
v1-схема; при каждом открытии v2 проверяются форма таблицы, ограничения и FK.
Таблица без записи v2 и запись v2 без таблицы отклоняются до обслуживания.
Версия JSON payload состояния и frozen-файлы не менялись.

Тесты подтвердили переход v1→v2, сохранность чужого компонента, rollback
после удаления, отказ при дрейфе v1/v2, физические ограничения новой таблицы
и повторное открытие. Целевой набор: **26 passed**; связанный набор с
модульными границами: **71 passed**. Расширенный SQLite-запуск остановлен
после **83 passed, 12 failed**: общие CAS/touch-тесты доходят до прежнего
создания `SessionSnapshot` без обязательного `chart` в SQLite adapter. Это
реализация карточки 07. Полный `pytest` и сквозной restart здесь не запускались.
