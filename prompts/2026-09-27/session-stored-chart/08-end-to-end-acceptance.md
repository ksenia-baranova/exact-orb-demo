# Промт 08. Сквозная приёмка сохранённой карты

**Дата:** 2026-09-27.
**Ветка:** `feat/session-stored-chart`.
**План:** [M1-5.2](../../../docs/project_management/implementation_plans/session_stored_chart_implementation_plan.md), карточка 08.
**Статус:** выполнен 2026-09-27.

## Человеческое описание: что и зачем мы делаем

Предыдущие этапы научили приложение сохранять карту вместе с сессией и
возвращать её из SQLite. Теперь нужно проверить весь путь глазами
пользователя: построить карту, закрыть приложение, открыть его заново и
увидеть тот же результат без повторного расчёта. Также проверяем, что новая
версия расчёта помечает сохранённую карту как устаревшую, а не молча заменяет
её другим результатом.

Последняя приёмка охватывает сброс, первую неудачную попытку, две вкладки,
конкурирующие команды и неопределённый ответ базы о записи. Это нужно, чтобы
передать M1-6 проверенный компонентный контракт: транспорт сможет добавить
cookie и HTTP bootstrap, опираясь на подтверждённое поведение хранения и
восстановления. Результаты и оставшиеся границы записываем в репозитории.

## Задача

Выполни карточку 08 плана. Сверь ADR-0040, S-01–S-12, sequence 001–007,
актуальные requirements, runtime composition и существующие тесты. Сохрани
несвязанные изменения дерева. Не создавай коммит, ветку, push или PR.

1. Проверь build → закрытие runtime → новый runtime с тем же SQLite и пустым
   расчётным кэшем → `ContextService.load` + `session_view`: тот же сохранённый
   артефакт без вызова resolver/cache/engine; другая версия расчёта даёт
   `chart_stale` при неизменном payload.
2. Проверь пустую сессию и пустой повторный вход после reset. Отказ первого
   build до CAS не должен сохранять ввод; после повторного входа состояние
   остаётся пустым.
3. Проверь две вкладки и конкурентные команды с одной исходной версией через
   управляемые `Event`/barrier. После подтверждения B вкладка A видит новую
   карту при следующем load; конфликт не перезаписывает победителя.
4. Проверь неопределённый commit и точный retry: возможны только согласованные
   state+chart или отсутствие обеих; `AlreadyApplied` сохраняет карту первой
   подтверждённой операции. Реальный Handler → Orchestrator → SQLite должен
   подтвердить атомарную запись и `Superseded` без чужой карты.
5. Сопоставь существенные стрелки sequence с фактическими INFO и DEBUG.
   Исправь подтверждённые расхождения в целевых тестах и актуальных документах,
   не редактируя исторические промты 01–07. Обнови roadmap фактическим статусом
   только после успешной приёмки.

## Приёмка и отчёт

Сначала запусти целевые интеграционные тесты, затем связанные session и
application, затем полный локальный `pytest`. Зафиксируй точные команды,
результаты, ограничения и покрытие S-01–S-12 в плане. Проверь
`git diff --check` и ссылки изменённой документации. Отметь выполненной
карточку 08 только после доказанной компонентной приёмки; публичный HTTP
bootstrap остаётся M1-6.
