# Промт 13a.1. Проверка build owner и конечность shutdown checkpoint

**Статус:** исполнен 2026-10-02; результаты — §25.1 implementation plan.
**Зависимость:** промт 13a.
**Источник:** оставшиеся замечания ревью другой моделью после 13a, проверенные
Developer по текущему коду. Результат запиши в §25.1 implementation plan.

## Цель и границы

Закрепи поведение shutdown после grace для отменённого build owner без живого
resolver leader и исключи бесконечный цикл, когда task завершён, но ещё числится
в registry. Сохрани DP-HTTP-04 и §11.3: после grace нет дополнительного срока;
`runtime.aclose()` допустим только при нулевой активности, иначе fail-fast.
Не меняй публичные HTTP ответы, лимиты admission, runbook и production logging.
Старые промты не редактируй. Не создавай commit, push или PR.

## Исполнение

1. Сначала сопоставь замечания с текущими `app.py`, `routes/build.py`,
   `test_lifecycle.py` и §11.3. Проверь, не покрывает ли существующий тест
   именно отмену build owner на grace при пустом `runtime.drain()`.
2. Добавь один детерминированный regression-тест этого сценария. Блокирующий,
   но отменяемый `execute` достигается до shutdown; fake scheduler доводит
   shutdown до grace. Проверь, что owner завершён, permit освобождён после
   terminal execute, runtime закрыт перед каталогом, итог `resources_released`,
   а для request есть ровно один terminal log с тем же request_id. Позитивный
   контроль должен доказывать, что `execute` действительно стартовал.
   Если тест падает из-за короткого checkpoint, исправь checkpoint без
   wall-clock ожидания и без освобождения permit при живом leaf.
3. Для ветки `_wait_for_quiescence`, где все зарегистрированные задачи уже
   `done()`, оставь возможность отработать queued done callbacks, но ограничь
   повторные проходы независимо от продвижения scheduler. Если registry так и
   не очищен, верни fail-fast. Добавь управляемый regression-тест с завершённой
   задачей, оставшейся в registry, и непродвигаемым scheduler. Докажи, что
   shutdown завершается, занятые ресурсы не закрываются и остаются retained.
4. Не заменяй ожидание произвольным `sleep`/TTL; допускается только конечный
   event-loop checkpoint, уже утверждённый §11.3. Меняй актуальные
   requirements/sequence diagrams лишь при реальном изменении контрактного
   порядка; факт отсутствия такого изменения отметь в отчёте.

## Проверка и отчёт

Сначала новые целевые тесты, затем `python -m pytest tests/http_api -q`,
затем полный `python -m pytest -q`; используй `-p no:cacheprovider`, если
проверка запускается без cache provider. Выполни `git diff --check`.
В §25.1 implementation plan запиши причину, фактические изменения, точные
команды и результаты, незакрытые ограничения. Не заявляй внешние/Caddy/HTTPS
проверки, если они не выполнялись.
